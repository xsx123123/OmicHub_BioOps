### 2.2 根因（确认）

`post_room_message` 的 Phase 0 新增去重预检（`agentteams_service.py:1102-1103`）调用 `get_case_events(..., limit=200)`；Bridge events 端点硬限制 `1 <= limit <= 100`，超限返回 422（`integrations/agentteams/bridge/cygnusx_agentteams_bridge/app.py:519-520`）。422 在平台侧 `_request_as` 被转换为 `BusinessError("Agent 协作中心暂时不可用")`（`agentteams_service.py:1386-1395`）→ HTTP 400。这发生在 `room.user_message` 写入（`:1135`）**之前**，且异常未被捕获 → 消息不落库、celery 响应任务不投递。

Phase 0 前端每条消息都生成并发送 `client_message_id`（`AgentTeamsRoomView.vue:675, 778`；`api/agentTeams.ts:243`），所以该预检**必然执行、必然 422、必然失败**。基线对照：`git show aad9d66` 的 AgentTeamsRoomView.vue / agentTeams.ts 中无 `clientMessageId` 任何匹配；基线 `post_room_message` 无 `client_message_id` 参数与预检。

**同型 bug（本次新发现）**：`get_room_response_timing_summary` 用 `limit=1000`（`agentteams_service.py:963-975`）→ 新端点 `GET /cases/{id}/response-timing` 必然 400。

### 2.3 三层问题回答

1. **异常抛在哪**：平台 → Bridge `GET /v1/cases/{id}/events?limit=200`，Bridge 返回 422；平台 `_request_as` 转为 BusinessError 400 抛回 API 层，在 room.user_message 落库之前中断。
2. **为什么 scrna 路径"幸免"**：代码级不存在能解释此现象的路由分支差异——三条消息走不同分支（R2-1 无执行动词→CHAT→Manager 会诊；R2-2/R2-3 有执行动词但无数据对象→CLARIFY，`agentteams_execution_intent.py:60-79`），但断点 A 在更上游的消息写入处，与分支无关。**且生产日志不支持"R2-1 正常"**：15:00:56(+0800) 创建的 case `af843de6`（07:00:56 UTC）同样 `GET events -> 422`、`POST messages -> 400`，另伴随 `POST work-items -> 422 ×3`（Flow 阶段物化失败）与 07:00:58 的 consultation 500；用户 07:01:29 删除后 07:01:48 重建 `98bccf9d`，同样失败。bridge 持久 audit 中当日全部 5 个 case 零事件。**结论：高度怀疑 R2-1 实际也失败，"全链路正常"是用户侧感知（乐观上屏等）与现实的偏差**；唯一 messages 201 成功记录是 09:55(+0800) 的 `93fccc45`（Phase 0 部署前）。
3. **为什么前端显示空白而非错误**：Case 创建路径不经过断点 A（201 成功）；事件列表为空 → `projectCaseEvents([])` 返回空（`agentTeamsRoom.ts:1175-1179`）→ 渲染 `<NEmpty description="暂未产生协作事件" />`（`AgentTeamsRoomView.vue:1383`）；`detail.status='received'` → 阶段条停"已接收"（`:1341-1343` + `agentTeamsPreStartStatuses`）。background 刷新失败一律静默（`:610`）；只有首屏非 background 拉取失败才弹 toast（`:609-616`）——这就是 R2-2（空白）与 R2-3（空白+toast）的差异：R2-3 的首屏 `selectCase` 拉取直接撞上失败。

## 6. F. 可观测性现状与埋点需求

### 6.1 现状（一个 Case 从创建到终态）

- **有记录**：HTTP 请求级 audit（web 中间件）；Bridge 事件审计（audit.jsonl 持久）；celery 任务日志；route_decision/澄清/会诊等房间事件（写入成功时）；lease_expired/timeout sweep 审计。
- **盲区**：① room.user_message 写失败 → 用户无任何告警；② Bridge 4xx/5xx 被平台抹平为 400"暂时不可用"，真实错误码丢失；③ 前端 background 刷新/SSE 断流完全静默；④ claim→execute 租约窗口无心跳无审计；⑤ envelope parse_success 只进 telemetry 不进事件流；⑥ case_store 加载失败无日志；⑦ 部署版本（git SHA）不可考，事故时跑的代码与 HEAD 对不上（本次已实际阻碍定位）；⑧ Matrix Gateway 全天不可用、RocketMQ worker 崩溃循环，均无告警；⑨ Bridge audit 被 ~650 万条 inbox_polled 噪音淹没。

### 6.2 埋点需求清单（目标：任意故障 Case 5 分钟内定位到层）

1. 每个 Case 一条不可变路由事件：输入消息 ID/文本 hash、registry 快照版本、`display_lead_planner` 与 `actual_plan_target` 同事件（Phase 0 已部分做，需强制非空校验）。
2. 消息写入链路逐跳事件：`received → dedup_check(passed/failed+reason) → persisted(event_id) → dispatched(celery task_id)`；任一跳失败写 `room.message_failed` 审计事件并对用户可见。
3. Bridge 校验错误结构化回传：HTTP 错误体携带 machine-readable code（如 `LIMIT_EXCEEDED`），平台按 code 映射文案而非一律"暂时不可用"。
4. 租约全生命周期审计：claimed → first_heartbeat → renew_started/stopped → renew_result（每次）→ sweep_decision → retry/timeout，统一 trace_id；claim→execute 窗口纳入监控。
5. repair 链路审计：validator 错误列表、prompt hash、模型响应 hash、parse_success、attempt 号，随 case 事件流可查。
6. 会诊信封解析结果（parse_success）升格为 Case 事件而非仅 telemetry。
7. case_store 加载失败必须 logger.exception + 启动健康检查失败，禁止静默 `{}`。
8. 部署可观测：/healthz 输出 git SHA 与构建时间；所有日志带 version 字段。
9. 前端：background 刷新连续失败 N 次后降级提示；SSE 断流状态条；删除操作超时后按"结果未知"处理并主动对账（重新拉列表）。
10. 外部依赖（Matrix Gateway、Bridge、Redis、RocketMQ worker）存活与 provisioning 失败率告警。
11. Bridge audit 降噪：inbox_polled 类心跳事件采样或分离存储。
