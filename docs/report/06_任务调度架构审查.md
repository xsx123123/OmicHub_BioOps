# 06 · 任务调度架构审查

> 核心问题：当前调度架构是否适合扩展到万人级？答案：**架构设计合理但单机实现，需重构为分布式**。

## 一、当前调度架构全景

```
用户提交 → TaskService.submit()
  → GenericFlowBuilder 生成 config.yaml/samples.csv/contrasts.csv 到 {storage}/users/{uid}/results/{flow_id}/{task_id}/
  → TaskDomainService 创建任务（PENDING）
  → run_snakemake.delay() 投递 Celery
  → 状态推进 QUEUED

Celery Worker 消费 analysis 队列:
  → run_snakemake task (asyncio.run 包裹)
  → LocalSnakemakeExecutor._execute()
  → subprocess 调用 snakemake CLI
  → stdout/stderr 缓冲后回写 DB + Redis Pub/Sub
  → 成功：ReportService 生成报告 + TaskCookieConsumer.on_complete 结算饼干
  → 失败：记录 error_message + 退预扣饼干

实时日志: Celery → Redis Pub/Sub → 前端 WebSocket/SSE 订阅 task:{id} 频道

定时任务 (Celery Beat):
  - 02:00 cleanup_expired（僵尸会话/临时文件/冷数据归档）
  - 03:00 reconcile_used_storage（物理目录对账）
  - 02:30 cookie_daily_reconcile（饼干日终对账）
  - */5min sandbox_recycle_expired（沙盒超时回收）
```

## 二、调度架构评估

### 2.1 优点（设计层面优秀）

| 设计点 | 评价 | 说明 |
|--------|------|------|
| 执行器抽象 | ✅ 优秀 | BaseExecutor + Local/Binary/Remote，registry 注册，可扩展 Nextflow/WDL |
| ExecutionContext | ✅ 优秀 | 把执行所需打包，执行器不碰 DB/Redis，纯净可测试 |
| 回调解耦 | ✅ 优秀 | on_log/on_progress 回调，日志持久化交给调用方 |
| 状态机 | ✅ 优秀 | PENDING→QUEUED→RUNNING→SUCCESS/FAILED/CANCELLED，TaskDomainService 统一转换 |
| 饼干集成 | ✅ 优秀 | 预扣→结算→退还四点集成，多退少补 |
| 双栈解耦 | ✅ 优秀 | Web 控制面与 Worker 计算面独立编排，可水平扩展 Worker |

### 2.2 问题（实现层面瓶颈）

| # | 问题 | 等级 | 影响万人级 |
|---|------|------|-----------|
| S-1 | 单一 analysis 队列 | P0 | 所有任务（分析/下载/沙盒/清理）挤一个队列，长任务阻塞短任务 |
| S-2 | 无优先级调度 | P0 | config.py 定义了 PRIORITY_HIGH/NORMAL/LOW 但未启用，紧急任务排队 |
| S-3 | 单 Celery Beat | P0 | Beat 单点，崩了定时任务全停（prod.yml replicas:1 但无故障转移） |
| S-4 | asyncio.run 每任务新循环 | P1 | NullPool 规避了连接复用问题，但每任务新建 DB 连接，万人并发会耗尽连接 |
| S-5 | 无任务去重 | P1 | 同用户重复提交相同任务无法识别，浪费资源 |
| S-6 | 无死信队列 | P1 | 失败任务无重试策略配置，无 DLQ 隔离毒消息 |
| S-7 | Redis Pub/Sub 日志无持久化 | P1 | 订阅者不在线时日志丢失（已落 DB 但实时窗口丢） |
| S-8 | work_dir 路径硬编码宿主 | P0 | `/home/zj/pipeline/RNAFlow/snakefile` 完全非可移植 |
| S-9 | 无资源感知调度 | P0 | 任务不感知 Worker 负载/磁盘/内存，可能调度到满载节点 |
| S-10 | worker_prefetch_multiplier=1 | P2 | 长任务公平但短任务吞吐低，应分队列区分 |

## 三、万人级调度架构重构方案

### 3.1 多队列分层调度

```python
# celery.py 重构
celery_app.conf.task_routes = {
    "cygnusx.tasks.analysis.run_snakemake": {"queue": "analysis",
        "priority": 5, "rate_limit": "10/m"},  # 重计算，限流
    "cygnusx.tasks.download.run_download": {"queue": "download",
        "priority": 3},  # IO 密集，独立队列
    "cygnusx.tasks.sandbox.*": {"queue": "sandbox",
        "priority": 8},  # 交互式，高优先
    "cygnusx.tasks.storage.*": {"queue": "maintenance",
        "priority": 1},  # 维护任务，低优先
    "cygnusx.tasks.cookie.*": {"queue": "maintenance"},
}
```

**队列与 Worker 池对应**：
- `analysis` 队列：大内存 Worker（64C/256G），跑 Snakemake
- `download` 队列：高带宽 Worker，跑 EBI 下载
- `sandbox` 队列：GPU Worker（可选），跑代码沙盒
- `maintenance` 队列：轻量 Worker，跑清理/对账

### 3.2 优先级调度

```python
# 提交时按用户等级与任务类型设优先级
priority = compute_priority(
    user_tier=user.tier,        # premium=10 / standard=5 / free=1
    task_type=task.flow_id,     # interactive > batch
    is_retry=False,
)
run_snakemake.apply_async(args=..., queue="analysis", priority=priority)
```

Redis Broker 原生支持 priority（`broker_transport_options = {'priority_steps': list(range(10))}`）。

### 3.3 Beat 高可用

**方案**：废弃单进程 Celery Beat，改用 **K8s CronJob**：
- 每个 cron 任务一个 K8s CronJob，跑一次性 Celery task
- K8s 保证 CronJob 调度的单实例与故障转移
- 或用 `celery-beat-redbeat`（Redis 存储 beat schedule，多 beat 实例选举 leader）

### 3.4 资源感知调度

**短期（Celery 内）**：
- Worker 启动时声明 `resources`（cores/memory/gpu）
- 任务声明 `requirements`，Celery `task_annotations` 路由到匹配 Worker

**中期（K8s）**：
- 每个 Snakemake 任务 = 一个 K8s Job
- K8s Scheduler 原生资源感知调度
- 用 `Kueue`（K8s batch 调度）做排队与配额

**长期（集群）**：
- Snakemake 原生支持 Slurm/LSF/K8s 后端
- `execution.remote` 模式：HTTPExecutor → 集群头节点 → sbatch

### 3.5 死信队列与重试

```python
@shared_task(
    bind=True,
    autoretry_for=(TransientError,),
    retry_backoff=True,        # 指数退避
    retry_backoff_max=600,
    retry_jitter=True,
    max_retries=3,
    retry_policy=...,
)
def run_snakemake(self, ...):
    ...
```

失败 3 次进 DLQ（`analysis.dlq` 队列），人工干预。

## 四、集群执行模式落地

### 4.1 当前 local.py 的问题

```python
# local.py:72-93 — 命令拼接
cmd = ["snakemake", "-s", snakefile, "--cores", str(cores), ...]
process = await asyncio.create_subprocess_exec(*cmd, ...)
```

- 直接在 Worker 容器内跑 snakemake，依赖宿主 conda（`/home/zj/miniconda3`）
- 万人级不可能所有计算节点都装 conda + 流程代码

### 4.2 三种集群执行方案

**方案 A：Snakemake + Slurm（推荐，HPC 场景）**

```python
# infrastructure/execution/slurm.py
class SlurmSnakemakeExecutor(BaseExecutor):
    async def execute(self, ctx: ExecutionContext) -> ExecutionResult:
        # 生成 sbatch 脚本
        sbatch_script = self._render_sbatch(ctx)
        # 提交到 Slurm
        result = await asyncio.create_subprocess_exec(
            "sbatch", "--parsable", input=sbatch_script, ...
        )
        job_id = (await result.stdout.read()).strip()
        # 轮询 squeue 直到完成
        while True:
            status = await self._poll_slurm_job(job_id)
            if status in ("COMPLETED", "FAILED"):
                break
            await asyncio.sleep(30)
        # 从共享存储读结果
        return ExecutionResult(...)
```

Snakemake 原生 `--profile slurm` 即可提交到 Slurm，无需改流程代码。

**方案 B：Snakemake + K8s（推荐，云原生场景）**

```python
# Snakemake 8.0+ 原生支持 K8s 后端
cmd = ["snakemake", "-s", snakefile, "--kubernetes",
       "--container-image", flow_image, ...]
```

每个 rule 变成一个 K8s Pod，Snakemake 做 DAG 调度。

**方案 C：Nextflow 替换（长期，若需多云可移植）**

Nextflow 原生支持 K8s/Slurm/AWS Batch/Google Life Sciences，但需重写流程。

### 4.3 流程代码容器化

**当前问题**：`flows/rna_seq.yaml` 硬编码 `/home/zj/pipeline/RNAFlow/snakefile`。

**万人级方案**：
1. 每个流程打包成 Docker 镜像：`cygnusx/flow-rnaseq:v1.0`（含 Snakefile + conda env）
2. YAML 声明 `execution.container_image`
3. Snakemake `--use-singularity` 或 `--container-image` 在隔离环境跑
4. K8s Job 用该镜像创建 Pod

```yaml
# flows/rna_seq.yaml 重构
execution:
  snakefile: "/workflow/Snakefile"          # 容器内路径
  container_image: "cygnusx/flow-rnaseq:v1.0"
  default_resources:
    cores: 8
    memory: 16G
```

## 五、调度架构适配性结论

| 场景 | 当前架构 | 万人级要求 | 差距 |
|------|----------|-----------|------|
| 并发用户 | <20 | 10000+ | S-1 队列分层 + Worker 水平扩展 |
| 任务吞吐 | 10/天 | 1000+/天 | S-4 连接池 + S-9 资源感知 |
| 任务类型 | 单一分析 | 分析/下载/沙盒/交互混合 | S-1 多队列 |
| 优先级 | 无 | VIP/普通/免费分级 | S-2 优先级 |
| 高可用 | 单 Beat | 调度器 HA | S-3 K8s CronJob |
| 执行环境 | 单机 conda | 集群/云 | S-8 容器化 + 集群执行器 |
| 资源隔离 | 无 | 租户配额 | E-2 资源限额 |

**结论**：当前 Celery + 本地 subprocess 架构**适合 <50 人组内场景**，万人级需重构为**多队列 + 优先级 + K8s/Slurm 集群执行 + 容器化流程**。执行器抽象（BaseExecutor）设计良好，新增 SlurmExecutor/K8sExecutor 即可，无需大改业务层。
