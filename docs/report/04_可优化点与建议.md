# 04 · 可优化点与建议

> 按 P0（阻塞上线）/ P1（应尽快）/ P2（建议迭代）三级分类。
> 每项含：现状、风险、落地路径。

## P0 — 阻塞上线（必须修复）

### P0-1 测试覆盖严重不足

**现状**：后端 227 个 Python 文件 / ~23K LOC，测试仅 16 个文件 / 1194 LOC（`tests/`）。关键服务几乎无测试：
- `chat_service.py`（951 行，AI 编排核心）— 0 测试
- `agent_service.py`（418 行，调度中枢）— 仅集成测试 2 个
- `file_service.py`（702 行，多租户隔离）— 0 测试
- `cookie_service.py`（506 行，虚拟货币）— 0 测试
- `task_service.py`（195 行，流程执行）— 仅集成测试

**风险**：单人开发 + 无测试网 = 每次改动都可能引入回归。todo.md 中 9+ 处「待真实环境验证」即因此而来——沙箱无 DB 访问，无法端到端验证。

**落地路径**：
1. 优先为核心服务补单测：`agent_service.assemble_context`、`chat_service.stream_agent_chat`、`file_service` 的路径隔离与配额、`cookie_service.adjust_balance` 的 CHECK 约束边界。
2. 用 `pytest-asyncio` + `httpx.AsyncClient` + testcontainers（PG/Redis）搭建集成测试基座。
3. Makefile 已有 `test-cov`，CI 中加 `--cov-fail-under=50` 门禁（先定 50%，逐步提升）。
4. 把 todo.md 里「待真实环境验证」项转化为集成测试用例。

### P0-2 核心模块「待真实环境验证」未闭环

**现状**：todo.md 中多处核心模块标注「待真实环境验证」「待补」，包括：
- Agent 调度闭环（agent_id → MCP tool_call → tool_result → 继续生成）— ⚠️
- 数据管理多租户隔离（init/chunk/merge/quota/download/续传/越权404）— ⚠️
- 饼干调账（负数金额 CHECK 约束）— ⚠️ 真实环境待执行 `make migrate`
- alembic upgrade head 多个迁移沙箱未实跑 — ⚠️

**风险**：这些是生产链路必经路径，未验证即上线 = 高概率 500。

**落地路径**：
1. 用 docker-compose 拉起真实环境，逐项执行 todo 中「待真实环境验证」清单。
2. 特别验证：Agent 绑定真实 model_id 后诱导 MCP tool_call 闭环；文件越权 404；饼干负数调账。
3. 验证后回写 todo.md 勾选，并沉淀为回归测试。

### P0-3 生产级安全审查 115 项问题多数未修

**现状**：`docs/CygnusX_生产级优化建议文档.md` 审查发现 115 项问题（34 P0 / 51 P1 / 30 P2），但多数未落地。关键未修项：
- PostgreSQL / Redis 单点故障，无主从、无备份
- 沙盒 Docker Socket 挂载 + 无 seccomp/AppArmor = 容器逃逸风险
- 无监控告警体系（仅 Flower + loguru，无 Prometheus / 告警通道）
- 全局限流仅 IP 级，无 per-user / per-route

**风险**：私有化部署也面临硬件故障与恶意用户（沙盒逃逸可接管宿主）。

**落地路径**：
1. **沙盒加固**（最高优先）：移除 Docker Socket 挂载，改用 gVisor/Kata Containers 或 seccomp profile；限制 CPU/内存/PIDs；网络隔离。
2. **备份**：至少加 `pg_dump` 定时备份到独立卷 + Redis RDB；写恢复演练文档。
3. **监控**：引入 `prometheus-fastapi-instrumentator` + Grafana，对 5xx 错误率 / 任务失败率 / 队列深度设告警。
4. **限流细化**：`RateLimitMiddleware` 增加 per-user 维度（从 request.state.user_id），对 `/chat/stream`、`/tasks/submit` 单独配额。

### P0-4 数据库 schema 与 ORM 历史不一致风险

**现状**：todo.md 记录 cookie_pricing 表缺列导致 500（2026-07-04 修复），属「历史迁移遗漏」。说明迁移与模型同步存在缺口。24 个迁移 revision 命名混乱（早期 hash `08ab25316cc1` + 后期 `a1b2c3d4e5f6` 风格混合），出现过 Multiple Heads 分叉。

**风险**：空库从头 upgrade 可能因 down_revision 指错而表不存在报错；生产库缺列突发 500。

**落地路径**：
1. CI 中强制跑 `make check-migrations`（已有脚本 `scripts/check_migrations.py`，但无 CI）。
2. 新增迁移规范：统一用 `make migrate-new` 生成，revision 用语义化短 hash，禁止手写。
3. 上线前在干净环境跑一遍 `alembic upgrade head` → 启动应用 → 冒烟测试。

## P1 — 应尽快修复

### P1-1 Legacy/Current AI 双轨并存

**现状**：两代 AI 架构同时存在：
- Legacy（WebSocket）：`api/v1/ai.py` + `application/services/ai_service.py`（347 行）+ `infrastructure/ai_provider/litellm_provider.py`（320 行）+ `kimi.py` + 前端 `composables/useAIWebSocket.ts` + `components/AIChat.vue` + `components/chat/`
- Current（SSE Agent）：`api/v1/chat.py` + `chat_service.py`（951 行）+ `openai_compatible.py` + 前端 `useAgentChatStream.ts` + `AgentWorkspace.vue` + `components/ai-chat/`

**风险**：维护两套 Provider、两套流式协议、两套前端组件，认知负担大；新人易混淆；litellm 重依赖与自研 openai_compatible 功能重叠。

**落地路径**：
1. 确认 Legacy 无活跃流量（查 `/api/v1/ai/ws` 调用日志）。
2. 下线顺序：前端移除 `AIChat.vue` 入口 → 后端 `ai.py` 路由标 deprecated → 一个版本后删除 `ai_service.py` + `litellm_provider.py` + `kimi.py` + `useAIWebSocket.ts`。
3. 保留 `ai_repository.py`（会话历史）但迁移到 chat 体系。

### P1-2 巨型文件需拆分

**现状**：

| 文件 | 行数 | 问题 |
|------|------|------|
| `ProfileView.vue` | 1512 | Bento Grid 全塞单文件，含 8 个卡片逻辑 |
| `chat_service.py` | 951 | stream_chat + stream_agent_chat + 会话管理 + 消息持久化混在一起 |
| `FilesView.vue` | 1155 | 上传 + 列表 + 下载 + 配额展示单文件 |
| `DefaultLayout.vue` | 1149 | 侧边栏 + 顶栏 + 用户菜单 + 主题切换单文件 |
| `file_service.py` | 702 | 路径工厂 + 上传 + 合并 + 配额 + 列表单文件 |
| `KimiMessageItem.vue` | 884 | 消息渲染 + tool_call 气泡 + Pyodide 执行单文件 |
| `cookie_service.py` | 506 | 账户 + 交易 + 定价 + 监控单文件 |
| `SettingsView.vue` | 819 | 多 Tab 配置单文件 |

**风险**：单文件过大 = 难审查、难测试、易冲突。

**落地路径**：
1. `ProfileView.vue` → 拆为 `ProfileCard*` 子组件（UserInfo/KPI/RecentTasks/Security/Preferences/ApiKeys/Privacy/Audit 各一）。
2. `chat_service.py` → 抽 `AgentOrchestrator`（循环 + tool_call）+ `ChatRepository`（持久化）+ `ChatService`（薄编排）。
3. `DefaultLayout.vue` → `AppSidebar` + `AppHeader` + `UserMenu` 子组件。
4. `file_service.py` → `FilePathFactory` + `UploadService` + `QuotaService` + `FileQueryService`。

### P1-3 前端三套流式实现需统一

**现状**：
- `useChatStream.ts`（assistant_id 路径，Legacy SSE）
- `useAgentChatStream.ts`（agent_id 路径，Current SSE）
- `useAIWebSocket.ts`（Legacy WebSocket）

**风险**：SSE 解析逻辑重复，事件类型（text/tool_call/tool_result/error/done）处理分散。

**落地路径**：随 P1-1 Legacy 下线后，合并 `useChatStream` 与 `useAgentChatStream` 为单一 `useChatStream(payload)`，内部按 payload 字段分派。

### P1-4 BioTools 模块全程 Mock

**现状**：`docs/26.7.5/` 与 todo.md（2026-07-02）显示 BioTools（FASTQ QC / IGV / BLAST / 绘图）「当前阶段仅搭建前端 UI 骨架与静态交互，全程使用 Mock 数据，后端 API 在后续阶段逐步接入」。`router/index.ts` 路由已注册但 `src/cygnusx/tools/` 下无后端路由。

**风险**：用户可见入口但功能不可用，体验割裂。

**落地路径**：
1. 要么后端补 `/api/v1/tools/` 路由组（按 todo「后续阶段」计划：Rust 质控 + Celery BLAST 队列 + igv.js）。
2. 要么前端对未接入工具加「即将上线」占位，避免误操作。

### P1-5 CI/CD 缺失

**现状**：无 `.github/workflows/`，无 GitLab CI。所有检查（lint/typecheck/migrate-check）依赖开发者手动跑 `make`。分支有 6 个 feature 分支未清理。

**风险**：无自动化门禁 = 迁移链断裂、类型错误、lint 失败可进主干。

**落地路径**：
1. 加 `.github/workflows/ci.yml`：`ruff check` + `mypy` + `vue-tsc --noEmit` + `npm run build` + `make check-migrations` + `pytest`。
2. PR 必须过 CI 才能合并。
3. 清理已合并的 feature 分支。

### P1-6 配置分散且优先级隐晦

**现状**：三套配置源（`.env` / `core/config.py` 60+ 项 / `data/*.yaml` 业务配置），优先级关系不直观。`welcome_yaml` 硬编码 `/data/cygnusx/welcome/` 路径（config.py:116），与 `storage_path` 配置脱钩。

**风险**：配置项难发现，易遗漏；路径硬编码导致部署目录变更时断裂。

**落地路径**：
1. `config.py` 中所有路径配置统一基于 `storage_path` 派生（`welcome_yaml = f"{storage_path}/welcome/welcome.yaml"`）。
2. 整理配置文档表（配置项 / 来源 / 默认值 / 优先级），并入 README 或独立 `docs/configuration.md`。

## P2 — 建议迭代优化

### P2-1 文档冗余清理

**现状**：`docs/` 下 8+ 份 "copy" 文件、多版本架构文档（v2/v3/docx/md）、`docs/modules/` 与 `docs/docs/modules/` 重复、`docs/ JBrowse_2/` 目录名含前导空格、`docs/app/` 疑似未集成的独立 app。

**落地路径**：
1. 删除所有 `* copy.md` / `* copy.docx`。
2. 保留 v3 架构文档，旧版本移入 `docs/archive/`。
3. 合并 `docs/docs/` 到 `docs/`，删除重复。
4. 修正 `docs/ JBrowse_2/` → `docs/jbrowse_2/`。
5. 评估 `docs/app/` 去留。

### P2-2 引入国际化框架

**现状**：全中文硬编码（前端模板字符串、后端错误消息、YAML 文案）。`data/CygnusX.yaml` 已外置部分文案，但无系统化 i18n。

**落地路径**：引入 `vue-i18n`，把 `data/CygnusX.yaml` 的文案机制扩展为多语言 key-value；后端错误消息用 error code + 前端翻译。

### P2-3 可观测性增强

**现状**：仅 `loguru` 日志 + Flower 监控。无结构化日志规范、无分布式 tracing、无业务指标（任务成功率/Token 消耗/沙盒使用率）。

**落地路径**：
1. loguru 输出 JSON 格式（便于 ELK 采集）。
2. 引入 OpenTelemetry，对 FastAPI + Celery + DB 调用链埋点。
3. 业务指标：任务成功率、Agent tool_call 命中率、文件配额使用率、饼干消耗趋势。

### P2-4 依赖精简

**现状**：
- `litellm>=1.60.0`（重依赖，100+ 供应商）与自研 `openai_compatible.py` 功能重叠，Legacy 下线后应移除。
- `snakemake>=8.0.0` 是重依赖，但仅 worker 栈需要，web 镜像可拆分。

**落地路径**：
1. Legacy AI 下线后，从 `pyproject.toml` 移除 `litellm`。
2. 拆分 Dockerfile：web 镜像不装 snakemake，worker 镜像装。

### P2-5 远程执行模式补全

**现状**：`infrastructure/execution/remote.py` 存在但未完整跑通 Slurm/SGE。里程碑 Phase 3 设计的远程模式未交付。

**落地路径**：若有集群需求，按设计文档实现 HTTPExecutor（FastAPI 副进程部署在头节点，翻译 sbatch/qsub）；若无需求，文档标注「暂不支持」避免误导。

### P2-6 饼干系统并发压测

**现状**：`add_used_storage` 已用原子累加防并发双计，饼干 `adjust_balance` 有 CHECK 约束，但全链路未压测。生产级审查报告 P0 标注「并发扣费竞态」。

**落地路径**：用 `locust` 或 `k6` 模拟 20 并发用户同时提交任务扣饼干，验证余额不超支、交易流水无丢失。

### P2-7 知识库与 JBrowse 完善

**现状**：
- 知识库仅 3 篇正文（getting-started / rna-seq-tips / atac-seq-guide），内容偏薄。
- JBrowse `igv.js` 未真实引入（IGVBrowserView 用占位），`JBrowseViewer.vue` 存在但功能完整度待验证。

**落地路径**：补充知识库 SOP（实验流程、参数调优、FAQ）；引入 igv.js 配合 BAM/BigWig Range Requests。

## 优化优先级路线图

| 阶段 | 时间 | 目标 | 关键项 |
|------|------|------|--------|
| **紧急（阻塞上线）** | 1-2 周 | 消除生产风险 | P0-2 真实环境验证 + P0-3 安全加固（沙盒/备份/监控）+ P0-4 迁移规范 |
| **短期** | 2-4 周 | 可维护性基线 | P0-1 测试覆盖 + P1-1 Legacy 下线 + P1-5 CI/CD |
| **中期** | 1-2 月 | 工程质量提升 | P1-2 巨型文件拆分 + P1-4 BioTools 后端 + P1-6 配置治理 |
| **长期** | 持续 | 体验与扩展 | P2 全系列 |

## 一句话总结

CygnusX 的架构设计前瞻且落地扎实（DDD + YAML 流程引擎 + Agent MCP 闭环 + 双栈部署），但从「能跑」到「可上线」还差**测试网、安全加固、真实环境验证、Legacy 清理**四件大事。建议优先补测试与 CI、跑通待验证项、加固沙盒与备份，再逐步拆分巨型文件与下线 Legacy AI。
