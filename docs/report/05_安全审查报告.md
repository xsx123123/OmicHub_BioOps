## 二、认证与身份安全

### 2.1 JWT 实现（core/security.py）

**现状**：HS256 对称签名，Access 30min / Refresh 7d，2FA 用 TOTP + 5min 中间态 challenge token，decode 失败返 None，无黑名单。

**问题**：

| # | 问题 | 等级 | 说明 |
|---|------|------|------|
| A-1 | JWT 无吊销机制 | P0 | 登出/改密/封禁后，Access Token 在 30min 内仍有效，被盗无法即时止损 |
| A-2 | Refresh Token 无轮换 | P0 | 刷新时旧 refresh token 仍有效，可被重放（auth_service.py:191） |
| A-3 | HS256 对称签名 | P1 | 密钥泄露可伪造任意 token，万人级应改 RS256/Ed25519 |
| A-4 | 无 token 重用检测 | P1 | 未记录 refresh 使用轨迹，无法识别被盗后的异常刷新 |
| A-5 | 2FA 仅可选 | P2 | 管理员可不开 2FA，敏感操作无强制二次验证 |

**万人级方案**：
1. Redis token 黑名单：登出/封禁时把 access_token jti 写入 Redis（TTL=剩余有效期），AuthMiddleware 校验时查黑名单。
2. Refresh Token 轮换 + 重用检测：旧 refresh 入黑名单，检测到已黑名单 token 被使用 → 全量吊销 + 告警。
3. 引入 jti + 设备指纹：payload 加 jti + UA hash，支持单设备登出。
4. RS256 非对称签名：签发密钥仅 auth 服务持有，验签公钥分发给所有服务（K8s 多服务必备）。
5. 敏感操作强制 2FA：用户管理、饼干调账、AI Provider 配置、流程 YAML 编辑均要求二次验证。

### 2.2 密码安全（core/security.py:47-58）

**现状**：bcrypt + gensalt，实现正确。

**问题**：无密码强度后端校验、无密码历史、无登录失败锁定（全局限流 100/60s 过宽）。

**万人级方案**：后端 UserRegisterRequest 加强度校验（≥10 位 + 大小写+数字+符号）；Redis 记录失败次数，5 次锁定 15min；密码历史表禁止重复最近 5 个。

## 三、授权与访问控制

### 3.1 RBAC（middleware/rbac.py）

**现状**：仅 admin/user 两级，require_roles 实时查库。

**问题**：

| # | 问题 | 等级 | 说明 |
|---|------|------|------|
| B-1 | 仅两级角色 | P1 | 万人级需流程级/数据级/项目空间级权限 |
| B-2 | 无租户/组隔离 | P0 | 仅 user_id 隔离，万人级需 lab_group/tenant 维度 |
| B-3 | Admin 全权 | P1 | 无「流程管理员」「用户管理员」「财务」分离 |

**万人级方案**：RBAC + ABAC 混合。角色 super_admin/lab_admin/researcher/guest；资源带 lab_group_id + visibility(private/group/public)；新增 lab_groups/group_members/resource_policies 表。

### 3.2 JBrowse /tracks 路径越权（🔴 致命）

**现状**（nginx.conf:125-136）：
- `location ^~ /tracks/` 直接 `alias /data/cygnusx/`（所有用户数据根目录）
- `Access-Control-Allow-Origin *`（任意域可访问）
- IP 白名单被注释掉
- **无任何鉴权**：任何能访问 nginx 的客户端，知道用户 ID 路径即可下载任意用户的原始数据/结果

**风险**：组学数据（FASTQ/BAM/VCF）泄露，含品种信息、基因型，对农作物研究是核心资产。

**万人级方案**：
1. 移除 nginx 静态 alias，改 FastAPI 鉴权代理：`GET /api/v1/files/secure-tracks/{path}` 校验 JWT + 资源归属/共享权限后用 `FileResponse` + Range 支持。
2. 临时过渡：保留 alias 但启用 IP 白名单 + 加 `internal` 标记 + 经 X-Accel-Redirect 鉴权代理。

## 四、沙盒隔离（🔴 最大风险点）

### 4.1 现状（infrastructure/sandbox/pool.py）

**致命问题**：`pool.py:49` 用 `docker.from_env()`，需要 `/var/run/docker.sock` 访问权限。但当前 docker-compose.yml **未挂载 docker.sock 到 web 容器** —— 这意味着：
- 当前容器化部署中**沙盒功能实际不可用**（is_available 返回 False，降级报错）
- 若为启用沙盒而挂载 docker.sock，则 **web 容器获得宿主 Docker 控制权 = 容器逃逸**，可启停/删除任意容器、挂载宿主任意目录

**其他沙盒问题**：

| # | 问题 | 等级 | 说明 |
|---|------|------|------|
| D-1 | Docker Socket = 宿主 root | P0 | 挂载 docker.sock 等同 `--privileged`，可逃逸到宿主 |
| D-2 | 无 seccomp/AppArmor | P0 | 用户代码可调用任意系统调用（ptrace/mount/socket） |
| D-3 | 无 user namespace 隔离 | P1 | 容器内 root = 宿主 root（除非加 userns-remap） |
| D-4 | 无只读根文件系统 | P1 | 用户代码可写入容器任意目录、植入后门 |
| D-5 | 网络未隔离 | P1 | sandbox_docker_network 默认 cygnusx_default，可访问 DB/Redis 内网 |
| D-6 | 无 PID/进程数限制 | P2 | fork bomb 可拖垮宿主 |
| D-7 | 无 CPU/内存硬限制 | P2 | 仅 mem_limit + cpu_shares（软限制），无 nano_cpus 硬限制 |
| D-8 | 用户代码无审计 | P1 | 不记录谁执行了什么代码，无法追溯恶意行为 |

**万人级方案**（三选一，按隔离强度递增）：

**方案 A（推荐，K8s 原生）**：废弃 Docker-in-Docker，改 **K8s Job per 代码执行**：
- 每次代码执行创建一个 K8s Job（轻量 pod，自动回收）
- Pod 配置：`runAsNonRoot: true`、`readOnlyRootFilesystem: true`、`seccompProfile: RuntimeDefault`、`networkPolicy: deny-all`、`resources.limits` 硬限制
- 数据卷用 ReadOnlyMany 挂载用户数据，输出走对象存储
- 优势：K8s 原生隔离、资源限额、自动回收、与集群统一调度

**方案 B（gVisor）**：沙盒镜像用 gVisor runtime（`runtimeClassName: gvisor`），用户态内核拦截系统调用，阻止逃逸。适合保留现有 Docker pool 架构的过渡期。

**方案 C（Kata Containers）**：每个沙盒独立轻量 VM，硬件级隔离。最强但开销最大，适合高敏感场景。

## 五、任务调度安全

### 5.1 命令注入面

**现状**：
- `local.py:72-93`：snakemake 命令用 list 形式 `create_subprocess_exec`（非 shell），参数直接拼接 —— **不存在 shell 注入**，✅ 正确
- `binary.py:33`：同样 list 形式，✅ 正确
- 但 `config_file_param`、`snakefile` 路径来自 YAML 配置，若管理员写入恶意 YAML 可执行任意流程 —— 需校验 snakefile 路径在白名单目录内

**问题**：

| # | 问题 | 等级 | 说明 |
|---|------|------|------|
| E-1 | snakefile 路径无白名单 | P1 | flows/*.yaml 的 execution.snakefile 可指向任意路径，如 `/home/zj/pipeline/RNAFlow/snakefile`（硬编码宿主路径） |
| E-2 | 无租户资源限额 | P0 | 任务 cores 从 YAML 读（默认 4），用户可提交 cores=64 任务耗尽集群 |
| E-3 | work_dir 无磁盘配额硬限 | P1 | 仅 user.used_storage 软检查，任务中间文件可超额 |
| E-4 | 任务日志含敏感信息 | P2 | Snakemake 日志全量回写 DB + Redis，可能含样本名/路径 |

**万人级方案**：
1. snakefile 路径校验：必须位于 `flows/` 或配置的 pipeline 白名单目录内，resolve() 后校验前缀。
2. 租户资源限额：User 表加 `max_cores`/`max_parallel_tasks`，提交时校验；Celery 队列按租户分。
3. 磁盘配额：work_dir 用 XFS quota 或 K8s PVC resources.limits.ephemeral-storage 硬限。
4. 日志脱敏：扩展 sensitive_keywords 机制到任务日志。

## 六、数据存储安全

### 6.1 API Key 加密（core/security.py:13-44）

**现状**：Fernet 对称加密，密钥 `ai_provider_key_encryption_key` 单一固定值，首次部署后不可更改。

**问题**：

| # | 问题 | 等级 | 说明 |
|---|------|------|------|
| F-1 | 加密密钥单点 | P0 | 密钥泄露 = 所有 AI Provider API Key 泄露；密钥丢失 = 所有配置不可解密 |
| F-2 | 无密钥轮换 | P1 | 固定值不可更改，无法应对密钥泄露事件 |
| F-3 | 密钥明文存 .env | P1 | .env 文件无加密，宿主被入侵即泄露 |

**万人级方案**：引入 KMS（Key Management Service）：
- **K8s 场景**：用 Kubernetes Secrets + 云 KMS（阿里云 KMS / AWS KMS）管理 DEK（Data Encryption Key），加密后的 DEK 存 Secret，运行时解密。
- **密钥轮换**：支持多版本主密钥，加密时记 key_version，解密时按 version 路由。
- **信封加密**：主密钥（KEK）存 KMS 不出域，数据密钥（DEK）加密后存 DB，每个 AI Provider Config 独立 DEK。

### 6.2 数据库与备份

**现状**：PostgreSQL 单实例无主从、无备份、无 PITR（Point-in-Time Recovery）。Redis 单实例无持久化策略配置。

**万人级方案**：
1. PostgreSQL：主从流复制 + PgBouncer 连接池 + WAL 归档到对象存储（PITR）+ 每日全量逻辑备份。
2. Redis：AOF + RDB 持久化 + Sentinel 哨兵高可用（或 Redis Cluster）。
3. 备份加密：备份文件用 KMS 加密后存对象存储，异地容灾。

## 七、传输安全

### 7.1 CORS（core/config.py:51）

**现状**：`cors_origins = ["http://localhost:5173", "http://localhost:3000"]`，生产应改为实际域名。但 `allow_credentials=True` + `allow_methods=["*"]` + `allow_headers=["*"]` 过宽。

**万人级方案**：cors_origins 从环境变量读白名单域名列表；allow_methods 限定实际用到的（GET/POST/PUT/PATCH/DELETE）；allow_headers 限定（Authorization/Content-Type）。

### 7.2 HTTPS

**现状**：prod.yml 支持 SSL 但证书路径硬编码 `/etc/ssl/certs/ssl-cert.pem`。无 HSTS、无证书自动续期。

**万人级方案**：K8s 用 cert-manager + Let's Encrypt 自动签发续期；Ingress 加 HSTS header（`Strict-Transport-Security: max-age=31536000; includeSubDomains`）。

## 八、供应链安全

**现状**：无 CI 门禁、无镜像签名、无依赖扫描。Dockerfile 用 `:latest` tag（uv 镜像）。

**万人级方案**：
1. CI 流水线：GitHub Actions 跑 ruff/mypy/vue-tsc/pytest + Trivy 依赖扫描 + Cosign 镜像签名。
2. 镜像锁定：所有 FROM 用 `@sha256:...` digest 锁定。
3. 准入策略：K8s 用 Kyverno/OPA Gatekeeper 拒绝未签名镜像。

## 九、运维与可观测

**现状**：仅 loguru + Flower。

**万人级方案**：
1. 指标：prometheus-fastapi-instrumentator 暴露 `/metrics`，Grafana 看板（QPS/延迟/错误率/队列深度/任务成功率）。
2. 日志：loguru JSON 输出，Filebeat 采集到 Loki/ELK。
3. 追踪：OpenTelemetry，FastAPI + Celery + DB 全链路 trace。
4. 告警：Alertmanager → 钉钉/飞书，5xx >1%、队列积压 >100、任务失败率 >10% 触发。
5. 入侵检测：Falco（容器运行时行为检测）+ 审计日志 SIEM 对接。
