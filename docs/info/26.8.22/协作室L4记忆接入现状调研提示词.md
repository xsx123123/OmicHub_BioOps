# 协作室 L4 × 记忆系统接入现状调研提示词

> 版本：v1.1 ｜ 日期：2026-08-21
> 任务性质：**只查不改的代码调研**。供 kimi code 执行；报告回来后设计评审侧核对并转化为 L4 记忆适配方案。
> 起因：平台记忆框架文档（`memory_architecture.md`，2026-08-18）自承"不是所有入口统一 Runtime，普通聊天/Studio/AgentTeams 各装各的上下文"。评估结论：L1 无需记忆（零 token 层）、L2 完全接入、L3 文件型异构接入均合理；**L4 是最薄弱环节**，需先拿代码证据再设计。

## Part 1 背景与已知锚点

**记忆系统要点（被调研对象）**：
- v2 灰度中（`memory_v2_enabled` 默认 False）：`memory_blocks` 常驻块（user_id+agent_id+block_name 唯一键、乐观锁）+ `memory_facts` 语义召回（scope: profile/preference/project/summary、superseded 修正链、content_hash 幂等、时间衰减）；
- 读：`AgentMemoryService.build_prompt_context(_v2)` 装配 `<user_memory>` 不可信注入（3200 字节预算）；
- 写：memory 工具包（`data/ai/tools/memory.yaml`：cygnusx_save_memory / update_memory_block / search_memory / forget_memory）+ Celery `settle_session_memory(session_id)` 增量沉淀（游标 `chat_sessions.last_settled_message_id`、区间幂等 range_key、LLM 抽持久事实）；
- 写入纪律：v2 开启时 ChatService 把"只记持久偏好/纠错/长期项目事实，不记一次性任务"追加进系统提示词。

**L4 链路已有证据锚点（来自能力咨询调研报告，按当前代码校准）**：
- 房间回复链：`POST /rooms/{room_id}/messages` → Celery `respond_to_room_namespace_message`（`src/cygnusx/infrastructure/celery_app/tasks/agentteams.py:98`）→ `agentteams_room_response_service.py:239 respond_room` → `:297 _respond_locked` → `:1699 _build_question` → `:1579 _manager_agent_with_audit` → `AgentConsultationService.run_consultation`（`:293`）；`assemble_context` 实际位于 `src/cygnusx/application/services/agent_service.py:763`，由 `run_consultation` 在 `agent_consultation_service.py:325` 调用；
- 房间 LLM 会诊的用量落库与扣费由 `AgentConsultationService._record_usage`（`:921`）调用 `agentteams_usage_service.py:38 record_consultation_usage`；仅在 token 用量有效且 `requester_ref` 可解析为 UUID 时，才创建/更新 `agentteams:<case_id>` 的 `ChatSession` 并写入 assistant `ChatMessage`（`agentteams_usage_service.py:66-127`），不要预设每次会诊都落库；
- Manager 已声明 memory 工具包：`data/ai/agentteams_manager.yaml:71` 的 `tool_packs` 含 `memory`；这是配置证据，不等于房间实际调用或 prompt 注入证据；
- 房间链路有用户偏好 SELECT：`agentteams_room_response_service.py:1621-1639`，读取 `UserModel.preferences` 下的 `agentteams` 子对象，并由 `_build_question` 的 `preferences` 参数用于称呼、语言、风格、自主模式等话术偏好。

**设计原则（调研结论的评价标尺）**：
1. Case 事实以事件流/血缘为准，长期记忆不得充当 Case 事实的事实源（记忆会漂移，execution_log 不会）；
2. "关于人的记忆"（profile/preferences）与"agent 策展的工作习惯"是两个语义层，跨层连续性需求不同；
3. 愿景前提不可触碰：L4 定位与成本闸门、Manager 五职责、专家四段契约、甲方完整回路。

## Part 2 调研提示词（paste-ready）

```
只做代码级调研，禁止修改任何文件。所有结论标注文件路径与关键代码行；置信度分「已证实（附证据）/ 未找到（明说没有）/ 存疑（说明缺什么证据）」三档；不要用配置存在代替调用链证据——必须追到实际调用点。

背景：CygnusX 记忆系统（memory_blocks/memory_facts/settle，详见 `src/cygnusx/application/services/agent_memory_service.py` 与 `src/cygnusx/infrastructure/celery_app/tasks/memory.py`）在 L2 聊天接入、L3 Studio 走文件型记忆。现在需要弄清 L4 协作室（AgentTeams 房间）的实际接入状态。已知锚点：房间回复走 `agentteams_room_response_service.py` 的 `respond_room` → `_respond_locked` → `_build_question`（当前约 `:1699`）→ `AgentConsultationService.run_consultation`（当前约 `:293-325`，上下文装配实际进入 `agent_service.py:763`）；会诊用量落库路径为 `agent_consultation_service.py:_record_usage` → `agentteams_usage_service.py:record_consultation_usage`，其合成会话格式为 `agentteams:<case_id>`，不是固定的 room 命名空间格式；Manager 配置声明挂了 memory 工具包（`data/ai/agentteams_manager.yaml:71`）。

Q1 L4 读取面：房间回复链路的上下文装配是否调用 `AgentMemoryService.build_prompt_context` 或 `build_prompt_context_v2`？即 Manager 在房间里作答时，prompt 里有没有 `<user_memory>` 注入（常驻块 + 事实召回）？逐分支确认：主回路（`_respond_locked` 中约 `:427`）、@专家直答（`_respond_locked` 中约 `:591-666`）、tool_execute（约 `:900-1030`）、多专家会诊分支。另查 `agentteams_room_response_service.py:_manager_preferences`（当前约 `:1621-1639`）的用户偏好 SELECT 实际读的是什么、注入到哪。v2 开关 on/off 两种状态下分别是什么行为？

Q2 settle 覆盖范围（重点风险）：`settle_session_memory` 的投递点在哪里（核对 `chat_service.py:_enqueue_memory_summary` 与 `:_maybe_enqueue_memory_settle` 的具体条件）？房间会诊产生的合成会话 `agentteams:<case_id>` 是否可能满足投递条件被 settle；注意该会话由 `agentteams_usage_service.py` 创建，通常只写 assistant 用量消息，且会话状态为 `system`、模式为 `agentteams`，并且创建时没有显式设置 `ChatSessionModel.agent_id`。若会 settle：settle 的 LLM 抽取会以什么 `(user_id, agent_id)` 写入 `memory_facts`（特别核实是否落成 `agent_id == ""`）？Case 临时事实（样本分组、文件路径、中间决策）是否会借此进入长期记忆？若不会，给出阻断它的具体代码（会话类型标记？来源过滤？还是根本没接投递点）。同时确认 settle 游标对这种合成会话的行为。

Q3 分区语义：L4 中 Manager 调用 `cygnusx_save_memory` / `cygnusx_search_memory` 时，实际使用的 `(user_id, agent_id)` 是什么——是否为 `agentteams-manager`？必须同时核对 `agent_memory_tool_service.py:_memory_agent_id`：`profile/preference` 写入会把 `agent_id` 归一为 `None` 以实现跨 Agent 共享，而 `project/summary` 写入及搜索使用当前 ToolInvocationContext 的 `agent_id`；因此不能笼统地以“按 agent_id 全隔离”下结论。L2 聊天同工具用的 `agent_id` 是什么（不要预设为 `agent-general`，追到运行时 `ctx.agent.agent_id`）；据此给出事实结论：甲方在 L2 存的偏好，L4 的 Manager 能否召回到（按 scope 区分共享/隔离）？多专家会诊中专家角色（`agent-qc`/`agent-data`/领域专家）有没有挂 memory 工具、有没有记忆注入、写入落在哪个分区？

Q4 写入纪律与敏感拦截在 L4 的生效状态：v2 开启时追加的"记忆写入纪律"（只记持久偏好等四条）是否出现在 L4 房间/会诊的系统提示词装配里？敏感信息拦截（API Key/Token/密码）对房间链路模型发起的 cygnusx_save_memory 是否同样生效（同一服务入口还是旁路）？

Q5 Studio↔L4 边界：Studio 的 MEMORY.md/.memory/ 文件型记忆与 Case 工作区是否有任何交集（房间/Case 是否读写工作区记忆文件、cygnusx_workspace_remember 是否对 L4 角色可用）？Case 绑定项目后，项目工作区记忆与 case 血缘各自承载什么，现状有没有重叠写入？

交付格式：
1. 五节事实清单（每节：结论 / 证据位置 / 三档置信度）；
2. 一张 L4 记忆数据流图：读取注入点、模型主动写、settle 异步写三条链路，标注每条链路的 (user_id, agent_id) 与落表；
3. 风险登记册：按"Case 事实泄漏进长期记忆 / 跨层失忆 / 纪律或拦截在 L4 失效 / 其他"分类，每项给出证据与严重度建议；
4. 汇总表：读取面 / 写入面 / settle 面 / 纪律面 × L2 / L3 / L4 的接入状态矩阵。
```

## Part 3 设计侧预判（待报告证实/推翻）

1. **Q1 预判**：房间链路大概率**没有** `<user_memory>` 注入（文档自承各入口各装；能力咨询调研中 `_build_question` 注入清单未见记忆项）——Manager 挂着记忆工具却看不到记忆上下文，只能靠主动 search。若证实，适配方向是把 `build_prompt_context_v2` 接进房间装配点。
2. **Q2 预判**：合成会话很可能**没有** settle 投递点（settle 挂在 ChatService 会话阈值上，房间走 Celery respond 任务）——若证实则风险不存在但要在适配方案里写明"永远不为 agentteams 合成会话开 settle"的禁区；若推翻（会 settle），升 P0：Case 事实正在持续渗入长期记忆。
3. **Q3 预判**：分区隔离属实（Manager 与 general 互不可见）——这本身可作为设计选择保留，但"跨层失忆"是否符合甲方体验需要用户决策（共享 profile 层 / 维持全隔离 / 显式同步机制）。
4. 任何情况下**不改**的方案锚点：Case 事实源永远是事件流+血缘；记忆只承载"关于人的软偏好"。
