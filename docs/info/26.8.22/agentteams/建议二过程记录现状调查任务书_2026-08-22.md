# 建议二「Case 过程全量记录」现状调查 · 任务书

> 日期：2026-08-22
> 用途：交给编码 Agent 对现状代码做**只查不改**的证据化调查，调查结果发回后由本对话逐项核对。
> 上游文档：《协作室两项优化建议调研_2026-08-22.md》（原调研）、《协作室两项需求审核意见_2026-08-22.md》（审核意见，下称「审核文档」）。
> 原则：只做代码级调研与评估，**禁止修改任何代码**；先读代码再下结论；所有结论必须标注 `文件:行号`；无法核实的条目标「未找到/待确认」，禁止猜测。

---

## 1. 调查背景（给编码 Agent 的上下文）

平台计划为协作室 Case 增加「每步详细信息全量记录」（LLM 输入全文、输出全文、思考过程、工具调用/结果原文），最终支撑过程回看与可复现。原调研文档已给出一份 as-built 评估（结论均带文件:行号），本次调查的任务是：

1. **证实/证伪**原调研的关键结论（行号可能因代码迭代漂移，以实际代码为准）；
2. **补齐**原调研未覆盖的事实（调用路径覆盖面、MinIO 对象布局现状、权限校验点、遥测透传链路）——这些是审核文档 §2 标出的机制空白，是后续「阶段 0 设计」的输入；
3. 对「**一处覆盖三条路径**」给出明确裁决（审核文档 §2.5，本次调查的第一优先级）。

## 3. 交付格式（写死——同时是拿回报告后的核对 checklist 基准）

1. **A 节裁决结论**（一段话 + 调用链图）：三条路径是否共用执行节点 / 共用 provider，真正的「一处覆盖」埋点在哪一层。
2. **B 节核实表**：每条给出 ✅证实 / ❌证伪 / ⚠️部分成立 + 实际代码证据（文件:行号 + 关键代码摘录）；行号漂移的给出新行号。
3. **「路径 × 记录粒度」矩阵**：三条调用路径 ×（prompt 全文 / 输出全文 / reasoning / 工具参数原文 / 工具结果原文 / 模型与采样参数 / 关联键），每格标 已持久化 / 仅内存 / 截断 / 不存在 + 代码位置。
4. **C/D/E/F 事实清单**：按节组织，每条带代码位置。
5. **风险与意外发现**：调查中发现的、不在上述清单内但与「过程记录」相关的隐患（如已有未用的字段、半成品实现、明显的坑）。
6. **不做任何代码修改，只输出报告。** 找不到的东西写「未找到」，不要推断。

## 5. 拿回报告后的核对 checklist（本对话侧执行）

- [ ] A 节裁决是否与旧调研「一处覆盖三条路径」冲突 → 冲突则在审核文档留修正记录（哪条旧判断、被什么证据推翻）；
- [ ] B 节逐条对照：证伪的条目要区分「行号漂移」与「结论本身错了」；结论错了的回写修订原调研；
- [ ] 矩阵里的「不存在」先区分**刻意如此**（如结论截断可能是有意的存储控制）与**真缺失**，别把 ❌ 直接转成待办；
- [ ] 检查是否存在「只差一次调用/登记」的低成本止血点（如 session.id 注入已存在，只差把 `agentteams:{case_id}` 传进去），抽出来做阶段 0 前置，不照搬报告排期；
- [ ] C 节若发现已有「MinIO 侧车对象」先例 → 阶段 0 的对象布局直接套该先例，设计成本大降；
- [ ] E 节事实直接填入审核文档 §2.3 的可见性矩阵，定稿权限设计；
- [ ] 报告自身完整性：矩阵缺格、B 表缺行的，让编码 Agent 补全后再定稿；
- [ ] 核对结论落成三块（确认的问题 / 保留意见 / 修订后的行动顺序），追加进审核文档。
