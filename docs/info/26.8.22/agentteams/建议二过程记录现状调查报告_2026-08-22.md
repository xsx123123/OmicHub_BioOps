### A2 三条路径是否共用 `llm_call_node`

**否。三条路径完全不经过 `llm_call_node`。**

- `llm_call_node` 定义于 `src/cygnusx/infrastructure/execution/langgraph_nodes.py:94`。
- 它被 `LangGraphRuntimeService` 包装（`langgraph_runtime.py:54`）。
- 在 `src/cygnusx` 范围内，仅 `chat_service.py:8691` 与 `:8849` 使用 `LangGraphRuntimeService`。
- AgentTeams 的 `agent_consultation_service.py`、`parallel_subagent_service.py`、`agentteams_room_response_service.py` 均未 import/call `llm_call_node`。

因此，`llm_call_node` 只能覆盖 AI 聊天/Studio 工作流里走 `LangGraphRuntimeService` 的分支，**覆盖不了 AgentTeams 的任何 LLM 调用**。

### A3 三条路径是否共用 provider 层

**是。三条 AgentTeams 路径最终都收敛到 `openai_compatible.py` 的 `ProviderManager.chat_stream`。**

- 入口：`parallel_subagent_service.py:655`
- 统一包装器：`openai_compatible.py:663-713` `ProviderManager.chat_stream`
- 实际 provider：`openai_compatible.py:196` `OpenAICompatibleProvider.chat_stream` → `:381` `httpx.stream("POST", .../chat/completions)`
- AgentTeams 范围内**未找到**绕过 provider 直接调 litellm/httpx 的地方。

**「一处覆盖」埋点层级裁决：**

- 若只要求「拦截所有 LLM 调用」：在 `openai_compatible.py:663`（`ProviderManager.chat_stream`）或 `:682`（进入具体 provider 前）埋点即可一处覆盖 AgentTeams 全部调用。
- 若还要求带上 `case_id` / `work_item_id` / `round_number`：**必须埋在 `parallel_subagent_service.py:655` 之前**（如 `:637` 拿到 `round_number`、`:625` 拿到 `child_session_id` 后），或改造调用链把业务键通过 `kwargs` 透传到 provider 层。
- 埋在 `llm_call_node` 会**完全漏掉 AgentTeams**。

### A4 业务关联键在哪一层可得

### C2 启动重放机制

`bridge/audit.py:119-134`：

```python
def _load_minio(self) -> None:
    self._idempotency.update(self._minio.read_receipts())
    self._archived_room_ids.update(self._minio.list_archived_room_ids())
    for case_id in self._minio.list_case_ids():
        for event in self._minio.read_events(case_id):
            self._ingest(event)
```

重放顺序：

1. 恢复 `receipts/` 幂等 receipt；
2. 扫描 `archive/rooms/` 建立已归档房间集合；
3. 遍历 `cases/` 下每个 case，按卷序读取事件并喂入 `_ingest` 重建内存索引。

卷读取顺序：`minio_store.py:182-190` 保证 `audit.jsonl` 最前，其余 `audit-YYYYMMDD.jsonl` 按字典序（即时间序）。

## 风险与意外发现

1. **`llm_call_node` 与 AgentTeams 完全无关**。旧调研中“一处覆盖三条路径”的假设不成立；若按此设计实施，会漏掉全部协作室 LLM 调用。
2. **`session.id` 未在 AgentTeams 链路注入**。管理端无法按 Case 聚合 Trace，过程记录也难以与 OTel span 关联；只需在平台端点或 Bridge/Gateway 显式设置 `session_id_var` 即可低成本修复。
3. **`correlation_id` 有读取逻辑但无写入点**。`agentteams_audit_events.py:45` 定义了常量、`agentteams_audit_chain_service.py:179` 只负责提取，但生产代码没有地方写入，导致审计链的 correlation 能力目前为空转。
4. **Trace 在 Bridge→Gateway→平台三跳全断**。跨服务问题定位困难；`work_item.trace_id` 已经存在却未进 `consult_payload`。
5. **`room.agent_message` 截断长度不一致**。主路径与工具执行路径使用常量 `10_000`，但 `@Manager` 直答路径硬编码 `8_000`（`agentteams_room_response_service.py:672`）。
6. **已有「大对象写 MinIO、事件/DB 行里带 s3_uri」先例**。阶段 0 设计过程记录对象布局时可直接复用该模式，降低设计成本。
7. **Redis 审计 stream 是全局单条且无 MAXLEN/TTL**。在 MinIO 模式下，stream 事件（`room.agent_stream`）仍进全局 Redis stream，长期运行可能膨胀；当前只在 Case 下线时手动 `XDEL` 裁剪。
8. **Provider 层函数签名不含业务键**。若要在 provider 层做「一处覆盖」且保留 `case_id`/`work_item_id`/`round`，需要改 `ProviderManager.chat_stream` 的调用方透传 `kwargs`，或把埋点下沉到 `parallel_subagent_service._child_loop`。
9. **前端事件时间线只展示 `summary`**。即使后端未来写入完整 prompt/output，也需要新增接口或扩展 `payload` schema，否则前端不会自动展示。
