## 0. 结论先行

| 建议 | 是否合理 | 改造规模 | 关键决策点 |
|---|---|---|---|
| 1. 邀请平台其他用户加入房间（"+"按钮邀请、被邀请人弹窗确认、创建者为管理员） | **合理，且大部分积木已存在** | 平台侧中等；Bridge 侧取决于协作深度 | Bridge 单 `requester_ref` 语义是否放开（见 §1.6） |
| 2. Case 每步详细信息（模型思考+输入）全部记录并可复现 | **方向合理，但现阶段差距大，需分层补** | 大；建议只做「记录全量化」，「重新执行复现」暂不作承诺 | LLM 内容记录补在 provider/执行节点层（见 §2.6） |

两条建议都符合协作室 L4 愿景（多人协作 + 可审计可复现），且都能在不推翻现有架构的前提下增量落地。

## 1. 建议一：邀请平台用户加入协作室房间

### 1.1 需求拆解

1. 房间输入框旁加「+ / 邀请」按钮，可搜索并选择平台其他用户；
2. 被邀请用户在平台收到弹窗/通知，可选择是否加入；
3. 接受后，该房间出现在被邀请人的协作室房间列表中；
4. 创建者（owner）是房间管理员。

### 1.2 现状：房间是严格单主模型

- 房间表 `AgentTeamsRoomModel`（表名 `agentteams_rooms`）只有 `owner_id: String(50)` 一个归属字段，**无任何成员/角色字段**（`src/cygnusx/infrastructure/database/models/chat.py:83-109`）。
- 所有房间端点统一走 `AgentTeamsRoomService.get_room()`，非 owner 直接 403（`src/cygnusx/application/services/agentteams_room_service.py:191-199`）；`list_rooms` 只查 `owner_id == current_user`（`:183-189`）。create/list/get/delete、element-session、messages、confirm-proposal、events/stream 无一例外（`src/cygnusx/api/v1/agentteams.py:704-882`）。
- **双层隔离**：除 DB owner 校验外，房间事件流挂在 Bridge 侧，命名空间以 `requester_ref=owner_id` 创建（`agentteams_service.py:1430-1447`），每次拉事件/发消息都经 `_get_case_for_requester` 校验（`agentteams_service.py:1228-1232`）。
- 立项确认卡消费硬编码「只有房间所有者可消费立项确认令牌」（`agentteams_room_service.py:455-456`）。
- 房间/Case **没有任何 role 或 admin 概念**，唯一权限判据就是 `owner_id == current_user`；平台级 admin 对房间也无隐式越权。

### 1.3 可复用的现有积木（这是「合理」的主要依据）

| 需求 | 现成积木 | 位置 |
|---|---|---|
| 成员表模型 | `TeamModel + TeamMemberModel`（角色 owner/writer/reader + 唯一约束），是房间成员表的直接模板 | `infrastructure/database/models/team.py:23-65` |
| 定向通知（被邀请人提示） | `NotificationModel.target_user_id` + `NotificationService.create`；前端铃铛+未读角标+通知抽屉 | `models/notification.py:13-37`、`api/v1/notification.py`、`frontend/src/components/NotificationDrawer.vue`、`layouts/DefaultLayout.vue:490-495` |
| 邀请按钮 UI 模式 | 房间头部按钮区（设置抽屉按钮模式）、`MentionMenu` 弹层交互 | `AgentTeamsRoomView.vue:1714`、`KimiChatInput.vue:1254-1255` |
| Matrix 侧多用户入房 | 用户 Matrix 身份派生天然支持任意平台用户（`cygnusx-user-<uuid>` 动态解析）；Gateway 已有 invite+join 兜底原语；`element-session?room_id=` 已能"先幂等入房再签发" | `agentteams_service.py:94-108`、Gateway `config.py:167-189`、`matrix_client.py:58-82`、`app.py:129-149` |
| 实时消息分发到多个客户端 | SSE 事件流本来就是服务端 0.5s 轮询包装，多个用户各自拉流即可，无单消费者假设 | `agentteams_room_service.py:356-373`、`agentteams.py:855-882` |

### 1.4 缺口（需要新建的）

1. **房间成员表**（全新）：`agentteams_room_members(room_id, user_id, role, invited_by, status=pending/accepted/declined)`，直接套 `TeamMemberModel` 模式。`owner_id` 保留为房主/管理员语义——「创建者是管理员」这一点现状已经天然成立。
2. **邀请端点组**（挂在 `api/v1/agentteams.py`）：发起邀请（owner-only）、我的待处理邀请列表、接受/拒绝。接受时：写成员行 → Matrix ensure/join → 定向通知邀请人。
3. **非管理员用户搜索端点**（邀请选择器的数据源）：现在用户列表仅 admin 可用（`api/v1/users.py:182-197`），`get_user` 非本人 403（`:200-212`）。需新增一个仅返回 id/nickname/avatar 的最小目录端点。
4. **通知的「接受/拒绝」动作**：通知模型无 action 字段，需前端按通知类型特判渲染按钮，或扩展 payload。实时性注意：通知角标搭 60s 轮询便车（`DefaultLayout.vue:226-228`），**被邀请人最晚 60 秒才看到提示**；要「即时弹窗」需新增推送通道（房间 SSE 是每房间独立通道，不适合作全局通知总线）。
5. **前端**：房间列表接口要返回「我作为成员的房间」；邀请 Modal + 成员列表；被邀请方通知特判。

### 1.5 不要走的弯路

- **不要用 `@用户名` 做邀请入口**。现有 `@` 点名是前端插纯文本、后端正则解析（`agentteams_mention_resolver.py:12-86`），未识别的 @ 词会作为 `unknown_mentions` 交 Manager 评估——用 @ 邀请用户会和 Agent 点名解析撞车。邀请必须走独立 UI（头部「+」按钮 + Modal）。

### 1.6 关键架构决策点：Bridge 的单 `requester_ref`

这是整个需求里**唯一真正动架构的地方**。Bridge 侧房间命名空间和 Case 都绑单一 `requester_ref`（`agentteams_service.py:1228-1232, 1430-1447`），成员的请求会被拒。两条路线：

- **路线 A（推荐先做）：成员可聊天可看，owner 持单。** 平台侧把 `get_room`/`list_rooms` 放宽为「owner 或 accepted member」，成员发言以成员身份写事件（actor 字段天然支持），但立项、审批、删除仍 owner-only。不动 Bridge 模型，改动集中在平台房间服务 + 前端 + 通知，约 1-2 周量级。
- **路线 B（完整多用户协作）：Bridge 支持参与者列表。** 要动 Bridge 的 Case 模型、`create_room_namespace` 的 requester 写入、事件校验，以及 Redis 反向同步绑定（现值格式 `room_id|requester_ref` 单值，`agentteams_room_sync_service.py:116`）改为按 sender identity 反查平台用户（Gateway 已有反向解析 `config.py:191-204`）。影响面跨三个进程，建议作为第二阶段。

其余零散决策：成员是否可立项（`agentteams_room_service.py:455-456` 的 owner 硬断言）；删除房间时 Matrix 离房要遍历所有成员身份（现只离 owner，`:232-243`）。

## 2. 建议二：Case 分析每步详细信息的记录与复现

### 2.1 现状一句话

**终态结论、结构化判决、产物血缘都已持久化且可核验；但模型的 prompt 全文、输出全文、思考过程（reasoning）没有任何持久化落点——只记了聚合指标和截断摘要。**

### 2.2 各层记录粒度实测

**平台 Agent 运行时（会诊/房间响应）**
- LLM 调用的 OTel span 只有 `ai.status / duration_ms / prompt_tokens / completion_tokens / finish_reason`，**不含 prompt、输出、reasoning 文本**（`infrastructure/ai_provider/litellm_provider.py:186-197`、`openai_compatible.py:673-702`）。
- `logs/cygnusx.spans.json.log` 是 OTel `JsonlSpanExporter` 的 span 级 trace（管理端瀑布图用），不是 LLM 内容 trace（`core/span_store.py:44-58`）。
- 会诊每轮的 `round_reasoning` 只累积在内存 state 供回灌下一轮模型，**不落库**（`infrastructure/execution/langgraph_nodes.py:118-168`）。
- Manager 思考流（`room.agent_stream`，≥24 字符一条，payload 含 `channel=reasoning|content`）投影到 Bridge——**但 MinIO 模式下 stream 类事件不持久**，只走 Redis 热缓存，进程重启即丢（`bridge/audit.py:6-13, 36, 231-248`）。用户只能在 SSE 在线时看到，刷新后历史不可得。
- 持久化的只有终态：`room.agent_message`（content 截断 + manager_report 结构化结论，`agentteams_room_response_service.py:548-561, 1056-1072`）；会诊用量隐藏消息只存 `conclusion[:2000]` + usage（`agentteams_usage_service.py:98-113`）。

**Worker / Bridge 层**
- Worker 是薄壳：LLM/工具调用全部发生在平台侧（Bridge→Gateway→会诊服务代跑），Worker 自身不记录执行过程（`worker/production_runner.py:251-328`）。
- 上报粒度是「结论级」：`execution_summary` 是任务目标截断 1800 字符；work item `summary=gateway_result.conclusion` ≤4000 字符（`bridge/service.py:1213-1347`、`models.py:330, 402`）。
- 平台代跑产生的步骤证据由 `_BridgeEvidenceProjector` 投影，但全是截断摘要：工具参数 `args_summary[:N]`、结果 `result_summary[:500]`，超长合并省略；**没有 prompt/LLM 输出投影**（`agent_consultation_service.py:108-254`）。
- Bridge 事件结构只有 `event_id/recorded_at/case_id/actor/event_type/payload`，**没有 model/prompt/tokens 字段**（`bridge/audit.py:206-218`）；`correlation_id 无写入点`（现状文档 §9.3）。

**复现能力**
- `case_artifact_versions.environment_snapshot` 只记 `agent_id/capability/work_item_id/app_version/app_git_sha/execution_summary[:2000]`——无模型版本、无参数、无 prompt、无镜像 digest（`agent_consultation_service.py:854-861`；模型注释自证「不做环境声明式抽象」，`models/chat.py:118-120`）。
- **事件重放**：Bridge 启动时全量重放 MinIO 事件卷重建状态机时间线（`audit.py:119-134`）——可以做到「时间线重放」，但 stream 事件不在卷里，Manager 逐字符思考流在历史重放中丢失。
- **重新执行复现：做不到。** 缺完整 prompt、模型名/采样参数、工具结果原文、随机种子、执行环境版本。
- 产物本身可验证（sha256 + 血缘 DAG + 存储 URI）：**「结果可核验」成立，「过程可复现」不成立**。

**前端展示粒度**
- Case 视图只渲染事件 summary + 证据卡 + 血缘 + 判决计数，不展示任何 LLM 输入/输出/思考（`AgentTeamsCaseView.vue:551, 619-620`）。
- 房间「底层任务事件」折叠区只显示「工具名+成败+耗时」级信息（`frontend/src/utils/agentTeamsRoom.ts:940-984`）。

### 2.3 差距清单与建议补法

| # | 缺口 | 建议补法 | 层 |
|---|---|---|---|
| 1 | LLM 输入全文（每轮 messages + system prompt） | 在 `llm_call_node`（`langgraph_nodes.py:94-168`）按 case_id/work_item_id 写 MinIO 对象，或在 provider span 上挂 `llm.prompt` 属性导出独立存储 | 平台 provider/执行节点层（一处覆盖房间响应、会诊、Worker 代跑三条路径） |
| 2 | LLM 输出全文 + reasoning 全文 | 最稳：轮末把 `round_text/round_reasoning` 整轮落一条 business 事件或 MinIO 对象。便宜但有副作用的方案：把 `room.agent_stream` 从 stream 类改为 business 持久化（`audit.py:36`）——会加剧已知写放大问题（现状文档 §9.1），不推荐单独做 | 平台执行节点层 |
| 3 | 工具调用/结果全文 | `_BridgeEvidenceProjector` 增加「原文侧车」MinIO 对象存储，事件里只留引用 URI（`agent_consultation_service.py:150-152, :181` 的截断点不动） | Bridge 审计层 |
| 4 | 模型身份与采样参数 | 扩 `environment_snapshot` 加 `model/provider/temperature/deep_thinking`，并记录 Worker/Gateway 侧版本/镜像 digest | 血缘登记层 |
| 5 | 跨服务关联 | 打通 `correlation_id`：Bridge 把 request 的 trace_id 透传进 consult_payload；平台侧 `CygnusXSpanProcessor` 已能注入 session.id（`span_store.py:47-58`），用 `agentteams:{case_id}` 作 session_id 即可串联 | Bridge + 平台 telemetry |
| 6 | 随机性（种子/温度快照） | 依赖 #4 补齐后才有意义；重放定位保持「时间线重放」，「重新执行复现」需 1-5 全部落地后再评估 | — |

### 2.4 建议的落地分期

- **P0（记录全量化）**：差距 #1 #2 #3——LLM 输入/输出/思考/工具原文全量落 MinIO 对象存储，事件只留引用。这一步做完，「每一步的详细信息全部记录」即达成，且顺带解决「思考流刷新后丢失」的用户可见问题。
- **P1（可检索可展示）**：#4 #5 + 前端 Case 视图增加「步骤详情」面板（模型输入/输出/思考按轮展示）。
- **P2（复现）**：基于 P0/P1 的快照做「按记录重新执行」能力；这需要模型版本固定、种子可控，属研究级目标，建议单独立项评估，不作为本优化的承诺项。

## 3. 两个建议的关联

两件事实际上互为前置：

- 邀请成员后，**新成员看历史房间时看不到 Manager 的思考流**（stream 事件不持久，§2.2）——建议二的 P0 恰好补上这块，让后加入的成员能完整回看分析过程；
- 多人协作后，「谁触发了哪次模型调用、模型当时看到了什么」变成审计刚需（不再只是 owner's own business），记录全量化的价值进一步放大。

因此推荐顺序：**建议二 P0（记录全量化）先行或与建议一路线 A 并行**，两者都不动 Bridge 核心模型，风险可控。
