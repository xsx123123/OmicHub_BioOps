## 2. 验收前需要注意的 4 个点

### 2.1 设计弱点：邀请「拒绝」没有服务端终态记录（建议修订）

- §4.2 状态机：decline → 删行「不存在」；拒绝终态只靠通知 UI「在当前浏览器持久保留该展示状态」（§7.1）。
- 后果：
  - 换浏览器 / 清缓存即丢失「已拒绝」展示；
  - owner 侧永远没有「B 拒绝过邀请」的服务端事实；
  - 审计上「谁被邀请过、谁拒绝了」无迹可查——与本期「过程可审计」的总目标相悖。
- **建议**：恢复任务书原方案——保留成员行、状态标 `declined`（`responded_at` 记录拒绝时间）。与「拒绝后 owner 可再次邀请」天然兼容（再邀请时把 declined 行重置为 pending 即可，幂等约束不受破坏）。
- 若坚持删行方案，须在架构文档中显性记录该取舍及理由。

### 2.2 admin 授权口径是新增变化，验收需确认实现依据

- 原调研确认过「平台级 admin 对房间无隐式越权」；现 §4.3 / §6 赋予 admin 读房间与 turns 的权限。
- 方向合理（审计姿态），但属口径扩张，验收时确认两点：
  1. admin 判定有明确的**服务端**依赖（角色字段/权限依赖注入），不接受前端传参；
  2. admin 的读权限不泄漏为写权限——admin 不能替 owner 消费立项确认、不能邀请/移除成员（§4.3 已写「平台管理口径」，需验收落实）。

### 2.3 §8 与 §13 的措辞易混淆（建议加一句区分）

- §8 止血项 2 落地的是 `trace_id` 透传（Bridge `work_item.trace_id` → `consult_payload` → 平台 `request_id_var`）；
- §13 挂账的「跨服务 correlation_id 写入点」是审计链的**另一个字段**（`agentteams_audit_events.py:45` 常量，调查报告 B6 确认生产代码仍无写入点）。
- 两者不是一回事。现写法容易让后来人误判「trace 透传做了 = correlation 债已清」。建议 §13 该条目补一句：「trace_id 透传（§8.2）已落地；此处挂账的是审计链 correlation_id，仍为空白」。

### 2.4 最大剩余风险：Matrix 仍是开发态

- §2 标注「开发态 Matrix」；§4.4 的入房/离房级联（accept 入房、退出/移除/删房离房遍历）全部未经验证。
- §12 验收门中「邀请接受」「拒绝、移除与删房」两行本质是 Matrix 验证——**建议验收时最先跑这两行**；它们挂了，后面几行测过也不算数。

## 3. 建议的验收执行顺序（对 §12 八场的重排）

| 顺序 | 场景 | 理由 |
|---|---|---|
| 1 | 邀请接受（含 Matrix 入房） | Matrix 是最大未验证面，先引爆 |
| 2 | 拒绝、移除与删房（含 Matrix 离房遍历） | 同上；同时覆盖成员状态机全路径 |
| 3 | 多轮过程记录（MinIO 对象 + DB 行数 + 全文一致） | 核心建设，独立于 Matrix |
| 4 | 记录容错与追踪（断 MinIO 不阻塞 + span → turn_record_uri 跳转） | 不变量验证 |
| 5 | owner 历史回看（刷新/重登后 turns 逐轮展开） | 解决 stream 不持久老问题的直接证据 |
| 6 | 成员真实归因（actor=B、actor_user_id=B、requester_ref=owner） | A1+ 决策的核心承诺 |
| 7 | 字段与操作授权（member 无 messages/reasoning；删房/立项被拒） | 可见性矩阵 + owner-only 边界 |
| 8 | 回归（SSE/虚拟列表/事件游标/Bridge 重启不丢 turns） | 收尾 |

每场保存可复查证据（截图 + 接口响应 + MinIO 对象 key 清单）。任何场景不通过，把现象发回本对话做根因归因后再出修复提示词，**不接受编码 Agent 自报通过**。
