> 日期：2026-08-22
> 上游文档：原调研 → 审核意见 → 调查报告（均已核对）。本任务书是最终施工依据，阶段化 paste-ready 提示词 + 人工验收 checklist。
> 总原则：验收权在用户手里，不接受编码 Agent 自报通过；每条修复/建设带 e2e 验收条款，不接受只跑单测。

## 0. 调查报告核对结论（决策依据）

### 0.1 采纳的事实裁决

1. **埋点层裁决**：三条 LLM 路径（房间响应/会诊/Worker 代跑）全部收敛到 `parallel_subagent_service.py:655` 的 `provider_manager.chat_stream`；`llm_call_node` 只服务 AI 聊天/Studio，与 AgentTeams 无关。主埋点定在 `parallel_subagent_service._child_loop`（`:600-655`，可拿 `round_number:637`、`child_session_id:625`）。
2. **业务键透传**：provider 层签名无业务键；平台已有 ContextVar 模式（`session_id_var`/`request_id_var`，`core/span_store.py:44-58`、`middleware/trace_context.py:42-53`），新增 `agentteams_ctx_var` 同款透传 `case_id/work_item_id/round_number/actor_user_id`。
3. **存储先例**：`MinioStore.put_case_object` + `case_artifact_versions.storage_uri` 的「大对象写 MinIO、关联行带 s3_uri」模式直接复用为过程记录的对象布局模板。
4. **止血点**：`session.id` 未注入（只差一次 `session_id_var.set`）；`work_item.trace_id` 存在但未进 `consult_payload`；截断常量 10k/8k 不一致；Redis 全局 stream 无 MAXLEN/TTL。

### 0.2 修正记录（旧判断被调查推翻）

| 旧判断（出处） | 新证据 | 修正为 |
|---|---|---|
| 「倾向 provider/网关层统一埋点」（审核意见 §2.5） | provider 层拿不到业务键（报告 A4）；但执行节点层单点即可覆盖三条路径（报告 A3） | 主埋点 = `parallel_subagent_service._child_loop`；ContextVar 透传业务键 |
| 「在 `llm_call_node` 一处覆盖三条路径」（原调研 §2.3 差距 #1） | `llm_call_node` 与 AgentTeams 零交集（报告 A2） | 放弃该方案 |

### 0.3 业界方案选型结论

现阶段业界标准做法（OTel GenAI 语义约定，2025–2026 收敛）：prompt/输出全文**不进 span 属性**（PII 风险），而是 opt-in 内容捕获、与 span 经 trace_id 关联、全文落对象存储/冷存、日志只留引用[^1^][^2^][^3^]；审计记录要求结构化 schema（trace_id、session_id、model+版本、input/output、tool_calls、user_id、token 数）、append-only、与分析系统分离存储[^4^]；记录写入必须异步非阻塞[^5^]。平台现状（OTel span + MinIO 先例 + ContextVar 模式）与该方案同构，**自研薄层即可，不引入 Langfuse 等外部组件**。

## 1. 总体设计契约（阶段 1/2 的共同地基）

### 1.1 过程记录 schema（单条 LLM 调用记录，JSON）

```json
{
  "record_id": "uuid4",
  "recorded_at": "ISO8601",
  "case_id": "...", "work_item_id": "...", "agent_id": "...",
  "round_number": 3, "call_seq": 1,
  "child_session_id": "agentteams:{case_id}:child:{run_id}",
  "requester_ref": "平台用户id（Bridge 身份）",
  "actor_user_id": "实际触发用户id（多人协作后与 requester_ref 可不同）",
  "trace_id": "...", "span_id": "...",
  "provider": "...", "model": "...",
  "sampling": {"temperature": 0.7, "max_tokens": null, "deep_thinking": true},
  "messages": [{"role": "system", "content": "全文"}, {"role": "user", "content": "全文"}],
  "output_text": "输出全文",
  "reasoning_text": "思考全文（无则 null）",
  "tool_calls": [{"name": "...", "arguments": "原文 JSON"}],
  "usage": {"prompt_tokens": 0, "completion_tokens": 0, "total_tokens": 0},
  "duration_ms": 0, "finish_reason": "...", "status": "ok|error",
  "error": null
}
```

### 1.2 MinIO 对象布局（复用 C3 先例）

```text
bucket: agentteams-evidence（与产物证据同 bucket，配置已有）
key:    cases/{case_id}/turns/{work_item_id}/{round_number:04d}/call-{call_seq:02d}-{record_id}.json
```

- 每次 LLM 调用一个对象（点查友好、无追加竞争、天然 append-only）；
- 索引不靠扫对象：平台侧新增 DB 表 `agentteams_turn_records`（record_id 主键，case_id/work_item_id/round_number 索引列 + s3_uri + 摘要列：model、tokens、duration、status、actor_user_id），列表查询走 DB，全文按需 GET 对象；
- span 上新增引用属性（不动内容）：`gen_ai.request.model`、`gen_ai.usage.*` 沿用现有 `ai.*` 之外可选补齐，另加 `agentteams.turn_record_uri` 指向 MinIO 对象——业界「span 留引用、全文走对象存储」的落地[^1^][^3^]。

### 1.3 可见性矩阵（过程记录 × 房间角色，两需求耦合点）

| 数据层 | owner | accepted member | 平台 admin |
|---|---|---|---|
| 终态结论 / 证据卡 / 血缘 / turns 列表（摘要列） | ✅ | ✅ | ✅ |
| 工具参数/结果原文 | ✅ | ✅ | ✅ |
| LLM 输出全文 | ✅ | ✅ | ✅ |
| **prompt 全文 / reasoning 全文** | ✅ | **❌ 默认不可见** | ✅（审计姿态） |

turns 接口在服务端按角色过滤字段，**不依赖前端隐藏**。

### 1.4 邀请成员的 Bridge 身份决策（A1+，替代审核意见里的 A1/A2 待决）

采 **A1+（平台代持 + 全程真实身份标注）**：

- Bridge 侧 `requester_ref` 仍用 owner（不动 Bridge 模型，调查报告确认 Bridge 改动面跨三进程，路线 B 阶段再动）；
- 平台侧做自己的成员鉴权：所有房间端点改为「owner 或 accepted member」；
- 成员触发的动作，事件 `actor` 字段写真实成员身份；过程记录 `actor_user_id` 写真实用户——**审计归因在平台层是实的**，A1 原方案「归因虚」的缺陷由 1.1 schema 的 `actor_user_id` 补齐；
- 路线 B（Bridge 原生成员列表）保持为后续阶段，不阻塞本次交付。

## 2. 分阶段实施

### 阶段 0：止血前置包（0.5–1 天，纯低风险）

内容：① AgentTeams 会诊入口注入 `session_id_var = f"agentteams:{case_id}"`；② Bridge 把 `work_item.trace_id` 写进 `consult_payload`，Gateway 透传，平台端写入 `request_id_var`；③ `room.agent_message` 截断常量统一为 `_ROOM_REPLY_CONTENT_MAX_CHARS`（修 `:672` 硬编码 8000）；④ Redis 审计 stream 加 MAXLEN 近似裁剪（XADD MAXLEN ~ N）。

- owner 邀请 user B → B 的通知出现「接受/拒绝」→ 接受后 B 的房间列表

   - 点击展开调 turns/{record_id} 显示：模型输入（messages 按 role 分
     段渲染）、思考过程（reasoning_text，等宽字体块）、输出全文、
     工具调用原文；
   - 后端已对 member 剔除敏感字段，前端对缺失字段显示「无权查看」
     占位，不做前端权限判断逻辑。
4. 顺手项：房间列表（mine/invited 标记）按 role 显示「我创建的/邀请我的」
   分组或角标。

## 验收

- 步骤详情面板：多轮 Case 展开每轮，prompt/思考/输出完整且与后端记录
  一致；member 账号看到「无权查看」占位；

### 阶段 5：Case 流程 HTML 报告导出（1–2 天，可独立于阶段 4 先行）

设计定调：**报告是已有数据的渲染导出层，不新增记录系统**。数据源全部现成——turns API（每轮全文）、events API（时间线）、artifact-lineage（血缘）、environment_snapshot（模型参数）。唯一编码**不新建 ID 体系**，从既有 ID 派生短码，与平台记录一一对应。

编码规则：

| 对象 | 短码格式 | 对应平台记录 |
|---|---|---|
| LLM 步骤 | `TRN-{round:04d}-{call_seq:02d}-{record_id前8位}` | `agentteams_turn_records.record_id` + MinIO 对象 key |
| 时间线事件 | `EVT-{event_id前8位}` | Bridge 事件卷 `event_id` |
| 产物 | `ART-{artifact_version_id前8位}` | `case_artifact_versions` 行 |

报告内每步同时显示短码与完整 ID（可复制），页脚附报告自身的 sha256——报告也是可追溯产物。

```text
【阶段 5 提示词：Case 流程 HTML 报告导出】

任务：为协作室 Case 增加「流程网页报告」导出。先读以下文件再动手：
- api/v1/agentteams.py（turns/events/artifact-lineage 接口与权限校验）
- application/services/agentteams_turn_recorder.py（turns 索引表结构）
- infrastructure/storage/minio_store.py（:93 put_case_object 先例）
- application/services/agentteams_artifact_lineage_service.py（血缘登记先例）

## 建设内容

1. 后端报告生成服务（新模块 agentteams_flow_report_service.py）：
   - 数据装配：复用 turns 列表/详情、case events、artifact-lineage 的现有
     查询（含 _get_case_for_requester 权限校验），不绕过任何既有授权；
   - 唯一编码：按任务书规则派生短码（TRN-/EVT-/ART- 前缀 + 对应 ID 前 8 位），
     每步同时展示短码与完整 ID，短码旁给「复制」按钮；
   - 渲染：服务端模板生成单文件 standalone HTML（内联 CSS，零外部依赖，
     离线可打开），结构为：概览（case 信息/统计）→ 房间对话摘要 →
     协作时间线（事件带 EVT 编码）→ 步骤详情（按 work_item→round 分组，
     每步带 TRN 编码，含 messages/reasoning/output/工具调用）→ 产物血缘
     （ART 编码 + sha256）→ 页脚（生成时间、生成者、记录总数、报告 sha256）；
   - 角色裁剪：按请求者角色渲染——member/admin 以外的裁减口径与 turns
     接口一致（member 版剔除 messages/reasoning 段落，原位标注「已按权限
     裁剪」）；裁剪发生在服务端渲染层，前端不参与；
   - 产物化：生成的 HTML 经 put_case_object 写入
     cases/{case_id}/reports/flow-{yyyymmdd-HHMMSS}.html，并登记进
     case_artifact_versions（sha256 + storage_uri + producing_event_id），
     使报告进入血缘 DAG 可被反查校验。
2. 端点（api/v1/agentteams.py）：
   - POST /cases/{case_id}/reports/flow：生成 + 登记血缘，返回 artifact 信息；
   - 下载复用现有 artifacts 通道，不新建下载链路。
3. 前端（AgentTeamsCaseView.vue）：「步骤详情」区块头部加「导出流程报告」
   按钮，调用后以下载/新标签页打开；生成中转圈，失败显示错误态，不猜权限。

## 验收
- owner 跑一个多轮 Case 后导出报告：离线打开 HTML，每个步骤有 TRN 短码，
  随机抽 3 个短码反查 turns 接口/MinIO 对象，ID 一一对应；
- 报告中 prompt/reasoning/output 与 turns 详情一致；
- member 账号导出：报告中无 prompt/reasoning，原位有「已按权限裁剪」标注；
- 血缘接口能查到该报告产物（sha256 与文件实际哈希一致）；
- 非成员访问生成端点 403。
```

**人工验收 checklist（用户手测）**

| 操作 | 期望现象 | 不通过处理 |
|---|---|---|
| owner 导出并离线打开报告 | 步骤齐全、短码可读、样式不依赖网络 | 检查是否引入了外部 CSS/JS |
| 抽 3 个 TRN 短码去 turns 接口反查 | 一一对应到同一条记录 | 检查短码派生规则与 record_id 截取 |
| member 账号导出 | 无 prompt/reasoning，有裁剪标注 | 检查渲染层是否走了服务端裁剪 |
| 血缘面板查看报告产物 | 有 ART 条目，sha256 可校验 | 检查血缘登记是否在生成成功后执行 |

## 3. 风险与回退

| 风险 | 缓解 |
|---|---|
| 过程记录写 MinIO 增加 I/O | 异步非阻塞写入；记录失败仅告警；单对象 KB~几十 KB 级，远小于 50MiB 事件卷 |
| Redis stream MAXLEN 裁剪误删未消费事件 | 保守默认值 + 配置项可调；business 事件本就走 MinIO 优先，Redis 只是热缓存 |
| 成员可见性矩阵误配导致越权看 prompt | 过滤在服务端接口层；阶段 4 场景 1/2 专门验收 |
| A1+ 下 Bridge 审计仍显示 owner | 已知取舍，平台层 actor_user_id 补实；路线 B 立项时再动 Bridge |
| 阶段间依赖 | 阶段 0/1 不依赖成员功能可独立上线；阶段 2 的 turns 字段过滤依赖阶段 1 接口（若阶段 1 未上，阶段 2 先跳过该过滤项） |
| 报告与记录漂移 | 报告生成后 turns/事件仍在追加，报告是时点快照——页脚标明生成时间与记录总数；报告产物 append-only 不回删，重新导出生成新版本 |
