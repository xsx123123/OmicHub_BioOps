# 调查任务提示词（v2）：Snakemake 规划 Agent × CygnusX BioOps 平台衔接框架 + 统一异步任务模型

> 使用方式：将本提示词整体发给具备代码仓库读取能力的编程 Agent（如 Kimi Work / Claude Code 等），并先补全文末【需要你填写的信息】中的路径与背景。
> v2 更新：新增"统一异步任务模型与 Agent 后台续跑机制"的调查范围，要求评估平台现有任务状态机的统一程度及迁移路径。

## 一、背景

CygnusX BioOps 是一个面向生命科学的受控计算实验与可信交付平台，核心设计原则是"AI 只调度、不生成；计算只发生在专家验证的资产内"。平台已具备以下能力：

- 表单化流程提交、参数白名单、任务队列（Celery）、幂等提交键
- 受控执行底座：DAG 调度、计划确认门、Artifact Registry、PostgreSQL Outbox + Redis Stream 事件机制、三级质量门、HITL 人工审批
- 项目制存储：`projects/{slug}/runs/{任务名}-{时间戳}/` 沙箱归档、AGENTS.md 台账、run 级 README、环境快照、MD5 产物指纹、一键重跑命令
- 领域 Agent 声明式装配（身份/提示词/工具包/能力边界）、Skill 市集
- MCP 工具挂载层，Agent 通过 MCP 与平台交互

另有一个**独立开发完成的 Snakemake 规划 Agent**（可根据已有 Snakemake 分析流程进行自主规划），并编写了 Snakemake 插件，可将运行进度以机器可读形式推送出来。**该 Agent 尚未与平台融合。**

### 目标架构愿景（供调查参照，不代表代码现状）

平台侧希望演进为**统一异步任务模型**：所有长耗时环节（Celery 流程任务、Snakemake 执行、Skill 调用、质量门判定、人工审批等待）抽象为同一种 Run，共享一套状态机：

```
queued → plan_pending(计划确认门) → running → qc_gated(质量门/审批)
       → completed → archived        （失败分支: failed；超时分支: stale → failed）
```

每个执行器只是一个 adapter：认领任务、推进状态、发事件。在此模型上，Agent 的体验是：**提交即返回 run_id → 任务后台执行 → Agent 处理其他工作 → 任务完成（含失败）后被唤醒 → 凭 run_id + project_slug 续跑原工作**。续跑记忆依赖 AGENTS.md 台账与 run 级归档，而非会话上下文。设计底线：异步的是等待，不是管控——事件仍全量进证据链，续跑动作仍走 Skill 契约与权限边界。

## 二、调查目标

全面调查两个代码库的现状，回答两个问题：

1. **衔接问题**：Snakemake 规划 Agent 以最小侵入方式接入平台受控执行底座，需要打通哪些接口、补齐哪些差距、守住哪些边界？
2. **统一化问题**：平台现有各执行路径的任务状态机有多统一？距离上述"统一异步任务模型"差多远？Snakemake Agent 作为第一个新执行器接入时，应如何落地这套模型，为后续执行器迁移铺路？

产出可供直接排期的集成与统一化方案，而非概念性建议。

## 四、调查任务

### A. Snakemake 规划 Agent 侧现状

1. 整体架构：技术栈、入口形态（CLI / 服务 / 库）、进程模型，是否能独立运行。
2. 规划能力：输入是什么（用户自然语言需求？结构化任务描述？项目上下文文件？），输出是什么——是完整 Snakemake workflow（Snakefile + config）？还是 DAG 计划（rule 列表 + 依赖 + 参数）？rule 的来源是自由生成还是来自既有 rule 库的选择与组装？
3. 执行方式：Agent 是否自行执行 Snakemake，还是只产出计划由外部执行？是否有 dry-run / 计划预览能力？
4. Snakemake 插件：插件的触发点（如 `onjobstart`/`onjobfinish` 等回调）、推送的事件内容（任务 ID、rule 名、进度、状态、日志路径？）、推送通道（HTTP / 消息队列 / 文件？）、事件格式（JSON schema 是否已定义）。
5. 对外接口：是否已有 API、CLI 命令或 MCP server；能否被平台以"提交计划并执行"的方式调用。
6. 状态持久化：规划结果、执行状态、产物清单目前落在哪里（本地文件 / 数据库 / 无持久化）。
7. 事件完备性：插件事件能否覆盖统一状态机全部状态（含 plan_pending、qc_gated、failed、stale），缺哪些、补起来要改哪里。

### B. 平台侧衔接框架现状

1. 任务提交链路：从表单/Agent 提交到 Celery 到集群执行的完整调用链，涉及哪些服务与模块；幂等键在哪里生成、在哪里校验、防重窗口多大。
2. 队列体系：Celery 队列如何划分（按任务类型？按优先级？），broker 是什么，长任务如何管理（超时、心跳、worker 占用策略），是否已有"轻量投递 + 事件驱动"的任务形态。
3. **任务状态机普查（v2 新增，重点）**：
   - 列出平台当前所有"长耗时/异步"执行路径（至少覆盖：表单化流程任务、Skill 执行、AI 助手触发的分析、质量门判定、人工审批等待、多角色协同层任务）；
   - 每条路径的状态枚举定义在哪里（数据库字段？代码常量？分散还是统一）；
   - 是否已存在全局 Run/Task 注册表或统一任务模型；各路径的状态命名与流转是否一致；
   - 事件生产者与消费者清单（谁发事件到 Redis Stream、谁消费），事件 schema 是否统一。
4. 事件机制：Redis Stream 的 stream 命名规则、事件 schema（字段、状态枚举）、Outbox 表结构与投影重建逻辑；Redis 不可用时 Outbox 重建覆盖哪些事件类型。
5. 执行底座接口：计划确认门的触发点与数据结构（计划以什么格式进入确认门）、DAG 调度器如何接收一个计划、质量门在链路的哪些环节挂钩、审批令牌如何签发与核销。
6. Artifact Registry 与结果中心：产物如何登记（路径、MD5、类型、归属 run）、结果中心的查询接口、归档到 `projects/{slug}/runs/` 的代码入口（是否已有统一归档函数可复用）。
7. **续跑机制现状（v2 新增，重点）**：
   - AGENTS.md 台账的写入时机、条目结构、谁负责追加；
   - run → project → 会话的绑定关系存在哪里，任务完成后 Agent 凭哪些键能找回现场；
   - 现有的通知/唤醒机制（站内通知？webhook？Agent 轮询？），失败任务是否有通知；
   - 会话关闭或上下文滚动后，平台侧有无任何"恢复会话现场"的既有能力。
8. **背压与配额现状（v2 新增）**：是否已有按项目/按用户的并发限制、队列公平性、限流机制；幂等键目前的实际防护范围。
9. 监控中心：进度展示的数据来源（订阅哪个 stream？轮询哪个接口？）、目前展示到任务级还是 rule 级粒度。
10. MCP 层：现有 MCP server 暴露了哪些工具（清单 + 入参出参）、权限模型（只读/写操作如何区分）、Agent 侧如何调用 MCP；新增只读监控工具（list_runs、get_run_status、get_run_logs、verify_artifact 等）的边际成本。
11. 权限边界：平台代码中在哪里强制 Agent 无 Shell / 无流程 YAML 写权限 / 无数据库写权限；新增"Snakemake 计划提交"与"后台任务续跑"能力时，这些约束的挂接点在哪里。

### C. 差距与衔接点分析

1. **控制流**：Agent 的规划输出 → 平台计划确认门 → Celery 投递，每一跳的接口差距（格式、协议、鉴权）。
2. **数据流**：输入数据（FASTQ/BAM 等项目空间文件）如何被 Snakemake 执行时引用；产物如何回流到 Artifact Registry 并自动归档（MD5、环境快照、一键重跑命令是否可自动生成）。
3. **事件流**：Snakemake 插件事件 → Redis Stream 的统一 schema 映射；监控中心、Agent MCP 消费同一条 stream 的可行性。
4. **统一化差距（v2 新增）**：以目标状态机为基准，逐条执行路径评估——状态命名是否可映射、事件是否齐、归档是否统一、迁移到统一模型各自需要改动什么；给出"哪些路径可低成本收编、哪些必须先重构"的分层结论。
5. **续跑链路差距（v2 新增）**：从"任务完成事件"到"Agent 恢复工作"全链路逐跳核查——事件是否携带 run_id + project_slug、台账是否可定位现场、通知是否覆盖失败场景、有无背压保护；缺哪几跳、每跳的最小补法。
6. **权限与治理**：Agent 组装流程与平台"流程不由 AI 生成"原则的张力——现有 rule 库/流程资产如何约束 Agent 的组装空间；新组合的人工确认门挂在哪里；后台续跑动作如何确保仍走 Skill 契约与权限边界。
7. **可靠性**：Celery 重复投递防护（幂等键复用）、Snakemake 执行失败/中断的检测与恢复、stale 任务检测（心跳/超时）、Redis 不可用时 Outbox 重建是否覆盖新事件类型。

## 五、必须回答的关键问题清单

1. Agent 的规划输出与平台计划确认门的输入格式差多少？能否直接转换，转换层写在哪一侧？
2. 平台是否已有可复用的"提交外部执行器任务"通道，还是必须为 Snakemake 新增一条 Celery 任务链？
3. Snakemake 插件推送的事件字段，能否覆盖平台监控中心现有展示所需的最小字段集？缺哪些？
4. 产物自动归档到 `projects/{slug}/runs/{任务名}-{时间戳}/` 并生成证据胶囊（MD5 + 环境快照 + 重跑命令），现有归档代码的复用度有多高？
5. **平台现有任务状态机分散在几处？若定义统一 Run 模型，改动面最小的落点在哪里（新表？新服务？扩展现有任务表）？**
6. **Agent 后台续跑链路目前最缺的一跳是什么？用现有 AGENTS.md 台账 + 事件通知能否以最小改动打通？**
7. MCP 监控面要新增哪些只读工具？现有 MCP 框架加工具的边际成本如何？
8. 整个集成中，哪些环节会触碰"Agent 无写权限"红线，各自的兜底方案是什么？
9. 若只做最小可用集成（MVP），最短路径是什么？砍掉哪些非关键环节后仍然守住质量门与证据链底线？统一状态机是 MVP 的一部分还是 MVP 之后再统一？

## 六、交付物要求

1. **现状架构说明**：两个代码库各自的架构摘要（关键模块 + 文件路径）；当前数据/控制/事件三条流的走向；各执行路径任务状态机分布图。
2. **接口清单表**：所有潜在衔接点，格式为：`衔接点 | 提供方(文件:行号) | 消费方(文件:行号) | 现状(可直接对接/需适配/需新建) | 适配工作量估计(人日)`。
3. **差距分析**：按第四部分 C 的七个维度组织，每条差距给出证据（文件路径 + 关键代码摘录）。
4. **统一化评估（v2 新增）**：以目标状态机为基准的统一化差距矩阵（执行路径 × 状态机/事件/归档/续跑/背压五列），以及各执行路径的收编顺序建议（Snakemake 先行，其余按成本排序）。
5. **集成方案**：给出 1 个推荐方案 + 至多 1 个备选，各自包含：组件改动清单（新增/修改的模块）、接口定义草案（统一事件 schema、Run 状态机定义、计划格式、MCP 工具签名、续跑唤醒接口）、实施步骤排序（每步可独立验收）、工作量估计。
6. **风险与边界清单**：触碰平台既有设计原则的点及规避方式；失败模式与兜底（含 Agent 批量投递打满队列、失败任务无人唤醒、stale 任务悬挂）。
7. **MVP 路径**：最短可用集成链路，明确哪些能力后续再补；说明 MVP 是否包含统一状态机，若不包含，差异如何隔离。
