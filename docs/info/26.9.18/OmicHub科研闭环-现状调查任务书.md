## 1. 背景与目标

平台正在评估引入"会话全程计算"的科研闭环能力，参考对象是 OpenAI4S 的四个机制：

1. **Code-as-Action**：代码单元（cell）是引擎原生动作，不占 tool 轮次；
2. **会话状态跨执行保留**：用户可在同一 session 内基于上一轮结果持续迭代计算；
3. **cell 内回调宿主**：执行代码中可同步问模型 / 派子 agent / 提交远程计算；
4. **不可变执行历史**：历史即真相，可确定性导出（.ipynb）、可复现、可审计。

**已定的吸收原则（调查的前提，不是调查对象）**：

- 吸收"契约"不吸收"架构"：历史不可变、终态不可重开、sha256 产物对账、幂等提交等
  正确性契约要；单机 persistent kernel 进程治理不要；
- 执行器保持容器 + 一次性进程不变，会话状态用"工作区文件系统持久化"而非热进程；
- 现有可复现能力（每次运行详情落盘、环境 provenance 快照、按项目保存调用历史）
  是底座，不是被替换对象。

**用户最大的担忧**：完整接受 OpenAI4S 的一套会导致现有"用历史对话恢复项目"的能力
失效或语义分叉。因此本次调查的第一优先级是**把现状事实查清楚**，尤其是恢复链路依赖
的隐含假设。

## 调查背景

平台现有可复现设计：每次运行的详细信息（日志、产物、环境快照如 conda-explicit.txt /
environment.yml / software-versions.txt / pip-freeze.txt）全量落盘，并按项目保存每次
工具调用历史，目标是"后续重复执行和项目交接可以完全用历史对话恢复"。

平台现考虑引入参考 OpenAI4S 的四项能力：cell 作为执行一等单元、会话状态跨执行保留、
cell 内 LLM 回调宿主、不可变执行历史 + .ipynb 导出。但担心与现有可复现设计冲突
（尤其是历史恢复的等价性），因此需要先查清现状。

## 调查任务

### A. 会话与执行模型现状

1. 执行入口：sandbox_execute / chat_sandbox_execute / tool_orchestrate（PTC）三个工具
   的定义位置、入参出参、调用链（从 LLM tool_call 到容器内一次性进程的完整路径），
   三者分工与重叠。
2. 进程与容器模型：容器生命周期（warm pool？Studio 懒启动+休眠？beat 空闲回收？）、
   每次执行新起进程的具体方式（python -c <b64> / Rscript / 临时脚本？）、
   Redis busy lease 的串行化机制、执行超时与资源限制（600s / 50 次上限 / rlimit 等）
   分别在哪些文件生效。
3. 状态持久化：执行之间状态靠什么保留（文件系统路径约定？约定目录在哪？）、
   会话工作区目录如何隔离与寻址、容器回收后什么保留什么丢失。

### B. 历史与可复现现状（本次调查重点）

1. 落库语义：metadata_json.tool_invocations 与 timeline 的完整结构；流式中间 chunk
   是否落库（落库还是不落）；瞬态状态（审批中等）存哪、TTL；刷新页面后会话如何重建，
   重建的是"终态快照"还是"完整过程"。
2. 运行详情保存：每次运行具体保存哪些信息、由哪个模块在什么时机写入；环境快照
   （conda-explicit.txt / environment.yml / software-versions.txt / pip-freeze.txt）
   的生成位置、触发时机、与会话的关联键。
3. 项目级历史：按项目保存调用历史的表结构与写入点；"用历史对话恢复项目"的完整
   链路（谁读历史、怎么重放、能恢复到什么粒度）。
4. 分享与导出：studio sharing 快照包含哪些内容；当前有无任何形式的会话/历史导出。

### C. 安全、审批与审计现状

1. 审批闸：APPROVAL_REQUIRED_TOOLS 的完整名单与拦截点分布；legacy 循环
   （chat_service）与 LangGraph 两条执行路径是否都有审批闸，语义是否一致。
2. 审计：audit_logs 表、infrastructure/studio/audit.py 结构化日志、middleware/audit.py、
   OTel span 各自的覆盖点；一次工具执行会留下几份审计记录。
3. 沙箱：容器硬化（cap_drop / seccomp / read-only rootfs / 网络三档 / egress proxy）
   的配置位置与生效范围。

### D. 四项目标能力的接入就绪度评估（基于 A–C 的事实）

对每一项输出四小节：现有可复用机制（代码证据）/ 缺口 / 与现有设计的冲突点 /
最小侵入落点建议（具体到文件与函数）。

1. 会话状态跨执行保留（工作区文件系统持久化方案，不引入持久 kernel 进程）：
   现有工作区目录机制能复用多少？容器 warm pool / 休眠 / beat 回收会不会清掉状态？
   多租户隔离是否还成立？
2. cell 作为执行一等单元（notebook 式展示与寻址，不改执行器）：
   现有 StudioCodeCard / tool_call 投影机制离 cell 语义差多远？tool_call_id 定向与
   fallback 匹配的现状？
3. PTC 白名单增加 LLM 回调（cell 内问模型）：
   PTC_ALLOWED_TOOLS 现状、加 LLM handler 需要动哪些地方、子进程跑在宿主上的
   安全边界问题是否因此放大。
4. 不可变执行历史 + 流式 chunk 落库 + 产物 sha256 对账 + .ipynb 导出：
   现有落库层改动面；sha256 对账加在哪个环节成本最低；导出需要的历史字段是否已齐。

### E. 风险专项（逐项给证据与判断）

1. 历史恢复等价性：现有"恢复项目"链路依赖哪些隐含假设（无跨执行状态？环境快照
   可重建一切？）？若引入会话状态跨执行保留，恢复的会话与原始执行状态是否还等价？
   哪些场景会打破等价？
2. 资源回收：会话状态保留与容器 warm pool、beat 空闲回收、多租户配额之间的
   相互作用，有无泄漏路径。
3. 语义分叉：同一项目内新旧形态若并存，agent 可见工具集、审批、审计是否会出现
   两套语义；现有代码里是否已有"新旧路径并存"的先例（legacy vs LangGraph），
   当时如何收敛。
4. 长任务矛盾：600s / 50 次等现有限制与"全程计算"诉求的差距；已有哪些机制
   （Overdrive DAG、MAS Apptainer、RemoteSnakemakeExecutor）可以承接长任务，
   各自的接线状态。
