# 建议追问 Chips（Suggested Follow-ups）功能实现计划

> 版本：v1.0（2026-09-04 定稿）
> 定稿决策：点击行为 = 混合模式（普通项直接发送 / 需补充信息项填入输入框）；
> 内容来源 = 结构化 `suggestions` 字段优先 + 前端解析"可选下一步"编号列表兜底。

## 背景与目标

用户在平台上让 Agent 完成分析任务（如系统发育树构建）后，Agent 会在回复末尾给出
"可选下一步"编号列表（如：标签精简/分组着色、进化枝注释、支持度叠加、版式调整）。
现状是用户需要手动打字复述其中一条才能继续，链路断裂。

目标：在 assistant 回复（含分析产物卡片）下方渲染一行可点击的建议条
（Follow-up Chips，业界成熟模式：Gemini 相关问题、Perplexity Related、
ChatGPT suggested follow-ups），点击后自动把该建议作为下一轮用户消息发送给
Agent，实现"一键接续分析"。

## 需求清单

1. 每条 assistant 回复完成后，在其气泡/产物卡片下方展示 2~4 条建议 Chips。
2. 点击行为分两种（混合模式）：
   - `send`：chip 文案直接作为用户消息发送，chips 消失；
   - `prefill`：chip 文案填入输入框光标处，用户可编辑/补充（如上传 .contree
     文件）后自行发送。判定规则：文案含"提供/上传/文件/路径"等需用户补充信息
     的关键词时用 prefill，其余用 send。结构化数据可由 `action` 字段显式指定，
     优先级高于关键词判定。
3. 内容来源双轨：
   - 优先：后端/Agent 在流式响应末尾输出结构化 `suggestions` 数组
     （字段：`label` 短标签 / `prompt` 完整发送文案 / `action` send|prefill）；
   - 兜底：结构化字段缺失时，前端用正则解析回复 Markdown 中"可选下一步"章节
     的编号列表（`1. xxx：yyy`），`label` 取冒号前短名，`prompt` 取整条文本，
     `action` 走关键词判定。
4. 生命周期：流式输出期间不渲染（等回复完成后出现）；点击任一 chip 或用户手动
   发送消息后，当前 chips 消失；收到新回复后刷新为新一组。
5. 样式：圆角胶囊（pill），与平台现有淡紫/蓝色系及卡片圆角体系一致，hover
   高亮，一行放不下时横向滚动，不挤压产物卡片布局。
6. 健壮性：解析失败或建议数为 0 时不渲染、不报错、不留空白占位。

## 分阶段实现

### 阶段 1：纯前端最小可用版（解析兜底 + 混合点击）

不依赖后端改动，直接消费现有"可选下一步"文本，最快见效、独立可验收。

- 改动点：
  - 新建 `SuggestionChips` 组件（props：`suggestions: Array<{label, prompt, action}>`，
    事件：`send(prompt)` / `prefill(prompt)`）；
  - 在 assistant 消息渲染组件（含分析产物卡片的消息类型）底部挂载该组件；
  - 新增解析工具函数 `parseNextStepSuggestions(markdown)`：定位"可选下一步"
    章节 → 提取编号列表项 → 拆 `label`/`prompt` → 关键词判定 `action`；
  - `send` 走现有发送消息的 action（与用户在输入框回车完全同一路径）；
    `prefill` 写入输入框的响应式值并 focus。
- 对应提示词：见下方【阶段 1 提示词】。
- 验收：见【验收 checklist】阶段 1 部分。

### 阶段 2：结构化 suggestions 字段（后端/Agent 侧配合）

- 改动点：
  - 与后端约定流式响应事件格式：回复结束事件中附带
    `suggestions: [{label, prompt, action}]`（JSON）；
  - 前端消息模型新增 `suggestions` 字段，渲染时优先消费结构化数据，
    缺失时回退到阶段 1 的正则解析；
  - Agent 侧提示词约束：仅在存在明确下一步时输出 2~4 条，无建议时不输出该字段。
- 对应提示词：见下方【阶段 2 提示词】。
- 验收：见【验收 checklist】阶段 2 部分。

### 阶段 3：体验打磨

- chip 文案超过 ~20 字截断，完整文案入 `title`/tooltip；
- 键盘可达（Tab 聚焦、Enter 触发）、`aria-label`；
- 出现/消失动画只用 transform/opacity，≤200ms，尊重 prefers-reduced-motion；
- 窄屏（移动端）横向滚动 + 边缘渐隐遮罩。

## 阶段 1 提示词（可直接粘贴给编码 Agent）

```text
你是一名资深前端工程师。项目技术栈：Vue3 + Pinia + SSE 流式渲染（若与仓库实际
栈不符，以实际代码为准并说明差异）。

任务：在现有对话页中新增"建议追问 Chips"功能。先阅读现有代码：assistant 消息
渲染组件、分析产物卡片组件、输入框组件、发送消息的 Pinia action，复用现有组件
与样式体系，禁止重构无关代码、禁止改动路由与既有消息流逻辑。

## 功能需求

1. 新建 SuggestionChips 组件：接收 suggestions 数组
   （{label: string, prompt: string, action: 'send' | 'prefill'}），
   渲染为一行圆角胶囊按钮，位于 assistant 消息气泡/产物卡片下方、消息列表之内。
2. 新增解析工具 parseNextStepSuggestions(markdown)：
   - 定位回复中"可选下一步"（兼容"下一步建议"等变体标题）章节；
   - 提取其下的有序列表项（形如 `1. 标签精简/分组着色：把叶片名改成……`）；
   - label 取冒号/破折号前的短名（无则截断前 12 字），prompt 取条目全文；
   - action 判定：条目文本含"提供/上传/文件/路径"任一关键词 → 'prefill'，
     否则 → 'send'；
   - 最多取 4 条；解析不到任何条目时返回空数组（组件不渲染）。
3. 点击行为：
   - action='send'：调用与输入框发送完全相同的消息发送 action，参数为 prompt，
     发送后清空当前 chips；
   - action='prefill'：把 prompt 写入输入框响应式值（不发送），输入框 focus
     并将光标置于文末，chips 保留至用户真正发送后清空。
4. 生命周期：仅在 assistant 消息流式输出完成后渲染（监听现有"回复完成"状态）；
   用户发送新消息或收到新回复时，旧 chips 消失/被新一组替换。
5. 边界情况：suggestions 为空、解析失败、回复中无"可选下一步"章节时，组件
   不渲染、不报错、不留空白占位；历史消息重新渲染时同样按上述规则处理。

## UI 要求

- 复用平台现有设计 token：圆角与现有卡片一致，胶囊边框/文字用现有淡紫-蓝色系
  变量，hover 时背景浅色高亮；字号比正文小 1~2px。
- 一行放不下时横向滚动，不换行、不挤压产物卡片；与上方卡片间距 8~12px。
- 出现动画仅用 opacity/transform，时长 ≤200ms，尊重 prefers-reduced-motion。

## 数据与接口

- 本阶段纯前端实现，数据来源为现有消息内容（Markdown 文本），不新增接口、
  不使用 mock 数据。

## 验收标准

- [ ] 用含"可选下一步"4 条编号列表的回复测试：渲染 4 个胶囊，label 为短名
- [ ] 点击普通条目（如"标签精简/分组着色"）：等价于手动输入该条目全文并发送
- [ ] 点击含"提供 .contree"的条目：文本进入输入框且未发送，可继续编辑
- [ ] 回复无"可选下一步"章节时无任何渲染与报错
- [ ] 流式输出过程中不渲染，完成后才出现
- [ ] 发送任意消息后旧 chips 消失
- [ ] 控制台无 warning/error，现有消息流与产物卡片功能不受影响
```

## 阶段 2 提示词（可直接粘贴给编码 Agent）

```text
你是一名资深全栈工程师。在阶段 1（SuggestionChips 前端组件 + 正则解析兜底）
已完成的基础上，为建议追问功能增加结构化数据通道。先阅读阶段 1 的前端实现与
现有 SSE 流式响应的事件封装代码，禁止改动无关模块。

## 功能需求

1. 后端/Agent 侧：回复结束事件（或新增独立事件）中附带 suggestions 字段：
   suggestions: Array<{label: string, prompt: string, action: 'send'|'prefill'}>，
   2~4 条；无明确下一步时不输出该字段（不要输出空数组占位）。
   action 规则：需要用户提供文件/路径/额外信息的条目用 'prefill'，其余 'send'。
2. 前端：
   - 消息模型新增 suggestions 字段，随消息持久化（历史消息刷新后 chips 仍在）；
   - SuggestionChips 数据源优先级：消息上的结构化 suggestions > 阶段 1 的
     正则解析结果；结构化字段存在时不再执行解析；
   - 结构化数据的 action 以字段值为准，不再走关键词判定。
3. Agent 输出约束写进系统提示词/输出协议：label ≤ 12 字，prompt 为可直接
   发送的完整指令句，suggestions 仅在回复确含可选下一步时给出。

## 验收标准

- [ ] 带结构化 suggestions 的回复：chips 文案/行为与字段完全一致
- [ ] 无结构化字段的旧格式回复：仍按阶段 1 正则解析正常渲染（兜底未回归）
- [ ] 结构化字段存在但为空数组/缺失时不渲染、不报错
- [ ] 刷新页面后历史消息的 chips 仍正确渲染
```

## 验收 checklist（用户手测对照表）

| # | 操作 | 期望现象 | 不通过时的处理 |
|---|---|---|---|
| 1 | 让 Agent 跑一个分析任务，回复含"可选下一步"列表 | 回复完成后下方出现 2~4 个胶囊，文案为各条目短名 | 截图发给编码 Agent，要求检查 parseNextStepSuggestions 的章节定位正则 |
| 2 | 点击"标签精简/分组着色"类普通条目 | 该条目全文作为用户消息直接发出，Agent 开始下一轮 | 检查是否误走了 prefill 分支（关键词误判），把误判词条反馈给编码 Agent 调词表 |
| 3 | 点击含"提供 .contree"的条目 | 全文填入输入框且未发送，可手动补一句/上传文件后发 | 同上，调关键词表或等阶段 2 用 action 字段显式指定 |
| 4 | 问一个不会有下一步建议的问题（如闲聊） | 不出现任何胶囊，控制台无报错 | 反馈编码 Agent 检查空态分支 |
| 5 | 在 chips 存在时手动输入并发送任意消息 | 旧 chips 消失 | 检查消息发送后 chips 清理逻辑是否挂在发送 action 上 |
| 6 | 流式输出过程中观察 | chips 不出现，回复完成瞬间才淡入 | 检查渲染条件是否绑定了"回复完成"状态而非"有内容" |
| 7 | （阶段 2）刷新页面看历史消息 | 历史回复的 chips 仍正确渲染 | 检查 suggestions 字段是否随消息持久化 |

## 风险与回退

- **正则解析脆**：Agent 回复格式变动（标题改名、列表样式变化）会导致解析为空。
  应对：兜底失败时静默不渲染（不会出错只是没 chips），阶段 2 结构化字段上线后
  解析仅作降级路径。
- **关键词误判 send/prefill**：个别条目被误判会直接发送半截指令。应对：关键词
  表集中维护、易调整；阶段 2 后以 action 字段为准。
- **与虚拟列表的交互**：消息列表若为虚拟滚动，chips 高度变化可能引起跳动。
  应对：渲染前预留固定行高，或在 item 高度测量中纳入 chips 高度。
- **回退方案**：组件独立挂载、单开关控制（feature flag 或一行 v-if），出问题
  直接隐藏组件即可，不影响消息主链路。
