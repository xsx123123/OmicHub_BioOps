# 协作室 Manager 反复追问数据来源 — 代码调研提示词

> 日期：2026-08-20
> 用途：将下方【调研提示词】整段粘贴给编码 Agent（kimi code / Claude Code / CODEX 等）执行；调研完成后把报告发回，再定修改方案。
> 关联文档：《AgentTeams部门协作架构评估与实现计划.md》《Manager人格分层实施手册-通用助手与部门经理共存.md》

---

## 症状记录（2026-08-20 截图实证）

用户在 AgentTeams 协作室发送：

> 我有6个小鼠肺部单细胞样本 3vs3，我需要对其进行分析，样本是 tp53 mutation vs tp53 WT

随后出现**三轮重复的"确认数据来源"追问**：

1. 16:10 Manager 文本消息：「需要你先确认数据来源，再启动执行。」
2. 16:10 询问工具卡片（状态显示"已收集信息"）：「收到你的执行请求……但还缺少明确的作用对象（输入文件/数据）。请确认数据来源：上传文件后执行（推荐）」
3. 16:11 Manager 文本消息（与第 1 条逐字相同）：「需要你先确认数据来源，再启动执行。」
4. 紧随其后又是一张追问卡片：「仍未拿到可执行的作用对象：请直接上传文件，或回复工作区文件名/路径（如 genes.xlsx），或公共数据库 accession/检索关键词。」（附选项：我去上传文件 / 回复文件名或路径 / 先不执行了）

**问题定性**：
- 同一诉求被重复表达 3+ 次，体验差；
- 第 2 条卡片状态为"已收集信息"，但第 3/4 条仍在追问同一问题——疑似澄清答复未被消费，或追问被重复触发；
- 16:10 与 16:11 两条文本逐字相同——疑似重复生成/重复发送，而非 LLM 自然表述。

## 调研提示词（整段粘贴给编码 Agent）

```text
【任务性质】只做代码级调研与评估，禁止修改任何代码、配置、数据库。
先读代码再下结论；所有结论必须标注文件路径与关键代码位置（文件:行号/函数名）。
凡涉及"触发了几次/有没有消费"的结论，必须以后端审计事件、服务日志或 DB 记录
为物证，不得以前端界面表现为依据（前端存在乐观上屏，可能制造假象）。

【症状背景】
AgentTeams 协作室中，用户发送一条分析请求（6 个小鼠肺部单细胞样本 3vs3，
tp53 mutation vs WT），Manager 在 1 分钟内重复追问"确认数据来源"3 次以上：
- 16:10 文本「需要你先确认数据来源，再启动执行。」
- 16:10 询问工具卡片（卡片状态显示"已收集信息"）
- 16:11 文本「需要你先确认数据来源，再启动执行。」（与 16:10 逐字相同）
- 紧接着又一张追问卡片「仍未拿到可执行的作用对象：请直接上传文件，
  或回复工作区文件名/路径（如 genes.xlsx），或公共数据库 accession/检索关键词」

【调研清单：逐项给出证据】

一、消息生成链路（谁说了这几句话）
1. 定位「需要你先确认数据来源，再启动执行。」这句话的来源：是
   agentteams_room_response_service.py 中的硬编码模板，还是 LLM 生成？
   若是模板，模板在哪；若是 LLM 生成，对应提示词段落在哪。
2. 定位询问工具卡片的生成入口：AskUser/澄清卡的创建函数、卡片状态机
   （"已收集信息"状态由什么事件置位）。
3. 梳理一条用户消息进入协作室后的完整处理链路：
   接收 → 路由决策 → Manager 回复生成 → 澄清卡生成，各环节各自会
   产生哪些消息/卡片，标注代码位置。

二、重复触发的根因（为什么问了很多次）
4. 用后端物证回答：16:10 与 16:11 两条逐字相同的文本，对应几次
   LLM 调用、几次消息写入事件？审计事件中各有几条 room.agent_message？
5. 检查是否存在以下任一模式，逐项确认或排除（给证据）：
   a. 澄清卡状态更新（如"已收集信息"）触发了新一轮 Manager 回复生成；
   b. 定时任务/reconcile/watcher 轮询循环重放了对同一条用户消息的处理
      （注意：精确节律重复 = 轮询循环 + 去重缺失的典型特征）；
   c. 同一条用户消息被两个入口消费（如 SSE 推送 + 历史重载、或
      路由层与响应层各处理一次），缺少 message_id 幂等去重；
   d. 询问工具返回结果后，结果被当作"新的用户输入"再次进入追问逻辑。
6. 检查澄清答复的消费逻辑：用户通过卡片选项或文字回复数据来源后，
   该回复路由到哪里？是否有"该澄清已闭合、不再追问同一问题"的状态标记？
   现状下同一 Case 内 Manager 是否会对已澄清过的维度再次发问？

三、提示词层（话术从哪里来）
7. 列出 Manager 房间提示词中所有与"确认输入/数据来源/作用对象"相关的
   指令段落（含 _build_question() 及系统提示词），标注文件与行号。
8. 检查提示词中是否缺少以下约束：
   - 同一澄清问题在同一 Case 中只问一次（询问前去重）；
   - 优先自行检索工作区文件，确实没有可用输入时才向用户追问；
   - 追问时合并为一条消息（文本与卡片不重复表达同一诉求）。

四、工作区文件感知（Manager 是否"先看再问"）
9. Manager 回复生成时，系统是否注入了当前工作区文件清单/Case 已有产物？
   若没有，Manager 无从判断"用户是否已有数据"，只能一律追问——
   确认这是否为设计缺口。
10. 用户消息中提到的样本信息（数量、分组、比较设计）是否被结构化提取
    并带入后续澄清，还是每轮都从原文重新理解？

【交付格式】
A. 调用链路图：一条用户消息 → 各消息/卡片的产生路径（标注代码位置）。
B. 事件时序表：本次症状对应的后端审计事件清单（时间、事件类型、
   payload 关键字段、由哪段代码写入）。
C. 根因判定：上述第 5 条 a–d 逐项 ✅确认/❌排除/⚠️待验证，附证据。
D. 提示词层问题清单：第 7–8 条发现的缺失约束。
E. 最小改动建议：按"改动面小 → 大"排序的修复方案候选（只列方案与
   涉及位置，不要实施）。
F. 与上述描述不符之处的差异清单。
```

## 拿回报告后的核对要点（供下一轮使用）

1. **区分"话术问题"与"机制问题"**：如果根因是重复触发（机制），只改提示词没用；如果是提示词缺少去重约束（话术），机制不用动。报告的第 C 节是分流关键。
2. **"已收集信息"卡片状态**：确认该状态是否真的代表"用户已答复"，还是仅代表"卡片已展示"——命名误导会掩盖答复未消费的 bug。
3. **修复必须带端到端验收**：复现截图场景（发同样的单细胞分析请求），断言协作室只出现一次数据来源追问（一条消息或一张卡片，不同时出现）。
4. **警惕修复引入第二轮故障**：若新增"询问前去重/预检索"逻辑，需核对去重键设计与既有消息幂等机制（client_message_id / causation_event_id）是否一致。
