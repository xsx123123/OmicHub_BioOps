## 0. 结论摘要

1. 截图中第一次“Manager 文本”`需要你先确认数据来源，再启动执行。`与紧随其后的数据来源卡片，按当前代码**不是两次后端生成**：它们是**同一条** `room.ask_user` 事件的 `content` 和 `questions` 字段。前端把同一个投影消息先渲染为气泡、再渲染 `AskUserCard`，因此必然出现“文本 + 卡片”两段视觉表达。见 `src/omichub/application/services/agentteams_room_response_service.py:795`、`src/omichub/application/services/agentteams_room_response_service.py:801`、`frontend/src/utils/agentTeamsRoom.ts:666`、`frontend/src/views/AgentTeamsRoomView.vue:1629`、`frontend/src/views/AgentTeamsRoomView.vue:1635`。
2. 第二轮“仍未拿到可执行的作用对象”是执行澄清状态机的**预期分支**：若用户点击“我去上传文件”或“使用工作区已有数据（请回复文件名或路径）”，该回传文字本身仍不包含文件、路径、显式引用或可执行数据对象，后端会记录答复后发第 2 轮卡片；单元测试已锁定此行为。见 `src/omichub/application/services/agentteams_room_response_service.py:584`、`src/omichub/application/services/agentteams_room_response_service.py:599`、`tests/unit/test_agentteams_room_response_service.py:803`、`tests/unit/test_agentteams_room_response_service.py:833`。
3. 卡片显示“已收集信息”**不等于后端已成功消费并完成数据来源补全**。提交点击时前端会在网络请求完成前直接把 `ask.answered = true`；历史投影还会把该卡片后的任意用户消息标为“已答”。后端实际消费后另行 best-effort 写 `room.ask_user_answered`，但前端“已收集信息”并不读取该事件。见 `frontend/src/views/AgentTeamsRoomView.vue:784`、`frontend/src/utils/agentTeamsRoom.ts:1317`、`src/omichub/application/services/agentteams_room_response_service.py:922`。
4. 截图中的两次完全相同文本，最符合“第 1、2 轮 `room.ask_user` 均携带同一个固定 `content` 模板”的代码事实；这**不需要 LLM 参与**，也不必然意味着同一用户原消息被重放。固定话术位于 `_emit_execution_clarify()`。当次究竟有几条 `room.ask_user`/`room.agent_message`、是否有重投递，当前无原始审计，不能下确定结论。
5. 当前工作树（未提交改动）新增了按 `room.user_message.event_id` 的 Redis 响应去重，目标是覆盖任务重试、broker 重投递和双通道调度；但它尚非 `HEAD` 已提交基线，且 Redis 读取失败会降级为继续处理。因此不能用它倒推 2026-08-20 截图发生时已被保护。见 `src/omichub/application/services/agentteams_room_response_service.py:56`、`src/omichub/application/services/agentteams_room_response_service.py:233`、`src/omichub/application/services/agentteams_room_response_service.py:409`。

## B. 关键文案与卡片状态机

### B1. “需要你先确认数据来源”不是 LLM 文案

该句是 `_emit_execution_clarify()` 写入 `room.ask_user.payload.content` 的硬编码模板，位置为 `src/omichub/application/services/agentteams_room_response_service.py:801`。同一函数第 1 轮写“收到你的执行请求……请确认数据来源”（`:777`），第 2 轮写“仍未拿到可执行的作用对象”（`:788`）。

此路径在 `_maybe_start_chat_execution()` 返回 `clarified` 后于 `src/omichub/application/services/agentteams_room_response_service.py:277` 提前返回，因此**该轮 LLM 调用数应为 0**；也不会写 `room.agent_message`。其唯一面向用户的终态证据事件是 `room.ask_user`。

普通 Manager 会诊才走 `AgentConsultationService.run_consultation()`，位置为 `src/omichub/application/services/agentteams_room_response_service.py:324`；若模型给出 `ask_user`，也只写一个 `room.ask_user`，位置为 `:364`；无问题时才写 `room.agent_message`，位置为 `:386`。

### B2. “已收集信息”实际代表什么

`AskUserCard.vue` 的“已收集信息”标签只受 `ask.answered` 控制，见 `frontend/src/components/ai-chat/AskUserCard.vue:114`、`:206`。该值有两条前端来源：

- 用户点击提交时，`submitRoomAskAnswers()` 在网络请求完成前直接设置 `ask.answered = true`、`ask.answers = answers`，见 `frontend/src/views/AgentTeamsRoomView.vue:784`。
- 重放事件历史时，`markAskRequestsAnswered()` 将一张卡片之后遇到的**任意**用户消息先视为“已答”；只有能解析出 `【澄清回复】` 格式时才消费该消息并填回答案，见 `frontend/src/utils/agentTeamsRoom.ts:1317`。

后端并不存在“把原 `room.ask_user` 状态改为已收集”的更新；它只是对收到的回复另写 `room.ask_user_answered`，见 `src/omichub/application/services/agentteams_room_response_service.py:941`。因此截图中的标签不能证明：用户已上传文件、指定路径、答复已被执行分支消费，或 Case 已具备可执行对象。

### B3. 为什么同一话术会出现两次

第 1、2 轮澄清均固定将 `content` 写成同一个字符串，而问题正文才随 `round_no` 改变；见 `src/omichub/application/services/agentteams_room_response_service.py:777`、`:788`、`:801`。所以“16:10 与 16:11 文本完全相同”与“两张不同轮次的 `room.ask_user` 卡片”完全一致；仅凭 UI 不能断定为“LLM 生成两次”或“相同消息写入两次”。

更重要的是，第 1 轮的两个选项“上传文件后执行（推荐）”与“使用工作区已有数据（请回复文件名或路径）”都允许用户仅选择计划，而不提供对象。测试明确确认这类回复会推进第二轮：`tests/unit/test_agentteams_room_response_service.py:803` 覆盖“我去上传文件”，`:833` 覆盖“使用工作区已有数据（请回复文件名或路径）”。

## E. 提示词层与工作区感知

### E1. 相关指令位置

- 房间专用系统指令 `_build_question()`：要求缺少关键信息时使用 `ask_user`，且 `conclusion` 不重复问题正文，见 `src/omichub/application/services/agentteams_room_response_service.py:1153`、`:1160`、`:1167`。
- 真正触发本症状的执行对象判定不由 LLM 提示词决定，而由规则分类器完成：`context_refs`、文件名或少数数据对象命中才算对象；否则 `clarify`，见 `src/omichub/application/services/agentteams_execution_intent.py:67`、`:91`、`:99`。
- 当前 Manager 实际优先使用 `agent-general`，见 `src/omichub/application/services/agentteams_room_response_service.py:1057`；该 YAML 指向 `data/ai/prompts/general.md`，见 `data/ai/general.yaml:1`、`:9`。通用提示词要求“未明确数据文件时先 `ask_user`”，并禁止自行选择工作区文件，见 `data/ai/prompts/general.md:113`。
- 全局工作区工具提示则要求先检查工作区文件、用户已给关键信息时不重复澄清，见 `src/omichub/infrastructure/mcp/presets.py:56`。

### E2. 缺失或冲突

1. **缺少“执行对象澄清卡只展示卡片，不再展示同义气泡”的渲染约束。** 后端把同义引导文本塞入 `payload.content`，前端同时展示 `content` 和 `AskUserCard`，形成确定性的重复表达。
2. **缺少“用户选上传/工作区已有数据但尚无具体对象”的单步收敛设计。** 当前第 1 轮选项本身允许不提供对象，而规则要求对象，必然可能再问第 2 轮。
3. **缺少“已收集信息”的后端事实语义。** UI 用乐观和邻近消息推断代替审计 `room.ask_user_answered` 或真实文件引用，标签会把“点击了选项”误标为“信息已收集”。
4. **缺少当前 Case 工作区清单注入。** `_build_question()` 仅注入“本条发言引用文件”，没有查询/列入当前 Case 的已有文件、Case `context_refs` 或已产物，见 `src/omichub/application/services/agentteams_room_response_service.py:1125`、`:1139`、`:1171`。`_latest_message_context_refs()` 也只取与最新文本匹配的 `room.user_message`，见 `:1095`。因此 Manager/规则无法仅凭“工作区里可能已有数据”作出判断。
5. **样本设计没有结构化持久化。** 当前用户原文只在 `room.user_message.content` 与最近动态摘要中出现；没有看见针对“6 个样本、3 vs 3、tp53 mutation vs WT”的独立 schema/字段抽取事件。`origin_content` 仅保留字符串前 600 字，见 `src/omichub/application/services/agentteams_room_response_service.py:807`、`:961`。第二轮依靠回填原文重新组合，而非结构化研究设计。

## F. 最小改动建议（仅建议，不实施）

按改动面由小到大排序：

1. **前端去重展示（最小、直接消除截图中“文本 + 卡片”）**：对 `execution_object` 类型的 `room.ask_user`，不渲染 `payload.content` 气泡，仅展示 `AskUserCard`；或后端将该字段置为空，仅保留卡片问题。涉及 `frontend/src/views/AgentTeamsRoomView.vue:1629` / `src/omichub/application/services/agentteams_room_response_service.py:801`。验收：首轮仅一张卡片，不能同时出现同义文本气泡。
2. **合并首轮选择与对象输入**：将“上传文件后执行”改为上传/引用控件，或在选择“工作区已有数据”时同卡要求填写路径；不能把“未来会上传”当作已经补齐。涉及 `src/omichub/application/services/agentteams_room_response_service.py:777`、`frontend/src/components/ai-chat/AskUserCard.vue:27`。验收：单击可执行选项即提供可判定对象；否则明确显示“等待上传”而不是第二次相同追问。
3. **修正卡片状态语义**：提交中显示“正在提交”，只在 API 成功且历史/SSE 出现对应答复后标“已提交”；“已收集信息”仅在存在 `room.ask_user_answered` 且答案通过对象判定或进入明确等待上传状态时显示。涉及 `frontend/src/views/AgentTeamsRoomView.vue:784`、`frontend/src/utils/agentTeamsRoom.ts:1317`、`src/omichub/application/services/agentteams_room_response_service.py:922`。

## G. 端到端验收与取证要求

1. 复现输入：“我有 6 个小鼠肺部单细胞样本，3 vs 3，tp53 mutation vs tp53 WT，需要分析。”不带文件引用。
2. 断言 Bridge 审计中只有一条首轮 `room.ask_user`，`payload.clarify_kind=execution_object`、`payload.round=1`；首轮无 `room.agent_message`，无 `run_consultation` 对应会诊事件。
3. 断言前端只显示**一项**数据来源追问（文本气泡或卡片二选一，推荐卡片）；不得同时显示固定话术气泡与卡片。
4. 选择“我去上传文件”后，断言 UI 明确为“等待上传”，或在同一交互中上传文件；不得把它显示为“已收集信息”。
5. 上传或 @ 引用真实文件后，断言后续 `room.user_message.context_refs` 非空，且后端改走 `room.route_decision` / planning，不再产生 `room.ask_user` round=2。
6. 用相同 `client_message_id` 重发请求、模拟 Celery retry/重复投递；按 `causation_event_id` 断言最多一个终态 `room.ask_user` 或 `room.agent_message`。

## H. 与症状描述的差异清单

- “第 2 条卡片状态已收集信息”不能证明澄清答复已被后端消费；它可由本地乐观状态或任意后续用户消息触发。
- “第 1 条文本”和“第 2 条卡片”当前代码可由**同一** `room.ask_user` 事件产生，不能把它们直接计为两条后端消息。
- “16:10 与 16:11 两条文本相同”与两轮固定模板完全吻合，不能仅据文字相同断言 LLM 重复生成。
- 若用户确实已提交可识别文件名、路径、`context_refs` 或 accession，而仍收到第 2 轮卡片，则属于待生产审计确认的异常：应重点检查 `room.user_message` 的实际 payload 是否保留引用，以及响应任务是否取到了同一条事件；当前仓库无该 Case 的原始证据，不能继续归因。
