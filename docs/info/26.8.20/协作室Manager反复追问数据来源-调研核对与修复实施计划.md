# Part 1. 调研提示词存档

## 症状记录（2026-08-20 截图实证）

用户在 AgentTeams 协作室发送：

> 我有6个小鼠肺部单细胞样本 3vs3，我需要对其进行分析，样本是 tp53 mutation vs tp53 WT

随后出现**三轮重复的"确认数据来源"追问**：

1. 16:10 Manager 文本消息：「需要你先确认数据来源，再启动执行。」
2. 16:10 询问工具卡片（状态显示"已收集信息"）：「收到你的执行请求……但还缺少明确的作用对象（输入文件/数据）。请确认数据来源：上传文件后执行（推荐）」
3. 16:11 Manager 文本消息（与第 1 条逐字相同）：「需要你先确认数据来源，再启动执行。」
4. 紧随其后又是一张追问卡片：「仍未拿到可执行的作用对象：请直接上传文件，或回复工作区文件名/路径（如 genes.xlsx），或公共数据库 accession/检索关键词。」（附选项：我去上传文件 / 回复文件名或路径 / 先不执行了）

**问题定性**：
- 同一诉求被重复表达 3+ 次，体验差；
- 第 2 条卡片状态为"已收集信息"，但第 3/4 条仍在追问同一问题——疑似澄清答复未被消费，或追问被重复触发；
- 16:10 与 16:11 两条文本逐字相同——疑似重复生成/重复发送，而非 LLM 自然表述。

## 调研提示词（整段粘贴给编码 Agent）

```text
【任务性质】只做代码级调研与评估，禁止修改任何代码、配置、数据库。
先读代码再下结论；所有结论必须标注文件路径与关键代码位置（文件:行号/函数名）。
凡涉及"触发了几次/有没有消费"的结论，必须以后端审计事件、服务日志或 DB 记录
为物证，不得以前端界面表现为依据（前端存在乐观上屏，可能制造假象）。

【症状背景】
AgentTeams 协作室中，用户发送一条分析请求（6 个小鼠肺部单细胞样本 3vs3，
tp53 mutation vs WT），Manager 在 1 分钟内重复追问"确认数据来源"3 次以上：
- 16:10 文本「需要你先确认数据来源，再启动执行。」
- 16:10 询问工具卡片（卡片状态显示"已收集信息"）
- 16:11 文本「需要你先确认数据来源，再启动执行。」（与 16:10 逐字相同）
- 紧接着又一张追问卡片「仍未拿到可执行的作用对象：请直接上传文件，
  或回复工作区文件名/路径（如 genes.xlsx），或公共数据库 accession/检索关键词」

【调研清单：逐项给出证据】

一、消息生成链路（谁说了这几句话）
1. 定位「需要你先确认数据来源，再启动执行。」这句话的来源：是
   agentteams_room_response_service.py 中的硬编码模板，还是 LLM 生成？
   若是模板，模板在哪；若是 LLM 生成，对应提示词段落在哪。
2. 定位询问工具卡片的生成入口：AskUser/澄清卡的创建函数、卡片状态机
   （"已收集信息"状态由什么事件置位）。
3. 梳理一条用户消息进入协作室后的完整处理链路：
   接收 → 路由决策 → Manager 回复生成 → 澄清卡生成，各环节各自会
   产生哪些消息/卡片，标注代码位置。

二、重复触发的根因（为什么问了很多次）
4. 用后端物证回答：16:10 与 16:11 两条逐字相同的文本，对应几次
   LLM 调用、几次消息写入事件？审计事件中各有几条 room.agent_message？
5. 检查是否存在以下任一模式，逐项确认或排除（给证据）：
   a. 澄清卡状态更新（如"已收集信息"）触发了新一轮 Manager 回复生成；
   b. 定时任务/reconcile/watcher 轮询循环重放了对同一条用户消息的处理
      （注意：精确节律重复 = 轮询循环 + 去重缺失的典型特征）；
   c. 同一条用户消息被两个入口消费（如 SSE 推送 + 历史重载、或
      路由层与响应层各处理一次），缺少 message_id 幂等去重；
   d. 询问工具返回结果后，结果被当作"新的用户输入"再次进入追问逻辑。
6. 检查澄清答复的消费逻辑：用户通过卡片选项或文字回复数据来源后，
   该回复路由到哪里？是否有"该澄清已闭合、不再追问同一问题"的状态标记？
   现状下同一 Case 内 Manager 是否会对已澄清过的维度再次发问？

三、提示词层（话术从哪里来）
7. 列出 Manager 房间提示词中所有与"确认输入/数据来源/作用对象"相关的
   指令段落（含 _build_question() 及系统提示词），标注文件与行号。
8. 检查提示词中是否缺少以下约束：
   - 同一澄清问题在同一 Case 中只问一次（询问前去重）；
   - 优先自行检索工作区文件，确实没有可用输入时才向用户追问；
   - 追问时合并为一条消息（文本与卡片不重复表达同一诉求）。

四、工作区文件感知（Manager 是否"先看再问"）
9. Manager 回复生成时，系统是否注入了当前工作区文件清单/Case 已有产物？
   若没有，Manager 无从判断"用户是否已有数据"，只能一律追问——
   确认这是否为设计缺口。
10. 用户消息中提到的样本信息（数量、分组、比较设计）是否被结构化提取
    并带入后续澄清，还是每轮都从原文重新理解？

【交付格式】
A. 调用链路图：一条用户消息 → 各消息/卡片的产生路径（标注代码位置）。
B. 事件时序表：本次症状对应的后端审计事件清单（时间、事件类型、
   payload 关键字段、由哪段代码写入）。
C. 根因判定：上述第 5 条 a–d 逐项 ✅确认/❌排除/⚠️待验证，附证据。
D. 提示词层问题清单：第 7–8 条发现的缺失约束。
E. 最小改动建议：按"改动面小 → 大"排序的修复方案候选（只列方案与
   涉及位置，不要实施）。
F. 与上述描述不符之处的差异清单。
```

## 拿回报告后的核对要点（供下一轮使用）

1. **区分"话术问题"与"机制问题"**：如果根因是重复触发（机制），只改提示词没用；如果是提示词缺少去重约束（话术），机制不用动。报告的第 C 节是分流关键。
2. **"已收集信息"卡片状态**：确认该状态是否真的代表"用户已答复"，还是仅代表"卡片已展示"——命名误导会掩盖答复未消费的 bug。
3. **修复必须带端到端验收**：复现截图场景（发同样的单细胞分析请求），断言协作室只出现一次数据来源追问（一条消息或一张卡片，不同时出现）。
4. **警惕修复引入第二轮故障**：若新增"询问前去重/预检索"逻辑，需核对去重键设计与既有消息幂等机制（client_message_id / causation_event_id）是否一致。

# Part 2. 调研报告核对结论（2026-08-20）

> 核对对象：`协作室Manager反复追问数据来源-代码调研报告_2026-08-20.md`
> 总体评价：格式齐全（A–H 节完整，无矩阵缺格），证据边界标注诚实，可采用。

## 2.1 确认的问题

| # | 问题 | 关键证据 | 性质 |
| --- | --- | --- | --- |
| 1 | "文本+卡片"重复表达 = 同一 `room.ask_user` 事件的 `content`/`questions` 被前端渲染两次 | `room_response_service.py:795,801`、`agentTeamsRoom.ts:666`、`AgentTeamsRoomView.vue:1629,1635` | 确定性 UI bug |
| 2 | 第 2 轮追问是**必然发生**的设计缺陷：第 1 轮选项本身不含对象，选完仍不满足规则判定 | `room_response_service.py:777,788`；单测 `test_...:803,833` 已锁定该行为 | 交互设计缺陷（核心） |
| 3 | "已收集信息"是前端乐观标记，不读后端审计 | `AgentTeamsRoomView.vue:784`、`agentTeamsRoom.ts:1317`、`AskUserCard.vue:114` | 状态语义误导 |
| 4 | 追问触发在**规则分类器**而非 LLM 提示词，LLM 调用数为 0 | `agentteams_execution_intent.py:67-99`、`room_response_service.py:277` | 分流结论：改提示词无效 |
| 5 | "先看再问"缺口：Manager 提示词不注入 Case 工作区文件清单 | `room_response_service.py:1125,1139,1171` | 设计缺口 |
| 6 | 双投递幂等风险：缓解代码（Redis 去重）在工作树中**未提交** | `room_response_service.py:233`、`agentteams.py:611`（无条件 delay） | 安全隐患 |

## 2.2 保留意见

1. **当次事件计数未实证**：报告 C 节事件时序为"代码预期"而非生产审计。16:10/16:11 各写了几条 `room.ask_user`，需拉生产 Bridge `audit.jsonl`（按 `case_id` 过滤、按 `event_id/recorded_at/payload.round` 排序）才能闭环。此项**挂起待验证**，不阻塞阶段 0/1 施工。
2. **F2（选项与对象输入合并）改动面被报告低估**：AskUserCard 需支持文件上传/路径填写控件，属组件级改动，排入阶段 1，不与阶段 0 止血并列。

## 2.3 旧判断修正记录

- 修正：调研提示词中"16:10 与 16:11 逐字相同 → 疑似重复生成/重复发送/轮询重放"的猜测，被报告证据降级——更可能是两轮 `room.ask_user` 共用同一固定 `content` 模板（`_emit_execution_clarify()` 硬编码），不需要 LLM 参与，也不必然意味着消息重放。以报告 D 节判定（a 排除、b 基本排除、c ⚠️、d 确认为设计链路）为准。

# Part 3. 修复实施计划

## 3.1 阶段 0：止血（前端去重渲染 + 幂等固化）

收益最快、不依赖架构改动，直接消除截图中"文本+卡片"双显示与双投递隐患。

```text
【任务性质】在现有代码基础上增量修改，禁止重构无关模块；先读
《协作室Manager反复追问数据来源-代码调研报告_2026-08-20.md》再动手，
其中文件:行号锚点改动前先确认仍有效。

【实现内容】
1. 前端去重渲染：对 payload.clarify_kind == "execution_object" 的
   room.ask_user 投影消息，不渲染 payload.content 的文本气泡，
   仅渲染 AskUserCard。
   涉及：frontend/src/views/AgentTeamsRoomView.vue:1629,1635、
   frontend/src/utils/agentTeamsRoom.ts:666。
   约束：其他类型 ask_user 的渲染行为不变（只动 execution_object 分支）。
2. 幂等固化：
   a. 将当前工作树中未提交的 Redis 响应去重（按 room.user_message.event_id）
      整理为正式提交；Redis 读取失败降级为继续处理的行为保留，
      但降级时必须写审计事件 room.dedup_degraded（含原因）；
   b. API 层 post_room_message() 返回 deduplicated=True 时，
      不再调用 respond_to_room_message.delay()；
      涉及 src/cygnusx/api/v1/agentteams.py:611、
      src/cygnusx/application/services/agentteams_service.py:1378；
   c. 响应事件携带 causation_event_id = 源 room.user_message.event_id；
      澄清答复事件携带 answer_to_event_id = 对应 room.ask_user.event_id。

【验收（端到端，不接受只跑单测）】
| 操作 | 期望现象 | 不通过时的处理 |
| --- | --- | --- |
| 发送"我有6个小鼠肺部单细胞样本 3vs3，tp53 mutation vs WT，需要分析"（不带文件引用） | 只出现一张数据来源卡片，无同义文本气泡 | 检查 clarify_kind 分支是否漏判；截图对比 |
| 同一 client_message_id 重复提交同一消息 | Bridge 审计中最多一条终态 room.ask_user；无重复 Celery 投递 | 检查 API 层 deduplicated 分支是否生效 |
| 模拟 Celery retry/重复投递同一 event_id | 按 causation_event_id 断言最多一个终态响应事件 | 检查 Redis 去重键设计 |
| 停掉 Redis 后发消息 | 功能正常继续，审计出现 room.dedup_degraded | 检查降级分支是否静默 |
```

## 3.3 阶段 2：体验深化（工作区预检 + 结构化 intake）

```text
【任务性质】在阶段 1 基础上实施；阶段 0/1 的事件 schema 不变。

【实现内容】
1. 工作区/Case 文件预检（对应报告 E2-4/F5）：
   - _maybe_start_chat_execution() 在判定 clarify 前，先查询当前 Case
```

## 3.4 挂起项：生产取证（不阻塞施工，建议并行）

从生产 Bridge 按 `case_id` 拉取该次会话的 `audit.jsonl`，按 `event_id/recorded_at/payload.round` 排序，回答：16:10/16:11 各写了几条 `room.ask_user`、有无重复投递。若发现事件数超出代码预期（如三条以上 `room.ask_user`），回到报告 D 节 c 项重新排查双投递。

## 3.5 总验收 Checklist

- [ ] 首轮只出现一项数据来源追问（卡片，无同义气泡）
- [ ] 首轮即可完成"给对象"，不再必然触发第 2 轮追问
- [ ] "已收集信息"有后端事实语义（room.ask_user_answered + 对象判定通过）
- [ ] 幂等：重复 client_message_id / Celery retry / 重复投递均最多一个终态事件
- [ ] Redis 降级有审计事件（room.dedup_degraded），无静默
- [ ] 响应事件带 causation_event_id，答复带 answer_to_event_id
- [ ] 工作区已有文件时改确认式提问（阶段 2）
- [ ] 样本设计入结构化 intake，后续轮次复用（阶段 2）
- [ ] 生产取证闭环：当次事件计数与代码预期一致（挂起项）

## 3.6 风险登记

| 风险 | 缓解 |
