## Part 1 症状与预期

**用户实际操作**：在协作室输入「你可以干什么呀」。

**实际输出**（原样摘录关键句）：
- Manager 列出 5 条静态能力描述（需求承接与澄清/分析规划与专家调度/质量管控/结果汇总与交付/跨阶段协调）；
- 结尾出现：「**当前协作房间已就绪，状态为「已接收」。你可以直接告诉我你的研究需求或想要完成的任务，我会评估信息完整性后进入规划阶段。**」+ 两条"建议"后缀。

**预期行为**：
1. 能力咨询属于咨询类输入：不得改变房间状态、不得产生任何 proposal/Case 侧事件、不得把话锋推向"进入规划阶段"（那是甲方提出真实需求后才该有的引导）。
2. 回复中不得出现内部状态机语言（"状态为「已接收」"这类房间状态页脚属于实现细节，按"让用户看到科学、看不到管道"原则不应上屏）。
3. 能力描述必须与能力目录（`data/ai/agent_ability.yaml`）实况一致——Manager 应查询目录作答，而不是背诵 prompt 里的静态清单。

**已知背景（调研时先验证这些前提是否仍成立，勿重复已排除方向）**：
- Case 解耦已修：闲聊/咨询不建 Case，Case 只在立项确认后创建。本次大概率没建 Case，疑点不在此——但**需要审计事件证明本次交互零 proposal 侧事件**（回归确认）。
- "反复追问数据来源"的根因是规则分类器 + 固定模板 + 单步收敛；其修复计划阶段 1/2 的施工状态未知，本次症状（能力咨询被推入接单话锋）与它是同族问题，需确认分类器是否仍未区分"咨询 vs 需求"。
- F3 已落地"能力先查目录再声称"的行为规范；F4 已有 `case_facts_query` 工具与 introspection 端点（仅 case 事实维度）。能力目录/房间元数据的查询通道是否存在，现状未知。

## Part 6 修复实施计划

### 根因定型（一句话）

分类器只闸门副作用、不闸门话锋：chat 态与接单共用同一份 prompt 注入（含 Case 状态与"进入规划阶段"引导），人格 prompt 还主动要求把内部状态说给用户；能力回答无目录注入、无查询工具，只能靠模型即兴背诵——于是必然漂移。

### 阶段 A：chat 态话术收口（代码 + 人格文案）

- **A1** `_build_question` 分支化（`agentteams_room_response_service.py:1659-1742`）：chat 态（主回路调用点 `:427`）走咨询专用构建——不注入 `Case 当前状态`（`:1738`）、不注入"下一步进入规划/确认/执行/交付"指令（`:1722-1725`）、澄清协议段（`:1726-1733`）替换为"纯咨询直接作答，禁止输出 ask_user"。tool_execute 分支（`:940-950`）与 @专家分支（`:607-615`）属工单语境，保持现状。
- **A2** `data/ai/prompts/agentteams_manager.md:20-23` 改写：删去对纯咨询"结合 Case 状态说明进展"的要求；"说明下一步阶段"限定于已立项 Case 语境。按 F6"解释 why"风格：内部状态机语言是管道不是科学，甲方看到「已接收」只会困惑。
- **A3 红线**：禁止改 `classify_execution_intent` 四态与 `:828-829` 短路（已验证正确）；咨询零接单侧事件维持；不动 `general.yaml`。

### 阶段 B：能力查询工具化（新工具 + prompt 改造）

- **B1** 新增 `ability_catalog_query` 工具：包装 `AgentTeamsCapabilityRegistry.snapshot()`（`agentteams_capability_registry.py:387-417`，与 `GET /capabilities` 同一实现源）；默认返回 summary 层，支持按 agent_id 取 detail（呼应 F5 渐进暴露）；只读；注册进 `tools_schema.yaml` + 挂入 `agentteams_case` 工具包（`data/ai/tools/agentteams_case.yaml`）——Manager 已挂该包，零配置获得。
- **B2** `agentteams_manager.md` 能力自述段（`:8-9` 附近）改写：删静态背诵清单，改为"被问能力时先用 ability_catalog_query 拉目录实况再按四段契约口径作答；不得声称目录外能力（质量管控属 agent-qc）；为什么——目录是活文档，背诵会腐烂"（"缓存路由而非缓存事实"模式）。
- **B3 顺手项**：`subagents_spawnable` 补入注册表快照字段（`agentteams_capability_registry.py:165-183`）。
- **B4 缓项**：`room_state_query`（房间元数据查询）暂不做——报告确认用户态 REST 可查，Manager 侧需求不强，待有真实场景再立。

### 阶段 C：验收（单测 + E2E + 幻觉防线）

- **C1 单测**：chat 分支 `_build_question` 产物中不含状态注入与接单引导语；`ability_catalog_query` 输出与 registry snapshot 一致、detail 按需加载；`room_state_query` scope 锁定当前房间（拒绝外部 room_id 入参）。
- **C2 E2E-17**：未立项房间输入「你可以干什么呀」→ 回复不含「已接收」「进入规划阶段」字样、无 ask_user 卡、自述能力项全部能在目录中找到、「质量管控」不作为 Manager 自身能力出现；输入「hi」→ 无状态页脚、无澄清卡。
- **C3 回归**：执行类输入（如"帮我做这批样本的 RNA-seq 差异分析"）→ 仍正常出立项确认卡（room.proposal_confirm）；@专家 与 tool_execute 分支话术不变。
- **C4 幻觉防线断言**：E2E 中把回复提到的能力项与目录快照做集合包含断言（回复能力 ⊆ 目录）。
