## Part 1 症状与预期

**用户实际操作**：在协作室输入「你可以干什么呀」。

**实际输出**（原样摘录关键句）：
- Manager 列出 5 条静态能力描述（需求承接与澄清/分析规划与专家调度/质量管控/结果汇总与交付/跨阶段协调）；
- 结尾出现：「**当前协作房间已就绪，状态为「已接收」。你可以直接告诉我你的研究需求或想要完成的任务，我会评估信息完整性后进入规划阶段。**」+ 两条"建议"后缀。

**预期行为**：
1. 能力咨询属于咨询类输入：不得改变房间状态、不得产生任何 proposal/Case 侧事件、不得把话锋推向"进入规划阶段"（那是甲方提出真实需求后才该有的引导）。
2. 回复中不得出现内部状态机语言（"状态为「已接收」"这类房间状态页脚属于实现细节，按"让用户看到科学、看不到管道"原则不应上屏）。
3. 能力描述必须与能力目录（`data/ai/agent_ability.yaml`）实况一致——Manager 应查询目录作答，而不是背诵 prompt 里的静态清单。

**已知背景（调研时先验证这些前提是否仍成立，勿重复已排除方向）**：
- Case 解耦已修：闲聊/咨询不建 Case，Case 只在立项确认后创建。本次大概率没建 Case，疑点不在此——但**需要审计事件证明本次交互零 proposal 侧事件**（回归确认）。
- "反复追问数据来源"的根因是规则分类器 + 固定模板 + 单步收敛；其修复计划阶段 1/2 的施工状态未知，本次症状（能力咨询被推入接单话锋）与它是同族问题，需确认分类器是否仍未区分"咨询 vs 需求"。
- F3 已落地"能力先查目录再声称"的行为规范；F4 已有 `case_facts_query` 工具与 introspection 端点（仅 case 事实维度）。能力目录/房间元数据的查询通道是否存在，现状未知。

## Part 2 调研提示词（paste-ready）

```
只做代码级调研，禁止修改任何代码。所有结论标注文件路径与关键代码行；结论分"已证实（附证据）/ 未找到（明说没有）/ 存疑（说明缺什么证据）"三档。

背景：用户在协作室输入「你可以干什么呀」，Manager 回复了 5 条能力清单 + 一句「当前协作房间已就绪，状态为「已接收」……我会评估信息完整性后进入规划阶段」+ 两条建议后缀。预期：能力咨询不改房间状态、不输出内部状态页脚、能力描述应与能力目录实况一致。

Q1 意图分类路径：追踪该输入在 room_response_service（agentteams_room_response_service.py）及 agentteams_intent_router.py / agentteams_route_decision.py 中的完整分类与路由链路。该输入被分到了哪个分支（咨询 / 接单 intake / 其他）？判定依据是什么规则？给出决策链每一环的代码位置。

Q2 状态页脚来源：全局搜索字符串「当前协作房间已就绪」「已接收」「进入规划阶段」及等价模板片段，定位这句页脚的产出位置——是固定模板拼接还是 LLM 生成？它在哪些分支（咨询/接单/闲聊）会被注入回复？修复"hi 不建 Case"时加的闲聊/咨询分支是否也带这个页脚？

Q3 能力清单来源：回复中那 5 条能力描述（需求承接与澄清/分析规划与专家调度/质量管控/结果汇总与交付/跨阶段协调）的出处——是 agentteams_manager.yaml / prompts/agentteams_manager.md 中的静态文案，还是运行时从 data/ai/agent_ability.yaml 渲染？若为静态文案，给出具体文件与行号，并对比其与能力目录 summary 层的漂移程度（目录里有哪些能力是该清单没提的 / 清单里有哪些描述与目录契约不一致）。

Q4 查询通道现状：①case_facts_query 工具与 /api/v1/agent-teams/introspection/* 端点当前能查什么（模板清单、受限 SQL 表白名单）——能否回答"能力目录""房间元数据/房间状态"类问题？②平台的 MCP 工具注册表中是否已存在协作室自省/能力目录类工具（注意既有结论：平台工具已全量 MCP 化，subagents_spawnable 待入注册表）？③Manager 角色的工具注入清单里有没有可用于回答能力咨询的查询工具？

Q5 零副作用回归确认：给出该类咨询输入实际会产生的审计事件清单（代码路径推导即可，无需实跑）——确认不产生 room.proposal_*、confirm_token、Case 创建等任何接单侧事件；若会产生 room 状态变更（如 status 迁移、last_activity 之外的写入），逐条列出。

Q6 同族修复状态：对照《协作室Manager反复追问数据来源-调研核对与修复实施计划》的阶段 1（分类器区分咨询/需求）与阶段 2（UI 双渲染/单步收敛），核实这两阶段是否已施工、施工到什么程度；若部分施工，指出本次症状落在哪个未施工环节。

交付格式：
1. 六节事实清单（每节：结论 / 证据位置 / 三档置信度）；
2. 一张「你可以干什么呀」从进入到出文的完整调用链图（标注每个分支点）；
3. 汇总表：问题点 × 根因层级（分类器 / 模板注入 / prompt 静态文案 / 查询通道缺失）× 修复面估计（配置 / 代码 / 新工具）。
禁止修改任何文件。
```

### 与《协作室框架全景文档评审结论-2026-08-21》核实提示词的重叠分工

若两份提示词同批发给编码 Agent，重叠项证据共用、不重复调查：

- 本提示词 Q1（意图分类链路）↔ 评审结论 P0-1（路由层静默回落的代码路径）——Q1 的调用链图覆盖该核实面；路由无命中直达兜底专家的具体代码位置，在 Q1 结果中一并标注即可；
- 本提示词 Q4（查询通道现状）↔ 评审结论 N4（自省端点授权粒度与 SQL 绕过证据）——Q4 只回答「能查什么」；授权粒度与绕过用例证据以评审结论 Part 5 的 N4 为准。

全景文档的其余缺陷项（评审新增 N1–N3、N5、N6，及其自列 P0-2~P0-4、P1-5~8、P2-9~11）**不在本文档范围**，统一由《评审结论》Part 5 的核实提示词承载，两份文档合起来才是当前全部待核事项的完整集。

## Part 3 设计侧预判（待报告证实/推翻，先不定稿）

1. **根因预判**：Q1+Q2 大概率证实——咨询与接单在分类器里未分流（同族问题），且状态页脚是固定模板在 intake 分支的拼接。若证实，修复面在分类器规则 + 模板注入条件，**不是** Manager 提示词改写能解决的。
2. **能力清单**：Q3 大概率证实为静态文案。修复方向按"缓存路由而非缓存事实"模式：Manager prompt 里删掉背下来的能力清单，改写为"回答能力类问题时，先用查询工具拉取能力目录实况，再组织语言"。
3. **查询工具形态**：Q4 的结果决定形态——若现有工具包可扩展，优先扩展（一个工具包内加 ability_catalog_query / room_state_query 两个工具）；若平台生态以 MCP server 为单位注册，则挂"协作室自省"MCP 工具组。两者都行，原则是复用 F4 的安全口径（只读、scope 限定、审计）。
4. **红线**：修复不得引入"咨询也建 Case"或"咨询触发立项确认卡"的回退；成本闸门语义不变。
