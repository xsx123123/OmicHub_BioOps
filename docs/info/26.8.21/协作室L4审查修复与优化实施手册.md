## 阶段 0：安全止血（最高优先，均为小改动）

> 目标：堵死审批旁路与审计伪造两个高位洞，加 confirm_token 脱敏护栏，
> 消掉 agent_stream 刷屏。均在 1–2 个文件内可完成，不依赖阶段 1 的工程闭环。

```text
【任务性质】紧急安全修复，最小改动：禁止重构、禁止夹带功能改动。
每项修复附改动文件清单与验证证据。先读审查报告 B 节与 D 节#2 再动手。

【修复 1：B1 审批旁路（最高优先）】
根因：/v1/worker-tokens 的 known_identities 含 approval-authority
（bridge/app.py:412-414），持 manager 凭证者可自铸审批 token，
绕过人工审批直接驱动写操作。
要求：
1. approval-authority 从 worker-tokens 可铸造身份中移除；
   approval token 只能由审批卡确认链路签发（approval 端点内部），
   且 token 绑定 case_id + approval_id + plan_hash，一次性、短时效；
2. 全仓检索 approval-authority 的其他签发/接受点，确认无第二旁路；
3. 审计存量：列出当前已签发的 approval-authority 类 token，
   全部吊销并重新经审批链路签发；
4. 回归测试：构造"manager 凭证请求 approval token"场景，断言 403；
   审批确认链路正常签发不受影响。

【修复 2：B2 审计伪造面】
根因：/v1/cases/{id}/evidence 无角色约束，任意 worker token 可伪造审计事件。
要求：
1. evidence 写入限定身份白名单（如 workflow-operator 与持有效租约的
   case 绑定 worker），其余身份 403；
2. 写入事件强制携带 causation_event_id 并在写入侧校验其存在性，
   无因果锚点的事件拒绝入流；
3. 回归测试：无关联 token / 非绑定 worker 写 evidence 被拒。

【修复 3：B3 confirm_token 脱敏护栏】
现状核对结论：owner 校验已兜住跨用户攻击面（中危，非跨用户漏洞），
但明文入事件流 + SSE/分页无脱敏仍需护栏。
要求：
1. room.proposal_confirm 事件写入后，confirm_token 字段在以下三处
   一律脱敏（置 null 或哈希化）：SSE 推送、events 分页响应、
   AuditRoomMirror 镜像载荷；
2. confirm-proposal 端点校验 token 时同时校验操作者 = 房间 owner
   （保留现有 owner 校验，补充显式断言与审计记录）；
3. 测试：事件流全出口（SSE/分页/Matrix 镜像）均不泄露 token 明文。

【修复 4：D#2 agent_stream 刷屏与写放大】
要求：
1. AuditRoomMirror 跳过 room.agent_stream（瞬态事件）—— Matrix 不再
   每 24 字符刷屏；
2. room.agent_stream 移出 MinIO 持久事件流，改走 Redis pub/sub
   （SSE 打字机消费方不变）；历史重放以 room.agent_message 终态为准；
3. 验收：流式回复期间 Matrix 房间只有终态消息；MinIO 事件流对象
   不再因打字机增量触发全卷读写。

【通用验收（端到端）】
| 操作 | 期望现象 | 不通过时的处理 |
| --- | --- | --- |
| manager 凭证请求 approval-authority token | 403 + 审计记录 | 检查 known_identities 与签发点是否清干净 |
| 普通 worker token 写 evidence | 403 | 检查角色白名单生效点 |
| 创建立项确认卡后观察 SSE/分页/Matrix | 三处均无 token 明文 | 检查是否有第四出口（如 audit-chain） |
| 立项确认（owner 本人） | 正常通过，token 一次性消费 | 回归确认未误伤正常流程 |
| 发起一次流式回复 | Matrix 无增量刷屏；MinIO 对象无打字机写放大 | 检查 mirror 过滤与事件分级 |
```

【验收（人工）】

## 阶段 2：正确性加固（数据可信度）

> 目标：修掉会把错误状态固化进事实源的正确性缺陷。依赖阶段 0/1 完成
> （否则修了也部署不上去）。

```text
【任务性质】最小改动正确性修复，每项带回归测试。

【修复 1：D#6 CaseStore 幽灵态固化】
根因：MinIO 快照写失败时 in-memory 已先更新；无 Redis 部署下，
后续全量写会把幽灵态固化进 MinIO（审查报告严重度上修）。
要求：
1. 采用 persist-then-commit：内存态提交前快照写必须成功；
   写失败回滚内存态并抛错（约 20 处调用点，逐点改造并列表）；
2. 若个别调用点改造成本过高，至少保证：快照写失败 = Case 操作失败 +
   结构化告警，禁止内存态继续推进；
3. 回归测试：注入 MinIO 写失败，断言操作失败、内存态回滚、
   后续读取无幽灵态。

【修复 2：幂等 receipt 持久化（遗留 #8）】
现状：幂等 receipt 靠启动重放 omic_task.submitted 重建，未持久化。
要求：receipt 随事件流/快照一并入 MinIO；重启后不依赖全量重放。
验收：重启后立即重放相同请求，幂等命中不依赖重放完成度。

【修复 3：会诊异常事件因果链（遗留 #3）】
要求：run_consultation 调用链显式传入触发 event_id，
consultation.parse_failed 等异常事件携带 causation_event_id。
验收：构造解析失败场景，audit-chain 输出中异常事件因果链完整。
```
