## 症状与预期（复述）

**用户操作**：在协作室输入「你可以干什么呀」。

**实际输出**：Manager 列出 5 条静态能力描述（需求承接与澄清 / 分析规划与专家调度 / 质量管控 / 结果汇总与交付 / 跨阶段协调），结尾带「当前协作房间已就绪，状态为「已接收」。你可以直接告诉我你的研究需求或想要完成的任务，我会评估信息完整性后进入规划阶段。」+ 两条"建议"后缀。

**预期**：
1. 能力咨询属咨询类输入：不得改变房间状态、不得产生 proposal/Case 侧事件、不得把话锋推向"进入规划阶段"；
2. 不得出现内部状态机语言（"状态为「已接收」"）；
3. 能力描述必须与能力目录（`data/ai/agent_ability.yaml`）实况一致——应查询目录作答，而非背诵 prompt 静态清单。

## Q1 意图分类路径

**结论（已证实）**：协作室链路**不存在"咨询 vs 接单/intake"的分类器区分**。唯一的本地意图分类是执行意图四态（execute / tool_execute / clarify / chat），判定依据为纯正则关键词表，无 LLM 调用。「你可以干什么呀」命中 **chat** 分支；chat 与"接单对话"**共用同一条 Manager LLM 主回路**——这是页脚混入的结构性原因。

**决策链逐环证据**：

1. 分类器本体：`src/cygnusx/application/services/agentteams_execution_intent.py:99-121`（`classify_execution_intent`）。规则顺序：
   - ① 命中一票否决词 → chat（`:38-57`，词表含"能做什么/你会什么/介绍一下/是什么/hi/hello"等）；
   - ② 无执行动词 → chat（`:60-65`）；
   - ③ 动词+作用对象 → execute / tool_execute；
   - ④ 动词无对象 → clarify。
2. 逐条核对「你可以干什么呀」：不含"能做什么"（是"干什么"）、不含任何否决词；执行动词表（分析/运行/读取/绘图…）一个都不含 → 在 `:115-116` 返回 `CHAT`。（正则静态推演 + 实测 `classify_execution_intent('你可以干什么呀', [])` 返回 `chat`）
3. 调用点：`agentteams_room_response_service.py:813` `intent = classify_execution_intent(content, refs)`；`:828-829` `if intent is ExecutionIntent.CHAT: return "none"` → 直接落入 Manager LLM 通用回复路径（`:427` 起），**没有任何"咨询专用"处理，也没有禁状态页脚的护栏**。
4. 模块 docstring 自证设计意图：`agentteams_execution_intent.py:3-6`（"历史上曾因关键词误触发，把纯咨询问题送进 planning 流水线…任何歧义都判 chat/clarify"）——chat 是"咨询/寒暄"的唯一下水道，但 chat 之后去向与 intake 对话完全相同。

**附带发现：静默回落路径（与本症状无关，同属一类隐患）**：

- execute 态下"路由无命中直达兜底专家 agent-code"：`agentteams_room_response_service.py:859-866`（`infer_intent_route` 无命中返回 None）→ `:900` `target_agent_id = route.lead_planner if route else DEFAULT_LEAD_PLANNER`，`DEFAULT_LEAD_PLANNER = "agent-code"`（`agentteams_service.py:76`）。仅 route_decision 卡里记 `fallback_reason`（`agentteams_route_decision.py:216-219`）。
- 关键词路由本体：`agentteams_intent_router.py:135-222`（trigger_hints 子串匹配+评分）；`:5` docstring 明说"识别不了返回 None，调用方保持 agent-code 兜底"。
- Manager 人格降级兜底：`agentteams_room_response_service.py:1534-1565`（agentteams-manager 不可用→agent-general→任意 planner_eligible，落 `room.manager_persona_fallback` 审计，非完全静默）。
- chat 态不经过任何路由，直接 LLM，无回落问题。

**入口链路（已证实）**：

`POST /rooms/{room_id}/messages`（`src/cygnusx/api/v1/agentteams.py:741-775`）→ `AgentTeamsRoomService.post_room_message` 落房间命名空间事件流（`agentteams_room_service.py:203-220`）→ Celery `respond_to_room_namespace_message`（`infrastructure/celery_app/tasks/agentteams.py:98-145`）→ `AgentTeamsRoomResponseService.respond_room`（`agentteams_room_response_service.py:239-295`）→ 未立项房间以 `room-<room_id>` 伪 Case 走 `_respond_locked`（`:297`）。

## Q2 状态页脚来源

**结论（已证实，形态与设计侧预判相反）**：「当前协作房间已就绪，状态为「已接收」……进入规划阶段」这句话是 **LLM 生成，不是固定模板拼接**。源码与 YAML/prompt 中均无此字面串。

**证据**：

- 全仓 grep「协作房间已就绪 / 状态为 / 评估信息完整性 / 进入规划阶段」：源码零命中（仅 evidence/ 与 docs/ 调研记录、前端状态标签映射 `frontend/src/utils/agentTeamsStatus.ts:7` 的"已接收"标签命中）。模板片段「房间已就绪」同样零命中。
- 页脚的三项原料全部注入在 LLM prompt 里：
  - `Case 当前状态：received` —— `agentteams_room_response_service.py:1738`（`_build_question` 拼 `f"Case 当前状态：{case.status}"`；房间命名空间记录在 Bridge 侧创建时即 `status="received"`，`integrations/agentteams/bridge/cygnusx_agentteams_bridge/service.py:1503`）；
  - "说明下一步进入规划、确认、执行、交付哪个阶段"的指令 —— `_build_question` `:1722-1725`；
  - Manager 系统人格同款指令 —— `data/ai/prompts/agentteams_manager.md:20-23`（"纯咨询与进展询问：直接以部门经理口吻回答，**结合 Case 状态说明进展**"、"需要执行的分析请求：说明当前 Case 与目标是否一致，以及下一步进入规划、确认、执行、交付中的哪个阶段"）。即人格 prompt 主动要求把内部状态机语言说给用户听。
- 旁证（历史运行实测）：`evidence/e2e-2026-08-21/E2E-11/room_events_full.json` 中 "hi" 的回复即以 room.ask_user 形式产出「协作房间已就绪，当前 Case 处于「已接收」状态…再进入规划与确认阶段」——同一 prompt 结构、不同措辞，佐证是模型自由生成。

**页脚注入范围（已证实）：不区分分支**——凡是走 Manager LLM 主回路的回复都带这套 prompt 原料：

- `_build_question` 被三处复用：主回路（`agentteams_room_response_service.py:427-436`，chat/咨询/接单对话共用）、tool_execute 分支（`:940-950`，status 写死为 "tool_execute"）、直接 @专家 分支（`:607-615`，同样拼 Case 状态）。
- "hi 不建 Case"修复并未新增独立的闲聊/咨询回复分支；修复实质是"会话-工单解耦"（未立项房间走命名空间流 + execute 态先落立项确认卡，`respond_room` `:254-262`、`_maybe_start_chat_execution` `:867-880`），chat 态仍走同一条 LLM 主回路，**闲聊/咨询回复天然带状态页脚原料**（E2E-11 的 "hi" 回复即为实证）。
- 代码侧唯一的回复后处理是 `_gate_unstarted_handoff_language`（`:1172-1178`，只替换"已交接/已派发"类措辞），无任何剥离状态页脚的机制。

**"两条建议后缀"来源（已证实）**：LLM 信封的 `recommendations` 字段，前端固定以"建议"标签渲染：

- 信封契约要求输出 `recommendations` 数组：`agent_consultation_service.py:484-488`（`_build_instruction` 的 envelope_clause）；
- 后端透传：`agentteams_room_response_service.py:477-484`（`manager_report.recommendations`）；
- 前端渲染：`frontend/src/views/AgentTeamsRoomView.vue:1945-1948`（`manager-report__label` 写死"建议"，逐条 li 渲染）。

## Q3 能力清单来源

**结论**：回复中 5 条能力描述（需求承接与澄清 / 分析规划与专家调度 / 质量管控 / 结果汇总与交付 / 跨阶段协调）**不是运行时从 `data/ai/agent_ability.yaml` 渲染的**；但其原文也**不在** `agentteams_manager.yaml` 或 `agentteams_manager.md` 里——全仓 grep（`需求承接|跨阶段协调|专家调度|质量管控|结果汇总`）仅命中调研提示词文档本身，无任何代码/配置出处。它们是 **LLM 对静态 prompt 文案的即兴改写**。Manager 房间回复链路上**没有注入**能力目录。

**证据位置**：

- Manager 房间回复的用户侧问题由 `_build_question` 拼装，只注入 Case 目标/状态/研究设计/最近动态/文件引用/回复偏好，**无任何能力目录内容**：`src/cygnusx/application/services/agentteams_room_response_service.py:1659-1742`（已证实）。
- 房间会诊走 `AgentConsultationService.run_consultation`，系统提示来自 Agent YAML 的 `prompt_file`（即 `agentteams_manager.md`），registry 仅用于白名单校验，未注入目录：`src/cygnusx/application/services/agent_consultation_service.py:311-342`（`assemble_context` 于 :325）（已证实）。
- 能力目录 summary 层只注入**聊天路由** prompt（`ROUTER_CATALOG_SUMMARY_KEYS`，`src/cygnusx/application/services/chat_service.py:359-367`）；detail 层只在多专家会诊分支按选中候选加载（`chat_service.py:6191-6202` 调 `capability_detail_context`，实现于 `agentteams_capability_registry.py:347-363`）。两处都不覆盖房间 Manager 回复（已证实）。
- 最接近的静态来源（5 条的"原型"）：
  - `data/ai/prompts/agentteams_manager.md:8-9` —「接单、说明触发理由、选择规划专家、审核计划、协调专家、点评结果、汇总交付」；
  - `data/ai/agentteams_manager.yaml:55-57` — `default_role` 与 `capability_scope: [需求接单, 规划协调, 计划审核, 进度跟踪, 结果点评, 汇总交付]`。
- 目录中 Manager 自己的条目：`data/ai/agent_ability.yaml:41-49`，`detail.capabilities` 为 `[需求接单, 规划协调, 计划审核, 进度跟踪, 结果点评, 汇总交付]`，`chat_entry: false`（:43）。

**置信度分档**：

- 「非运行时渲染」——已证实（回复链路注入面无目录）。
- 「逐字 5 条在 yaml/md 中」——未找到（全仓无此文案，属模型即兴改写）。
- 「改写自 md:8-9 与 yaml:55-57」——存疑但高度可能（语义一一对应；缺运行时 prompt 落盘日志佐证）。

## Q4 查询通道现状

### ① `case_facts_query` 与 `/api/v1/agent-teams/introspection/*` 能查什么

**结论（已证实）**：能查本 Case 的**产物 / 事件 / 审批 / QC 判决**四类事实；**不能**回答"能力目录"类问题；房间元数据/房间状态只能**间接部分**回答。

- 工具定义：`tool_configs/tools_schema.yaml:264-291`（`case_facts_query`，service=`AgentTeamsIntrospectionService.query_case_facts_tool`）。
- 端点：`POST /api/v1/agent-teams/introspection/query`（`src/cygnusx/api/v1/agentteams.py:936-956`，集成 token 鉴权）；`GET /introspection/schema`（:959-966）。
- 预置模板 5 个：`artifact_versions / event_timeline / pending_approvals / artifact_lineage / schema`（`agentteams_introspection_service.py:67-69`）。
- 受限 SQL 表白名单仅 3 张：`case_artifact_versions / case_artifact_dependencies / qc_verification_checks`（:72-76），强制注入 `case_id` 过滤（:533），禁括号/子查询/IN/BETWEEN（:124、:763）。
- scope 强制 Case 维度；`room-*` 命名空间直接拒绝（:287-288）；denied 关键词审计（:81-120）。
- **能力目录**：白名单无 agent/能力表，模板无 capabilities —— **未找到支持**。
- **房间元数据/状态**：无房间表、无 room 模板；仅 `pending_approvals` 会读 `room.proposal` 立项卡（:505-517）、`event_timeline` 含房间命名空间事件（schema 文档 :11）。房间详情只能走用户态 REST `GET /rooms/{room_id}`（`agentteams.py:725`），**不在自省面内**。
- 附带发现：`GET /api/v1/agent-teams/capabilities`（`agentteams.py:112`，集成 token）返回运行时能力快照（registry `snapshot()`，`agentteams_capability_registry.py:387-417`），能答能力目录——但它是 HTTP 端点，**未包装成模型可调用工具**。

### ② MCP 工具注册表中的自省/能力目录工具

**结论（已证实）**：builtin MCP 注册处无协作室自省/能力目录类工具；但 `case_facts_query` 等 agentteams 工具经 `cygnusx-tools` builtin preset 动态汇入 MCP 面。

- `presets.py` 的 `PLATFORM_PRESET_TOOLS` / `PLATFORM_HANDLERS`（:1221-1619）共 18 个平台工具，**无** introspection/capability 类（最接近的是 `platform_list_agent_skills`，:1339-1360，查技能绑定而非能力目录）。
- `cygnusx-tools` preset 由 `tools_schema.yaml` 动态构建（`presets.py:1635-1704`），因此 `case_facts_query`（tools_schema.yaml:264）实际已在 MCP 面内。
- 既有结论核实：「平台工具已全量 MCP 化」**属实**——`_apply_tool_packs` 把 `builtin_tools` 映射到 `CYGNUSX_TOOLS_SERVER_ID`、`platform_tools` 映射到 `CYGNUSX_PLATFORM_SERVER_ID`（`src/cygnusx/infrastructure/config/agent_loader.py:232-236`），且不再隐式注入默认 server（`agent_service.py:309-310`）。
- 「subagents_spawnable 待入注册表」**仍属实**：派生工具 `parallel_subagents` 已注册（`tools_schema.yaml:78-108`，要求目标 Agent 标 `subagents_spawnable`，:103），运行时由 `parallel_subagent_service.py:238-243` 与 `chat_service.py:3171、:8066` 直接读 `agent.features` 校验；但 `AgentTeamsCapabilityRegistry.agent_capabilities()` 的快照字段（`agentteams_capability_registry.py:165-183`）**不含** `subagents_spawnable`——该标记尚未进入注册表快照。

### ③ Manager 的工具注入清单

**结论（已证实）**：`agentteams_manager.yaml:21-22` 显式 `mcp_ids: []`、`skill_ids: []`；实际挂载全部来自 `tool_packs: [workspace, research, memory, agentteams_case]`（:64），经 `agent_loader.py:194-252` 展开为：

## Q5 零副作用回归确认

**结论（已证实，达标）**：「你可以干什么呀」被判为 `chat` 态，**不产生任何接单侧事件**（无 `room.proposal_*`、无 confirm_token、无 Case 创建），房间行（`agentteams_rooms`）无任何写入；链路上仍会产生 1 条用户发言事件 + 若干房间级审计/投影事件 + 一次 LLM 会诊带来的主库写入（合成会话用量落库与饼干扣费）。

**决策链逐环证据**：

1. **入口落盘**：`POST /rooms/{room_id}/messages` → 只写 Bridge 事件 `room.user_message`（房间命名空间流 `room-<room_id>`），未立项房间不触碰房间行。
   - `src/cygnusx/api/v1/agentteams.py:741-775`（741 端点；757-758 `deduplicated=True` 时不再派发 Celery——阶段 0 幂等固化已生效）
   - `src/cygnusx/application/services/agentteams_room_service.py:203-220` → `agentteams_service.py:1458-1496`
2. **响应任务**：`respond_to_room_namespace_message` → `respond_room()`，未立项房间转到命名空间 case_id `room-<room_id>` 走 `respond()`。
   - `src/cygnusx/infrastructure/celery_app/tasks/agentteams.py:98-145`（130 调 `respond_room`）
