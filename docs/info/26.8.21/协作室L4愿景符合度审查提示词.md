## 审查背景与目标

升级文档自称三大问题域（MinIO 化 / Case 解耦 / L4 前置）"全部代码已落地并测试通过"，
但其遗留 #1 同时承认：**地基修复 + 全部升级代码仍在工作树，未分组提交、
未逐条人工验收、e2e 未进 CI**。"已实现" ≠ "已提交已部署已验收"——08-19 事故
（断点 A/F，修复未提交导致 HEAD 仍是事故代码）正是这个落差造成的。

**本次审查的唯一目标：用代码证据 + 生产物证，逐项验证 L4 愿景是否真实生效——**

- 组织模型：用户=甲方；Manager=客户经理（接单、澄清、组队、审批、整合交付）；
  领域 Agent=部门负责人；Worker=执行员工
- 核心原则：人和岗位分离；群聊式沟通+工作流式执行；先冻结计划再理解变更；
  **真实计算必须人工审批（不可旁路）**

不是再查一遍架构描述对不对，而是验证"愿景的每一条"在运行系统里是否成立。

## 拿回报告后的核对要点（供下一轮使用）

1. **先回答"生产在跑什么"再谈愿景**：C 节若显示生产仍是事故代码或中间态工作树，
   则第一行动是提交验收闭环（复用地基手册阶段顺序），愿景验证全部降级为
   "代码级预估"，不能当成已生效。
2. **愿景矩阵里区分两种 ✅**："代码存在 + e2e/生产证据"才算生效；"代码在但没验证"
   一律 ⚠️，别让编码 Agent 用单测绿替代端到端证据（08-19 断点 A 正是这么漏的）。
3. **confirm_token 若证实未过滤**：属安全隐患级，排期压过一切功能项；
   止血方案（镜像/SSE 层过滤敏感字段）不依赖 token 机制重设计，先做。
4. **"组队"若证实是关键词机械命中**：这与愿景"Manager 选规划专家"有差距但
   不算 bug——列为愿景深化项，不要混入缺陷修复排期。
5. **刻意不做不算缺口**：`bioops-delivery.yaml` 无代码加载、M7 拒绝一等 Team
   资源这类设计决策，报告若列为缺口要剔除。
6. **报告自身完整性**：A 节矩阵缺格、判定缺证据位置的，补全后再定稿。
