## Part 1. 持久层与文件体系 MinIO 化

### 1.1 现状问题（证据）

- Bridge Case 状态 = 本地 JSON 文件 + Redis 共享状态（`case_store.py`）；断点 F：`_load()` 对 JSON 损坏静默返回 `{}`（`case_store.py:149-152`），重启后全部 Case 无声消失——**本地文件是单点故障，Redis 是易失缓存，两者都不是持久层**。
- 审计事件流 `audit.jsonl` 同样落在 Bridge 本地（`audit.py`），且已被 ~650 万条 `worker.inbox_polled` 噪音淹没。
- 官方对标：HiClaw/AgentTeams 的模型是**容器无状态，逻辑状态与共享文件全部进 MinIO**，容器重建零状态损失。主后端已有 MinIO，Bridge 没有用上。

### 1.2 设计要点

**原则：MinIO 是事实源，Redis 只是热缓存，本地文件废除。**

1. **事件流对象化**：每个 Case 的审计事件 append 到 MinIO 对象
   `agentteams/cases/{case_id}/events/audit.jsonl`（追加写；单对象过大时按天分卷
   `audit-YYYYMMDD.jsonl`）。写入协议：**先 MinIO 落盘成功 → 再更新 Redis 热态 →
   再 SSE 广播**。MinIO 写失败即操作失败（fail fast），禁止"先缓存后补写"。
2. **状态快照**：Case 状态机当前态定期快照到
   `agentteams/cases/{case_id}/snapshot.json`（每 N 个事件或状态迁移时）；
   启动恢复顺序 = 读最新快照 → 重放快照之后的事件 → 进入服务。
   快照与事件流一致性校验（快照内嵌 last_event_id，对不上即告警拒绝启动）。
3. **损坏处理**：任何对象读取/解析失败 = 告警 + 拒绝启动（与地基手册阶段 0
   修复 2 的 fail-fast 口径一致，只是存储后端换了）。
4. **文件体系衔接**：《L4文件系统融合手册》已定义逻辑层（Case 绑定项目 run 目录、
   产物进 `output/`、context_refs 协议路径）。本方案只要求：该手册落地时，
   run 目录的物理承载确认在 MinIO 桶内（与主后端文件系统同桶或同源），
   不要在 Bridge 本地再长一份文件存储。
5. **噪音治理前置**：`worker.inbox_polled` 这类心跳事件**不进 MinIO 事件流**
   （只进 Redis 计数/指标），否则迁移只是把噪音搬了个家（与 Part 3.4 联动）。

### 1.3 编码 Agent 提示词

```text
【任务性质】在现有 Bridge（integrations/agentteams/bridge/）基础上实施持久层
MinIO 化改造。禁止改变审计事件 schema 与 SSE 契约对外字段；先读
case_store.py、audit.py、room_mirror.py 再动手。

【目标】MinIO 为事实源、Redis 为热缓存、本地 JSON 文件废除；Bridge 容器
重建后零状态损失。

【实现内容】
1. 新增 MinIO 存储适配层（bridge 内，沿用主后端 MinIO 连接配置注入方式，
   bucket 建议 agentteams）：
   - 事件 append：agentteams/cases/{case_id}/events/audit.jsonl，
     单对象超阈值（建议 50MB）按天分卷；append 失败 = 操作失败；
   - 快照：agentteams/cases/{case_id}/snapshot.json，
     内嵌 last_event_id；状态迁移或每 200 事件触发一次；
   - 启动恢复：读快照 → 校验 last_event_id 与事件流连续性 → 重放增量；
     任何失败拒绝启动并结构化告警。
2. case_store 改造：_load()/_save() 切换到 MinIO 适配层；Redis 仅作
   热缓存与分布式锁，不作为状态事实源；本地 JSON 代码路径删除
   （保留一次性迁移工具：读既有本地 JSON → 写 MinIO → 校验后归档）。
3. 写入顺序硬约束：MinIO 落盘 → Redis 更新 → SSE 广播；在代码评审
   检查点与测试中固化（构造 MinIO 故障注入，断言操作失败且 Redis
   不出现"幽灵成功"状态）。
4. 心跳/轮询类事件（worker.inbox_polled 等）不进事件流对象，只进
   Redis 指标计数。
5. 健康检查扩展：/healthz 增加 minio 连通性与最近写延迟指标。

【验收（端到端，不接受只跑单测）】
| 操作 | 期望现象 | 不通过时的处理 |
| --- | --- | --- |
| 正常跑一个 Case 后删除 Bridge 容器重建 | 全部 Case 状态与事件流完整恢复，房间历史可重放 | 检查恢复链路哪一步读了本地/Redis |
| 损坏 snapshot.json（改 last_event_id） | Bridge 拒绝启动 + 告警 | 检查校验是否被跳过 |
| MinIO 停服后发消息 | 操作显式失败，审计无半写状态，Redis 无幽灵态 | 检查写入顺序是否被违反 |
| 迁移工具跑既有本地数据 | MinIO 事件数 = 本地事件数，逐 case 对账输出 | 对账不平禁止切换流量 |
| 跑 1 小时 worker 轮询 | MinIO 事件流零 inbox_polled 条目 | 检查心跳过滤位置 |
```

## Part 2. 会话-工单解耦（Case 按需创建）

### 2.1 现状问题（证据）

- 房间无自有存储：每条消息强制挂在 Case 下，Case 事件流是唯一事实源
  （框架调研报告 §二）。
- 每条 `room.user_message` 无条件进入意图三态分类（chat/clarify/execute）
  （`agentteams_room_response_service.py:540` 一带），闲聊也走执行管线——
  "反复追问数据来源"症状（08-20 调研定案）即此耦合的副产品。
- 五步进度条（计划→审批→执行→质控→交付）与 Case 状态机绑定，
  无 Case 概念之外的"纯对话"形态。

### 2.2 设计要点（松绑路线）

**核心：房间是持久的轻量会话实体；Case 是房间内"经用户确认执行"才创建的正式工单对象。**

1. **房间实体化**：新增房间会话元数据表（主库）：room_id、标题、创建人、
   绑定的 case_id（可空）、创建/更新时间。纯聊天阶段的消息仍走 Bridge 事件流
   （复用现有投影与 SSE 链路），但事件挂在 room 维度而非强制 case 维度——
   Bridge 侧支持 `case_id=null` 的房间事件流（或引入 room 级事件命名空间，
   方案细节由编码 Agent 评估两选一并说明理由）。
2. **Case 创建时机后移**：意图分类为 chat/clarify → 只对话，不创建 Case；
   意图为 execute → Manager 先给"立项确认卡"（分析目标、涉及部门、预计流程），
   用户确认后才创建 Case 并绑定当前房间。**确认前的澄清对话不发生在 Case 内**。
3. **五步进度条按 Case 存在性渲染**：无 Case → 显示轻量会话头（房间标题 +
   "尚未立项"引导）；有 Case → 现有五段步骤条。
4. **终态后再发言**：Case closed/delivery_ready 后房间仍可继续对话；
   新的 execute 意图 → 提示"基于上一 Case 的交付继续（关联引用）还是新建工单"。
5. **既有 Case 兼容**：历史"发言即 Case"数据不动；新逻辑只作用于新房间。
6. **四件事的保留**（审查报告核对基准）：审批/质控/契约/审计全部只在
   Case 存在后激活——它们本来就是工单级语义，松绑不影响其完整性。

### 2.3 编码 Agent 提示词

```text
【任务性质】实施协作室"会话-工单解耦"改造。前置：先读
agentteams_room_framework_research_2026-08.md §二/§四、
agentteams_room_response_service.py 的意图分类与 _emit_execution_clarify、
前端 AgentTeamsRoomView.vue 的步骤条渲染条件。
本改造不改审批/质控/审计的任何 Case 内逻辑。

【实现内容】
1. 房间实体化：新增房间元数据表与 CRUD（主库），字段含 room_id/title/
   owner/case_id(nullable)/created_at/updated_at；Bridge 侧支持房间级
   事件流（case_id 可空）——评估"事件挂 room 维度"与"room 命名空间"
   两个实现方案，选一个并写决策理由（事件 schema 对外字段不变）。

   - 意图 chat/clarify → 现有对话链路，不创建 Case；
   - 意图 execute → 不直接建 Case，先生成"立项确认卡"（目标/部门/流程
     摘要 + 确认/修改/取消三选项）；确认后才创建 Case 并回写房间绑定；
   - 立项前的澄清问答全部发生在房间维度。

   - 无 Case 房间：隐藏五步进度条，显示轻量会话头与"描述需求即可开始"

| --- | --- | --- |

| 发"我有6个小鼠样本3vs3要分析" | 先对话澄清 → 立项确认卡；确认后才出现 Case 与进度条 | 检查 Case 创建时机 |
| 立项确认前刷新/重进房间 | 对话历史完整（房间级事件流重放） | 检查房间级事件持久化 |
| Case 交付完成后继续提问 | 可正常对话；新执行需求给"继续/新建"选择 | 检查终态后路由 |
| 打开历史旧 Case 房间 | 只读正常，进度条与事件渲染无回归 | 投影层双维度兼容检查 |
```

  不自有清单）；房间关键词路由的 trigger_hints 继续来自 flows YAML，
  但路由结果必须落在注册表内已登记 agent，未命中走统一 fallback。
