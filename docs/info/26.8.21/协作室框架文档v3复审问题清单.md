## A 类：上线前阻断项

### A1. 新房间链路交付物化不触发（原遗留 #3 上修）

**现象**：房间立项路径创建的 Case 永远不执行交付物化——产物不落入项目目录，
"我的文件"中不可见；而旧 `POST /cases` 直建路径的 Case 交付物化正常。
**位置**：`agentteams_room_service.py` 的 `_create_confirmed_case`
硬编码 `project_id=None`，导致永不进入 `_materialize_case_delivery`。
**严重度**：**阻断**。愿景"Manager 整合交付"在新主链路上断裂；
新旧路径交付行为双重标准（同样一个分析需求，走哪个入口决定用户能不能拿到结果）。
**修复要求**：立项 Case 接入与旧路径一致的物化链路（`project_id` 从房间
立项上下文解析或立项卡中采集）；若新路径有意采用不同物化方案，
须显式设计并写清两路径口径。
**验收（e2e-10）**：房间立项 → 审批 → 执行 → 交付，产物出现在项目目录
`projects/<slug>/runs/` 下且"我的文件"可见；新旧两路径各跑一遍，行为一致。

### A2. 复合游标双流归并分页缺陷（原遗留 #5 上修）

**现象**：房间事件分页接口（`GET /rooms/{id}/events`，复合游标
`ns:<id>|case:<id>` 双流归并）存在两个缺陷：
① 归并后单页最多返回 2×limit 条（未截断）；② 同刻事件的 tie-break 规则
与 audit-chain 使用的 `(recorded_at, event_id)` 口径不一致。
**位置**：`agentteams_room_service.py` 复合游标事件聚合；
`agentteams_audit_chain_service.py` 排序口径。
**严重度**：**阻断**。分页层错误的直接后果是用户侧消息丢失或重复显示；
两种口径并存意味着同一批事件在"房间视图"和"审计链视图"里顺序可能不同。
**修复要求**：归并结果截断到 limit；tie-break 统一为
`(recorded_at, event_id)` 单一口径（两处共用同一比较函数）；
游标推进逻辑覆盖"一页内两流均有同刻事件"的边界。
**验收（e2e-9）**：构造跨流同刻事件 + 分页边界重叠场景，翻页遍历全程
断言不重不漏；同一 Case 的房间视图与 audit-chain 输出顺序一致。

### A3. @直答失败静默无回退（原遗留 #6 上修）

**现象**：用户 @某领域 Agent 直答失败时，后端仅返回 `direct_failed` 状态，
不自动回退 Manager——用户侧表现为**发消息后没有任何回复**。
**位置**：`agentteams_room_response_service.py` direct 分派分支。
**严重度**：**阻断**。违反平台"显式失败"原则（08-19 根因报告定案的
30+ 处静默失败同型病）；用户无法区分"Agent 在想"与"系统坏了"。
**修复要求**：direct 失败/超时（30s 可配）时 Manager 降级接管，
发可见消息（"该部门暂时无法响应，已记录，由我转达或稍后重试"）+
审计事件 `room.agent_timeout`；禁止静默。对齐《AgentTeams部门协作架构
评估与实现计划》Part 2.7 的既定降级路径。
**验收（e2e-11）**：构造目标 Agent 直答失败（注入故障），断言出现
Manager 降级消息 + 审计事件；正常直答路径不回归。

## B 类：口径修正（文档与代码核实）

### B1. confirm_token 脱敏时点未闭环

**现象**：v3 文档称修复为"confirm_token **消费后**全出口脱敏"——但立项卡
在 **pending 期间（用户尚未点击）**是否仍在 SSE 推送 / 分页响应 /
audit-chain 输出中携带明文 token，文档未说明。同时第四节立项卡契约仍写
"`confirm_token`：一次性令牌，仅事件携带"，与脱敏护栏的口径冲突。
**位置**：`agentteams_room_service.py` confirm_proposal / 事件投影出口；
框架文档第四节契约段。
**严重度**：中。若 pending 期明文可见，护栏存在窗口期（owner 校验仍兜底，
非跨用户漏洞，但违背最小暴露原则）。
**修复要求**：核实 pending 期各出口的 token 可见性；正确口径应为
**写入后即全出口脱敏**（token 只在 confirm 请求的一次性校验中使用），
若非如此则补齐；同步改写框架文档第四节契约描述。
**验收**：立项卡 pending / 已消费两状态下，SSE、分页、audit-chain、
Matrix 镜像四出口均无 token 明文。

### B2. persist-then-commit 与快照口径矛盾

**现象**：v3 第十节称遗留 #6 修复为"`_persist` 改**增量写**"，而第五节仍写
"每次状态迁移写一次**全量** `snapshot.json` envelope"——增量与全量的真实
关系未说明，启动恢复（读快照→校验 last_event_id→重放增量）对增量快照的
处理语义不明。
**位置**：`integrations/agentteams/bridge/.../case_store.py` `_persist`；
`minio_store.py` 快照/恢复；框架文档第五节。
**严重度**：中。恢复链路语义若真变了而文档没跟上，下次故障排查会被误导；
且该修复目前只有单测证据。
**修复要求**：明确增量写与 snapshot.json envelope 的真实关系并改写文档；
**恢复语义必须进真实服务演练**（非 mock MinIO 单测）。
**验收（e2e-8）**：真实服务上删除 Bridge 容器重建（含增量快照场景），
断言零状态损失；损坏快照拒启动并告警。

### B3. 立项卡 participants[] 来源未注明

**现象**：立项确认卡契约含 `participants[]`，文档行文让读者以为这是
Manager "组队"决策的结果；08-21 审查已证实现状 = flow YAML 关键词
**机械命中**，Manager LLM 未做任何选专家决策。
**位置**：框架文档第四节契约段；`agentteams_intent_router.py` 路由链路。
**严重度**：低（文档误导，非代码缺陷），但会继续误导后续维护者。
**修复要求**：契约段补注现状口径（participants = 路由规则静态命中，
Manager 真实组队决策属愿景深化项）。
**验收**：文档读者无歧义；愿景深化项在手册阶段 3 已有登记，无需重复排期。

## C 类：新观测项（低成本，随阶段 2 顺带）

### C1. 闲聊数据永久进事实源且无删除通道

**现象**：房间命名空间事件流（含全部纯闲聊内容）与 Case 事件一样完整
MinIO 持久化；同时房间删除/归档端点未实现（原遗留 #8）。两者叠加 =
闲聊数据**不可删除、无限膨胀**，且占用事实源存储与审计链查询带宽。
**位置**：Bridge `_create_room_namespace` 事件流持久化路径；
房间端点清单（无 DELETE /rooms）。
**严重度**：中（随使用量增长）。另涉及数据治理：用户闲聊内容长期留存
应有明确策略。
**修复要求**：短期先加房间事件量监控指标（Prometheus/OTel）；
随后设计房间级 GC/归档策略（如未立项房间 N 天无活动可归档，
归档 = 事件流转冷存 + 房间标只读）。
**验收**：监控面板可见各房间事件量；GC 策略文档化（哪怕只定口径未实施）。

### C2. 两处"无证据的静默行为"

**现象**：① 用户自建 agent 不再进入 chat 路由候选后**静默回落、无告警**
（原遗留 #10）——生产若存在自建 agent，用户会发现"我的 agent 消失了"
而平台无任何记录；② L2→L4 的咨询否决词（veto）命中后**不写遥测/审计**
（原遗留 #4）——"介绍"裸子串过宽有误判面，误判发生时无法被发现与回溯。
**位置**：chat 路由候选组装（注册表快照注入处）；
`agentteams_upgrade_advisor.py` veto 判定分支。
**严重度**：中。两项都违反"可观测"原则，修复成本均极低（各加一条
告警/审计事件）。
**修复要求**：自建 agent 回落时写 warning 日志 + 一次性用户可见提示；
veto 命中写审计事件（含命中词、原始消息摘要、会话 id）；
上线前执行 SQL 盘点生产是否存在自建 agent 并评估影响。
**验收**：构造两场景，分别断言有告警/审计记录可查。
