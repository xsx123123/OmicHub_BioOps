## 2. 部署形态与进程边界

```
甲方(前端) ── 平台 API (src/cygnusx) ── Gateway ── Bridge ── Worker(算力侧)
                  │                        │           │
              平台 DB (PG)              路由/会诊    MinIO 事件流 + 快照
```

- **平台侧**（`src/cygnusx`）：房间/Case 编排、甲方回路状态机、质量门评估、血缘表、自省查询端点。28 个 `agentteams_*` 服务（`src/cygnusx/application/services/`）。
- **Bridge**（`integrations/agentteams/bridge`）：Case 生命周期、审批签名（HMAC）、Worker 调度、质量门 API、MinIO 事件流写入。**不直连平台 DB**，只有两类通道：HTTP（CygnusXClient `/api/v1/*`、GatewayClient `/v1/scientific-interpretation`）+ 自有 MinIO bucket。
- **Worker**（`integrations/agentteams/worker`）：认领 Work Item、执行、上报产物（`artifact_hashes` + `source_refs`）。
- **存储分工**：Case 事件流与快照在 MinIO（`cases/{case_id}/events/audit.jsonl`，超 50MB 按天分卷；`snapshot.json` envelope 内嵌 `last_event_id` 做连续性校验）；平台 DB 存元数据表（`agentteams_rooms`、`agentteams_case_cursors`、`case_artifact_versions`、`case_artifact_dependencies`、`qc_verification_checks` 等）。

## 5. 核心机制现状（含 W0–W4 新增）

### 5.1 完成门（双闸，代码强制）

- **平台侧**：`ConsultationEnvelope.proposed_submission/hard_gate`；`_evaluate_hard_gate`（质量门时走指标门 + qc 结构化判决 merge，只加严不降级）；`_enforce_hard_gate`（BLOCKED 强制改写结论首行）。
- **Bridge 侧**：quality-gate API（`artifact_hashes` 必填登记），`quality_blocked` 阻断交付；Case 关闭需 `approved_submission` + 审批。

### 5.2 产物血缘（F1，W1 新增）

- 表：`case_artifact_versions`（version_no/producing_event_id/checksum_sha256/storage_uri/environment_snapshot）+ `case_artifact_dependencies`（DAG 边）。
- 硬约束：Worker 上报带产物但缺 `source_refs` → 状态迁移前 422 + `room.artifact_rejected` 审计事件。
- 服务：`agentteams_artifact_lineage_service.py`（`case_lineage` 一级展开 / `affected_by` 下游闭包 / `verify_checksum` 重算比对）。
- 交付附加：manifest 注入 `artifact_version_lineage`，`delivery-summary.md` 文末附血缘清单。
- 血缘三问可答：谁产出（事件可追溯）/ 是否篡改（checksum 三处交叉核对）/ 上游变了影响谁（DAG 查询）。

### 5.3 证据化验收（F2，W2 新增）

- qc 输出结构化 JSON：`claims[]`（断言原文/位置/类型）+ `checks[]`（pass/warn/fail/inconclusive + 证据指针 + 理由），权威 schema 在 `application/schemas/qc_verification.py`。
- 判决逐行落 `qc_verification_checks` 表 → qc 质量本身可统计（判决分布 × 返工率交叉验证）。
- 聚合规则：fail>0→BLOCKED（走返工）；inconclusive>0 且 fail=0→MANUAL_REVIEW（甲方/人工裁决）；空 checks→MANUAL_REVIEW 不放行。
- **编造引用专门条款**：声称查了外部库（ClinVar 等）给出数值但无证据指针 → 强制 fail（有单测锁定）。
- rubric 五条（非对称举证/证据位置加权/编造引用例外/核查后才判/不许报清单）写进 `qc.yaml` contract + `qc.md`，解释 why 风格。

### 5.4 自省查询面（F4，W3 新增）

- 端点（仅 `X-Integration-Token` 服务端到服务端，普通用户不可达）：
  - `POST /api/v1/agent-teams/introspection/query`（模板或受限 SQL）
  - `GET /api/v1/agent-teams/introspection/schema`（schema 文档，按需加载）
- 4 个预置模板：本 case 产物及版本 / 事件时间线 / 待办审批 / 血缘一级展开。
- 受限 SQL 最严口径：单表 SELECT、表白名单（3 张 case 维度只读表）、列白名单、`case_id = :case_id` 独立 AND 谓词强制注入、行数硬顶 200。
- denied 词边界匹配（密钥/token/宿主/基础设施类 + CJK 词），命中即拒 + `case.introspection_denied` 审计；放行查询写 `case.introspection_query` 审计，审计写失败 fail-closed。
- 工具挂接：builtin `case_facts_query` 进 `agentteams_case` 工具包，Manager/qc 无需改 YAML 即可发现。

### 5.5 渐进暴露能力目录（F5，W3 新增）

- 载体：`data/ai/agent_ability.yaml`（注意：`mas/agent_capabilities.yaml` 是 MAS 计划校验令牌表，不是目录本体）。
- 两层结构：`summary`（触发分类器：适用+不适用场景，常驻注入）+ `detail`（四段契约全文 + input_examples，会诊/派单确认时才加载）。
- 注入点：路由 catalog（`chat_service.py`）与 handoff 目录（`agent_service.py`）只渲染 summary；会诊分支按选中候选渲染 detail（`capability_detail_context`）。
- 实测（tiktoken cl100k，`scripts/measure_capability_catalog_tokens.py` 可复测）：注入 token **7189 → 4516，降 37%**（router -32%，handoff -44%）。
- 新增能力免改 Manager prompt 自动可发现（有测试锁定）。

### 5.6 组队链路（三件套 D1）

路由圈候选（关键词路由，`agentteams_intent_router.py` / `agentteams_route_decision.py`）→ LLM 组队会诊（`agent_consultation_service.py` / multi-expert consultation）→ 派单。能力注册表提供有序候选 + fallback 链（`agentteams_capability_registry.py`）。

### 5.7 反幻觉行为规范（F3，W0 新增）

12 个协作室角色的 yaml working_style + prompt md 双层注入：
1. 数据/数值/文献结论必须来自工具返回或产物血缘，拿不到就明说并回问甲方（编造会被 qc 判 fail 触发返工）；
2. 声明能力前先查能力目录，不在则按 not_suitable_for/handoff_when 转交，查询失败/未命中显式回问或转交，**禁止静默回落**（落实 C2）；
3. 引用产物必须用 version_id 不用文件名。

### 5.8 Prompt 写作规范与测量文化（F6/F7，W0 新增）

- ~120 条 ALWAYS/NEVER/禁止 式禁令改写为"规则+为什么+例外边界"三段式（对照表：`W0_禁令改写对照表.md`）。
- 57 个魔数配置补证据注释：实测 5.3% / 上游契约 7.0% / 待测 87.7%（清单：`W0_魔数证据注释清单.md`）。

### 5.9 审计总线

- 查询：`agentteams_audit_chain_service.py`（用户态 `get_case_audit_chain` / 运维态 `_ops`）；事件提取 `agentteams_audit_events.py`（`causation_event_id` 因果链）。
- 存储：Bridge → MinIO jsonl + 快照 envelope；取证 CLI `scripts/fetch_case_audit_chain.py`。

## 7. 已知待优化点清单（按价值排序）

### P0 — 影响正确性/可信性

1. **静默回落仍有实证残留**：F9 实测关键词路由对 viz/general/data/mcp-builder 类需求 12/30 样本静默回落 agent-code。F3 已在行为规范层禁止静默回落，但**路由层的代码级回落路径**尚未加"显式回问/转交"硬约束。建议：路由无命中时强制走澄清卡或 LLM 会诊，禁止直达兜底专家。
2. **3 个 alembic 迁移未实跑 upgrade**（本地 DB 不可达，仅离线 DDL 核对）：`v5w6x7y8z9a0`（血缘）、`w6x7y8z9a0b1`（qc 判决）。部署环境 migrate 后需冒烟验证。
3. **qc 结构化判决未跑过真实会诊**：schema 解析失败的真实触发率未知；降级路径只有单测覆盖。建议首批真实 case 上线后统计 `consultation.verification_degraded` 事件频率，若高发说明 prompt 契约与模型输出不匹配，需调 schema 或 prompt。
4. **F9 B 臂（LLM 会诊）真实运行未执行**：stub 数字不代表真实模型质量。有凭证后跑 `--llm-live`（建议 3 reps），用真实 mean±stddev 决定组队策略权重。

### P1 — 工程债

5. **既有测试失败存量**：全量 `tests/unit` 实测 64-65 个失败 + 5 errors（脏工作树既有状态，与本次施工无关，如 studio 工具数 12→13 断言过时、phylo 描述断言过时、evidence_projection 系列等）。建议单独立项清理，否则"新增失败"会被噪声淹没。
6. **`scripts/check_migrations.py` 自身既有失败**：其 AST 解析只认 `revision: str = ...` 注解形式，12 个历史迁移用裸 `revision = ...` 被判无法解析。工具需要修，否则迁移校验形同虚设。
7. **50 项魔数仍标"待测"**（87.7%）。最有价值的三项优先转实测：`worker_heartbeat_ttl_seconds=180`（配合 sweep 30s 测误回收率）、`omic_task_stall_timeout_seconds=900`（E2E-1 曾观测卡死 17min+ 未终止，看门狗正确性存疑）、`planning/execution_timeout=120/600`（用 E2E-1 规划段耗时校准）。
8. **F4 自省查询未做 ASGI 级集成测试**：端点只验证了路由注册 + 服务层单测。建议补起服务的集成测试或 e2e 用例（V6 的活链路验证）。

### P2 — 体验/效率

9. **前端未消费血缘清单与 qc 结构化判决**：`artifact_version_lineage`、`checks[]` 目前只在 manifest/报告文本层；前端时间线可加"血缘"与"qc 判决分布"展示位。
10. **自省查询的 prompt 引导可加强**：工具 description 已按触发分类器写法覆盖，但 Manager/qc 的 working_style 层尚未加"查历史先用 case_facts_query"的显式引导（F4 施工时标注的可选项）。
11. **F5 token 口径仅覆盖目录 JSON 文本**：ROUTER_SYSTEM_PROMPT 模板本身未计入（量级小），若要做完整预算审计可补齐。

### 边界提醒（有意不做）

- **F8 声明式环境（ENVS）**：属 L1 算力编排层，不入协作室；只吸收了 environment_snapshot 进血缘。L1 若做环境管理需单独立项。
- **F9 在线自扩展**：与"能力治理权在甲方/显式审批"冲突，永久不做；只保留离线 eval 闭环。
