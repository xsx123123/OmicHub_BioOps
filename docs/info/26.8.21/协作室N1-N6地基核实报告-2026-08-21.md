- D2（变更编排）：缺 token 确认、冻结快照、超时作废、branch hash 校验——编排层的强一致语义尚未实现。

  - 血缘缺口：`case_artifact_versions.version_no` 有 DB UNIQUE 约束兜底，但分配是 read-then-insert 竞态，冲突被 `except` 吞掉后无重试无告警——高并发下同工件版本号可能跳号或丢记录。

## N3 422 拒绝是否毒丸

**结论：不是毒丸，但确定性错误会白等整个租约周期。**

- 链路：worker 422 拒绝 → 租约超时（默认 300s）→ sweep 回收 → attempt 耗尽 → `timeout` 终态 + 级联 skip。任务最终能收敛，不会无限循环。
- 代价：确定性错误（如参数校验失败）也要走完 300s×3 的租约周期才判死，响应延迟被人为拉长。
- 缺口：缺端到端毒丸回归测试（模拟 worker 持续 422，断言最终 timeout 终态且次数有界）。

## N4 自省端点安全边界

**结论：API 面在"Bridge 可信"模型下属设计内，但令牌泄露面过宽；SQL 面已收窄。**

- API 面：自省端点仅有静态 integration token 校验，无 owner 级权限校验。对"Bridge 完全可信"的部署模型是可接受设计；一旦令牌泄露，任意人可读全量房间/Case 内省数据。
- SQL 面：收窄语法已实现且安全，43 条单测通过；缺 UNION、表别名两类显式用例（建议补，防回归）。
- 工具面：`room_state_query` 已锁 `room.owner`（scope 锁当前房间，不接受任意 room_id 入参）。

## N5 取证链可拼接性

**结论：取证链未拼接，08-19 那次取证实际是失败的。**

- MinIO 事件流（经 Bridge API 的 `fetch_case_audit_chain.py` / `export_agentteams_evidence.py`）与 PG 侧的判决/血缘表（`case_artifact_versions`、`qc_verification_checks`）之间没有单一工具能把两边按 case_id 合并成一条完整链。
- 后果：2026-08-19 的 agentteams-case-forensics 取证只拿到了事件流半边，判决与血缘证据缺失，结论不可靠。
- 建议（批 3 候选）：写一个合并导出工具，case_id 进、MinIO 事件 + PG 判决 + 血缘版本出。

## N6 confirm-proposal 并发安全

**结论：正常路径幂等有保障；真实窗口在远端 Bridge 建单成功后本地回滚的重试场景。**

- 已有保障：原子 UPDATE 占位 + 落败方回放现有 proposal + 单事务提交，同房间并发确认不会产生两张立项卡。
- 真实风险窗口：远端 Bridge 已建 Case 但本地事务回滚后，用户重试会在 Bridge 侧建第二个 Case（两边 case_id 分叉）。
