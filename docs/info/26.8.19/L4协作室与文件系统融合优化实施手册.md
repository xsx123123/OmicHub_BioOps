# L4 协作室 × 文件系统融合优化实施手册

> 版本：v1（2026-08-19）
> 依据：《CygnusX 用户文件与分析项目目录协议 v1.2》（下称"文件协议"）、
> 《多智能体协作室根因调查报告_2026-08-19》、《协作室平台异常排查与Codex审查计划》Part 9。
> 本文档给编码 Agent（Codex / Kimi Code）施工用：三项改造一份提示词，
> 验收标准写死，人工验收权在平台方。

## 一、目标与背景

**目标**：让 L4（团队协作室/MAS）接入统一文件系统，实现三件事——

1. **Case 绑定项目**：协作室 Case 创建时关联 `project_name`，不再是游离房间；
2. **MAS 交付入口**：专家产物按文件协议落入 `<run>/output/` 并登记目录表，
   协作室产出出现在"我的文件"（文件协议 §5 明确指出 MAS 当前无此入口）；
3. **context_refs 协议化**：上下文引用统一为 `projects/...` 相对路径，
   废弃裸 `file://{uuid}`——同时根治"产物不可见"与 file:// 断链两个病。

**背景证据**（编码 Agent 施工前必读）：

- 文件协议核心条款：统一路径工厂 `StoragePathFactory.create_project_run_dir()`；
  标准四层子目录 `input/output/work/logs`；目录表登记 `ensure_directory_chain()`；
  禁止直拼用户可见路径；禁止 UUID 出现在用户可见目录名。
- file:// 断链根因：`production_runner.py:186-209` 对 UUID 型 context ref 生成
  `file://{uuid}`；Worker 侧 `workspace_file_preview`
  （`agentteams_data_tool_service.py:57-69` + `pipeline_result_service.py:345-363`）
  只接受 workspace 相对路径，URI 被当普通路径解析失败，且错误文案统一为
  "文件不存在"掩盖真实原因。

## 二、前置依赖与施工顺序

- **依赖**：地基优化手册阶段 0 修复 1（context_refs 可读性预检）应先完成或并行——
  本手册的改造 3 会改变预检的判定依据（按协议路径），两边要对齐，避免双重标准。
- **顺序**：改造 1（Case 绑定项目）先行，改造 2、3 依赖它提供的项目上下文。

## 改造 1：Case 绑定项目

背景：协作室 Case 当前是游离房间，与用户项目目录无关联；文件协议规定
项目名称是分析任务的必填配置。

要求：
1. Case 创建（POST /api/v1/agent-teams/cases 及房间首条消息触发链）支持关联
   项目：project_name 字段（新 Case 必填或从既有项目选择，交互方案先出设计稿
   经确认后实现）；Case 记录持久化 project 关联（slug + run 路径）。
2. 一个 Case 对应一个 run 目录：create_project_run_dir(user_id, project_name,
   analysis_name="agentteams-case")，并 ensure_directory_chain() 登记；
   Case 的 context、产物、日志的根路径即该 run 目录。
3. 历史 Case 兼容：无项目关联的旧 Case 只读可用，不强制迁移。

验收：新建 Case 后，"我的文件"文件树出现对应 projects/<slug>/runs/
agentteams-case-<时间戳>/ 目录（含 input/output/work/logs 四个子目录）；
数据库目录表有对应记录。

## 改造 2：MAS 交付入口（agent-delivery 落地）

背景：文件协议 §5 明确 MAS 尚无面向"我的文件"的交付入口；Studio 报告交付
是已接入的参照实现（产物复制到 <run>/output/ 并登记目录表）。

要求：
1. Worker/专家产物统一写入 Case 绑定的 run 目录：中间文件进 work/、
   可交付结果进 output/、运行日志进 logs/；交付输入快照进 input/。
2. agent-delivery 完成交付汇总时：产物清单（artifact 引用）解析为 run 目录内
   实际文件，output/ 内容经 ensure_directory_chain() 全量登记，
   交付报告本身也写入 output/。
3. 下载/预览接口按 Case 记录的 run 路径读取，不假定任何历史 UUID 目录结构。

验收：一个跑通的 Case 交付后，"我的文件"中该 run 的 output/ 可见全部交付
产物与交付报告，可预览可下载；目录表记录完整。

## 改造 3：context_refs 协议化（废弃裸 file://{uuid}）

背景：production_runner.py:186-209 对 UUID 型 context ref 生成 file://{uuid}；
workspace_file_preview（agentteams_data_tool_service.py:57-69 +
pipeline_result_service.py:345-363）只接受 workspace 相对路径，导致解析失败
且错误文案掩盖原因（R1-4 目标漂移事故根因）。

要求：
1. 统一寻址：context_refs 中的文件引用一律使用相对用户工作区根目录的协议路径
   （projects/... 或 inbox/...）；生成侧（production_runner.py:186-209 及所有
   产生 context ref 的位置）不再生成裸 file://{uuid}。
2. 解析侧：workspace_file_preview 及同类工具显式支持协议路径；收到 file://
   形式时给出明确错误（"不支持的引用协议，应为工作区相对路径"），不得按普通
   相对路径静默失败；错误文案区分：路径不存在 / 是目录 / 协议不支持 /
   未登记的逻辑引用。
3. UUID → 路径映射：既有 UUID 型引用（数据库/审计中已存在的）提供一次性
   解析兼容层：能映射到实际路径的映射，不能映射的标记为不可读并交给
   context_refs 可读性预检阻断回问（与地基手册阶段 0 修复 1 的判定口径对齐，
   两处共用同一套"可读性判定"函数，禁止双重标准）。
4. 用户可见性：前端 @ 引用工作区文件时，生成与展示均使用协议路径与项目名，
   不出现 UUID。

验收：构造三种引用（协议路径 / 裸 file://{uuid} 可映射 / 不可映射），行为分别
为：正常预览 / 映射后正常预览或明确兼容提示 / 预检阻断并回问用户；
全链路不再出现目标漂移。

## 通用要求

- 每项改造附：改动文件清单、要点说明、迁移/兼容说明、测试（含至少一项
  端到端验证：Case 创建 → 执行 → 交付 → 我的文件可见）
- 涉及数据库变更的提供迁移脚本与回滚方案
- 完成后输出：三项验收的手动复现步骤
