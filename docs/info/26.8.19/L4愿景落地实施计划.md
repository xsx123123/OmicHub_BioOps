## 1. 总体判断

**这个愿景不需要另起炉灶。** 协作室骨架真实且完整：房间 API、Bridge、Worker 租约、
proposed_submission 完成门、澄清卡、人工审批、进度时间线均已实现。愿景文档 §8.2 的判定
成立——"能，且它是 L4 的正解"。

要做的是把它从"架构上的 L4"变成"事实上的 L4"，即补齐愿景定义的四个必要条件：

| # | 条件 | 核查结论 |
|---|---|---|
| 1 | 地基修完：失败显式化、状态可信、文件契约贯通 | **大部分已修但未提交**。手册阶段 0/2 的修复已在工作树落地；阶段 1（部署侧）未动；阶段 3 e2e 刚起步；总验收未跑 |
| 2 | L2→L4 升级规则定义 | **零代码**。仅文档。近似物只有 unified_intent_router 的 case intent（LLM 自由判定，非规则） |
| 3 | 双注册表/双路由统一 | **确认存在，未收敛**。房间关键词路由与 chat LLM 路由两条体系并存，能力目录不驱动房间路由 |
| 4 | 可观测性：审计总线 + 部署版本可考 | **无统一审计总线**。四条独立通道；/healthz 版本信息已在工作树补齐 |

**结论：当前为"L4 候选/演示态"。四条件满足后才是产品定义里的 L4。**

### 2.2 条件 3：双注册表问题（确认存在）

两条并存的路由体系，**未收敛**：

1. **房间关键词路由**（协作室内）：`agentteams_intent_router.py` 纯子串匹配
   （`hint in normalized` :160）；hint 三层来源：
   - `data/ai/flows/*.yaml` 的 `flow.trigger_hints`
   - `data/ai/domains/*.yaml` 别名
   - 硬编码 `_LEGACY_EXTRA_HINT_ALIASES`（:35-40）
2. **chat LLM 路由**（普通聊天）：`data/ai/prompts/router.md` system prompt +
   `unified_intent_router.py` 归一化（`chat_service.py:5580-5621`，开关
   `unified_intent_router_enabled`）；`agent_ability.yaml` 四段契约
   （capabilities / not_suitable_for / handoff_when / preferred_inputs）**只在这条链路**
   被消费（`agent_service.py:1047-1077` 注入 router prompt）。

即：能力目录（agent_ability.yaml）≠ 房间路由源（flows trigger_hints）。
改一处不生效另一处，display ≠ actual 的风险长期存在。

### 2.3 条件 4：审计通道现状（四条独立通道，无总线）

1. Bridge 持久审计：append-only JSONL（`gateway/cygnusx_agent_gateway/audit.py`）——
   生产被 ~650 万条 `worker.inbox_polled` 噪音淹没；
2. Case 事件流：Bridge case_store 内嵌，经 `GET /v1/cases/{id}/events` + SSE 暴露——
   事件类型已较全（room.* / work_item.* / consultation.parse_failed 等）；
3. 平台 HTTP 审计中间件 → `audit_logs` 表——与 Case 事件不连通；
4. 降级遥测：`collaboration_observability_service.py` +
   `agentteams_consultation_telemetry_service.py`——**无管理端面板**。

/healthz 版本可观测（build_sha/build_time）已在工作树补齐（bridge `app.py:214-222`）。

## 3. 实施路线（按依赖排序，每阶段独立可验收）

### Phase A：收尾地基（条件 1）——最优先，基本是"已做完没收口"

1. **提交工作树**：阶段 0/2 修复（断点 A、case_store fail-fast、U-1 三环、错误结构化
   透传、假登出、/healthz 版本）全部已改未提交。先提交、部署。
2. **阶段 1 部署侧两项**：恢复 Matrix Gateway（room provisioning 是新建 Case 硬阻塞）；
   修复 RocketMQ worker 崩溃循环。纯运维，代码已就绪。
3. **补齐 e2e 套件**：按手册补 E2E-2~6（limit 契约 / 16S route_unavailable /
   planning_failed / 删除对账 / 消息气泡），进 CI 默认跑。
4. **跑手册总验收 4 条**（含"任意故障 5 分钟定位到层"）。

**验收**：手册 checklist 全勾；e2e 套件 CI 默认跑绿；工作树无未提交修复。

### Phase B：失败显式化补环（愿景链路的两个 ❌）

1. **planning_failed 事件**：`agentteams_service.py:846-849` plan-01 创建失败 → 写 Case
   事件 + 前端可见提示，Case 不得静默停 received。
2. **route_unavailable 事件**：`agentteams_intent_router.py` 返回 None 时 → 写事件 +
   Manager 回问甲方（"该领域暂无专家，是否按通用流程处理？"），替代静默断链。
3. **甲方验收状态位**：Case 增加 `delivery_accepted / rework_requested` 终态（复用现有
   approve/reject 端点模式），交付后显式等甲方确认。
4. **租约盲区收尾**：claim 即起续租，或前置校验移到 claim 之前。

**验收**：E2E-3（16S）、E2E-4（注入 Bridge 故障）转绿；对抗场景失败全部显式可见。

### Phase C：双注册表统一（条件 3）——核心架构工作，需设计评审

目标：**`data/ai/agent_ability.yaml` 四段契约成为唯一权威源，房间路由从中派生。**

1. 给能力目录条目补 `trigger_hints` 字段（现散在 flows/*.yaml + domains/*.yaml +
   硬编码 `_LEGACY_EXTRA_HINT_ALIASES` 三处，收编进目录）。
2. `agentteams_intent_router` 改为从 `AgentAbilityCatalog` 读 hint；先**双跑对账**
   （关键词路由结果 vs 目录派生结果打日志比对），一致后切流量。
3. `flows/*.yaml` 保留执行定义（workflow/steps），路由元数据退役。
4. 灰度：先影子模式，再按 Case 百分比切换，保留回退开关。

**验收**：同一输入在房间与 chat 两链路得到同一 Agent；改一处目录两链路同时生效；
对账日志零分歧持续一周。

### Phase D：L2→L4 升级规则（条件 2）——决定商业可持续性的成本闸门

将 `unified_intent_router` 的 case intent 从"LLM 自由判定"改为**规则优先、LLM 兜底**：

1. 用户显式要求（"开协作室 / 正式交付"）→ 必升。
2. 规则判定：路由命中 Flow 步骤数 ≥3，或命中能力目录新增的 `requires_formal_delivery`
   标记 → 建议升级，出确认卡（复用现有 Case 确认卡）。
3. 其余留在 L2；16S 这类无专家请求在 L2 即被 route_unavailable 逻辑接住。
4. **加遥测**：统计 L4 进入率与单 Case token 消耗——愿景文档警告：L4 若成默认入口，
   token 成本失控。

**验收**：轻量咨询不进协作室；升级判定可审计（每次决策记录触发条件）；L4 进入率有面板。

### Phase E：统一审计总线 + 可观测（条件 4）

做**汇聚层**而非替换架构：

1. 以 Bridge Case 事件流为主干，平台侧 audit_logs、降级遥测、consultation telemetry
   统一打 `case_id / correlation_id` 汇聚查询。
2. 治理 Bridge JSONL 噪音：`worker.inbox_polled` 降采样或移出审计流。
3. 管理端只读面板：按 Case 查全事件链 + 按时间查故障。

**验收**：手册总验收第 3 条——任意构造故障 5 分钟内通过事件流/日志定位到层。

### Phase F：愿景完整形态（远期，与 C/D/E 可并行）

- 独立 Manager LLM Agent（接单/派单/验收/交付/例外处理五项职责归于一个真实 Agent）。
- provenance 三层标注：agent-delivery 输出 schema 加 provenance 字段，交付报告每条结论
  强制标"本平台计算 / 文献证据 / 综合推断"。
- `@` 提及定向投递、变更冻结状态机、部门并行——按
  《agentteams_department_collaboration_architecture_2026-08.md》Phase 1-3 推进，
  排在四条件之后。

## 4. 顺序与工作量建议

**A → B → C → D → E，不要颠倒。**

- A/B 是收口性质，一周级工作量，大部分是"已做完未提交 + 补两个事件 + 跑验收"；
- C 是唯一需要设计评审的架构改动（双注册表统一），有回退方案先行；
- D 代码量最小但最容易被跳过——它是四个条件里决定商业可持续性的一个；
- E 可与 C/D 部分并行；
- F 在四条件全部满足、协作室成为"事实上的 L4"之后再排期。

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 工作树修复提交时与 HEAD 冲突或引入回归 | 提交前跑手册阶段 0/2 验收 checklist + 新增 e2e 用例先红后绿 |
| 路由统一切换导致既有 Case 路由漂移 | 双跑对账 + 灰度 + 回退开关；flow_id 下划线规范不动 |
| 升级规则误判把轻量任务拦进 L4 | 规则只出"建议升级"确认卡，不强制；遥测监控进入率 |
| 审计汇聚成新的大而全工程 | 只做查询汇聚层，不替换现有四通道的写入路径 |
