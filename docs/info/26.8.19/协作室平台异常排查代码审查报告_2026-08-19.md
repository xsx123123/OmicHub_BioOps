# 协作室平台异常排查报告（只读定位）

日期：2026-08-19
范围：Phase 0 后 AgentTeams 协作室中 ATAC-seq、16S 请求异常
基线：`aad9d66` 之后至当前 `HEAD=4680155`
约束：本次只读排查，未修改任何业务代码。

## 1. 执行摘要

### 1.1 可以确认的事实

1. 当前代码中的关键词路由可正常识别 scRNA 和 ATAC：
   - `我有单细胞/Cell Ranger关键词的请求` → `scrna_seq` / `agent-scrna`。
   - `我有 ATAC-seq 数据，想做差异 peak 分析` → `atac_seq` / `agent-atacseq`。
   - `分析 16S 微生物组测序数据` → 无候选路由，返回 `None`。
2. 本地没有事故时段（15:21–15:24）的服务端日志、Bridge Case 快照、Bridge 审计文件或数据库快照，因而不能把事故的具体异常栈、HTTP 响应体、Case ID、事件数量写成已证实事实。
3. 当前实现存在明确的“触发失败只记录 warning、不向上抛错”路径：规划工作项创建或 Case 状态更新失败时，`start_chat_planning()` 会吞掉异常并返回；上层随后仍记录 `planning started`。这足以解释“Case 创建成功、仍停在已接收、时间线没有路由/派单”的表现，但由于缺少事故原始日志，结论等级为“高度怀疑”，不是运行时确证。
4. “Agent 协作中心暂时不可用”由 Bridge 请求异常统一转换而来，当前代码不会保留响应体；只保留状态码日志，且前端直接展示 API 的 `detail`。因此现有静态证据无法确定当时具体失败接口和响应体。

### 1.2 根因结论（三层）

**异常抛在哪：** 事故最可能抛在“执行意图 → `start_chat_planning()` → Bridge 创建 `plan-01` 或更新 Case 状态”的上游交接处，而不是 Bridge worker 的心跳/续租阶段。16S 还存在更早的确定性缺陷：当前 Flow 注册表没有 16S/微生物组 Flow，`infer_intent_route()` 返回 `None`。对 ATAC，路由本身并未复现失败，仍需事故日志确认是 Bridge 请求失败、审计写入失败，还是 Celery 调度失败。

**为什么 scrna 路径幸免：** scRNA 同时命中 `单细胞` 和 `cellranger` 两个已注册 hint，得到明确的 `scrna_seq` / `agent-scrna` 路由；该路径不依赖通用兜底。ATAC 也能命中一个 hint，但 16S 当前完全没有候选。注意：这解释了 scrna 与 16S 的差异，不能单独证明 ATAC 事故的具体异常点。

**为什么前端只显示空白而不是报错：** 业务层把 Bridge/规划触发失败设计为 best effort：`start_chat_planning()` 捕获所有异常后只写 warning；房间响应层也捕获触发异常并返回 `none`，继续完成普通 Manager 回复流程。前端又采用 optimistic 用户消息与事件流/轮询投影；当后端没有产生 `room.route_decision`、`plan-01` 或其他事件时，事件数组保持为空，UI 只能渲染“暂未产生协作事件”。只有后续的列表、详情或 SSE Bridge 请求本身失败时，才会出现“Agent 协作中心暂时不可用”。

### 2.2 规划触发链与静默失败

`src/omichub/application/services/agentteams_room_response_service.py:577-607` 的 execute 路径先调用 `infer_intent_route()`，异常时仅记录：

```text
AgentTeams route resolution failed: {}
```

随后仍调用 `start_chat_planning()`；若无路由则把目标回退到 `DEFAULT_LEAD_PLANNER`。

`src/omichub/application/services/agentteams_service.py:775-845` 的 `start_chat_planning()` 负责：

1. 预检 `context_refs`；
2. 推导 target；
3. `POST /v1/cases/{case_id}/work-items` 创建 `plan-01`；
4. `POST /v1/cases/{case_id}/state` 更新为 `planning_running`。

该函数在 `src/omichub/application/services/agentteams_service.py:844-849` 捕获创建工作项或状态更新异常，只写：

```text
AgentTeams chat planning start failed: {}
```

然后正常返回。上层在 `src/omichub/application/services/agentteams_room_response_service.py:600-616` 又把该调用视为成功路径，并记录：

```text
AgentTeams chat execution intent detected, planning started
```

这构成当前最重要的状态一致性缺陷：日志“planning started”不等价于 Bridge 已创建 `plan-01` 或已进入 `planning_running`。

### 2.3 前端文案与失败接口

- 日志只输出 method、path、status 或异常类名，不输出响应体：`src/omichub/application/services/agentteams_service.py:1386-1403`。

前端通过 `frontend/src/views/AgentTeamsRoomView.vue:877-918` 发起 SSE：

而普通 API 失败在 `frontend/src/views/AgentTeamsRoomView.vue:576-585、614-726` 读取 `cause.response.data.detail` 并展示。由此可确认文案的产生机制，但不能从当前本地材料确认 15:23 当时究竟是：

## 3. 基线回归审查（`aad9d66..4680155`）

### 3.1 已确认的风险点

- `agentteams_room_response_service.py:586-588`：路由解析异常被转成 `route=None`，后续使用通用 planner；没有为 fallback 写一条结构化失败事件。
- `agentteams_room_response_service.py:966-968`：`room.route_decision` 审计写入失败只记录 warning 并返回；因此路由卡可能完全不可见。
- `agentteams_service.py:844-849`：`plan-01` 创建/状态推进失败只记录 warning，不改变 Case 状态、不写失败事件、不向 API 返回失败。
- `agentteams_service.py:441-450、475-479`：能力检查失败降级为“不可用”结果，但能力审计写入也属于 best effort，可能再次丢失真实原因。
- `agentteams_service.py:1386-1403`：Bridge 错误被统一映射为友好文案，响应体没有进入日志或审计，阻碍事后定位。

### 3.2 未发现可据此直接定案的证据

静态 diff 能证明上述异常处理存在，不能证明它们在 15:21–15:24 被执行。尤其是：

- ATAC 的 `infer_intent_route()` 当前可成功返回；
- fallback `agent-code`/`agent-general` 的具体调用结果没有事故日志；
- Bridge worker 心跳/续租代码不是本次事件的直接证据，因为连 `plan-01` 是否创建都没有运行时记录。

## 4. 修复方案（确认后再改）

### P0：让“规划失败”成为可见、可查询的状态

1. `start_chat_planning()` 不要把 Bridge 创建工作项和状态推进的异常静默吞掉。
2. 在同一个 Case 上写入结构化 `room.planning_failed` 或 `case.handoff_failed` 事件，至少包含：`stage`、HTTP method/path、status code、响应体截断、异常类型、trace/request ID、route input、resolved target。
3. 只有确认 `POST work-items` 和 `POST state` 都成功后，才记录 `planning started`；否则返回明确的失败结果并把 Case 标记为 `execution_failed` 或专用的 `planning_failed`。
4. 保留用户消息，但在时间线展示“已收到请求，规划启动失败，可重试”，不能渲染成空白。

### P0：修复 16S 路由能力缺失

1. 明确是否支持 16S/微生物组；若支持，新增正式 Flow、planner、Bridge workflow、能力注册和 trigger hints，至少覆盖 `16S、微生物组、扩增子、OTU、ASV、QIIME2、DADA2`。
2. 若暂不支持，不要静默走通用规划；产生可见 `route_unavailable` 事件，说明“当前没有 16S 专项 Worker”，并允许用户选择通用分析或稍后重试。

### P1：路由审计必须是可靠性边界

`room.route_decision` 是观察事件可以 best effort，但不得让审计失败导致“无卡片、无错误、无状态变化”。至少要：

- 记录本地结构化日志和 request/trace ID；
- 将审计失败计入 response result；
- 在 API/前端显示“路由卡写入失败”，而不是时间线空白；
- 对展示路由与实际派发目标不一致设置可查询的 WARN。

### P1：Bridge 错误保留原始证据

在 `_request_as()` 和 SSE 代理中保存安全截断后的：status、response body、Bridge URL path、request ID、trace ID。前端继续只显示友好文案，但运维端能查询原始响应。

## 5. 回归测试建议

必须新增并运行以下 fallback 端到端用例：

### E2E-1：未命中专项 Flow 的 fallback 执行

输入：`分析 16S 微生物组测序数据`，无文件引用。
断言：

1. Case 创建成功且保留 `room.user_message`；
2. 路由结果明确为 `route_unavailable` 或通用 fallback，包含 `fallback_reason`；
3. `plan-01` 创建成功时，Case 进入 `planning_running`，事件包含目标 planner；
4. `plan-01` 创建失败时，Case 不得保持静默的 `received`，必须有 `planning_failed` 事件和前端可见错误；
5. API 响应必须区分“消息已落库”和“Manager 调度失败”。

### E2E-2：ATAC fallback/专项路由完整链路

输入：`我有 ATAC-seq 数据，想做差异 peak 分析`。
断言：

1. `room.user_message`、`room.route_decision` 顺序可查询；
2. 路由为 `atac_seq` / `agent-atacseq`；
3. `plan-01` 的 target 与 route decision 的实际目标一致；
4. Bridge 返回非 2xx 时，保存 status、响应体摘要和 trace/request ID；
5. 不得出现日志“planning started”但无 `plan-01` 的假成功。

### E2E-3：scRNA 对照回归

输入：含 `单细胞`、`Cell Ranger` 的请求。
断言：路由为 `scrna_seq` / `agent-scrna`，能产生路由卡、规划工作项、派单和 worker 可见事件。

### E2E-4：审计写入失败不吞主链路

注入：让 `post_case_evidence()` 在 `room.route_decision` 写入时抛异常。
断言：主链路结果必须显式标记审计失败；Case 仍不能被伪装成“规划已启动”；前端应有可见降级提示。

### E2E-5：Bridge 不可用与 SSE 失败

注入：Bridge `/healthz`、Case detail、events stream 分别返回超时、502、503。
断言：前端显示统一友好文案；后台日志保留真实 path/status/body；已落库的用户消息不丢失，时间线显示数据源不可用而不是空白。

## 6. 当前结论边界

本报告没有修改代码，也没有把缺失的日志、接口响应、DB 记录或 Bridge 状态补写成事实。当前最强结论是：

> 16S 存在可复现的“无专项路由”问题；ATAC 路由本身可复现成功。对于两起线上/现场 Case，最符合现有代码的故障机制是规划交接或审计/Bridge 请求失败后被 best-effort 异常处理吞掉，导致 Case 停留在 `received`、事件流为空；但在取得事故时段 stderr、Bridge 审计/Case 快照和接口响应前，不能把该机制升级为已证实根因。

要完成运行时定案，必须从可访问 Bridge/数据库环境重新采集：Case 列表/详情、完整事件流、`plan-01` 工作项、15:21–15:24 API access/error log、Bridge/Gateway/worker health 与请求日志，然后逐项替换本报告中的“未证实”标记。
