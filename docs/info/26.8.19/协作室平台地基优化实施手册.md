# 协作室平台地基优化实施手册

> 版本：v1（2026-08-19）
> 依据：《多智能体协作室根因调查报告_2026-08-19》（生产日志定案）+
> 《协作室平台异常排查与Codex审查计划》Part 5.6 优化清单。
> 本文档是可执行手册：四个阶段各含一份完整提示词，可直接贴给编码 Agent
> （Kimi Code / Codex）执行。主文档（审查计划）仍是总账，本文档专注施工。

## 使用原则（每个阶段通用）

1. **先止血后治病**：阶段 0 三条是低成本高收益，先行；阶段 1 基础设施不修，
   代码修得再好协作室也是残的。
2. **验收与实现分离**：编码 Agent 负责实现，验收按本文档的验收条款由人来核——
   不接受"我自己测过了"。
3. **单测过了 ≠ 系统能跑**：本次第二轮故障（断点 A）就是只过单测造成的回归。
   每个阶段必须带端到端验证；阶段 3 专门建 e2e 套件兜底。
4. **最小改动**：禁止重构、禁止改动无关模块、禁止变更事件契约对外字段。
5. 每个阶段独立可交付：前一阶段验收通过再开下一阶段。

## 阶段 0：立即止血（3 条，均为小改动）

```text
你是一名资深后端/前端工程师，对协作室平台实施三项紧急止血修复。根因已由生产日志
定案（2026-08-19 根因调查报告），本次为最小改动：禁止重构、禁止改动无关模块、
禁止变更事件契约对外字段。每项修复必须附带可运行的验证。

## 修复 1：断点 A——去重预检 limit 契约错位（最高优先级）

根因：post_room_message 的 client_message_id 去重预检调用
get_case_events(limit=200)（src/cygnusx/application/services/agentteams_service.py:1102-1103），
Bridge events 端点硬限制 1<=limit<=100（integrations/agentteams/bridge/
cygnusx_agentteams_bridge/app.py:519-520），超限返回 422，被 _request_as 抹平为
BusinessError 400"暂时不可用"（agentteams_service.py:1386-1395），异常抛在
room.user_message 落库（:1135）之前 → 消息不落库、celery 不投递、Case 零事件。
同型 bug：get_room_response_timing_summary 使用 limit=1000（:963-975）。

要求：
1. 统一修复平台侧所有超出 Bridge limit 上限的调用：全仓搜 get_case_events 及
   events 查询的 limit 实参，逐个人工核对（至少上述两处）
2. 平台侧调用前做参数钳制（clamp 到 100），不依赖远端报错；确需更大窗口时用
   分页游标（before/event_id）拉取
3. 新增平台-Bridge 参数契约测试：对 events 端点 limit 上下限做契约断言，
   进 CI 默认跑

验收：带 client_message_id 的发言在真实 Bridge 上 201 落库且时间线可见；
契约测试在 limit=200 场景下先红后绿。

## 修复 2：断点 F——case_store 静默丢全部 Case

根因：bridge case_store._load()（integrations/agentteams/bridge/
cygnusx_agentteams_bridge/case_store.py:149-152）对 OSError/JSON 损坏静默返回 {}，
Bridge 重启后全部 Case 无声消失（08-19 当日已实际发生）。

要求：
1. 状态文件读取/解析失败时 logger.exception 并拒绝启动（fail fast），
   禁止带空状态运行
2. 单条 Case 校验失败（:159-162）记 warning 并将跳过计数暴露到健康检查
3. 启动自检：状态文件可读且解析成功才判定 Bridge 健康

验收：构造损坏的状态文件，Bridge 拒绝启动并产生明确告警；
正常文件启动与既有行为不受影响。

## 修复 3：R2-5 显示层——假登出

根因：DefaultLayout 的 currentUser 只在 onMounted 由 authStore.fetchUser()
赋值一次且无 catch（frontend/src/layouts/DefaultLayout.vue:184-201）；fetchUser
失败 → currentUser 永久 null → displayName 回落"未登录"（:763/:849）；
localStorage 未动，刷新后 onMounted 重跑恢复。

要求：
1. fetchUser 增加 catch 与有限重试（指数退避，如 3 次）；失败时保留已有用户
   信息，不置 null
2. "未登录"与"用户信息加载失败"分文案；加载失败给重试入口
3. 回归测试：/auth/me 短暂 5xx 时不显示未登录、不清 localStorage

验收：模拟 /auth/me 500，账号区显示"加载失败（重试）"而非"未登录"；
刷新前后登录态一致。

## 通用要求

- 先读上述文件再动手，遵循现有代码风格
- 每项修复附：改动文件清单、要点说明、验证方式（测试命令或复现步骤）
- 提交前跑通相关测试与 lint
```

## 阶段 1：基础设施（不修这些，代码修好也是残的）

```text
你是一名资深 SRE/后端工程师，处理协作室平台的三项基础设施问题（2026-08-19 根因
调查报告定案）。先诊断后修复，改动最小化，每项修复需提供验证证据。

## 问题 1：Matrix Gateway 全天不可用

证据：生产 Matrix Gateway 全天无业务流量（仅 /healthz）；agentteams_bridge_settings
表 0 行；每个 Case 创建都 room provisioning failed（生产日志：
"room provisioning failed: Matrix Gateway 暂时不可用"）。

要求：
1. 诊断 Gateway 不可用的根因（配置缺失 / 网络 / 服务状态），输出诊断结论
2. 恢复 Case room provisioning 链路
3. 上线 provisioning 成功率监控与失败告警

验收：新建 Case 的 provisioning 成功；监控面板可见成功率，失败触发告警。

## 问题 2：RocketMQ worker 崩溃循环

证据：cygnusx-rocketmq-worker 容器处于 Restarting 崩溃循环。

要求：
1. 捞崩溃栈定位根因并修复
2. 若无法立即修复：给出不影响主链路的降级方案 + 崩溃告警，明确标注哪些功能
   依赖该 worker（评估影响面）

验收：worker 稳定运行；或降级方案生效且有告警，影响面文档化。

## 问题 3：DELETE 超时不匹配 + 部署版本不可观测

证据：web→bridge DELETE 客户端超时远小于 bridge 实际删除耗时（bridge 删除需先
cancel 再删记录，bridge service.py:3046-3076）→ web 报"删除失败"但 bridge 实际
200 删成（生产双侧日志证实）；事故时部署的代码版本不可考（疑似中间态工作树
直接部署）。

要求：
1. 对齐删除链路的超时配置，或将删除改为异步（先受理、后端完成后对账）
2. 前端删除超时按"结果未知"处理：主动重拉列表对账，不直接报失败
3. /healthz 输出 git SHA 与构建时间；所有服务日志带 version 字段

验收：慢删除场景下前端最终状态与 bridge 实际一致；/healthz 返回当前部署 SHA。

- 每项附：诊断结论、改动清单、验证证据
- 基础设施变更先出方案，经确认后执行；涉及生产数据的操作必须可回滚
```

## 阶段 2：核心机制（U-1 闭环 / 租约盲区 / 错误透传）

```text
你是一名资深后端工程师，修复协作室平台三项核心机制缺陷（2026-08-19 根因调查报告
定案）。最小改动，每项带回归测试与验收步骤。

## 修复 1：U-1 计划修复不收敛（三环联动）

环 1 信封解析静默降级：agent_consultation_service.py:607-620 解析失败降级为
ConsultationEnvelope(conclusion=原文)，proposed_submission 保持 None，
parse_success 仅进 telemetry（:688-695），Bridge/房间看到的是"completed"。
→ 要求：parse_success=false 升格为 Case 事件，对 Bridge 与房间可见。

环 2 repair 反馈无字段清单：bridge service.py:1497-1515 对 omitted-envelope
返回 []，反馈文案（:1542-1546）无字段清单、无 schema、充斥内部行话。
→ 要求：补 omitted-envelope 分支；反馈携带缺失字段清单与 schema 摘要。

环 3 重试时原始任务丢失：reset_planning_work_item（case_store.py:398-445）把
objective 整体替换为反馈并清空上下文，模型重试时看不到原始任务。
→ 要求：重试上下文 = 原始 objective + 校验反馈，禁止替换。

关联：no_progress 保护分支返回 status=ok 纯文本（parallel_subagent_service.py:895-934）
→ 要求：标记为 partial/guard_triggered，不得作为可交付结果直接进入验收。

验收：构造 proposed_submission=None 场景，3 次重试内收敛或产生显式失败事件；
全程事件流可查（parse_success、attempt 号、反馈内容）。

## 修复 2：断点 E——租约盲区

证据：续租协程只在 execute-readonly 请求存活期（bridge service.py:967-969 启动、
:1039-1042 finally 取消，节拍=deadline/3）；claim→execute 窗口无续租；
load_worker_profile 的 ValueError（production_runner.py:141/:145）不在 main()
捕获列表（:286）→ 进程退出、工作项滞留 claimed → 300s×3 → timeout，
Bridge 只见 lease_expired 无失败原因；续租协程异常即永久退出仅 warning
（service.py:1173-1182）。

要求：
1. 租约覆盖 claim→execute 窗口（claim 即起续租，或前置校验移到 claim 之前）
2. worker 前置异常写入失败原因事件，Bridge 可查
3. 续租异常写审计事件而非仅 warning

验收：worker 前置异常场景下，Bridge 审计含失败原因事件，而非纯 lease_expired×N。

## 修复 3：Bridge 错误结构化透传

证据：_request_as（agentteams_service.py:1374-1407）把非 404 的 4xx/5xx/网络错误
统一抹平为 BusinessError 400"Agent 协作中心暂时不可用"，真实错误码（如 422）
丢失，直接放大了断点 A 的排查难度。

要求：
1. Bridge 错误体携带 machine-readable code（如 LIMIT_EXCEEDED）
2. 平台按 code 映射用户文案，不再一律"暂时不可用"
3. 日志保留 status、响应体截断、path、trace ID；前端展示层文案可不变

验收：构造 422 场景，后台日志含真实 status/body/code，API detail 按 code 可区分。

## 通用要求

- 先读代码再动手；最小改动；每项附回归测试与验收步骤
```

**阶段 2 人工验收 checklist**

- [ ] worker 异常死亡场景：Bridge 有原因事件，不再只有 lease_expired

## 阶段 3：体验分级 + 端到端测试兜底

```text
你是一名资深全栈工程师，实施协作室平台的错误处理分级与端到端测试建设。

## 任务 1：前端错误分级

证据（根因调查报告前端清单）：全站 catch 一律 detail‖固定文案 toast，不区分
4xx/5xx/网络错误；background 刷新失败一律静默；authRefresh.ts:27 catch-all 把
refresh 接口的 5xx/网络抖动也判为"登录失效"（会真清 localStorage 登出）；
ProfileView.vue:311 一次 401 即 logout。

要求：
1. 统一错误分级：4xx 业务文案 / 5xx 可重试入口 / 网络错误区分提示
2. authRefresh 区分 401 与 5xx：仅 401 且 refresh 明确失效才登出；5xx/网络抖动
   保持登录态并退避重试
3. background 刷新连续失败 N 次显示状态条；SSE 断流显示连接状态
4. ProfileView.vue:311 按同一分级修正

验收：断网 / 500 / 422 三场景三种可区分提示；refresh 接口 5xx 不触发登出。

## 任务 2：端到端测试从零建设（进 CI 默认跑）

现状：tests/integration/ 对 agentteams 零覆盖；唯一 e2e 为 opt-in 且只打 Bridge
HTTP，不经房间路由、投影、前端——断点 A 这类平台-Bridge 契约错位正是它该拦的。

必建用例：
E2E-1 创建→路由→派发→投影全链路（scrna 输入，断言事件序列与 Case 状态机迁移）
E2E-2 平台-Bridge 参数契约（limit 边界值，防断点 A 回归）
E2E-3 未知领域输入（16S：route_unavailable 或显式 fallback 文案，不得静默断链）
E2E-4 规划失败显式化（注入 Bridge 故障：Case 不得静默停 received，须有
     planning_failed 事件与前端可见提示）
E2E-5 删除聊天室（含"超时但后端已删"的对账场景）
E2E-6 用户消息气泡可见性（发送→落库→渲染，防 R2-4 回归）

验收：套件进 CI 默认执行（非 opt-in）；断点 A 场景在套件中可先复现红灯。

## 通用要求

- 遵循现有测试风格；每个用例附断言说明
- 任务 1 的交互改动附改动前后行为对照
```
