#### RocketMQ 协议核查结论

当前部署的 Broker 镜像为 Apache RocketMQ `5.3.2`，但应用端并**不是** RocketMQ 5.x gRPC 客户端：Producer/Consumer 分别使用 `rocketmq.client.Producer`、`PushConsumer`、`set_name_server_address()` 和 NameServer 地址。这是 Apache RocketMQ 4.x Remoting 风格 API；仓库中未发现 gRPC Proxy 地址、5.x gRPC SDK 或 ONS SDK 配置。

因此，PPT/方案不得表述为“已采用 RocketMQ 5.x gRPC 协议，和阿里云 RocketMQ 5.x 协议兼容可平滑迁移”。准确表述应为：“本地 Apache RocketMQ `5.3.2` Broker 已与既有 Celery 任务模型完成灰度路由适配；应用端仍使用 4.x Remoting 风格 Python client。迁移到阿里云消息队列 RocketMQ 版前，需要针对目标实例完成客户端兼容性与收发/重试/延时消息的 staging 验证；若目标要求 5.x gRPC SDK，应先替换客户端适配层。”

#### NAS 核查结论

文件服务通过 `storage_path` / `StoragePathFactory` 对 POSIX 路径执行 `mkdir`、`resolve`、读写和路径越权校验；Docker Compose 仅把 `${CYGNUSX_DATA_ROOT}` bind mount 到 `/data/cygnusx`。这意味着部署人员**可以**将 NAS 挂载到该宿主目录后复用现有 POSIX 文件服务，但仓库未发现 NAS/NFS 配置、阿里云 NAS CSI 驱动、Kubernetes `StorageClass` 或 `ReadWriteMany` 声明，也没有 NAS 专用存储后端或验收记录。

所以 NAS 只能列为“OSS / 文件存储 NAS 的迁移路径（POSIX 挂载可承载）”，不能写成“已接入、已验证 NAS”。上线前至少要补：挂载与权限方案、跨 Web/Worker 的共享可见性、并发写入/锁、吞吐与延迟、故障恢复和备份演练。
