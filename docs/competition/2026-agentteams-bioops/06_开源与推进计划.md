# 开源交付与推进计划

## 1. 开源交付目标

OmicHub BioOps 的目标不是只开放一段 Demo 代码，而是开放一套可复用的“科研复杂任务多 Agent 协同模板”。对外发布将拆分为：

| 模块 | 交付内容 | 复用对象 |
| --- | --- | --- |
| `integrations/agentteams/teams/` | BioOps Team、角色身份、能力与禁止能力配置 | 希望构建科研/数据交付 Team 的 AgentTeams 开发者。 |
| `integrations/agentteams/skills/` | 预检、提交、监控、质控、交付等 Skill 契约 | 需要接入任意受控任务系统的应用团队。 |
| `integrations/agentteams/bridge/` | 非侵入式 Bridge 与契约测试 | 有既有业务系统、希望避免 Agent 直连内部数据库的企业。 |
| `data/ai/mas/` | Agent 能力表、Artifact Schema、工具策略 | 构建 DAG/Artifact 驱动协同系统的开发者。 |
| `docs/competition/2026-agentteams-bioops/` | 方案、Demo、评审映射、开源与安全说明 | 评委、合作伙伴、社区贡献者。 |

## 2. 文档与工程最低交付标准

复赛/决赛前应保证公开包至少包含：

- 项目 README：场景、架构、快速开始、角色边界、已实现/待实现状态。
- 部署说明：本地/staging 依赖、环境变量分类、Bridge 与 Worker 启动顺序、最小权限配置。
- 示例配置：脱敏 Team、Skill、项目参数、质量规则和测试数据 manifest。
- 测试说明：单测、Bridge contract test、Demo preflight 成功/阻断、完整链路的环境前提。
- 安全说明：密钥不入仓、浏览器不持有 Bridge secret、审批 token 生命周期、数据脱敏与日志边界。
- 第三方依赖与许可证清单：AgentTeams、OmicHub、工作流工具、容器镜像和知识库数据分别声明。

## 3. 版本治理

| 对象 | 版本策略 | 兼容性与回滚 |
| --- | --- | --- |
| Team / Agent Identity | 角色 ID 稳定；权限或协作语义变更提升主/次版本 | 新旧 Team 并存灰度；历史 Case 绑定原身份快照。 |
| Skill Contract | 采用语义版本；破坏性 I/O 变更新建版本 | Bridge 同时兼容一段时间；按 Case 记录 skill version。 |
| Quality Rule | 规则、阈值、适用范围显式版本化 | 规则升级不覆盖历史质量结论；支持复评。 |
| Artifact Schema | 类型稳定、字段扩展向后兼容 | 新消费者先校验 schema version，避免误读。 |
| Bridge API | `/v1` 保持稳定；新能力增加端点或可选字段 | 以 contract test 防止隐式破坏。 |

## 4. 推进路线图

### 初赛（当前）

- 完成场景、架构、角色、Skill、接口、安全与评审对照材料。
- 使用当前仓库的 AgentTeams Bridge、MAS、现有领域 Agent 配置和测试作为工程依据。
- 明确默认关闭、待部署验收和比赛增量，不夸大完成度。

### 复赛

- 新增并发布 `agent-data`、`agent-qc`、`agent-delivery` 的 Agent YAML、提示词、最小工具包、MAS 能力和 Artifact/质量契约；复用 `agent-general` 与领域分析 Agent，不复制已有工作流能力。
- 提供一个一键或文档化的 staging 环境，跑通 Case → 预检 → 审批 → 领域执行 Agent 提交/监控 → 质量门 → manifest。
- 准备脱敏 RNA-seq Demo 项目，完成主链路、预检阻断、质量人工复核三条录屏。
- 汇总 Trace/Log/Metrics 报告，覆盖端到端耗时、Skill 成功率、阻断原因和人工复核率。
- 补齐 Bridge 的生产持久化 Store 方案验证，保持现有接口契约不变。

### 决赛

- 将 AgentTeams Case 事件实时投影到 OmicHub 协作工作台；在已部署条件下演示 Matrix/Element 外部协作入口。
- 完成受控 RNAFlow/Apptainer Worker 的真实环境演练、失败恢复和资源配额验证。
- 发布可复用 Team/Skill 模板，并扩展一个非 RNA-seq 场景（如 ATAC-seq 或单细胞）以验证复用性。

## 5. 产业与科研合作诉求

项目希望对接以下伙伴，以验证真实价值而不是仅做技术演示：

| 合作对象 | 希望共建的验证场景 |
| --- | --- |
| 药企、CRO、转化医学平台 | 合规边界下的队列 RNA-seq/多组学项目交付、人工复核与审计。 |
| 种业、农业科研机构 | 多批次育种材料转录组分析、参考版本治理和可复制项目模板。 |
| 医学检验与科研服务机构 | 客户项目的预检、排队、质控签字、交付 manifest 和服务质量指标。 |
| AgentTeams / 开源社区 | Team 身份、Skill Contract、Bridge/MCP 适配、Case 可观测规范共建。 |
| 云与基础设施伙伴 | 受控任务执行、对象存储、向量/审计存储、可观测与成本治理验证。 |

## 6. 成功标准

在比赛结束时，项目至少以以下可验证结果衡量：

1. 评委可在隔离环境复现至少一条成功 Case 和两条异常 Case。
2. 每条 Case 均能导出角色、审批、任务、Artifact、质量决策和交付 manifest 证据。
3. 对每一个高风险工具调用，都能确认其角色身份、授权范围、幂等键与审计事件。
4. 新增一个流程或业务场景时，主要工作是配置 Team/Skill/Artifact/规则，而非重写协同主链路。
5. 公开材料足以让第三方理解系统边界、部署方式、测试条件与已知限制。
