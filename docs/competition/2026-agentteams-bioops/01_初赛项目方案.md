# CygnusX BioOps：面向生命科学研发的可审计多 Agent 协同基础设施

## 1. 项目概述

### 1.1 项目背景

在药物研发、种业育种、医学检验与科研服务企业中，一次组学分析交付通常横跨数据接收、样本与元数据核验、计算流程执行、质量控制、统计解读、图表与报告交付多个角色。当前协作普遍依赖人工在聊天工具、表格、脚本、任务系统之间传递信息，带来四类问题：

1. **任务链路断裂：** FASTQ、样本表、分组信息、参考基因组和分析参数分散，任何缺失都会在计算后期才暴露。
2. **责任与权限混杂：** 研究人员、分析工程师和质控人员共享高权限入口，难以界定谁批准了下载、谁提交了计算、谁放行了结果。
3. **结果难以复核：** 交付物往往只有一个压缩包；过程中的参数、质量指标、失败重试、人工判断和版本关系不完整。
4. **经验无法复用：** 同类项目每次都从自然语言沟通开始，无法沉淀为可复用的操作 Skill、质量规则和项目模板。

CygnusX BioOps 把“组学项目从数据接入到可信交付”定义为企业级复杂任务，构建由 AgentTeams 协同、CygnusX 执行与证据底座支撑的闭环系统。系统不让 LLM 直接操作宿主机或任意执行命令，而是把每一步约束为有身份、有输入输出契约、有审批边界、有证据记录的工作项。

### 1.2 目标用户与典型场景

| 目标用户 | 典型任务 | 主要收益 |
| --- | --- | --- |
| 药企转化医学/生信平台 | 临床队列 bulk RNA-seq 差异分析与报告交付 | 降低样本配置错误和结果追溯成本。 |
| 种业与农业科研团队 | 多批次转录组项目的质控、分析、可视化与可复现实验记录 | 统一流程版本、参考基因组与证据标准。 |
| 医学检验/科研服务机构 | 面向客户的标准化分析交付 | 让项目经理、计算人员、质控人员在同一 Case 中协作。 |
| 高校核心设施 | 多课题组并行提交的测序分析需求 | 以审批、队列和质量门控制资源与服务边界。 |

本次参赛 Demo 聚焦 **bulk RNA-seq 差异分析交付**。该场景输入清晰、链路完整，且可迁移到 ATAC-seq、单细胞、多组学和其他科学计算工作流。

### 1.3 一句话价值主张

> 把“研究人员提需求—分析人员跑流程—质控人员签字—项目经理交付”变成可执行的 AgentTeams Case：每一次调用有权限、每一个产物可追溯、每一个结论有证据、每一个高风险动作可审批和回滚。

## 2. 方案亮点

### 2.1 从对话式助手到可验证项目闭环

CygnusX 已具备领域 Agent、受控工作流、异步任务和结果工作台。BioOps 在其上增加 AgentTeams Case 协同层，将一次自然语言请求转化为结构化项目对象：`Case → Work Item → Skill 调用 → Artifact → Quality Decision → Evidence → Delivery Manifest`。

系统只在 Agent 间传递小型元数据、逻辑 Artifact 引用和短摘要，不在提示词或消息中传递原始 FASTQ、完整表达矩阵或长日志。这既控制上下文成本，也避免科研数据在协作链路中无边界扩散。

### 2.2 “责任分离”而非“一个万能 Agent”

核心工作组采用“**复用现有领域 Agent + 新增三个职责型 Agent**”的方式，而不是再引入一个与现有能力重叠的通用 Workflow Operator：

- **`agent-general`（现有，BioOps Manager）：** 接收需求、创建 Case、拆分工作项、汇总结论；不直接提交计算任务。
- **`agent-rnaseq` / `agent-atacseq` / `agent-scrna`（现有，领域执行 Agent）：** 根据任务模态承担已批准流程的提交、监控与领域分析；不修改流程 YAML、不拥有宿主机 shell。Manager 只从与任务模态匹配的 Agent 中选择一个执行者。
- **`agent-data`（新增，Data Steward）：** 预检项目元数据、样本表、分组、物种和参考版本；只读，不运行计算。
- **`agent-qc`（新增，Quality Auditor）：** 根据版本化 QC 规则核验任务与 Artifact；规则缺失时转人工复核，不以模型“感觉”替代质量判断。
- **`agent-delivery`（新增，Delivery Reporter）：** 汇总已验证的 Artifact、参数、质量结论和风险说明，形成可交付 manifest；不渲染或发布文件。

现有 `agent-code` 与 `agent-viz` 可作为并行审查者，分别承担复现性/脚本审查和图表规范审查；它们不进入关键执行权限链。

必要时可并行调用 CygnusX 领域专家（RNA-seq、单细胞、代码、可视化）进行科学解释或审查，但这些专家的能力仍受 Team 身份和 Bridge allowlist 约束。

### 2.3 AgentTeams 为协同设计基点

作品将 AgentTeams 的 Team、Role、Case、Work Item、审批、事件和房间体验映射到生信交付协作：

| AgentTeams 能力 | BioOps 映射 |
| --- | --- |
| Team / Role Identity | 现有 `agent-general` 与按模态选择的领域执行 Agent，加上新增 Data、QC、Deliver 角色的身份、令牌和禁止能力。 |
| Case | 一个用户项目的一次端到端分析交付单，包含 requester、项目引用、状态、审批和证据。 |
| Work Item | 可领取、可重试、可审计的预检、任务提交、监控、质控、报告等最小工作单元。 |
| 角色编排 | Manager 根据项目状态和依赖关系分派，允许预检/元数据审查并行，计算完成后才解锁质控与交付。 |
| 上下文传递 | 只传 `case_id`、逻辑项目/任务引用、Artifact URI、规则版本、摘要和 trace 标识。 |
| 审批与状态追踪 | 高风险动作经 AgentTeams 人工网关签发作用域受限、短时有效的 approval token；Case/Work Item 状态与证据事件可回放。 |
| 协作可视化 | CygnusX 工作台显示 Case、泳道进度、审批卡和证据；部署 Matrix/Element 后可将官方房间作为外部协作入口。 |

## 3. 端到端闭环设计

### 3.1 输入与任务拆解

研究人员提交“对这批 RNA-seq 样本做差异分析并出具交付报告”，同时上传或引用样本表、分组、物种、参考基因组版本和数据位置。Manager 创建 Case，生成以下依赖图：

```text
项目需求 / 数据引用
        │
        ▼
agent-data：project-preflight ── blocked ──► 请求补充元数据
        │ passed
        ▼
Manager：展示计划与风险 ──► 人工确认 / 签发审批令牌
        │
        ▼
领域执行 Agent：workflow-submit → workflow-monitor
        │
        ▼
agent-qc：quality-gate ── manual_review ──► 人工质控复核
        │ passed
        ▼
agent-delivery：delivery-pack → Delivery Manifest / 结果链接 / 复盘条目
```

对于需要领域解释的项目，`agent-qc` 后可并行派发 `scientific-interpretation`、`visualization-review` 或 `code-review` 工作项，并将结论作为 evidence reference 进入交付包；这些审查不会获得任务提交、取消、数据库、shell 或文件写权限。

### 3.2 上下文与状态传递

| 传递对象 | 内容 | 禁止内容 |
| --- | --- | --- |
| Case 上下文 | `case_id`、requester、项目逻辑引用、任务目标、审批状态、风险级别 | 用户密钥、宿主机路径、原始文件内容。 |
| Work Item | 指派角色、Skill、输入 Artifact 引用、截止时间、幂等键、状态版本 | 未授权流程参数、跨项目数据。 |
| Artifact | `omic://` 逻辑引用、类型、校验摘要、生产者、版本、质量状态 | 直接文件系统路径、完整矩阵或长日志。 |
| 事件 | `trace_id`、Case/Work Item ID、attempt、状态、错误类别、evidence reference | 任意敏感载荷或大文件。 |

CygnusX MAS 层采用 Run、Node、Artifact、Approval、A2A Event 的持久化模型。状态变更在数据库事务中与 Outbox 记录一起提交，再投递到 Redis Stream；消费端按事件 ID 或 dedupe key 幂等处理。该设计允许“至少一次”消息投递下的安全恢复，也允许从事件表重建投影。

### 3.3 工具调用、验证与交付

1. **预检：** `agent-data` 调用只读 `project-preflight`，确认样本表、分组、物种、参考版本和工作流前置条件；缺失则返回 `blocked`，绝不提交任务。
2. **审批：** Manager 展示成本、数据范围、目标流程和风险。研究人员或授权负责人确认后，由独立 approval gateway 签发仅能用于指定动作/Case/有效期的 token。
3. **执行：** Manager 将任务模态映射到对应的现有领域执行 Agent；该 Agent 调用受限的 `workflow-submit` 和 `workflow-monitor`。调用要求 `approval_token`、`idempotency_key`、`allowed_flow`，不暴露流程 YAML、shell 或数据库。
4. **验证：** `agent-qc` 获取任务状态与 Artifact 逻辑引用，按版本化质量规则判定 `passed`、`failed` 或 `manual_review`；无规则版本时必须人工复核。
5. **证据沉淀：** 关键调用和状态变化产生 evidence event，绑定 trace、规则版本、Artifact 引用、决策与原因。
6. **交付与复盘：** `agent-delivery` 只在必需 Artifact 完整时生成 Delivery Manifest；同时产出可复用的 runbook、失败原因和规则/Skill 改进建议。

## 4. 系统架构

```text
┌───────────────────────────────────────────────────────────────────┐
│  CygnusX 工作台 / Agent 协作中心 / 可选 Element 房间              │
│  Case 进度、审批卡、产物、证据、交付 manifest                     │
└──────────────────────────────┬────────────────────────────────────┘
                               │ 服务端代理（浏览器无 Bridge 密钥）
┌──────────────────────────────▼────────────────────────────────────┐
│ AgentTeams 协同层                                                    │
│ Team identities · Case/Work Item · 人工审批网关 · 事件/质量决策     │
└──────────────┬───────────────────────────────────┬────────────────┘
               │                                   │
┌──────────────▼──────────────┐       ┌────────────▼───────────────┐
│ Skill / Bridge 契约层        │       │ CygnusX Agent & MAS 层     │
│ 预检、提交、监控、质控、交付 │       │ Orchestrator、DAG、Artifact │
│ 幂等、超时、失败语义         │       │ Registry、HITL、Outbox      │
└──────────────┬──────────────┘       └────────────┬───────────────┘
               │                                   │
┌──────────────▼───────────────────────────────────▼───────────────┐
│ 受控执行与数据层                                                     │
│ 工作流 Worker / RNAFlow / 任务中心 / PostgreSQL / Redis Stream     │
│ 数据库、知识库、审计日志、指标与 Trace                              │
└───────────────────────────────────────────────────────────────────┘
```

### 4.1 分层原则

- **协同层不侵入业务内部：** AgentTeams Bridge 独立部署，不导入 CygnusX 内部模块，也不直接访问 CygnusX 数据库。
- **Agent 不拥有万能权限：** 工具包是最小授权组合；Agent 的可调用能力由 `data/ai/mas/agent_capabilities.yaml` 和 Bridge 身份 allowlist 双重限制。
- **流程执行与语言推理解耦：** LLM 负责拆解、解释和结构化决策；真实性由流程日志摘要、结构化 QC 指标、规则校验和 Artifact 完整性决定。
- **对外集成可替换：** 现阶段以 REST Bridge 作为等价工具协议；其 Schema、鉴权、幂等、失败处理和审计已独立定义，后续可封装为 MCP server，不需重写业务调用链。

## 5. Skill、RAG、工具与可观测性

### 5.1 Skill 工程体系

项目把稳定业务动作沉淀为 Skill，而不是用一段提示词临时完成：`project-preflight`、`workflow-submit`、`workflow-monitor`、`workflow-cancel`、`quality-gate`、`delivery-pack`、`scientific-interpretation` 等都定义了输入、输出、调用人、失败语义和权限边界。详细清单见 [03_Skill与工具接口清单.md](03_Skill与工具接口清单.md)。

CygnusX 的 `data/ai/skill_marketplace/` 已提供可安装 Skill 目录、版本元数据及可复用脚本；平台以 `data/ai/*.yaml`、tool packs、prompt、MCP 绑定和 MAS 能力表声明式装配 Agent。这使同一个 Skill 能被不同领域 Agent 或不同项目模板复用。

### 5.2 知识与上下文增强

本作品至少覆盖以下两类上下文能力：

- **共享状态管理（已具备基础）：** Case、Work Item、MAS Run/Node/Artifact/Approval/A2A Event 与工作区投影构成跨 Agent 的结构化共享状态。
- **可追溯记忆与证据（已具备基础）：** 交付 manifest、evidence event、规则版本、runbook 和 Artifact Registry 将历史项目决策沉淀为可查询记录。
- **知识库 RAG（比赛增量）：** 对 SOP、分析规范、QC 规则说明、客户交付模板和历史复盘建立分层检索。RAG 只能返回带来源和版本的证据片段；若证据不足，Agent 必须输出不确定性或发起人工追问，不能伪造科研结论。

### 5.3 可观测与评估

所有关键链路采用统一关联字段：`trace_id`、`case_id`/`run_id`、`work_item_id`/`node_id`、`attempt`、`dedupe_key`、Skill 名称、规则版本和 Artifact 引用。比赛 Demo 至少展示：

- **Trace：** 一次 Case 从预检到交付的角色流转与工具调用耗时。
- **Log：** 审批、重试、阻断、人工复核和交付事件，禁止记录原始敏感数据。
- **Metrics：** Case 完成率、首次预检阻断率、人工复核率、Skill 成功率、重试次数、端到端耗时与单 Case token/工具成本。

现有 MAS 架构已定义 trace 字段、日志关联规则和任务/事件投影；比赛期间将以可视化页面或导出报告呈现指标。可观测后端可接入 OpenTelemetry 兼容链路及 LoongSuite、AgentScope Studio 或 AgentLoop，但不以堆叠产品数量作为项目亮点。

## 6. 安全、审批与回滚

| 风险 | 控制措施 |
| --- | --- |
| 未授权计算或取消任务 | 仅当前 Case 被分派的领域执行 Agent 可调用提交/取消；提交和取消分别要求限定动作的短期 approval token。 |
| 跨项目数据泄露 | Bridge Case 查询按 `requester_ref` 在 CygnusX 服务端过滤；浏览器不持有 Bridge secret，也不直接调用 Worker。 |
| LLM 自行修改工作流 | Agent 不获得 shell、Docker daemon、任意网络、流程 YAML 或数据库写权限；只使用 allowlist 工具。 |
| 重试导致重复计算 | 请求携带 idempotency key；事件消费者以 event ID/dedupe key 幂等消费；自动重试有次数上限。 |
| 质量门被模型绕过 | `agent-qc` 基于结构化 QC 规则和 Artifact 完整性决策；规则缺失进入 `manual_review`。 |
| 错误交付或发布 | Delivery Pack 缺失必需 Artifact 时阻断交付；交付前保存 manifest、证据引用和审批轨迹。 |
| 外部依赖不可用 | 预检和工具调用使用显式 timeout/错误类别；Redis 不可用时可由 PostgreSQL Outbox 重建事件投影；高风险问题切换为人工处理。 |

回滚策略遵循“**停止新调度、保留证据、不破坏既有单 Agent 路径**”：可关闭 `MAS_ENABLED` 或 AgentTeams Gateway 功能开关；已发生的 Case、审批、Artifact 与事件继续保留，供审计与人工恢复。

## 7. 业务价值与可复制性

| 价值维度 | BioOps 机制 | 可量化指标（比赛评估口径） |
| --- | --- | --- |
| 效率 | 预检自动阻断缺失信息，角色并行审查，自动生成交付清单 | 项目从需求到可执行计划耗时、人工往返次数、平均交付周期。 |
| 质量 | 规则化质量门与 Artifact 完整性校验 | 首次通过率、人工复核率、缺失交付物率、重跑率。 |
| 风险 | 权限分离、审批令牌、幂等、审计、可回滚 | 未审批高风险调用数（目标为 0）、重复提交数、审计覆盖率。 |
| 成本 | 只传元数据和摘要，工具超时与预算受控 | 单 Case token/工具成本、无效计算占比、重试成本。 |
| 复用 | Skill、团队角色、接口和项目模板可配置 | 新增流程接入时间、Skill 跨项目复用次数、行业模板数。 |

可复制的不是某一个 RNA-seq 流程，而是“**受控任务交付 Case**”模式。将预检字段、允许的流程、Artifact 类型、质量规则与交付模板替换后，可迁移到 ATAC-seq、单细胞、药物筛选、临床报告审核、实验室质控甚至非生信的企业分析任务。

## 8. 当前工程基础与比赛交付计划

### 8.1 当前基础

- CygnusX 已声明式管理内置 Agent、提示词、工具包、Skill、MCP、运行镜像和 MAS 策略。
- MAS 已具备计划预览、能力校验、DAG、Artifact Registry、审批、Outbox、Redis Stream、重试、质量门和受控执行的实现基础；默认功能开关关闭，真实环境 E2E 仍需部署验收。
- AgentTeams 集成已提供独立 Bridge、Team/Skill 契约、Case/Work Item、角色身份、审批令牌、幂等、质量决策、证据事件和交付 manifest；比赛增量将把现有领域 Agent 接入该 Team，并新增 Data、QC、Deliver 三个专职 Agent；持久化生产 Bridge Store 仍是后续工作。
- 现有 staging Demo 可以验证预检通过与受阻分支；完整工作流需要显式 staging 审批和真实 CygnusX demo task payload。

### 8.2 比赛阶段目标

| 阶段 | 交付重点 |
| --- | --- |
| 初赛 | 完成方案、身份/Skill/接口契约、架构图、Demo 脚本、开源说明和评分点对照。 |
| 复赛 | 打通 AgentTeams Case 到 CygnusX Demo 项目；录制成功、预检阻断、质量人工复核三条可重复链路；提供部署包、样例数据、测试和 Trace/证据报告。 |
| 决赛 | 在本地或云端稳定演示完整链路，展示审批、异常恢复、角色协同、交付 manifest 和可观测看板；发布可复用的 Team/Skill 模板。 |

## 9. 结语

CygnusX BioOps 不把多 Agent 当作“让多个模型聊天”，而是把它作为面向高价值科研任务的责任分离与可信交付基础设施：**能拆解、能执行、能验证、能审计、能恢复、能积累经验**。这正是生命科学研发从零散 AI Demo 走向可运营生产系统所需要的能力。
