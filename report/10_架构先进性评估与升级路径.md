# 10 · 架构先进性评估与升级路径

> 评估基准：2025 年中组学平台 + AI Agent 平台双重对标
> 结论：AI 架构第一梯队，DDD 与流程引擎扎实；任务调度与 AI 知识检索两块存在代差

## 一、先进性总评

| 维度 | 评分 | 定位 |
|------|------|------|
| AI Agent 架构（MCP + Loop + SSE） | 9/10 | 第一梯队，领先 60% 国内组学平台 |
| 领域设计（DDD 12 子域四层） | 8/10 | 规范扎实，超出多数脚本堆叠型平台 |
| 流程引擎（YAML 声明 + GenericBuilder） | 8/10 | 配置即代码，扩展性强 |
| 任务调度（Celery 单队列） | 4/10 | 上一代方案，存在代差 |
| AI 知识检索（无 RAG/向量库） | 3/10 | 停在提示词层，"假智能" |
| 存储架构（文件 + PG 元数据） | 6/10 | 可用，缺 Lakehouse 前瞻 |
| 可观测性（无 OTel/Tracing） | 2/10 | 生产级空白 |
| 部署运维（Docker Compose，无 GitOps） | 4/10 | 组内够用，万人级不够 |

**综合：6.8/10 — 设计先进、实现待补。** 不是"落后"，是"先进的设计 + 部分代差的实现"。

## 二、已经先进的地方（保持，不要改）

### 2.1 MCP 协议接入 — 前沿

`mcp>=1.0.0` SDK + 三种 transport（stdio/sse/streamable_http）。多数组学平台的 AI 助手还在硬编码工具调用，你已经用了标准协议。这是 2024 年底 Anthropic 推出的开放标准，2025 年成为事实标准。

### 2.2 Agent 8 轮工具循环 — 前沿

`agent_service.py` 的 `assemble_context` + 调度中枢 8 轮 tool_call → tool_result → 继续生成，这是 2025 年主流 agentic loop 范式（对齐 OpenAI Assistants / Anthropic Claude）。比传统"调一次 LLM 返回"领先一代。

### 2.3 SSE 流式替代 WebSocket — 现代

与 OpenAI/Anthropic 官方流式接口对齐，Cherry Studio 范式。WebSocket 双向通道对 LLM 场景是过度设计。

### 2.4 YAML 声明式流程引擎 — 优秀

`flows/*.yaml` + `GenericFlowBuilder` 配置即代码，新增流程不改后端。对齐 Nextflow config-as-code 思想。仅补 `container_image` 字段即可。

### 2.5 OpenAI 兼容 Provider 抽象 — 正确

一套接口接所有模型（Kimi/智谱/litellm），不被厂商锁定。

### 2.6 DDD 12 子域四层分层 — 规范

超过 80% 的组学平台（多为脚本堆叠）。`domain/` 纯实体 + `application/` 服务 + `infrastructure/` 实现 + `api/` 入口，依赖方向正确。为未来微服务拆分铺路。

## 三、存在代差的 3 处（升级重点）

### 3.1 任务调度：Celery → Temporal / Argo（代差最大）

#### 现状问题

- 单一 `analysis` 队列，所有任务挤一起
- Worker 崩了任务就丢（Celery 不保证 durable execution）
- 生信流程跑 6 小时，中途失败只能整体重跑，无断点续跑
- 无重试策略、无 DLQ、无可视化 DAG
- `session.py` 用 `NullPool` 规避 `asyncio.run` 跨循环问题（万人级耗尽 DB 连接）

#### 为什么 Celery 不适合生信工作流

Celery 设计目标是**消息队列**（fire-and-forget），生信工作流需求是 **DAG 编排 + 持久化执行 + 断点续跑**，两者不匹配：

| 需求 | Celery | Temporal | Argo |
|------|--------|----------|------|
| 任务持久化（Worker 崩不丢） | 否 | 是 durable | 是 K8s 保证 |
| 断点续跑 | 否 | 是 任意 step | 是 step 级 |
| 重试策略 | 手动 | 是 内置 | 是 内置 |
| 补偿事务 | 否 | 是 Saga | 手动 |
| DAG 可视化 | 否 | 是 Web UI | 是 Web UI |
| 工作流版本化 | 否 | 是 | 是 |

#### 升级方案：TemporalExecutor（推荐）

你的 `BaseExecutor` 抽象（`base.py` 53 行，回调解耦）设计得非常好，新增 `TemporalExecutor` 即可，**业务层（TaskService/TaskDomainService）无需改动**：

```python
# src/omichub/infrastructure/execution/temporal.py
class TemporalExecutor(BaseExecutor):
    """Temporal 工作流执行器 — durable execution + 断点续跑"""

    async def execute(self, ctx: ExecutionContext) -> ExecutionResult:
        client = await Client.connect("temporal:7233")
        result = await client.execute_workflow(
            "SnakemakeWorkflow",
            {"snakefile": ctx.snakefile, "config": ctx.config_file, "cores": ctx.cores},
            id=f"omichub-{ctx.work_dir}",
            task_queue="snakemake",
            retry_policy=RetryPolicy(maximum_attempts=3),
        )
        return ExecutionResult(status="success", returncode=0, stdout=result)
```

Temporal Workflow 定义（Python SDK），每步独立 activity，失败自动重试，断点续跑：

```python
@workflow.defn
class SnakemakeWorkflow:
    @workflow.run
    async def run(self, params: dict) -> str:
        await workflow.execute_activity(
            prepare_workdir, params, start_to_close_timeout=timedelta(minutes=5))
        result = await workflow.execute_activity(
            run_snakemake_activity, params,
            start_to_close_timeout=timedelta(hours=24),
            retry_policy=RetryPolicy(maximum_attempts=3))
        await workflow.execute_activity(
            callback_result, result, start_to_close_timeout=timedelta(minutes=2))
        return result.stdout
```

注册到 registry（`registry.py`），`flows/*.yaml` 声明 `engine: temporal` 字段路由：

```python
_EXECUTORS = {
    "snakemake": LocalSnakemakeExecutor,
    "binary": BinaryExecutor,
    "temporal": TemporalExecutor,      # 新增
    "k8s-job": K8sJobExecutor,         # 新增（见报告 09）
}
```

```yaml
# flows/rna_seq.yaml
engine: temporal                    # 或 k8s-job / snakemake
container_image: omichub/flow-rnaseq:v1.0
snakefile: /workflows/rna_seq/Snakefile
```

#### 备选：Argo Workflows（K8s 原生）

如果你已全面上 K8s（报告 07 路线），Argo 是更轻量的选择，每个 step 一个 Pod，原生 retryStrategy：

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
spec:
  entrypoint: main
  templates:
    - name: run-snakemake
      container:
        image: omichub/flow-rnaseq:v1.0
        command: [snakemake, -s, /workflows/Snakefile, --cores, "8"]
      retryStrategy:
        limit: "3"
        backoff: {duration: "1m", factor: 2}
```

#### 迁移路径

| 阶段 | 时间 | 内容 |
|------|------|------|
| 1 | 1 周 | 部署 Temporal Server（K8s Helm）或 Argo（K8s Operator） |
| 2 | 1 周 | 实现 `TemporalExecutor` + SnakemakeWorkflow，单元测试 |
| 3 | 1 周 | registry 注册，flows/*.yaml 增加 `engine` 字段，灰度切换 |
| 4 | 1 周 | Celery 降级为"轻任务"（下载/清理/JBrowse 仍用），重计算走 Temporal |

**结论**：Celery 不必完全废弃（轻任务仍可用），但**重计算工作流必须迁到 Temporal/Argo**。这是万人级稳定性的基石。

### 3.2 AI 知识检索：无 RAG → 补 RAG + 向量库（"假智能"变"真智能"）

#### 现状问题

`agent_service.py:43` 的 `AgentContext.system_prompt` 是纯字符串拼接，知识库靠读盘 + 注入 prompt。用户问"水稻 RNA-seq 参比基因组怎么选"，AI 只能靠模型自身知识答，**检索不到你知识库里的 `rna-seq-tips.md`**。这是当前 AI 助手最大的"假智能"点。

#### 升级方案：RAG + pgvector（最省事）

你已有 PostgreSQL，加 `pgvector` 扩展即可，无需引入新中间件：


```python
async def assemble_context(self, agent_id: str, user_query: str = "") -> AgentContext:
    # ... 原有逻辑 ...
    if user_query:
        rag = RAGService(self._db, self._embedder)
        chunks = await rag.retrieve(user_query, top_k=5)

```

#### 向量模型选择

| 模型 | 维度 | 部署 | 推荐 |
|------|------|------|------|
| bge-m3 | 1024 | 自部署（GPU/CPU） | 是 中英双语，开源免费 |
| text-embedding-3-large | 3072 | OpenAI 兼容 API | 是 省事，已有 Provider 抽象 |
| Qdrant/Milvus | - | 独立中间件 | 否 万人级前 pgvector 够用 |

**推荐 bge-m3 自部署**（一个 Docker 容器），或用 Provider 抽象调云端 embedding API。

#### 迁移路径

| 阶段 | 时间 | 内容 |
|------|------|------|
| 1 | 3 天 | pgvector 扩展 + knowledge_chunks 表 + Alembic 迁移 |
| 2 | 3 天 | RAGService 实现（分块 + 向量化 + 检索） |
| 3 | 2 天 | 集成到 assemble_context，知识库文档批量索引 |
| 4 | 2 天 | 前端管理界面（上传知识文档 → 自动索引） |

**结论**：这是把 AI 助手从"假智能"变"真智能"的最小改动，ROI 极高。

### 3.3 多 Agent 协作：单 Agent → 多 Agent 编排（应对复杂分析）

#### 现状问题

`AgentContext` 是单 Agent 模式，一个 Agent 包打天下。复杂分析任务（如"分析这批 RNA-seq 并解释结果"）需要多角色协作：数据探查 → 流程选择 → 参数推荐 → 结果解读。单 Agent 上下文窗口很快撑爆，且无法专业化分工。

#### 升级方案：LangGraph 状态机编排

你的 `AgentContext` + `assemble_context` 已有 Agent 概念，扩展为多 Agent 是自然演进。推荐 LangGraph（状态机式，可控性强）：

```python
# src/omichub/application/services/multi_agent.py
from langgraph.graph import StateGraph, END

class MultiAgentOrchestrator:
    def __init__(self, agent_service: AgentService):
        self._agent_service = agent_service

    def build_graph(self) -> StateGraph:
        graph = StateGraph(AgentState)
        graph.add_node("explorer", self._explorer_agent)      # 数据探查
        graph.add_node("selector", self._selector_agent)      # 流程选择
        graph.add_node("advisor", self._advisor_agent)        # 参数推荐
        graph.add_node("interpreter", self._interpreter_agent)  # 结果解读
        graph.set_entry_point("explorer")
        graph.add_conditional_edges("explorer", self._route_after_explore)
        graph.add_edge("selector", "advisor")
        graph.add_edge("advisor", END)
        graph.add_edge("interpreter", END)
        return graph.compile()
```

#### 何时引入

**暂不急着全面多 Agent 化**。建议：
- 短期：单 Agent + RAG（3.2）已能覆盖 80% 场景
- 中期：复杂分析任务（多步骤、需专业化）引入多 Agent
- LangGraph 集成约需 2 周，建议作为万人级第二阶段

## 四、可前瞻升级的 2 处（观望，暂不动）

### 4.1 事件溯源（Cookie/计费系统）

**现状**：`cookie_service.py` 用状态表 + 流水表，`UPDATE balance` 直接改余额。

**更先进**：事件溯源 — 只追加事件（`CookieEarned`/`CookieSpent`/`CookieFrozen`），余额由事件回放计算。审计天然完整、可回放、可重构状态。

**建议**：**仅当饼干系统要承担真实结算/法务审计时才改**。当前组内激励用，状态表 + 流水表已够。改造成本高，ROI 不明。

### 4.2 Lakehouse 替代文件存储

**现状**：文件落 NAS/OSS，元数据存 PG，纯文件视角。

**更先进**：Lakehouse（Delta Lake / Iceberg on OSS）— 对象存储上的表格化数据，支持 ACID、time travel、schema evolution。组学 count matrix / metadata 用 Lakehouse 比纯文件更适合大规模查询。

**建议**：**暂不动**。生信工具链（Snakemake/R）对 Lakehouse 支持还不成熟，属于前瞻观望。等社区生态成熟（约 1-2 年）再评估。

## 五、不建议盲目跟风的（现在这样就对）

| 有人会推 | 但你不该跟 | 理由 |
|---------|-----------|------|
| 微服务拆分 | 保持模块化单体 | Martin Fowler 原则：先单体后微服务，万人级再拆。DDD 分层已为未来拆分铺路 |
| GraphQL | 保持 REST | REST + OpenAPI 对生信工具链更友好，GraphQL 适合前端聚合场景 |
| gRPC | 保持 HTTP | 内部服务间调用才需 gRPC，你当前单服务无需 |
| Service Mesh (Istio) | 暂缓 | K8s NetworkPolicy 已够用，Istio 复杂度对单人运维过重 |
| Kafka 代替 Redis | 保持 Redis | Kafka 适合事件流场景，你的 Celery Broker 用 Redis 足够 |

## 七、总结

**OmicHub 架构不落后，但有两处代差需要补齐。**

**先进的（保持）**：MCP 协议、Agent 工具循环、SSE 流式、YAML 声明式流程引擎、DDD 分层、Provider 抽象。这些是 2025 年第一梯队水准，不要改。

**代差的（补齐）**：
1. **任务调度 Celery → Temporal/Argo**：生信工作流的 durable execution + 断点续跑是刚需，Celery 给不了。`BaseExecutor` 抽象让迁移成本可控。
2. **AI 知识检索补 RAG + pgvector**：把"假智能"变"真智能"，10 天工作量，ROI 最高。

**前瞻的（观望）**：事件溯源（饼干商业化时）、Lakehouse（生态成熟时）。

**不要跟的**：微服务拆分、GraphQL、gRPC、Service Mesh、Kafka — 现在的选型是对的，盲目追新反而增加复杂度。

**一句话**：先补 RAG（10天立竿见影），再随 K8s 化补 Temporal（4周一劳永逸），其余按 09 册节点分离路线走。架构设计的底子是好的，不需要推倒重来，只需要在两个点上"换代"。
