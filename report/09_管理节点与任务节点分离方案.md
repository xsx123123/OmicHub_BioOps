# 09 · 管理节点与任务节点分离方案

> 目标：控制面（管理节点）与数据面（任务节点）物理分离，任务节点水平扩展到集群
> 这是支撑万人级与集群执行的核心架构改造

## 一、当前架构耦合问题

现状：web/beat/flower/db/redis 与 worker 共享同一台物理机的磁盘/CPU/内存，通过 bind mount `/data/omichub` 共享数据。

| # | 问题 | 影响 |
|---|------|------|
| N-1 | Web 与 Worker 共用 CPU | 重计算任务拖慢 API 响应 |
| N-2 | DB 与 Worker 共用磁盘 IO | 大文件读写影响数据库 |
| N-3 | 单机磁盘 | 无法扩容到 PB 级 |
| N-4 | Worker 扩容需同机共享存储 | 无法跨节点调度 |
| N-5 | 资源争抢无隔离 | 一个失控任务拖垮整个平台 |

## 二、目标架构：三层物理分离

- **控制面（管理节点）**：Web/Beat/Flower/Nginx + 云托管 DB/Redis。轻量，8C/16G，API 不吃资源。
- **数据面（任务节点池）**：Worker 按队列分组（analysis/download/sandbox/maintenance），HPA 按队列深度自动扩缩，挂载 NAS + OSS。
- **计算面（集群）**：Snakemake 流程容器化，提交到 Slurm/K8s Job，按任务拉起释放，64C/256G+。

数据流：管理节点 Worker 消费 Celery 队列 → 调用 Executor 提交到集群 → 集群跑 Snakemake → 结果写 NAS/OSS → Worker 轮询状态回写。

## 三、控制面设计（管理节点）

| 组件 | K8s 部署 | 规格 |
|------|---------|------|
| Web (FastAPI) | Deployment + HPA (3-20) | 2C/4G × N |
| Beat | Deployment (replicas=1) 或 K8s CronJob | 1C/1G |
| Flower | Deployment (replicas=1) | 1C/1G |
| Ingress | Ingress Controller + 云 SLB | - |
| PostgreSQL | **云 RDS 托管**（主从+PITR） | 8C/16G |
| Redis | **云 Redis 托管**（集群版） | 4G |

**Web 无状态化**：ProviderManager 单例改 Redis 缓存；会话全走 JWT + Redis 黑名单；大文件用 OSS 预签名 URL 直连，Web 不中转。

**Beat 高可用**：推荐 K8s CronJob 替代 Celery Beat（每定时任务独立 CronJob，K8s 保证单实例）；或 celery-beat-redbeat 多实例选举。

**Redis 用途分离**：Broker(db=1)/Result(db=2)/PubSub(db=3)/Cache(db=0)，万人级分独立实例避免相互影响。

## 四、数据面设计（任务节点池）

### 4.1 Worker 分组（按队列独立 Deployment）

- `analysis`（重计算）：16C/64G，replicas 2-10，nodeSelector compute-heavy
- `download`（IO 密集）：8C/16G，replicas 1-5
- `sandbox`（交互式）：4C/8G，replicas 1-5，用 gVisor runtimeClass
- `maintenance`（清理/对账）：1C/2G，replicas 1

### 4.2 HPA 按队列深度自动伸缩

用 Prometheus Adapter 暴露 `celery_queue_length` 自定义指标，HPA 按队列长度扩缩：队列 >10 扩容，<2 缩容，缩容冷却 5min，每次最多缩 50%。

### 4.3 Worker 镜像分层

- `Dockerfile.worker-base`：含 celery + snakemake 基础
- `Dockerfile.worker-analysis`：叠 conda 流程环境（或运行时 --use-conda 从 NAS 共享）

## 五、计算面设计（集群执行）

### 5.1 三种集群执行模式

**模式 A：Slurm 集群（已有 HPC）** — 新增 `SlurmExecutor`，生成 sbatch 脚本提交，轮询 sacct 状态，实时拉日志。

**模式 B：K8s Job（云原生，推荐）** — 新增 `K8sJobExecutor`，用 kubernetes Python SDK 创建 Job，每个任务一个 Pod，ttl_seconds_after_finished 自动清理。

**模式 C：Snakemake 原生后端（最省代码）** — Snakemake 8.0+ 原生支持 `--kubernetes` 或 `--profile slurm`，把每个 rule 变成 Pod/Job，无需自写 Executor。

### 5.2 流程容器化（关键前提）

每个 Snakemake 流程打包成独立镜像（`omichub/flow-rnaseq:v1.0`），`flows/*.yaml` 声明 `container_image` + `executor`（local/slurm/k8s），`registry.py` 注册三种执行器，`TaskService` 按 YAML 字段路由。

## 六、网络与存储拓扑

**网络隔离**（Namespace + NetworkPolicy）：
- `omichub-control`：web/beat/flower，仅允许 Ingress + 出站 DB/Redis/外网
- `omichub-compute`：worker-*，仅入站 Redis + 出站 NAS/OSS/集群
- `omichub-jobs`：K8s Job Pod，deny-all（仅 NAS/OSS，无外网）

**存储挂载**：

| 节点 | NAS 热 | NAS conda | OSS | 本地 ephemeral |
|------|--------|-----------|-----|---------------|
| Web | RO | - | 预签名 URL | - |
| Worker-analysis | RW | RO | RW | 临时 |
| Worker-sandbox | RO | - | - | 临时 |
| K8s Job | RW | RO | RW | 临时 |

## 七、落地路线

| 阶段 | 时间 | 目标 |
|------|------|------|
| 1 | 1 周 | 控制面上 K8s（Web/Beat/Flower，DB/Redis 云托管） |
| 2 | 1 周 | 数据面分离（Worker 独立 Deployment，NAS 接入） |
| 3 | 2 周 | 流程容器化（每流程打包镜像，YAML 声明 container_image） |
| 4 | 1 周 | 执行器扩展（K8sJobExecutor 或 SlurmExecutor，registry 注册） |
| 5 | 1 周 | 队列分层 + HPA（多队列路由 + Prometheus 自定义指标） |
| 6 | 持续 | 弹性优化（抢占式实例、成本监控） |

## 八、万人级容量规划

| 维度 | 估算 | 资源 |
|------|------|------|
| 日活用户 | 1000 | Web 5 副本 × 2C/4G |
| 并发任务 | 50 | analysis Worker 8 副本 × 16C/64G |
| 任务队列峰值 | 200 | Redis Broker 8G |
| 日新增数据 | 500GB | NAS 5TB + OSS 50TB |
| 并发 AI 对话 | 100 | LLM 限流 + 队列 |
| DB 连接 | 200 | PgBouncer 连接池 |

**弹性策略**：分析 Worker 队列 >10 扩容 <2 缩容冷却 5min；下载 Worker 固定 2 副本；沙盒用 K8s Job per 执行无常驻 Pod；凌晨低峰分析 Worker 缩到 2 省 75% 成本。

## 九、总结

管理节点与任务节点分离是万人级扩展的**架构基石**：

1. **控制面轻量化**：Web 只做 API + 编排，3-20 副本弹性
2. **数据面可扩展**：Worker 按队列分组，HPA 按队列深度自动扩缩
3. **计算面集群化**：Snakemake 流程容器化，提交到 Slurm/K8s Job，按任务拉起释放
4. **存储解耦**：NAS 共享热数据 + OSS 归档冷数据，ReadWriteMany 支撑跨节点调度
5. **网络隔离**：Namespace + NetworkPolicy，三面网络隔离

当前 `BaseExecutor` 抽象设计良好，新增 `SlurmExecutor`/`K8sJobExecutor` 即可，业务层（TaskService/TaskDomainService）无需大改。最大工作量在**流程容器化**与**存储抽象层落地**两项。
