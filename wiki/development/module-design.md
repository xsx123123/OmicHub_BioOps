# 模块设计与接入

新增或重构模块前，先在 `docs/` 的非归档位置完成设计文档，再开始编码。已有模块可在对应目录的
README、架构设计和测试中补充或更新设计说明；不要把日期归档当作唯一规范来源。

## 设计原则

| 原则 | 要求 |
|---|---|
| 分层清晰 | HTTP/API、应用服务、领域模型、基础设施各司其职 |
| 前后端契约优先 | 先定义 DTO、错误语义、权限，再实现页面 |
| 渐进式接入 | 复用现有认证、配置、任务、上传能力 |
| 配置外置 | 可运营内容放入 `tool_configs/`，密钥放入环境变量 |
| 默认安全 | 用户数据、任务、管理接口必须认证、授权、校验所属关系 |
| 可验证 | 每个模块写明验收标准与验证命令 |

## 模块设计文档模板

```md
# {模块中文名} 设计文档

## 1. 背景与目标
## 2. 业务模型与状态
## 3. 架构与目录
## 4. API 契约
## 5. 前端交互
## 6. 数据与安全
## 7. 实施步骤与验收
```

## 开始编码前的 8 个评审问题

1. 该能力属于平台业务、管理功能、生信工具、分析流程还是外部集成？
2. 谁可以看、创建、修改、删除和执行？资源所有权如何验证？
3. API 输入输出、分页/筛选、错误码和异步状态是什么？
4. 哪些数据需要持久化，哪些放 Redis/文件系统，保留和清理策略是什么？
5. 是否需要 Celery、WebSocket、Snakemake、Docker 或第三方 API？失败、超时和重试怎么处理？
6. 前端入口在哪里，如何在亮/暗主题和移动端呈现？
7. 哪些现有服务、组件、配置或文档能够复用？
8. 如何验证功能、权限、异常路径和回归风险？

## 生信工具强制基线

- 在 `tool_configs/tools_setting.yaml` 注册，必须指定 `group`。
- `group` 透传链路：YAML → Pydantic → DTO → API → 前端 `ToolItem`。
- 图形绘制工具必须形成“导入/粘贴/示例 → 列映射 → 校验 → 绘图 → 结果表 → PNG/SVG 导出”闭环。
