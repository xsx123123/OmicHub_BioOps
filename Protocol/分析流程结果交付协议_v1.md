## 一、背景与目标

### 1.1 问题陈述

「结果报告中心」（`/reports`，*查看和管理所有分析生成的报告，支持在线预览和下载*）需要承接分析中心所有流程的分析结果。当前流程结果到报告中心的链路**没有正式协议**，只有三条隐式约定：

| # | 现状约定 | 生产方 | 平台是否消费 |
|---|---------|--------|-------------|
| 1 | `{data_deliver}/Analysis_Report/index.html` 存在性 | RNAFlow `Report` rule（Quarto 容器） | ✅ `ReportService` 以"文件是否存在"判定 completed/failed，并作为预览文件 |
| 2 | `{data_deliver}/report_data/project_summary.json` | RNAFlow `generate_docker_json` rule | ✅ 仅取 `project_meta.client/species/genome_version` 与 `stats.total_samples` 拼标题和描述 |
| 3 | `{data_deliver}/delivery_manifest.json` + `.md5` | `rnaflow-cli deliver`（Rust 工具） | ❌ **平台完全不读** |

这套隐式约定存在五个明确的问题：

1. **信息量不足**：`reports` 表只登记了 1 个 HTML 文件（`report_files` 单行），样本列表、比较组、结果文件清单（DEG 表、表达矩阵、QC 报告）全部丢失，报告中心无法展示"相关结果的路径"，下载入口也只有主报告一个。
2. **路径约定不一致**：平台在 `work_dir`（`users/{uid}/tasks/{tid}/work/{flow_id}`）下扫描 `Analysis_Report/index.html`，而流程产物实际写在 `data_deliver`——`generic_builder` 的兜底值是 `work_dir.parent/data_deliver`，MAS 容器模式下又固定为 `/workspace/results`。三者未必同目录，扫描命中靠巧合。
3. **上下文不透传**：平台提交任务时生成的 `config.yaml` 里**没有** `task_id` / `user_id`，流程无从知道自己属于哪个平台任务、哪个用户。一旦流程跑在远端计算节点（跨服务器部署），"扫描目录"这条路就彻底断了。
4. **失败无结构**：流程失败时只有日志文本（`task.error_message` 截断 2000 字符），报告中心无法展示"失败在哪个阶段/哪条规则"。
5. **不可扩展**：字段硬编码在 `ReportService` 的扫描逻辑里，ATACFlow、单细胞等新流程没有表达自身结果（peak 文件、细胞矩阵）的位置。

### 1.2 目标

定义**一份 JSON 交付清单（Result Manifest）**作为流程 → 平台的唯一正式契约：

- **一个文件**：`{data_deliver}/result_manifest.json`，由流程在收尾阶段原子写出；
- **双向解耦**：流程不依赖平台任何 API，平台不依赖流程内部目录结构（只依赖 manifest 声明的路径）；
- **信息完整**：样本 ID、分析用户、样本数量、网页报告、网页报告路径、相关结果路径——一次交付全部携带；
- **双通道**：v1.0 文件通道（同文件系统，零依赖）；v1.1 预留 HTTP 推送通道（跨服务器 / 主动回调）；
- **可扩展**：语义化版本 + 宽容读取 + 开放枚举 + 流程自定义命名空间，新流程接入不需要改平台代码。

### 1.3 结论先行（回答需求疑问）

> "最终分析流程是不是需要将结果的相关信息使用 JSON 传递给后端？是不是包含样本 ID & 分析用户 & 样本数量 & 网页报告 & 网页报告路径 & 相关结果的路径？"

**是。** 这正是本协议的核心：流程在成功/失败收尾时写出一份 `result_manifest.json`，平台解析后落库到 `reports` / `report_files` 表。你列的六项信息在 Schema 中的落点：

| 需求信息 | Schema 落点 |
|---------|------------|
| 样本 ID | `samples[]`（sample / sample_name / group 逐条列出） |
| 分析用户 | `platform.user_id`（平台提交时注入 config，流程原样回显）+ `project.client`（业务侧客户名） |
| 样本数量 | `stats.sample_count` / `stats.group_count` |
| 网页报告 | `report`（格式、标题、大小、是否含 AI 解读） |
| 网页报告路径 | `report.entry`（相对 data_deliver 的路径，如 `Analysis_Report/index.html`） |
| 相关结果路径 | `files[]`（逐文件：相对路径、类型、类别、大小、md5、说明） |

### 1.4 与 FlowFrame 框架的分工

本协议与 `Protocol/FlowFrame/Flow_framework.md`（Flow 家族通用流程架构规范，下文简称 **FlowFrame**）是上下游关系而非重叠：

| | FlowFrame | ARDP（本协议） |
|---|-----------|----------------|
| 治理范围 | 流程**内部**架构：入口 snakefile 八步序列、配置四件套、01–03 通用层、`AnalysisTargets()`/`DataDeliver()` 目标生成系统、deliver/report 通用接口 | 流程 → CygnusX 平台的**结果交付**：`result_manifest.json` schema、传输通道、平台注册契约 |
| 适用对象 | Flow 家族全体成员（RNAFlow / SCRNAFlow / BTCRFlow / ATACFlow / WGSFlow） | Flow 家族成员 + 所有接入分析中心的流程（含非 Flow 家族流程） |
| 交界面 | `N-1.deliver.smk`（交付层）/ `N.Report.smk`（报告层） | manifest 写出（流程侧）/ `register_from_manifest()`（平台侧） |

协调原则：

- Flow 家族流程须先满足 FlowFrame §12.3 / §16.10 的接入判定，本协议 §9 清单在其之上**追加**；
- 本协议的命名约定（比较组命名 §4.6、模块键 §4.9、交付清单格式 §6.5）以 FlowFrame 强制条款为准；
- 两条 HTTP 通道职责分离：运行中进度走 FlowFrame §13.5 监控事件（`cygnusx.workflow_event.v1`），终态交付走本协议 manifest（§3.3、§6.1、§6.3）。

## 二、总体架构

### 2.1 数据流全景

```
┌─────────────── 提交阶段（平台 → 流程）────────────────┐
│  前端/AI 提交                                          │
│      │                                                 │
│      ▼                                                 │
│  TaskService.submit()                                  │
│      ├─ 生成 config.yaml                               │
│      │   └─ ★ 注入 platform 上下文块:                  │
│      │        { task_id, user_id, flow_id,             │
│      │          flow_version, submitted_by, server }   │
│      ├─ 生成 samples.csv / contrasts.csv               │
│      └─ 投递 Celery → Snakemake                        │
└────────────────────────────────────────────────────────┘
                         │
┌─────────────── 执行阶段（流程内部）────────────────────┐
│  Snakemake: QC → Mapping → RSEM → DEG → … → Report     │
│  流程对平台业务无感知，仅：                            │
│    1) 原样保留 config.platform 块                      │
│    2) 收集产物清单与统计                               │
└────────────────────────────────────────────────────────┘
                         │
┌─────────────── 交付阶段（流程写出）────────────────────┐
│  onsuccess / onerror（或收尾 rule）                    │
│      └─ ★ 原子写出 {data_deliver}/result_manifest.json │
│           (tmp 文件 + os.replace 原子改名)             │
└────────────────────────────────────────────────────────┘
                         │
┌─────────────── 注册阶段（平台消费）────────────────────┐
│  Celery 回调 (analysis.py, Snakemake 退出后)           │
│      └─ ReportService.register_from_manifest()         │
│           ├─ 发现 manifest（见 6.2 搜索顺序）          │
│           ├─ 校验 (manifest_version / 必填 / 路径安全) │
│           ├─ upsert reports（task_id 幂等键）          │
│           ├─ upsert report_files（files[] 逐条登记）   │
│           └─ 无 manifest → 回退旧约定（index.html 扫描）│
└────────────────────────────────────────────────────────┘
                         │
┌─────────────── 展示阶段（前端，现状不变）──────────────┐
│  /reports → GET /api/v1/reports（列表/筛选/统计）      │
│  预览 → GET /reports/{id}/preview（JWT, iframe srcdoc）│
│  下载 → GET /reports/{id}/files/{fid}/download（JWT）  │
└────────────────────────────────────────────────────────┘
```

### 2.2 设计原则

| 原则 | 说明 |
|------|------|
| **Manifest 优先，约定兜底** | 平台永远先找 manifest；找不到时回退到现有 `index.html` + `project_summary.json` 扫描，保证存量任务与未改造流程不受影响 |
| **平台注入，流程回显** | `task_id`/`user_id` 等身份信息由平台写进 config，流程不理解、不修改、原样回显。流程永远不需要调用平台 API 才知道"我是谁" |
| **相对路径** | manifest 内一切产物路径相对 `data_deliver` 根目录，交付目录整体迁移/打包后依然有效 |
| **声明式文件清单** | 平台只登记/服务 manifest 声明的文件，不做全盘目录扫描（可预期、可审计） |
| **失败也是一份交付** | 失败收尾同样写 manifest（`run.status=failed` + `error` 块），报告中心能展示失败原因而不只是一条截断日志 |
| **幂等注册** | 以 `task_id` 为幂等键 upsert，同任务的重试/补登记不产生重复报告记录；用户重跑产生新 `task_id`，按版本树挂接（见 §6.4） |

## 三、交付文件规范

### 3.1 文件位置与命名

| 项 | 规定 |
|----|------|
| 文件名 | 固定 `result_manifest.json`（不可配置，保证平台可发现） |
| 位置 | `{data_deliver}/result_manifest.json`，即交付目录**根**下 |
| 编码 | UTF-8，无 BOM，`\n` 换行 |
| 格式 | 合法 JSON（RFC 8259），顶层必须是 object；建议 2 空格缩进便于人工排查 |
| 大小 | SHOULD < 256 KB；MUST < 1 MB（samples 极多时裁剪 `files[]`，不要裁剪 `samples[]`） |
| 字段命名 | snake_case |
| 时间戳 | RFC 3339，UTC 带偏移，如 `2026-07-26T08:30:00+00:00` |
| 文件大小 | 字节数（整数） |
| 路径 | 相对 `{data_deliver}` 根的 POSIX 相对路径（`/` 分隔），禁止 `..` 逃逸（见 §10） |

### 3.2 原子写出（MUST）

manifest 是平台判定"交付完成"的信号，**必须原子写出**，防止平台读到半截文件：

```python
import json, os

def write_manifest_atomic(deliver_dir: str, manifest: dict) -> str:
    target = os.path.join(deliver_dir, "result_manifest.json")
    tmp = target + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(manifest, f, ensure_ascii=False, indent=2)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, target)   # POSIX 原子改名
    return target
```

### 3.3 写出时机

- **成功**：所有交付产物（HTML 报告、结果文件、`delivery_manifest.json`）就绪**之后**写出；manifest 是交付的"最后一笔"。
- **失败**：在 Snakemake `onerror` 中写出可写的部分（`run.status="failed"` + `error` 块），允许 `report`/`files` 缺失。
- **不存在"只成功一半"**：如果 HTML 报告未生成但流程退出码为 0，`run.status` 应如实写 `completed_no_report`，由平台决定展示策略。

**终态语义（MUST）**：manifest 仅表达终态（`completed` / `completed_no_report` / `failed` / `aborted`）。进行中的进度由任务系统承载，不属于本协议范围：Flow 家族流程由 `snakemake_logger_plugin_rich_loguru` 插件以 `cygnusx.workflow_event.v1` 事件推送至 `/api/v1/workflow-monitor/events`（FlowFrame §13.5）；平台 Celery 编排的任务由 Celery 事件 / 任务日志流承载。流程**不得**在运行中途写出或推送中间态 manifest。平台侧 `reports.status=generating` 由任务系统在创建报告行时写入、由任务事件驱动流转，manifest 只在终态出现一次（两者关系另见 §6.1 边界说明与 §6.3 澄清）。

## 四、Manifest Schema v1.0

### 4.1 顶层结构

```jsonc
{
  "manifest_version": "1.0",           // 必填，协议版本
  "kind": "cygnusx.analysis.result",   // 必填，固定值，用于将来多类型清单共存
  "platform":   { /* §4.2 平台上下文（平台注入，流程回显） */ },
  "run":        { /* §4.3 本次运行的身份与结局 */ },
  "project":    { /* §4.4 项目业务元信息 */ },
  "samples":    [ /* §4.5 样本清单 */ ],
  "stats":      { /* §4.5 汇总统计 */ },
  "comparisons":[ /* §4.6 比较组（可选） */ ],
  "report":     { /* §4.7 网页报告 */ },
  "files":      [ /* §4.8 结果文件清单 */ ],
  "modules":    { /* §4.9 流程模块执行情况（可选，流程特异） */ },
  "software":   { /* §4.10 软件版本（可选） */ },
  "metrics":    { /* §4.11 流程特异指标（可选） */ },
  "error":      { /* §4.12 失败信息（status=failed 时必填） */ },
  "extra":      { /* §4.13 自由扩展区 */ }
}
```

**必填块**：`manifest_version`、`kind`、`platform`、`run`、`project`、`stats`。
**条件必填**：`run.status == "failed"` 时 `error` 必填；`run.status == "completed"` 时 `report` 必填（除非 `completed_no_report`）。
其余均为可选，但**强烈建议**提供 `samples` 与 `files`——它们是报告中心价值的主体。

### 4.2 `platform` — 平台上下文（必填）

**由平台在提交时注入到流程 `config.yaml` 的 `platform` 键，流程原样回显。** 这是流程与平台任务关联的唯一纽带，流程不应修改其中任何字段。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `task_id` | string(uuid) | ✅ | 平台任务 ID（`tasks.id`） |
| `user_id` | string(uuid) | ✅ | 提交用户 ID（**"分析用户"**） |
| `submitted_by` | string | ⬜ | 提交用户名（冗余展示用，可空） |
| `flow_id` | string | ✅ | 流程标识（下划线纲目，与 `flows/*.yaml` 的 `meta.id` 一致）；Flow 家族枚举：`rna_seq` / `atac_seq` / `scrna_seq` / `btcr_seq` / `wgs` |
| `flow_version` | string | ⬜ | 平台侧 flow 定义版本，如 `2.2.0` |
| `server_id` | string | ⬜ | 平台实例标识，跨服务器推送时用于区分来源 |
| `submitted_at` | string(datetime) | ⬜ | 提交时间 |

```json
"platform": {
  "task_id": "3f2b…-…-c91a",
  "user_id": "a7e1…-…-44d2",
  "submitted_by": "zhangjian",
  "flow_id": "rna_seq",
  "flow_version": "2.2.0",
  "server_id": "cygnusx-main",
  "submitted_at": "2026-07-26T06:00:00+00:00"
}
```

> 独立运行流程（CLI 直跑、无平台参与）时：`task_id`/`user_id` 允许为 `null`，平台侧通过 HTTP 通道导入时须显式指定归属用户（见 §6.3）。

> **与监控通道对应**：`task_id` / `user_id` / `flow_id` 与 `monitor_config.yaml` 的 `cygnusx_task_id` / `cygnusx_user_id` / `cygnusx_flow_id`（FlowFrame §13.5）一一对应——平台在同一次提交动作中一致地注入两者，使运行中监控事件与终态 manifest 可按 `task_id` 关联。

### 4.3 `run` — 运行身份与结局（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `run_id` | string | ⬜ | 流程内部运行标识（如 RNAFlow MCP 的 run_id / Snakemake run uuid），无则与 `task_id` 相同 |
| `pipeline` | object | ✅ | `{ "name": "RNAFlow", "version": "0.1.9" }`；`version` 取自 `config.pipeline_version` 单一版本来源（FlowFrame §3.3，格式 `<X>Flow vX.Y.Z`） |
| `engine` | string | ⬜ | 工作流引擎，如 `snakemake-9.17.3` / `nextflow-24.04` |
| `status` | enum | ✅ | `completed` / `completed_no_report` / `failed` / `aborted` |
| `exit_code` | int | ⬜ | 引擎进程退出码 |
| `started_at` | datetime | ⬜ | 实际开始时间 |
| `finished_at` | datetime | ✅ | 收尾写出时间 |
| `duration_seconds` | int | ✅ | 运行耗时（秒），报告卡片直接展示 |
| `execution_mode` | enum | ⬜ | `local` / `cluster` / `mas`（容器 worker） |
| `output_dir` | string | ⬜ | 流程侧记录的交付目录路径，仅作排查参考，平台不以它为定位依据（平台定位 manifest 只信任务记录的 `result_dir`，见 §6.2） |
| `work_dir` | string | ⬜ | 中间结果目录绝对路径 |
| `log_path` | string | ⬜ | 主日志相对路径，如 `Analysis_Report/pipeline.log` |

**`status` 语义**：

| 值 | 含义 | 平台映射 `reports.status` |
|----|------|--------------------------|
| `completed` | 成功且 HTML 报告就绪 | `completed` |
| `completed_no_report` | 流程成功但报告生成被禁用/失败（如 `report: false`），或集群/无容器环境下报告降级为仅 `project_summary.json`（FlowFrame §6.5 降级路径） | `completed`（无预览按钮） |
| `failed` | 流程失败 | `failed` |
| `aborted` | 用户/系统中止 | `failed`（描述注明中止） |

### 4.4 `project` — 项目业务元信息（必填）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `project_name` | string | ✅ | 项目名，如 `PRJNA1224991` |
| `title` | string | ⬜ | 报告卡片标题；缺省时平台拼 `{client} - {flow_name} 分析报告` |
| `description` | string | ⬜ | 卡片描述；缺省时平台自动拼物种/基因组/样本数 |
| `client` | string | ⬜ | 客户/课题组（业务语义的"用户"，自由文本） |
| `species` | string | ⬜ | 物种 |
| `genome_version` | string | ⬜ | 参考基因组版本 |
| `library_type` | string | ⬜ | 文库类型，如 `fr-firststrand` |
| `tags` | string[] | ⬜ | 自由标签，供前端筛选/展示 |

### 4.5 `samples` 与 `stats` — 样本清单与统计

`samples` 是数组（强烈建议提供），每个元素：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `sample` | string | ✅ | 样本 ID（与 FASTQ 前缀 / BAM 文件名一致的原始标识） |
| `sample_name` | string | ⬜ | 展示用短名 |
| `group` | string | ⬜ | 实验分组 |
| `extra` | object | ⬜ | 流程特异样本级信息（如 `reads: 45000000, mapping_rate: 0.93`），前端可按流程渲染 |

> Flow 家族流程：样本表除通用必填列 `sample, sample_name, group` 外的组学专用列（SCRNAFlow 的 `platform, chemistry, expect_cells`、BTCRFlow 的 `platform, path` 等，FlowFrame §8.2）一律放入 `samples[].extra`，平台不为组学扩展列单独加字段。

`stats`（必填）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `sample_count` | int | ✅ | 样本数量 |
| `group_count` | int | ⬜ | 分组数 |
| `comparison_count` | int | ⬜ | 比较组数 |

`stats` 允许流程附加自定义键（如单细胞类流程的 `cell_count`、`median_genes_per_cell`）；平台不校验自定义键语义，原样存入 `result_meta`（§7.1）。观测规模过大（如万级细胞）时不要逐一展开到 `samples[]`，应使用聚合统计（另见 §5.4）。

```json
"samples": [
  { "sample": "L1MKL2302060-CKX2_23_15_1", "sample_name": "CKX2_1", "group": "CKX2" },
  { "sample": "L1MKL2302063-Wo408_1", "sample_name": "Wo408_1", "group": "Wo408" }
],
"stats": { "sample_count": 12, "group_count": 4, "comparison_count": 1 }
```

**仲裁规则**：`stats.sample_count` 与 `len(samples)` 不一致时（`samples` 已提供的前提下），平台以 `len(samples)` 为准登记并记录 WARNING 日志，**不判 manifest 无效**；仅提供 `stats` 未提供 `samples` 时以 `stats.sample_count` 为准。

### 4.6 `comparisons` — 比较组（可选）

差异分析类流程建议提供；`name` 约定 **`{Treat}_vs_{Control}`**（效应方向 = Treat 相对 Control，FlowFrame §8.5 强制条款）。存量流程的历史产物可能是反向命名（`Control_vs_Treat`，FlowFrame §15.3 已列为对齐项），平台不解析比较组名方向性、仅原样展示与深链。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | ✅ | 比较组名，如 `CKX2_vs_Wo408` |
| `control` | string | ✅ | 对照组 group 名 |
| `treat` | string | ✅ | 实验组 group 名 |
| `deg_count` | int | ⬜ | 差异基因数（可再拆 `up`/`down`） |
| `result_path` | string | ⬜ | 该比较组主结果相对路径（冗余于 `files[]`，方便深链） |

### 4.7 `report` — 网页报告（条件必填）

"网页报告"与"网页报告路径"的落点。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `format` | enum | ✅ | `html`（v1.0 仅要求平台支持 html；`pdf`/`notebook` 为预留值） |
| `entry` | string | ✅ | 入口文件**相对路径**，如 `Analysis_Report/index.html` |
| `title` | string | ⬜ | 报告内部标题 |
| `self_contained` | bool | ⬜ | 是否单文件自包含（RNAFlow Quarto `embed-resources: true` → `true`）。**平台预览的前提**：非自包含报告必须保证同目录资源完整，预览端点会按 entry 所在目录解析相对资源 |
| `size_bytes` | int | ⬜ | HTML 文件大小 |
| `generator` | object | ⬜ | `{ "name": "quarto", "version": "1.8.26" }` |
| `has_ai_interpretation` | bool | ⬜ | 仅当 AI 解读章节由流程自身生成时置 `true`；平台后置 AI 服务追加的解读由平台侧在 `reports` 行自行维护该标记，不通过修改 manifest 表达（双重来源的优先级见 §7.1） |

```json
"report": {
  "format": "html",
  "entry": "Analysis_Report/index.html",
  "title": "PRJNA1224991 RNA-seq 分析报告",
  "self_contained": true,
  "size_bytes": 18350021,
  "generator": { "name": "quarto", "version": "1.8.26" },
  "has_ai_interpretation": true
}
```

### 4.8 `files` — 结果文件清单（强烈建议）

"相关结果的路径"的落点。平台会把本数组**逐条登记进 `report_files` 表**（`is_primary` 指向 `report.entry` 对应条目），每个条目对应一个下载入口。

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `name` | string | ✅ | 展示名，如 `DEG 结果（CKX2_vs_Wo408）` |
| `path` | string | ✅ | 相对路径（文件或目录；目录以 `/` 结尾，平台按目录打包下载） |
| `type` | enum | ✅ | `html` / `pdf` / `csv` / `tsv` / `xlsx` / `png` / `zip` / `dir` / `other`（**开放枚举**，未知值平台按 `other` 渲染） |
| `category` | enum | ⬜ | 结果类别（**开放枚举**），见下表 |
| `size_bytes` | int | ⬜ | 文件大小 |
| `md5` | string | ⬜ | 文件 MD5（目录为空）；建议提供，与 `delivery_manifest.md5` 对齐 |
| `description` | string | ⬜ | 一句话说明 |
| `is_primary` | bool | ⬜ | 主文件，有且仅有一个为 `true`（应与 `report.entry` 一致）；缺省时平台把 `report.entry` 对应条目标为主 |
| `group` | string | ⬜ | 归属比较组/模块，供前端分组展示 |

**`category` 推荐词表**（可扩展，平台不强制）：

```
raw_data / qc / mapping / expression / deg / enrichment /
splicing / variant / fusion / assembly / report / log / other
```

```json
"files": [
  { "name": "HTML 分析报告", "path": "Analysis_Report/index.html", "type": "html",
    "category": "report", "size_bytes": 18350021, "is_primary": true },
  { "name": "DEG 结果（CKX2_vs_Wo408）", "path": "05_DEG/DESEQ2/CKX2_vs_Wo408_DEG.csv",

    "md5": "d41d8cd98f00b204e9800998ecf8427e", "group": "CKX2_vs_Wo408" },
  { "name": "全部比较组 DEG 统计", "path": "05_DEG/DESEQ2/All_Contrast_DEG_Statistics.csv",
    "type": "csv", "category": "deg", "size_bytes": 15234 },
  { "name": "表达矩阵（TPM）", "path": "03_Expression/Matrix/merge_rsem_tpm.tsv",
    "type": "tsv", "category": "expression", "size_bytes": 9821345 },
  { "name": "GO 富集结果", "path": "06_Enrichments/", "type": "dir", "category": "enrichment" },
  { "name": "Overall MultiQC 报告", "path": "01_QC/Overall_MultiQC/multiqc_report.html",
    "type": "html", "category": "qc", "size_bytes": 5234881 },

    "category": "log", "size_bytes": 45123 }

```

### 4.9 `modules` — 流程模块执行情况（可选，流程特异）

各流程自定义，平台原样存入 `reports` 的扩展字段、不解释语义，仅供前端按流程模板渲染。键为模块名，值至少含 `status`。Flow 家族流程的键**应当**与本流程 `MODULE_COLLECTORS` 注册表键一致（FlowFrame §5.1，如 `qc_clean` / `trimming` / `mapping` / `count` / `deg`），使模块开关、目标生成与报告展示共用同一套词汇：

```json
"modules": {
  "qc_clean":      { "status": "completed" },
  "mapping":       { "status": "completed", "tool": "STAR" },
  "count":         { "status": "completed", "tool": "RSEM" },
  "deg":           { "status": "completed", "tool": "DESeq2", "contrasts": 1 },
  "rmats":         { "status": "skipped", "reason": "config.rmats=false" },
  "gene_fusion":   { "status": "skipped" }
}
```

模块 `status` 推荐值：`completed` / `skipped` / `failed` / `warning`。

### 4.10 `software` — 软件版本（可选）

```json
"software": {
  "star": "2.7.11b", "rsem": "1.3.3", "deseq2": "1.42.0",
  "multiqc": "1.21", "fastp": "0.23.4"
}
```

### 4.11 `metrics` — 流程特异指标（可选）

供报告中心统计卡片 / AI 助手引用的结构化指标，键值扁平化：

```json
"metrics": {
  "mean_mapping_rate": 0.913,
  "mean_q30": 0.942,
  "total_deg_count": 1834,
  "median_genes_per_sample": 19204
}
```

### 4.12 `error` — 失败信息（failed/aborted 时必填）

```json
"error": {
  "stage": "mapping",
  "rule": "star_align",
  "message": "STAR exited with code 101: genome directory not found",
  "log_path": "Analysis_Report/pipeline.log",
  "failed_at": "2026-07-26T07:12:33+00:00"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `stage` | string | ⬜ | 失败阶段（对应 `modules` 键） |
| `rule` | string | ⬜ | 失败规则/进程名 |
| `message` | string | ✅ | 人类可读错误摘要（≤ 2000 字符） |
| `log_path` | string | ⬜ | 完整日志相对路径 |
| `failed_at` | datetime | ⬜ | 失败时间 |

### 4.13 `extra` — 自由扩展区

流程特异、尚未纳入标准 schema 的信息一律放这里，**命名空间前缀**避免冲突：

```json
"extra": {
  "x_rnaflow": { "loki_dashboard_url": "https://grafana.example/d/xxx" },
  "x_internal": { "cluster_job_id": "slurm-88431" }
}
```

平台对 `extra` 只存储、不解释。

## 五、兼容性与可扩展性规则

### 5.1 版本管理

`manifest_version` 采用 `MAJOR.MINOR`：

- **MINOR 升级**（1.0 → 1.1）：只增字段、只增枚举值。平台**必须**忽略不认识的字段（宽容读取），流程**不得**复用已有字段语义。
- **MAJOR 升级**（1.x → 2.0）：允许破坏性变更。平台按 major 分派解析器；无法识别的 major 版本 → 走兜底注册（见 §6.4）并记录告警日志，不使任务回调失败。

平台声明支持矩阵于 `report_service.py` 头部常量：

```python
SUPPORTED_MANIFEST_VERSIONS = {"1.0"}   # 精确匹配 MAJOR.MINOR
TOLERATED_MAJOR = 1                     # major 相同则尝试宽容解析
```

### 5.2 读取宽容规则（平台侧 MUST）

1. 未知顶层块 / 未知字段：忽略，不报错。
2. 开放枚举（`files[].type`、`files[].category`、`modules.*.status`）出现未知值：分别回退为 `other` / `other` / `warning`。
3. 可选块整体缺失：按缺省渲染，不影响注册。
4. 必填字段缺失/类型错误：**整份 manifest 判为无效**，走 §6.4 兜底，并把校验错误写入任务日志（`source="report"`）。

### 5.3 写出约束（流程侧 MUST）

1. 不得输出 `null` 以外的未知"占位值"（如 `"N/A"`、`"-"`）到数值字段——无值用 `null` 或省略字段。
2. 不得在 manifest 中携带平台无法展示的大体量数据（表达矩阵内容、序列）——只放**路径**。
3. 路径必须实际存在（除失败场景），平台注册时会做存在性校验，缺失条目登记为"文件已丢失"状态而非静默丢弃。

### 5.4 扩展路径（不需要改协议的情形）

| 需求 | 扩展方式 |
|------|---------|
| 新流程（ATACFlow / scRNAFlow）接入 | 实现必填块 + 自己的 `modules`/`metrics`/`extra.x_*`，平台零改动 |
| 报告新增 PDF 版本 | `files[]` 加一条 `type: "pdf"`；`report.format` 仍指主 HTML |
| 多样本级 QC 指标 | `samples[].extra` 内自由扩展 |
| 新文件类别 | `category` 直接用新词，无需等平台发版 |
| 大规模观测级统计（万级细胞） | 放 `metrics` / `stats` 自定义键，不进 `samples[]` |

## 六、传输通道与注册协议

### 6.1 通道总览

| 通道 | 版本 | 适用场景 | 触发方 |
|------|------|---------|--------|
| **A. 文件通道** | v1.0（默认） | 流程与平台共享文件系统（本地 / NAS 挂载） | 平台拉取（Celery 回调） |
| **B. HTTP 推送通道** | v1.1（预留设计） | 跨服务器计算节点、结果目录不回传、外部流程导入 | 流程推送 |

两通道**注册逻辑完全一致**（同一个 `register_from_manifest()`），差异只在"manifest 文本从哪里来"。

> **与运行监控通道的边界**：FlowFrame §13.5 定义的 `POST /api/v1/workflow-monitor/events` 接收**运行中进度事件**（`cygnusx.workflow_event.v1`，高频、流式、允许丢失重推）；本协议的结果注册通道接收**终态 manifest**（一次性、幂等、必须持久化）。两者共用 `task_id` / `user_id` / `flow_id` 身份三元组、可互相关联，但**不互相替代**：监控通道不接受 manifest，本协议通道不接受中间态事件。

### 6.2 通道 A：文件发现顺序（平台侧）

Celery 回调中按序查找，命中即停：

```
1. {task.result_dir}/result_manifest.json              # result_dir = 提交时持久化的 data_deliver（正式条款，见下）
2. {work_dir}/result_manifest.json                     # 直接在工作目录
3. {work_dir}/../data_deliver/result_manifest.json     # generic_builder 兜底布局
4. {work_dir}/data_deliver/result_manifest.json        # 嵌套布局
5. 以上目录中的 Analysis_Report/index.html + report_data/project_summary.json   # 旧约定兜底
```

**正式条款**：`generic_builder` 计算出的 `data_deliver` **必须**持久化到 `tasks` 记录（新列 `result_dir`）。平台定位 manifest 只信 `result_dir`（第 1 条）；第 2–4 条仅作为 `result_dir` 落库前存量任务的兼容兜底，新任务不允许依赖猜测路径。manifest 内的相对路径（`report.entry`、`files[].path`）一律以 `result_dir` 指向的目录为根解析。

### 6.3 通道 B：HTTP 推送（v1.1 预留）

为 `docs/分析中心_Celery_Snakemake_跨服务器部署实施方案.md` 中的跨节点场景预留：

```
POST /api/v1/internal/reports/ingest
Authorization: Bearer <CYGNUSX_INGEST_TOKEN_{NODE}>   # 每计算节点独立令牌，非用户 JWT（令牌模型见下）
Content-Type: application/json

body = result_manifest.json 全文
```

平台侧约束：

- 幂等键 `platform.task_id`；重复提交执行 upsert（状态可更新：generating → completed → failed 不允许回退到 generating）。澄清：这里的 `generating` 指平台侧 `reports` 行在任务提交时由任务系统创建的初始状态，其流转（generating → completed/failed）由**任务事件**驱动；manifest 本身只表达终态（§3.3），本协议不支持也不接受"进行中 manifest"的推送。
- `platform.user_id` 为 `null` 时拒绝（422）——推送方必须声明归属，或由令牌绑定的服务账号代为归属。
- 路径语义：推送场景下 `files[].path` 统一为**共享存储相对路径**（相对平台与计算节点约定的共享存储根）；平台以存储根白名单为根解析并校验落点，**明确禁止**复用远端节点的本地绝对路径（如容器内 `/workspace/results/...`，见 §11.1 的回传映射）。`run.output_dir` 仅为排查参考（§4.3），不参与路径解析。
- 令牌模型：每计算节点签发**独立令牌**，可单独吊销，并绑定来源 `server_id`——请求体 `platform.server_id` 必须与令牌绑定值一致，不一致返回 403。所有节点共享单一令牌为**反模式**：吊销影响面等于全部算力，且事故无法按节点归因。
- 速率与体积：单请求 ≤ 1 MB；每 task 每分钟 ≤ 5 次。

流程侧推送实现放在收尾钩子的**可选分支**：配置了 `platform.callback_url` 才推送，推送失败不影响本地 manifest 写出（本地文件始终是事实来源）。

### 6.4 注册决策矩阵

先厘清两个概念，矩阵据此分列：

- **重复注册**（同一 `task_id` 再次到达）：仅发生于回调重试、通道 A/B 重复投递、人工补登记——执行 upsert；
- **重跑**：用户在分析中心"重新运行"会生成**新 `task_id`**（平台行为，与 manifest 无关）→ 新增 `reports` 行，`version` + 1、`parent_id` 指向首版，版本树语义不变。

| 情形 | 平台行为 |
|------|---------|
| manifest 有效，`status=completed` | upsert `reports`(completed) + 逐条登记 `files[]` → `report_files` |
| manifest 有效，`status=completed_no_report` | 同上，`reports.status=completed`，无 primary html 时预览按钮隐藏 |
| manifest 有效，`status=failed/aborted` | upsert `reports`(failed)，`description` 拼入 `error.message`，不登记 files（或仅登记日志条目） |
| manifest 存在但校验失败 | 旧约定兜底注册 + 任务日志 WARNING（附校验错误明细） |
| 无 manifest，有 `Analysis_Report/index.html` | 现状逻辑（`project_summary.json` 补元信息） |
| 两者皆无 | `reports.status=failed`，description 注明"未发现结果交付清单" |
| 同 `task_id` 重复注册（回调重试 / 补登记） | upsert：更新 status / 文件清单（先删旧 `report_files` 再插），`created_at` 不变 |
| 重跑（平台生成新 `task_id`） | 新增 `reports` 行：`version` + 1、`parent_id` 指向首版（版本树语义不变），与首行并存，互不覆盖 |

### 6.5 与 `delivery_manifest.json` 的关系

`delivery_manifest.json`（Flow 家族统一交付工具 `flow-deliver` 的产物；RNAFlow/ATACFlow 当前名为 `rnaflow-cli deliver`，按 FlowFrame §13.3 统一更名）继续作为**交付目录自身的完整性清单**存在，角色不变，格式遵循 FlowFrame §6.4：顶层 `pipeline` / `version` / `project_name` / `created_at`，`files[]` 逐条含 `source`（工作目录源路径）/ `delivered_path`（交付相对路径）/ `size_bytes` / `md5` / `action`（默认 `copy`，禁止默认 symlink 交付）。

`result_manifest.json` 是**面向平台的语义清单**（挑选平台需要展示/下载的子集并赋予类别与说明）。前者面向数据完整性，后者面向展示契约；`result_manifest` 可以把前者作为 `files[]` 的一条（`category: log`）登记，其 `delivered_path` 可直接复用为 `result_manifest.files[].path`。

## 七、平台侧消费契约

### 7.1 Manifest → 数据表映射

**`reports` 表**（现状 18 列，建议新增 `result_meta JSON` 扩展列承载 samples/comparisons/modules/metrics/extra）：

| reports 列 | 取值来源 |
|-----------|---------|
| `task_id` | `platform.task_id` |
| `user_id` | `platform.user_id` |
| `flow_id` | `platform.flow_id`（回退 task.flow_id） |
| `flow_name` / `flow_icon` | flow 定义（`flows/*.yaml`）——平台侧补，不信 manifest |
| `flow_version` | `platform.flow_version` 回退 flow 定义 |
| `title` | `project.title` → `{client} - {flow_name} 分析报告` |
| `description` | `project.description` → 自动拼 `物种 | 基因组 | 样本数` → `error.message`（失败时） |
| `status` | §4.3 映射表 |
| `sample_count` | `stats.sample_count`；与 `len(samples)` 不一致时按 §4.5 仲裁规则以 `len(samples)` 为准 |
| `duration` | `run.duration_seconds` |
| `completed_at` | `run.finished_at` |
| `parent_id` / `version` | 保留现状（版本树），与 §6.4 一致：用户重跑 = 平台生成新 `task_id` → 新 `reports` 行，`version` + 1、`parent_id` 指向首版；同 `task_id` 的 upsert 仅用于回调重试 / 补登记，不产生新 version |
| **新列** `result_meta` (JSON) | `{samples, comparisons, modules, software, metrics, extra, error}` 原样存入 |
| AI 解读标记 | 双重来源：manifest `report.has_ai_interpretation`（流程自身生成的解读，§4.7）+ 平台后置 AI 服务在 `reports` 行维护的标记；两者并存时**平台后置标记覆盖流程声明**（平台对已交付 manifest 只读，不回写） |

**`report_files` 表**：`files[]` 每个条目一行；`path` 存 `{result_dir}/{path}` 拼接后的规范化绝对路径（`result_dir` 见 §6.2 正式条款；注册时即解析，下载时仍走 `_resolve_report_path` 的存储根校验）。

### 7.2 预览与下载（不变）

- 预览：`GET /reports/{id}/preview` 读 `is_primary=true` 的 html 条目，`PlainTextResponse` → 前端 `<iframe srcdoc sandbox="allow-scripts allow-same-origin">`。`report.self_contained=false` 的报告，需要额外按 entry 目录提供相对资源的受控访问（v1.0 先要求流程产出自包含报告，RNAFlow 已满足）。
- 下载：`GET /reports/{id}/files/{file_id}/download`，`FileResponse`；目录条目（`type=dir`）由平台按需打包为 zip 流式返回（实现可后置）。
- 安全：路径必须落在 `storage_path` 根内（现状 `relative_to` 校验保留）；manifest 里的 `..` / 绝对路径条目直接判无效。

### 7.3 前端增量（可分期）

v1.0 前端**零改动**即可获益（文件清单自动变多、描述更准确）。后续增量：

1. 卡片文件区按 `category` 分组展示（DEG / 表达 / QC…）；
2. 详情页渲染 `samples` 表与 `comparisons` 表（数据来自 `result_meta`）；
3. 失败卡片展示 `error.stage/rule/message`；
4. `has_ai_interpretation` 打 "AI 解读" 角标。

### 8.2 流程侧：新增 `generate_result_manifest` rule

manifest 是**交付层**的产物：目标注册进 `delivery_outputs(config)`（FlowFrame §5.4，与 `delivery_manifest.json` 同层），经 snakefile 的 `ALL_TARGETS` 唯一调用点复用，**禁止二次调用 `DataDeliver()`**（FlowFrame §5.6-2/5.6-3）。规则放在 `N-1.deliver.smk`；`report: true` 时以 input 函数声明 HTML 报告为依赖，DAG 会自动把报告 rule 排在本规则之前（执行顺序由依赖决定，与文件编号无关）；`report: false` 时该输入为空列表，manifest 照常产出（`run.status=completed_no_report`）：

```python
# rules/13.deliver.smk（示意）
def _manifest_inputs(wildcards):
    deliver = config['data_deliver']
    inputs = {
        "deliver": os.path.join(deliver, 'delivery_manifest.json'),
        "sample_sheet": config['sample_csv'],
        "contrasts": config.get('paired_csv', ''),
    }
    if config.get('report') is not False:   # report 层产物就绪后再写 manifest
        inputs["report_html"] = os.path.join(deliver, 'Analysis_Report/index.html')
        inputs["summary"] = os.path.join(deliver, 'report_data/project_summary.json')
    return inputs

rule generate_result_manifest:
    input: unpack(_manifest_inputs),
    output:
        manifest = os.path.join(config['data_deliver'], 'result_manifest.json'),
    run:
        import json, os, datetime
        import pandas as pd
        from pathlib import Path

        deliver = Path(config['data_deliver'])
        summary = json.loads(Path(input.summary).read_text(encoding='utf-8')) \
            if hasattr(input, 'summary') else {}
        df = pd.read_csv(input.sample_sheet)
        started = ...   # 从流程起始日志/记录取
        now = datetime.datetime.now(datetime.timezone.utc)

        # files[]：从 delivery_manifest.json 派生 + 人工赋类别
        html_path = deliver / 'Analysis_Report/index.html'
        has_report = html_path.exists()          # report: false 时降级 completed_no_report
        file_entries = [{
            "name": "HTML 分析报告", "path": "Analysis_Report/index.html",
            "type": "html", "category": "report", "is_primary": True,
            "size_bytes": html_path.stat().st_size,
        }] if has_report else []
        deg_dir = deliver / '05_DEG/DESEQ2'
        if deg_dir.exists():
            for f in sorted(deg_dir.glob('*_DEG.csv')):
                file_entries.append({
                    "name": f"DEG 结果（{f.stem.replace('_DEG','')}）",
                    "path": f.relative_to(deliver).as_posix(),
                    "type": "csv", "category": "deg",
                    "size_bytes": f.stat().st_size,
                    "group": f.stem.replace('_DEG', ''),
                })
        # ... expression / qc / enrichments 同理

        comparisons = []
        if input.contrasts and os.path.exists(input.contrasts):
            for _, row in pd.read_csv(input.contrasts).iterrows():
                comparisons.append({"name": f"{row.Treat}_vs_{row.Control}",   # Treat_vs_Control（FlowFrame §8.5）
                                    "control": row.Control, "treat": row.Treat})

        manifest = {
            "manifest_version": "1.0",
            "kind": "cygnusx.analysis.result",
            "platform": config.get("platform", {}),          # 原样回显
            "run": {
                "pipeline": {"name": "RNAFlow", "version": config["pipeline_version"]},
                "engine": f"snakemake-{snakemake.__version__}" if 'snakemake' in dir() else "snakemake",
                "status": "completed" if config.get("report") is not False else "completed_no_report",
                "finished_at": now.isoformat(),
                "duration_seconds": int((now - started).total_seconds()),
                "execution_mode": config.get("execution_mode", "local"),
                "output_dir": str(deliver),
                "log_path": "Analysis_Report/pipeline.log",
            },
            "project": {
                "project_name": config["project_name"],
                "client": config["client"],
                "species": config["species"],
                "genome_version": config["Genome_Version"],
                "library_type": config.get("Library_Types"),
            },
            "samples": [
                {"sample": r.sample, "sample_name": r.sample_name, "group": r.group}
                for r in df.itertuples()
            ],
            "stats": {
                "sample_count": len(df),
                "group_count": int(df['group'].nunique()),
                "comparison_count": len(comparisons),
            },
            "comparisons": comparisons,
            # report 块：report: false 时整体省略（配合 run.status=completed_no_report）
            **({"report": {
                "format": "html",
                "entry": "Analysis_Report/index.html",
                "self_contained": True,
                "size_bytes": html_path.stat().st_size,
                "generator": {"name": "quarto", "version": "1.8.26"},
            }} if has_report else {}),
            "files": file_entries,
            "modules": {
                "qc": {"status": "completed"},
                "deg": {"status": "completed" if config.get("deg") else "skipped"},
                "rmats": {"status": "completed" if config.get("rmats") else "skipped"},
                "gene_fusion": {"status": "completed" if config.get("gene_fusion") else "skipped"},
                "call_variant": {"status": "completed" if config.get("call_variant") else "skipped"},
            },
        }

        # 原子写出（§3.2）
        tmp = output.manifest + ".tmp"
        Path(tmp).write_text(json.dumps(manifest, ensure_ascii=False, indent=2), encoding='utf-8')
        os.replace(tmp, output.manifest)
```

```python
                    "duration_seconds": 0,
                    "output_dir": deliver,
                },
                "project": {"project_name": config.get("project_name", "")},
                "stats": {"sample_count": 0},
                "error": {
                    "rule": str(rule) if rule else None,
                    "message": (str(exception) or "pipeline failed")[:2000],
                },
            }
            tmp = os.path.join(deliver, "result_manifest.json.tmp")
            with open(tmp, "w", encoding="utf-8") as f:
                json.dump(manifest, f, ensure_ascii=False, indent=2)
            os.replace(tmp, os.path.join(deliver, "result_manifest.json"))
    except Exception:
        pass   # onerror 内绝不允许再抛异常
    raise      # 保持 Snakemake 失败语义
```

任何新流程接入报告中心，只需以下各项。**Flow 家族流程**（RNAFlow / SCRNAFlow / BTCRFlow / ATACFlow / WGSFlow）须先满足 FlowFrame §12.3 / §16.10 的接入判定，本清单在其之上追加：

## 十、安全与约束

1. **路径安全**：平台对 manifest 中所有路径执行规范化后校验 `relative_to(storage_root)`（沿用现状 `_resolve_report_path`）；含 `..`、绝对路径（`output_dir` 除外）、符号链接逃逸的条目 → 整份 manifest 判无效。
2. **内容安全**：manifest 不得包含序列数据、患者标识等敏感原文；只含路径、统计值与自由文本描述。`client` 等自由文本平台做长度截断（≤ 200 字符）与 HTML 转义后展示。
3. **体积约束**：`files[]` 建议 ≤ 500 条；超出时流程应只登记类别代表文件并保留 `delivery_manifest.json` 全量清单条目。
4. **预览沙箱**：iframe `sandbox="allow-scripts allow-same-origin"` 维持现状；自包含 HTML 内嵌脚本由流程构建链负责不自带恶意内容（内部流程，信任边界内）。
5. **幂等与竞态**：注册以 `task_id` 加锁 upsert；Celery 回调与 HTTP 推送并发时以数据库唯一约束兜底（`reports.task_id` 建议加唯一索引——注意版本树场景下为 `(task_id, version)` 唯一）。
6. **时钟**：流程节点时钟可能漂移，`duration_seconds` 以流程自测为准，平台不二次推算。
7. **交付链路留痕**：manifest 写出（文件通道）与推送（HTTP 通道）均应记录流程侧日志（路径、大小、推送响应码）；平台侧注册器将校验结果与登记明细写入任务日志（`source="report"`），保证交付链路全程可排障。

## 十一、与 MAS 编排及 Agent 消费的衔接

### 11.1 MAS 容器模式的产物回传映射

MAS 容器 worker 模式（`run.execution_mode: "mas"`）下，流程的 `data_deliver` 固定为容器内 `/workspace/results`（见 `src/cygnusx/infrastructure/mas/rnaflow.py` 预检契约）。该路径是节点本地路径，对平台无定位意义（这正是 §4.3 将 `output_dir` 降为参考信息的原因）。映射规则：

1. 节点结束时由 **MAS worker** 按产物回传链路把 `/workspace/results` 回传到用户 tasks 存储（`users/{user_id}/tasks/{task_id}/` 布局不变），回传落点即该任务的 `result_dir`；
2. manifest 的 `files[].path` 一律以**回传后**的交付目录为根（与 `result_manifest.json` 自身所在目录一致）——manifest 随产物一同回传，平台按 `result_dir`（§6.2）统一解析，无需感知容器内路径；
3. 回传顺序约束：其余产物先到位，`result_manifest.json` 最后到位（§3.2 的原子语义从"单文件"延伸为"单批次"）。

### 11.2 DAG 末节点统一交付

MAS 多节点 DAG 编排下，由**末节点**（汇聚节点）汇总各分支产物并产出 `result_manifest.json`，作为整个 Run 的统一交付物；报告中心经同一个 `register_from_manifest()` 链路承接 MAS 结果，**零改动**。`files[]` 条目的 `type` / `category` 词表与 MAS artifact schema 注册表对齐：两份词表**同源演进**（以本协议 §4.8 推荐词表为基线，MAS 注册表在同一 PR 内同步增删），避免两处维护导致词表漂移。

### 11.3 Agent 结构化消费路径（推荐）

平台将 manifest 的 `samples` / `stats` / `metrics` / `comparisons` / `error` 原样存入 `reports.result_meta`（§7.1）。Agent 助手回答"我的任务跑得怎么样？""这次分析有多少差异基因？"等问题时，**推荐路径是读取 `result_meta` 结构化字段，而非解析 HTML 报告或重扫结果目录**：

- 结构化读取快速、可确定性解析、对 token 预算友好；
- 与报告中心页面同源，AI 回答与页面展示天然一致；
- 仅当用户追问具体结果文件内容时，再经 `files[]` 路径走下载端点。

## 附录 E：`result_manifest.schema.json` 正本

本协议的机器可读规范性正本为 JSON Schema（draft 2020-12）文件：

```
platform_contracts/result_manifest.schema.json
```

**本文档为人读副本**；正本与副本不一致时，以 schema 文件为准，并于同日修订本文档（计入附录 F 变更记录）。存放位置建议为仓库顶层新建 `platform_contracts/` 目录（与 `flows/` 平级），平台与流程仓库通过同仓或 submodule 共享同一份文件。

**正本使用规则**：

| 侧 | 要求 |
|----|------|
| 流程侧 CI | 发布前用正本 schema 校验 manifest 样例（如 `check-jsonschema --schemafile platform_contracts/result_manifest.schema.json`） |
| 平台侧注册器 | `register_from_manifest()` 入口用**同一份** schema 文件校验；校验失败走 §6.4 兜底，不另写校验逻辑 |
| 协议升级 | MINOR 加字段先落 schema 文件，再更新本文档与附录 F |

## 附录 F：变更记录

### v1.0 → v1.1

本次为 MINOR 升级（按 §5.1 规则：仅增补与澄清，无字段语义破坏；v1.0 manifest 对 v1.1 平台保持完全兼容）：

1. **`task_id` 幂等键与版本树解耦**（§2.2、§6.4、§7.1）：明确"重跑 = 新 `task_id` → 新 `reports` 行，`version` + 1、`parent_id` 指向首版"，"同 `task_id` upsert 仅限回调重试 / 补登记"，v1.0 矩阵末行拆为两条独立规则；
2. **`run.output_dir` 降级**（§4.3、§6.2、§6.3、§7.1）：由必填降为可选参考信息；平台定位 manifest 改为只信 `tasks.result_dir`（§6.2 实施建议升级为正式条款）；推送场景路径语义改为共享存储相对路径 + 存储根白名单校验，禁止复用远端节点本地绝对路径；
3. **`has_ai_interpretation` 归属**（§4.7、§7.1）：仅表达流程自身生成的 AI 解读；平台后置 AI 标记在 `reports` 行维护且优先级高于流程声明；
4. **终态语义写死**（§3.3、§6.3）：manifest 仅表达终态，进行中进度属任务系统职责，流程不得写出/推送中间态 manifest；澄清 `reports.status=generating` 由任务事件驱动而非 manifest 驱动；
5. **schema 正本**（§9、附录 E）：新增 `platform_contracts/result_manifest.schema.json` 为机器可读规范性正本，流程侧 CI 与平台侧注册器共用同一份校验依据；
6. **样本数仲裁规则**（§4.5、§7.1）：`stats.sample_count` 与 `len(samples)` 不一致时以 `len(samples)` 为准并记 WARNING，不判无效；
7. **单细胞类流程预留**（§4.5、§5.4）：`stats` 允许自定义附加键（`cell_count` 等）；大规模观测级统计走 `metrics` / `stats` 自定义键，不进 `samples[]`；
8. **推送令牌模型收紧**（§6.3）：改为每计算节点独立令牌、可单独吊销、绑定来源 `server_id`，声明共享单令牌为反模式；
9. **交付链路留痕**（§10 第 7 条）：写出与推送均记流程侧日志，平台注册结果写任务日志；
10. **新增第十一章**：与 MAS 编排的衔接（`/workspace/results` 回传映射、DAG 末节点统一交付、`files[]` 词表与 MAS artifact 注册表同源演进）及 Agent 结构化消费推荐路径（读 `result_meta` 而非解析 HTML）。
