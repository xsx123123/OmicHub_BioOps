## 一、总原则

1. **构建期可换源、运行期可还原**：所有换源只影响镜像内配置，不得修改构建上下文之外的宿主机环境。
2. **换源层前置**：换源 `RUN` 指令必须放在该构建阶段（stage）第一个 `apt-get/pip/mamba` 使用**之前**，并尽量靠前，保证缓存命中率。
3. **多阶段各自处理**：多阶段构建中每个 stage 都是独立 rootfs，换源层**必须在每个用到包管理的 stage 各加一次**（参见 `deploy/docker/Dockerfile` 的 builder + runtime）。
4. **兜底源必备**：镜像源会抖动（实测 docker 构建网络到 USTC 曾超时），pip 必须配置 fallback；conda 不允许只留单一渠道。
5. **FROM 继承不重复**：子镜像 `FROM` 本仓库已换源的基础镜像时，无需重复换源（如 `tool_configs/terminal/docker/Dockerfile.*` 六个子镜像继承 `sandbox-terminal`）。

## 二、apt 源规范（Debian/Ubuntu 系）

### 2.1 Ubuntu 系（focal / jammy 等，使用 `/etc/apt/sources.list`）

在第一个 `apt-get update` 之前插入：

```dockerfile
# 构建期切换中科大 apt 源，加速 apt-get（Ubuntu 系）
RUN sed -i 's@//.*archive.ubuntu.com@//mirrors.ustc.edu.cn@g; s@//security.ubuntu.com@//mirrors.ustc.edu.cn@g' /etc/apt/sources.list
```

参考实现：`deploy/sandbox/Dockerfile`、`tool_configs/terminal/docker/Dockerfile`。

### 2.2 Debian 系（python:*-slim、micromamba 等）

bookworm 起源文件为 `/etc/apt/sources.list.d/debian.sources`，旧版为 `/etc/apt/sources.list`，**必须写成兼容两种的的形式**：

```dockerfile
# 构建期切换中科大 apt 源，加速 apt-get（兼容 debian.sources 与旧版 sources.list）
RUN if [ -f /etc/apt/sources.list.d/debian.sources ]; then \
        sed -i 's@//deb.debian.org@//mirrors.ustc.edu.cn@g; s@//security.debian.org@//mirrors.ustc.edu.cn@g' /etc/apt/sources.list.d/debian.sources; \
    else \
        sed -i 's@//deb.debian.org@//mirrors.ustc.edu.cn@g; s@//security.debian.org@//mirrors.ustc.edu.cn@g' /etc/apt/sources.list; \
    fi
```

参考实现：`deploy/docker/Dockerfile`、`deploy/docker/Dockerfile.worker`、`pipelines/ATACFlow/container_env/images/Dockerfile.template`。

### 2.3 可参数化（可选）

需要允许境外环境还原时，参考 `deploy/docker/Dockerfile.phylo` 的做法：

```dockerfile
ARG APT_MIRROR=http://mirrors.ustc.edu.cn
RUN sed -i -e "s|http://archive.ubuntu.com/ubuntu/|${APT_MIRROR}/ubuntu/|g" \
           -e "s|http://security.ubuntu.com/ubuntu/|${APT_MIRROR}/ubuntu/|g" /etc/apt/sources.list
```

### 2.4 交互阻塞防护

凡 apt 安装可能拉入 `tzdata` 等交互式包的镜像，必须在第一个 apt 层之前设置：

```dockerfile
ENV DEBIAN_FRONTEND=noninteractive \
    TZ=Asia/Shanghai
```

（2026-07-28 `cygnusx/sandbox-base` 曾因 tzdata 交互选时区卡死 400s+。）

## 三、pip 源规范

### 3.1 主源、回退源与多源选择规则

pip 的 `--extra-index-url` **不是故障转移开关**。它会把多个索引中的候选版本合并后再选择，不能保证先访问主源；如果候选页面或 wheel 链接指向境外 CDN，构建仍可能卡在 `files.pythonhosted.org`。因此本仓库禁止把多个 PyPI 镜像同时写入 `extra-index-url` 作为“兜底”。

统一采用以下策略：

1. 每次安装只使用一个 `index-url`（主源）；
2. 主源不可用时，由构建参数或 CI/部署脚本切换到另一个完整镜像后重试；
3. 不把 `pypi.org`、`files.pythonhosted.org` 放入国内构建的索引列表；
4. 不使用 `--trusted-host` 绕过 HTTPS 证书校验；只有明确的内部 HTTP 镜像并经过安全评审时，才允许单独豁免。

默认镜像可按构建环境选择：

| 环境 | 默认 `PIP_INDEX_URL` | 备用值 |
|---|---|---|
| 中国大陆构建节点 | `https://mirrors.aliyun.com/pypi/simple/` | `https://pypi.tuna.tsinghua.edu.cn/simple/` |
| 境外构建节点 | `https://pypi.org/simple/` | 组织内部 PyPI 代理 |
| 内网/生产构建 | 组织内部 PyPI 代理 | 经审计的国内镜像 |

镜像必须满足：支持 PEP 503 `/simple/` 接口、提供目标 Python/CPU 架构的 wheel、HTTPS 证书有效，并能下载依赖的实际文件，而不只是返回 package metadata。

### 3.2 Dockerfile 标准写法

在第一个 `pip install` 之前声明可覆盖参数；不要把镜像地址硬编码在每一条安装命令中：

```dockerfile
ARG PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/
ARG PIP_TIMEOUT=60
ARG PIP_RETRIES=5

# 只保留运行期确实需要的全局配置；PIP_INDEX_URL 由 ARG 注入，便于境外构建还原。
ENV PIP_INDEX_URL=${PIP_INDEX_URL} \
    PIP_DEFAULT_TIMEOUT=${PIP_TIMEOUT} \
    PIP_RETRIES=${PIP_RETRIES} \
    PIP_DISABLE_PIP_VERSION_CHECK=1

RUN python -m pip install \
    --no-cache-dir \
    --index-url "${PIP_INDEX_URL}" \
    --timeout "${PIP_TIMEOUT}" \
    --retries "${PIP_RETRIES}" \
    fastapi 'httpx>=0.27.0'
```

规则：

- Dockerfile 中的 `pip/pip3 install` 必须使用 `python -m pip` 或与当前 Python 明确绑定的 pip，并显式传 `--index-url`、`--timeout`、`--retries`。
- `PIP_INDEX_URL` 使用 `/simple/` 结尾的 HTTPS 地址；不要混用 `pypi.mirrors.ustc.edu.cn`、`mirrors.ustc.edu.cn/pypi` 等未经当前网络验证的历史地址。
- 多阶段构建中，每个实际执行 pip 的 stage 都必须声明/继承同一组参数；不能假定 builder 的 `/etc/pip.conf` 会进入 runtime stage。
- 只在需要时写 `/etc/pip.conf`。若写入，配置只能包含当前主源和超时/重试，不得再配置 `extra-index-url`：

```dockerfile
RUN printf '%s\n' \
      '[global]' \
      "index-url = ${PIP_INDEX_URL}" \
      "timeout = ${PIP_TIMEOUT}" \
      "retries = ${PIP_RETRIES}" \
      'disable-pip-version-check = true' \
      > /etc/pip.conf
```

- `env_file` 是运行期容器环境配置，**不会自动作为 Compose build arg**。需要在构建时切换镜像时，必须通过宿主机环境、Compose `build.args` 或 `--build-arg` 传入。
- `--no-cache-dir` 适用于最终镜像；在 BuildKit 构建中可优先使用 cache mount，避免重复下载：

```dockerfile
RUN --mount=type=cache,target=/root/.cache/pip,sharing=locked \
    python -m pip install \
      --index-url "${PIP_INDEX_URL}" \
      --timeout "${PIP_TIMEOUT}" \
      --retries "${PIP_RETRIES}" \
      fastapi 'httpx>=0.27.0'
```

### 3.3 镜像切换与故障回退

回退由构建调用方控制，不由 pip 的 `extra-index-url` 模拟：

```bash
# 主源：阿里云
PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ \
  docker compose -f deploy/agentteams/docker-compose.agentteams.yml \
  build cygnusx-agentteams-bridge

# 主源失败后，切换清华源重试
PIP_INDEX_URL=https://pypi.tuna.tsinghua.edu.cn/simple/ \
  docker compose -f deploy/agentteams/docker-compose.agentteams.yml \
  build cygnusx-agentteams-bridge
```

不得在一次构建中静默混用多个镜像；否则无法判断依赖实际来源，也不利于复现和审计。若组织确实需要统一代理，应使用单一内部 PyPI proxy，由代理负责上游回源和缓存。

### 3.4 构建前诊断与失败分类

遇到“每个 metadata 请求间隔几十秒”或 `ReadTimeoutError` 时，先区分 DNS、TLS、索引页和 wheel 下载，不要盲目增加重试次数：

```bash
MIRROR=https://mirrors.aliyun.com/pypi/simple
curl -fsSI --max-time 10 "${MIRROR}/fastapi/"
curl -fsSL --max-time 30 "${MIRROR}/fastapi/" | head
getent hosts mirrors.aliyun.com
```

| 现象 | 优先排查 | 处理 |
|---|---|---|
| `Could not resolve host` | Docker daemon/宿主机 DNS、代理 DNS | 修复 DNS 或配置 Docker daemon proxy；换镜像不能解决 DNS 本身 |
| TLS/证书错误 | CA 证书、系统时间、企业 MITM 证书 | 更新 `ca-certificates`，禁止用 `trusted-host` 粗暴绕过 |
| 索引页很快、wheel 很慢 | 镜像文件 CDN、出口带宽、目标架构 wheel | 更换完整镜像，检查目标 wheel URL 和大小 |
| metadata 每次都慢 | 镜像站延迟、代理 CONNECT、连接复用 | 先切换单一镜像，再调整 timeout/retries |
| `No matching distribution` | Python 版本、平台架构、包是否被镜像同步 | 检查 `python --version`、架构和包版本，不要直接加境外源 |

### 3.5 依赖解析、缓存与可复现性

- 生产镜像必须使用 lock/requirements 约束；`fastapi>=...` 这类范围依赖适合开发，不适合作为长期可复现的生产构建输入。
- 依赖文件变化前先单独验证索引页和 wheel 可下载，再进入完整镜像构建；避免在 Docker 构建中首次发现镜像缺包。
- 构建日志应保留实际 `PIP_INDEX_URL`（脱敏后）和 pip 版本；不要把访问令牌、私有源密码写进 Dockerfile、层历史或公开日志。
- pip 缓存应使用 BuildKit cache mount 或 CI 缓存；不要把宿主机 `~/.cache/pip` 直接 COPY 进镜像。
- 镜像切换后必须记录源地址、时间、Python 版本、平台架构和依赖锁文件 hash，保证失败可复现。

参考实现：`integrations/agentteams/bridge/Dockerfile`、`deploy/sandbox/Dockerfile`、`deploy/runtime-images/core.Dockerfile`、`deploy/studio/base.Dockerfile`、`tool_configs/terminal/docker/Dockerfile`。

### 3.6 uv 专项：四处独立加速点（缺一不可）

uv（`uv sync` / `uv pip install`）**完全不读 `/etc/pip.conf`**，且加速不是改一处就够——2026-07-28/08-07 实测有四个独立卡点：

**① uv 自身的安装来源**：禁止 `COPY --from=ghcr.io/astral-sh/uv:latest`——GHCR 在国内常被墙（本项目 worker 镜像历史注释原话 "GHCR commonly unavailable"）。统一从 PyPI 装：

```dockerfile
RUN python -m pip install --no-cache-dir --disable-pip-version-check \
    -i https://pypi.mirrors.ustc.edu.cn/simple "uv==0.6.14"
```

**② `pyproject.toml` 声明默认 index**（2026-08-07 新增）：在 `pyproject.toml` 中用 `[[tool.uv.index]]` 声明默认镜像源，这样**所有 uv 操作（本地开发 + Docker 构建）都自动走国内镜像**，无需每次手动传参：

```toml
# pyproject.toml
[[tool.uv.index]]
name = "ustc"
url = "https://pypi.mirrors.ustc.edu.cn/simple/"
default = true

[[tool.uv.index]]
name = "aliyun"
url = "https://mirrors.aliyun.com/pypi/simple/"
```

**③ 构建期 ENV + 命令级 `--index-url` 双保险**：Dockerfile 中仍保留 ENV（兼容未读取 pyproject.toml 的场景），且每条 `uv sync` / `uv pip install` 显式带 `--index-url`：

```dockerfile
ENV UV_INDEX_URL=https://pypi.mirrors.ustc.edu.cn/simple \
    UV_EXTRA_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/ \
    UV_HTTP_TIMEOUT=120 \
    UV_HTTP_RETRIES=5

# 每条命令都显式指定（防止 ENV 被覆盖 / cache mount 环境变量丢失）
RUN --mount=type=cache,target=/root/.cache/uv,sharing=locked \
    uv sync --frozen --no-dev --extra workflow --no-install-project \
    --index-url https://pypi.mirrors.ustc.edu.cn/simple/

RUN uv pip install --python /app/.venv/bin/python --no-cache \
    --index-url https://pypi.mirrors.ustc.edu.cn/simple/ \
    "some-package>=1.0"
```

**④ `uv.lock` 的钉死 URL**：锁文件记录每个包的绝对下载 URL（`url = "https://files.pythonhosted.org/..."`），`uv sync --frozen` 直接按锁内 URL 下载——**②③的 ENV/参数救不了**。锁文件若曾在境外 index 下生成（`uv lock`/`uv add`），必须在国内 index 下重新生成一次：

```bash
# 方式一：pyproject.toml 已配 [[tool.uv.index]] 时，直接 uv lock 即可
uv lock

# 方式二：未配置 pyproject.toml 时，临时指定
UV_INDEX_URL=https://pypi.mirrors.ustc.edu.cn/simple uv lock

# 验证：应输出 0
grep -c "files.pythonhosted.org" uv.lock
```

本仓库 `uv.lock` 已完成转换（235 包版本不变，全部 4204 个 URL 指向国内镜像）。**后续任何人在境外网络环境执行 `uv lock`/`uv add` 后，必须重跑上述转换命令**，否则所有用该锁的镜像构建退回境外下载。

**例外**：经 conda/mamba 安装的 uv（如 `deploy/runtime-images/core.Dockerfile` 的 `uv=0.5`）走 §4 的 conda 镜像，与上述四点无关。

参考实现：`deploy/docker/Dockerfile`、`deploy/docker/Dockerfile.worker`、`pyproject.toml`。

## 四、conda/mamba 源规范

在第一个 `mamba/conda` 安装命令之前写入 `~/.condarc`（root 构建则 `/root/.condarc`）：

```dockerfile
# 预置中科大镜像源，加速容器内 mamba/conda 环境安装
RUN printf '%s\n' \
      'show_channel_urls: true' \
      'default_channels:' \
      '  - https://mirrors.ustc.edu.cn/anaconda/pkgs/main' \
      '  - https://mirrors.ustc.edu.cn/anaconda/pkgs/free' \
      '  - https://mirrors.ustc.edu.cn/anaconda/pkgs/r' \
      '  - https://mirrors.ustc.edu.cn/anaconda/pkgs/msys2' \
      'custom_channels:' \
      '  conda-forge: https://mirrors.ustc.edu.cn/anaconda/cloud' \
      '  bioconda: https://mirrors.ustc.edu.cn/anaconda/cloud' \
      '  menpo: https://mirrors.ustc.edu.cn/anaconda/cloud' \
      '  pytorch: https://mirrors.ustc.edu.cn/anaconda/cloud' \
      'channel_priority: flexible' \
      'channels:' \
      '  - conda-forge' \
      '  - bioconda' \
      '  - menpo' \
      '  - defaults' \
      > /root/.condarc
```

要点（均为实测踩坑结论）：

- **`custom_channels` 的值必须是频道基地址**：写 `https://mirrors.ustc.edu.cn/anaconda/cloud`，Conda 会将键名（如 `conda-forge`）自动追加为实际频道路径。不得写成 `.../cloud/conda-forge`，否则会请求 `.../conda-forge/conda-forge/...` 并返回 404。
- **`custom_channels` 必须包含 bioconda**：只映射 conda-forge 时，`-c bioconda` 的包（r-base、bioconductor 系列）仍走境外 conda.anaconda.org，构建极慢。
- **`channel_priority: flexible`**：strict 在多渠道混装（bioconda + conda-forge + defaults）时容易无解；若业务确需 strict，需先在干跑（`--dry-run`）下验证。
- **不要再用 `conda config --add channels` 重复添加已列出的渠道**（会产生 warning 并改变渠道顺序）；如需调整，直接改这份 condarc 模板。
- micromamba 系镜像（`mambaorg/micromamba`）同理，写入 `/home/$MAMBA_USER/.condarc` 或 `/root/.condarc`（视运行用户而定，参考 `deploy/runtime-images/core.Dockerfile`）。
- **`.condarc` 必须写到 `$HOME` 下，而不是想当然的 `/root`**（2026-07-28 实测）：micromamba 按 `HOME` 环境变量找配置。基础镜像若设了 `ENV HOME=/home/<user>`（如 `sandbox-terminal` 的 `HOME=/home/cygnusx`），即使 `USER root` 构建，写 `/root/.condarc` 也会被**完全忽略且无任何报错**，静默回退境外 conda.anaconda.org 下载。规则：写 condarc 前先确认该镜像 `ENV HOME` 的值，两个家目录各放一份最稳。

## 五、依赖版本钉版规范

1. **禁止钉到补丁号的"小版本号"依赖上游长期留存**。实测案例：conda-forge 将 `matplotlib 3.9.0` 标记 broken 后下架，仅存 3.9.1+，导致 `matplotlib=3.9.0` 直接 `does not exist` 构建失败。
2. 生信/科学计算包统一**钉到小版本（minor）**：`matplotlib=3.9`、`scanpy=1.10`，让 solver 取该 minor 下最新可用补丁。
3. 新镜像或改 pin 后，**构建前必须 dry-run 验证**（避免构建跑到一半才发现无解）：

   ```bash
   docker run --rm <base-image> bash -c "
     <写入本规范 §4 的 .condarc>
     mamba create -n test --dry-run -y <全部 pin 列表> | tail -20"
   ```

4. 报错 `The following package could not be installed ... does not exist` 时，先查该版本是否被上游下架，不要盲目怀疑镜像源。
5. 大件依赖（PyTorch 等）必须前置处理，见 §5.1。
6. **Python/R 同环境共存时，R 版本须跟随 Python 栈的系统库**（2026-07-28 实测）：Python 科学栈（matplotlib→libharfbuzz）会拉入最新 `icu`（如 78.x），而旧版 `r-base`（4.3/4.4）只接受 icu 72~75，同环境安装必无解。规则：同一 conda env 混装 Python+R 时，`r-base` 钉**当前 conda-forge 最新 minor**（如 4.5），并在 dry-run 中用 `python=<x> icu=<env内版本> libharfbuzz` 预置环境后验证 R 层；实在无解则拆分为独立 R 环境（IRkernel 从 R 环境注册 kernel）。

### 5.1 大件依赖前置：GPU 包防护（避免单层 10 分钟+）

**现象**（2026-07-28 实测）：`cygnusx/sandbox-base` 构建到 `pip install scvi-tools ...` 一层耗时 **623 秒**，构建日志长时间无输出、看似卡死。

**根因**：PyPI 上的 Linux x86_64 版 `torch` 轮子自 2.x 起默认依赖一整套 NVIDIA CUDA 运行时（`nvidia-cublas-cu12`、`nvidia-cudnn-cu12` 等十余个 `nvidia-*` 包），pip 解析 `torch` 时会**静默拖回约 3GB** 的 GPU 依赖。即使走 USTC 镜像，3GB 下载也需要 10 分钟级；而纯 CPU 沙盒/分析容器根本用不到 CUDA，这些包纯属浪费时间和磁盘。

**标准做法**：凡 Python 依赖链含 PyTorch（`scvi-tools`、`torch-geometric`、`transformers` 等）的 CPU 镜像，必须**先用 mamba 装 CPU-only PyTorch，再 pip 装上层包**：

```dockerfile
# 先装 CPU-only PyTorch（走 USTC 镜像的 pytorch 渠道）。
# conda 的 pytorch 包自带 torch 的 dist-info，后续 pip 会判定 torch 依赖已满足，
# 不再从 PyPI 拉取 ~3GB 的 NVIDIA CUDA 依赖。
RUN mamba install -n <env> -y -c pytorch -c conda-forge \
        pytorch=<minor> \
        cpuonly \
    && mamba clean --all -y

RUN pip install --no-cache-dir "scvi-tools>=1.1.0" ...
```

**效果**（同机实测）：CPU 版 `pytorch 2.4.1 py3.11_cpu_0` 总下载 **272MB**（PyPI GPU 路线约 3GB，省 90%+），该层从 623s 缩到约 1 分钟。

**适用判断清单**（满足任意一条即应前置）：

- pip 依赖树含 `torch`（用 `pip install --dry-run <pkg> 2>&1 | grep -i torch` 可提前确认）
- 镜像无 NVIDIA GPU / 不挂 `--gpus`（本仓库所有沙盒与分析容器均属此类）
- 同类大件同理：`tensorflow`（CPU 镜像用 `tensorflow-cpu`）、`jax`（用 `jax[cpu]`）

参考实现：`deploy/sandbox/Dockerfile`（scvi-tools 前置 pytorch-cpu 层）。

### 5.2 境外大件制品本地化（vendor 模式）

**现象**（2026-07-28 实测）：`cygnusx/sandbox-gatk` 构建到 `wget https://github.com/.../gatk-4.5.0.0.zip` 一层耗时 **626 秒**，GitHub Release / AWS S3 在国内构建环境慢且不稳，且每次缓存失效都重新下载。

**标准做法**：凡 Dockerfile 需要从 GitHub Release、S3 等境外站点下载**不可经包管理器镜像获得**的大件制品（>10MB 的二进制发行包），一律本地化：

1. 制品预下载到构建上下文下的 `vendor/` 目录（与 Dockerfile 同级）；
2. Dockerfile 改 `wget` 为 `COPY vendor/<file> /tmp/...`，并在上方注释中保留原始 URL 的 curl 重新下载命令（方便升级版本时换新）；
3. 版本号继续用 `ARG` 贯通 `COPY` 文件名，升级版本只需改 ARG + 换 vendor 文件；
4. `vendor/` 目录加入 `.gitignore`（二进制不入库），新机/新克隆环境按 Dockerfile 注释重新下载一次即可；
5. 预下载在宿主机执行（宿主机网络通常优于 docker build 网络，且支持断点续传 `curl -C -`）。

```dockerfile
#   curl -L -o vendor/gatk-${GATK_VERSION}.zip \
#     "https://github.com/broadinstitute/gatk/releases/download/${GATK_VERSION}/gatk-${GATK_VERSION}.zip"
COPY vendor/gatk-${GATK_VERSION}.zip /tmp/gatk.zip
RUN unzip -q /tmp/gatk.zip -d /opt && rm /tmp/gatk.zip
```

**效果**：该层从 626s 缩到秒级（本地 COPY + 解压），且重复构建不再依赖境外网络。

参考实现：`tool_configs/terminal/docker/Dockerfile.gatk`（GATK + PLINK1/2 三个制品 vendor 化）。

### 5.3 GitHub 小件与安装脚本加速（代理/镜像站模式）

**现象**（2026-08-24 实测，`cygnusx/sandbox-terminal` 全量重建 217.6s）：`wget` GitHub Release 的 ttyd 二进制一层 **54.8s**，oh-my-zsh 安装脚本 + clone 一层 **33.5s**。这类制品只有几 MB，不值得 §5.2 的 vendor 化，但直连 GitHub 依然慢。

**标准做法**（按优先级递减）：

1. **发行版仓库优先**：凡是 apt/pip/conda 官方仓库已收录的工具，一律走包管理器，不从 GitHub 下载。例：`ttyd` 在 Ubuntu jammy universe 有 `1.6.3`，直接并入 apt 安装列表，版本差异须先核对 Dockerfile 所用参数/特性是否兼容。
2. **git 仓库与安装脚本走 Gitee 镜像**：Gitee `mirrors/*` 组织同步了常见开源仓库。oh-my-zsh 官方安装脚本支持 `REMOTE` 环境变量，脚本本体与 clone 可全部走 Gitee：

   ```dockerfile
   RUN export REMOTE=https://gitee.com/mirrors/oh-my-zsh.git BRANCH=master && \
       sh -c "$(curl -fsSL https://gitee.com/mirrors/oh-my-zsh/raw/master/tools/install.sh)" "" --unattended
   ```

   附带收益：镜像内 `.oh-my-zsh` 的 origin 指向 Gitee，运行期 `omz update` 自动更新也不碰 GitHub。
3. **GitHub Release 小件走代理前缀**：无法从包管理器或 Gitee 获得的 release 二进制/压缩包，用公共代理中转，代理地址必须做成可覆盖的 `ARG`（代理站更迭频繁，失效时换 `--build-arg` 即可，不改 Dockerfile）：

   ```dockerfile
   ARG GH_PROXY=https://gh-proxy.com/   # 备选：https://ghfast.top/；传空串还原 GitHub 直连
   RUN curl -fsSL -o /usr/local/bin/oh-my-posh \
         "${GH_PROXY}https://github.com/JanDeDobbeleer/oh-my-posh/releases/latest/download/posh-linux-amd64" && \
       chmod +x /usr/local/bin/oh-my-posh
   ```

   注意 GitHub Release 的两种 URL 形态：`latest` 用 `releases/latest/download/<file>`，钉版用 `releases/download/<tag>/<file>`，一个模板串不起来，需在 RUN 里按 ARG 分支拼接（参考实现见下）。

**边界与规则**：

- 本节全部作用于**构建期**，流量不过容器运行期白名单，**无需**联动 `data/ai/studio.yaml`（§6 只管运行期 Agent 安装）。
- 代理站是公共服务，**禁止**经代理下载任何需要认证/私有的资源；公开 release 制品可用。
- 钉版规范（§5）同样适用：默认可用 `latest` 保活，生产固化时应钉 tag 并记录。
- 选用代理前用 `curl -sIL --max-time 10 "${GH_PROXY}<github-url>"` 验证可达性（2026-08-24 实测：`mirror.ghproxy.com` 已不可达，`gh-proxy.com` / `ghfast.top` 正常）。

**效果**（同机实测预期）：ttyd 层 54.8s → 随 apt 层完成；oh-my-zsh 层 33.5s → 秒级；oh-my-posh 安装脚本路线（含境外 ohmyposh.dev）→ 代理直连约 1~2s。

参考实现：`tool_configs/terminal/docker/Dockerfile`（ttyd apt 化、oh-my-zsh Gitee 化、oh-my-posh gh-proxy 化）。

## 六、运行期网络白名单联动

沙盒容器走域名白名单（`data/ai/studio.yaml` 的 `network.mode: whitelist`）。**本规范引入的所有镜像源域名必须同步在白名单中**，否则运行期 Agent 在容器内 `pip/mamba install` 会被拦：

```yaml
allow:
  - pypi.org
  - files.pythonhosted.org
  - mirrors.aliyun.com
  - mirrors.ustc.edu.cn
  - pypi.mirrors.ustc.edu.cn
  - conda.anaconda.org   # 兜底，可保留
```

新增镜像源（如 ustc、腾讯云）时，Dockerfile 与白名单**必须同一次提交内同步修改**。

## 七、提示词（Agent Prompt）联动

镜像内配置解决"默认走哪"，提示词解决"Agent 主动安装时怎么走"。所有可能执行软件安装的 Agent 提示词（general / code / scrna / rnaseq / visualization 等）必须包含：

1. **统一使用 `micromamba install`**：沙盒镜像已预置本规范 §4 的 `.condarc`（conda-forge、bioconda 均已映射到中科大镜像），Agent 直接 `micromamba install -y -n base <pkg>` 即可，**不要**显式 `-c conda-forge` 或 `-c bioconda`（`.condarc` 默认频道已覆盖）；
2. **Bioconductor 专属包例外**：仅当包仅在 Bioconductor 频道发布时（如 `bioconductor-deseq2`），才需 `-c bioconductor`；
3. **禁止 `pip install`、`install.packages()`、`remotes::install_github()`**：所有包装一律走 conda 通道，GitHub 独占包无法安装时如实说明；
4. 安装失败提示网络错误时，优先建议重试或换兜底源，**不得让 Agent 自行添加未经白名单放行的域名**。

共享协议见 `data/ai/prompts/shared/sandbox_protocol.md`（`owners: [agent, studio]`，注入所有 Agent）；各 Agent 专属包表见 `code.md` / `scrna.md` / `rnaseq.md` / `visualization.md`。

- [ ] 版本钉到 minor 而非 patch（§5），且已 dry-run 验证
