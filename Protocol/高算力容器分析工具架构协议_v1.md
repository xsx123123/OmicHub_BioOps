## 一、背景与目标

### 1.1 问题陈述

CygnusX 工具箱已经拥有多个需要重计算的工具（BLAST、富集分析），其中 **GO / KEGG 富集工具**（`kegg-enrichment`）把「前端提交 → Celery 投递 → 独立 Worker 编排短生命周期 R 容器 → 标准产物回写 → 前端轮询渲染」这条链路实现得最为规整，并配有 `framework.md` 与 `KEGG_Docker_契约.md` 两份工具级文档。

但这条链路目前**只以"一个具体工具"的形态存在**，没有沉淀为可被后续工具直接引用的通用协议。新工具（如差异表达分析）要复用这套架构，只能靠"对照富集代码逐文件抄"，存在四个问题：

1. **隐性约定多**：哪些字段能回浏览器、容器命令怎么拼、CSV 列怎么恒定、退出码怎么表达局部失败——这些散落在富集的代码与两份文档里，没有一个"工具无关"的契约视角。
2. **边界易写坏**：`tools_design.md` §5.1.2 的强制条款（Web 不得持 Docker、提交必须立即返回、必须复用统一任务模型）是红线，但缺乏一份把红线落到"目录该长什么样、函数该怎么签名"的参考架构。
3. **命名/路径易漂移**：任务目录布局、`flow_id` 判别器、镜像命名、配置键命名若不统一，每个工具各写一套，运维与排障成本线性上升。
4. **产物可见性不统一**：工具产物默认只在任务内可下载，是否登记进 `file_records`（进而在「文件管理」可见）缺乏统一指引。

### 1.2 目标

把富集工具验证过的架构**抽象为一份工具无关的参考协议**，使任意同类新工具能够：

- **照骨架填空**：按 §3 的目录契约建包，按 §5 的运行契约实现六层，按 §10 清单逐项验收；
- **不碰接线**：路由自动发现（§3.2）、任务模型复用（§5.2）、前端工作台模板化（§7），新增工具**无需修改** `api/v1/router.py`、`tools/__init__.py`、任务/队列基础设施；
- **边界天然正确**：四层职责（§2.2）与强制条款（§11）把"Web 不持 Docker、提交立即返回、容器不碰数据库"写进契约；
- **命名/路径可预期**：统一的目录布局（§5.1）、镜像命名（§6.1）、配置键前缀（§4.3）。

### 1.3 结论先行

> "我一个新工具，是不是也按富集那套：前端表单提交 → 后端建任务投 Celery → Worker 起一个 R 容器跑脚本 → 出 CSV 和图 → 前端轮询画图？"

**是。** 这正是本协议固化的唯一范式。你要做的只是：

| 你要提供 | 落在哪 |
|---|---|
| 一个分析脚本（R/Python，optparse 风格 CLI，读挂载输入、写标准 CSV+图） | `tool_configs/<tool>/run_<tool>.R`，构建期烘焙进镜像 |
| 一个分析镜像（装好脚本运行环境） | `deploy/docker/Dockerfile.<tool>` → `<vendor>-<tool>:v1` |
| 一个工具子包（api/schema/config/service/tasks/runner 六件套） | `src/cygnusx/tools/<tool>/` |
| 一张工具箱卡片 + 一条前端路由 + 一个工作台页面 | `tools_setting.yaml` / `router/index.ts` / `<Tool>View.vue` |
| 一组配置键（镜像/网络/资源/超时） | `core/config.py` 的 `<tool>_*` 设置 |
| 一条 AI / MCP 工具契约（让 AI 助手也能调用） | `tool_configs/tools_schema.yaml`（§3.5，`backend_sync` 包裹 `submit`） |

其余（路由挂载、任务模型、队列、轮询、目录隔离）全部复用，零改动。

### 1.4 与既有规范的分工

| | `tools_design.md` §5.1.2 | **HCTP（本协议）** | ARDP |
|---|---|---|---|
| 层次 | **原则/强制条款**（必须异步、Web 不持 Docker、复用任务模型、Socket GID 规范） | **操作化参考架构**（目录骨架、函数签名、命令形态、CSV/退出码契约、配置三层、工作台模板） | 分析中心 Flow 家族的**结果交付**协议（`result_manifest.json`） |
| 治理对象 | 所有高算力工具的红线 | 同类工具如何把红线落成代码 | Flow（RNAFlow/ATACFlow…）→ 报告中心 |
| 关系 | 本协议**不得违反**其条款，并把其条款具象化 | 上游是 §5.1.2，下游是各工具实现 | **正交**：工具箱工具走本协议的任务内结果机制，不走 ARDP 的 manifest/报告中心 |

> **与 ARDP 的边界**：本协议的工具是「工具箱」里的**交互式单体工具**（一次提交一个分析，结果在任务内查询/下载，`task.parameters["result"]` + `result_path`）。ARDP 治理的是「分析中心」**Flow 家族流水线**（多阶段 Snakemake，结果经 `result_manifest.json` 进报告中心）。两者共用 `TaskModel` 与 `/data/cygnusx` 存储布局，但消费路径不同：一个工具**不要**为了进报告中心而写 ARDP manifest，除非它本质上是一条 Flow。

## 二、总体架构

### 2.1 数据流全景

```
┌──────────────── 提交阶段（浏览器 → Web API）────────────────┐
│  <Tool>View.vue 工作台                                        │
│      │ POST /<tool>/submit (multipart: 输入文件 + 参数)        │
│      ▼                                                         │
│  api.py (router/prefix/tags，自动挂载)                        │
│      ▼                                                         │
│  service.submit()                                             │
│      ├─ ① 从领域 YAML 解析配置（权威，不信前端传值）          │
│      ├─ ② 轻量校验 + 归一化输入（去空白/去重/格式）           │
│      ├─ ③ StoragePathFactory 建隔离任务目录                   │
│      ├─ ④ 把输入落盘到挂载根之下                              │
│      ├─ ⑤ 创建 TaskModel(flow_id="<tool-key>") 入库           │
│      ├─ ⑥ <tool>_task.apply_async(task_id)  投递 analysis 队列│
│      └─ ⑦ 立即返回 TaskDTO(status="queued")  ← 不等待计算     │
└────────────────────────────────────────────────────────────────┘
                         │  (Redis broker)
┌──────────────── 执行阶段（Celery Worker，持 Docker Socket）──┐
│  tasks.py @shared_task(queue="analysis")                      │
│      ├─ 自建 DB 会话，置 RUNNING + progress                   │
│      ├─ 重解析领域配置（权威）                                │
│      ├─ 由 task.work_dir 拼输入/输出路径                      │
│      └─ runner.run(params)：                                  │
│            docker run --rm --name <tool>-<tid8>               │
│              --network <net> -v <mount>:/data/cygnusx         │
│              --memory <m> --cpus <n> <image>                  │
│              Rscript /app/run_<tool>.R --input … --output …   │
│            asyncio.create_subprocess_exec + wait_for(超时)    │
└────────────────────────────────────────────────────────────────┘
                         │
┌──────────────── 容器阶段（短生命周期分析容器）──────────────┐
│  <image> 内 Rscript /app/run_<tool>.R                         │
│      ├─ 从 /data/cygnusx（== 宿主同路径）读输入与参考         │
│      ├─ 运行分析（clusterProfiler / DESeq2 / edgeR / …）      │
│      ├─ 写标准 CSV（列恒定，空结果仅表头）+ 图 PNG/PDF        │
│      └─ 退出码：0 成功；非 0 全部失败；局部失败保留成功部分   │
│      （--rm 退出即清理；容器无 DB 凭据、无用户令牌）          │
└────────────────────────────────────────────────────────────────┘
                         │
┌──────────────── 回写阶段（Worker 解析产物）──────────────────┐
│  tasks.py                                                     │
│      ├─ 校验退出码（失败 → error_message[:2000] + FAILED）    │
│      ├─ 解析标准 CSV → 结果 DTO                               │
│      ├─ 结果写回 task.parameters["result"] + result_path      │
│      └─ 置 SUCCESS + progress=100，commit                     │
└────────────────────────────────────────────────────────────────┘
                         │
┌──────────────── 展示阶段（浏览器轮询）───────────────────────┐
│  GET /<tool>/tasks/{task_id}  （setTimeout 递归，~1.5s）      │
│      └─ status=completed → 读 result → Plotly 交互渲染 + 表格 │
│         status=failed   → 展示 error_message                  │
│  GET /<tool>/tasks/{task_id}/download → 原始 CSV（鉴权+归属） │
└────────────────────────────────────────────────────────────────┘
```

### 2.2 四层职责边界（强制，源自 tools_design.md §5.1.2）

| 层 | **必须做** | **禁止做** |
|---|---|---|
| **Web API**（`api.py` + `service.py`） | 鉴权与数据归属校验、轻量输入校验、创建 `TaskModel`、投递 Celery、提供状态/结果/下载查询 | 安装 Docker CLI、挂载 Docker Socket、同步运行容器或任何高耗时子进程、等待计算结束才响应 |
| **Celery Worker**（`tasks.py` + `runner.py`） | 消费 `analysis` 队列、拼容器命令、控制超时/资源、解析约定产物、更新 `TaskModel` 状态 | 把结果只留在进程内存、绕过任务状态记录、直连业务数据库以外的外部系统做业务判断 |
| **分析容器**（`run_<tool>.R`） | 在隔离环境运行分析、把约定产物写入挂载任务目录、用退出码表达成败 | 访问 Web 会话、数据库凭据、用户认证令牌；直接写挂载目录之外的路径 |
| **前端工作台**（`<Tool>View.vue`） | 参数表单、提交、轮询、Plotly 交互渲染、CSV 导出、明确的状态/错误/空结果反馈 | 在浏览器里执行分析、把示例数据当真实任务提交、把内部运行细节（镜像名/容器路径）暴露为可编辑字段 |

### 2.3 设计原则

| 原则 | 说明 |
|---|---|
| **提交即返回** | `submit` 只做校验+落盘+建任务+投递，毫秒级返回 `task_id`；一切耗时在 Worker/容器 |
| **配置权威在后端** | 物种、参考路径、默认阈值由后端从领域 YAML 解析，前端传的参考路径一律不信、不外泄 |
| **同路径挂载** | 输入/输出/参考全部位于共享挂载根（默认 `/data/cygnusx`）下，宿主与容器内**绝对路径一致**，命令里一套路径两边通用 |
| **脚本烘焙进镜像** | 分析脚本构建期 `COPY` 进镜像（`/app/run_<tool>.R`），运行期不挂卷、不改脚本，保证可复现 |
| **标准产物契约** | 容器只认"固定列 CSV + 图 + 退出码"，Worker 只解析这一份契约；前后端都不依赖容器内部目录结构 |
| **失败也是一份结果** | 全部失败 → 非零退出 + 错误摘要回写；局部失败 → 保留成功部分 + 警告，不让一类失败拖垮另一类 |
| **任务模型唯一** | 所有工具复用同一个 `TaskModel` + `analysis` 队列 + 状态字段 + 目录隔离，以 `flow_id` 区分工具；**不得另造任务表/队列** |
| **双提交通道同入口** | 网页表单（§5.2）与 AI/MCP（§3.5）是两条提交通道，但都收敛到**同一个** `<Tool>Service.submit`——任务、状态、结果对人和 AI 完全一致，无需为 AI 单写逻辑 |

## 三、工具身份与注册契约

### 3.1 工具子包目录契约

每个高算力工具在 `src/cygnusx/tools/<tool>/` 下遵循固定六件套（富集为样板）：

```text
src/cygnusx/tools/<tool>/
├── __init__.py     # 一行 docstring 即可；无注册代码
├── api.py          # ★ 必须暴露模块级 router / prefix / tags
├── schema.py       # Pydantic DTO，继承 CygnusXBaseSchema
├── config.py       # <Tool>ConfigManager（mtime 热重载单例）+ 领域 Pydantic 模型
├── service.py      # <Tool>Service：submit / get_task / list_tasks / get_result_file
├── tasks.py        # @shared_task(queue="analysis") 的 Celery 任务
└── runner.py       # <Tool>DockerRunner：build_command() + run()
```

| 文件 | 职责 | 样板对照（enrichments） |
|---|---|---|
| `api.py` | 声明路由：`GET /<tool>/…`（species/config、submit、tasks、tasks/{id}、download） | `enrichments/api.py` |
| `schema.py` | 输入/输出 DTO、任务状态枚举 | `enrichments/schema.py` |
| `config.py` | 读 `tool_configs/<tool>/*.yaml`，Pydantic 校验，mtime 变更才重解析，**任何错误回退空配置不抛** | `enrichments/config.py` |
| `service.py` | 编排：校验→落盘→建 Task→投递→返回；以及查询/下载 | `enrichments/service.py` |
| `tasks.py` | Celery 任务：置运行态→重组参数→调 runner→解析产物→回写 | `enrichments/tasks.py` |
| `runner.py` | 拼 `docker run` 命令、`asyncio.create_subprocess_exec` 执行、超时控制 | `enrichments/runner.py` |

### 3.2 自动路由注册（无需改接线）

`src/cygnusx/tools/__init__.py` 提供自动发现：

```python
ROUTER_ATTR = "router"; PREFIX_ATTR = "prefix"; TAGS_ATTR = "tags"

def discover_tool_api_modules():
    # pkgutil.iter_modules 扫描 cygnusx.tools 每个子包，
    # 尝试 import <子包>.api，含 router 属性者收集

def register_tool_routers(api_router):
    # 对每个发现的 api 模块：prefix 缺省 = "/<子包名>", tags 缺省 = ["<子包名>"]
    # api_router.include_router(mod.router, prefix=prefix, tags=tags)
```

该函数在 `src/cygnusx/api/v1/router.py` 中**只调用一次**。因此：

- **契约**：`api.py` 必须在模块级暴露 `router: APIRouter`；可选 `prefix: str`、`tags: list[str]`。
- **结果**：新建 `<tool>/api.py` 即自动挂载到 `/api/v1<prefix>`，**无需修改** `router.py` 或 `tools/__init__.py`。
- **命名提示**：`prefix` 可与子包名不同（如子包 `enrichments` → `prefix="/enrichment"`），以路由可读性为准。

### 3.3 工具箱卡片注册

在 `tool_configs/tools_setting.yaml` 追加一张卡片（字段见 `tools_design.md` §5.1）：

```yaml
- key: "<tool-key>"            # kebab-case，唯一，与前端路由 token 一致
  title: "<中文名>"
  description: "<一句话>"
  icon: "<Ionicons5 图标键>"   # 需在 ToolsHubView.vue 的 ICON_MAP 登记
  gradient: "linear-gradient(135deg, #xxxxxx 0%, #yyyyyy 100%)"
  route: "/tools/<tool-key>"
  group: "function"            # sequence/visualization/genome/function/environment
  enabled: true
  order: 55                    # 升序
  config_dir: "tool_configs/<tool>"   # 有后端配置则填，纯前端工具留空
```

卡片经 `GET /api/v1/tools`（`registry` 工具）下发前端，`ToolsHubView.vue` 按 `group` 分组、`order` 排序渲染 `ToolCard`。

### 3.4 前端路由与图标

- 路由：`frontend/src/router/index.ts` 在 `DefaultLayout` 的 `children` 追加
  `{ path: 'tools/<tool-key>', name: 'tools-<tool-key>', component: () => import('@/views/BioTools/<Tool>View.vue'), meta: { title: '<中文名>', requiresAuth: true } }`。
- 图标：`tools_setting.yaml` 的 `icon` 是**字符串键**，须在 `ToolsHubView.vue` 的 `ICON_MAP`（`@vicons/ionicons5`）登记；未登记键回退 `AppsOutline`。

### 3.5 AI / MCP 工具注册与暴露契约

每个工具除了面向人的工具箱卡片（`tools_setting.yaml`，§3.3），还应作为 **AI 助手 / MCP 一等公民**暴露。这是**第二张注册表**，与前端展示解耦：

| | `tools_setting.yaml`（§3.3） | `tools_schema.yaml`（本节） |
|---|---|---|
| 消费方 | 前端工具箱（人） | LLM / AI 助手 / MCP 客户端 |
| 内容 | 卡片元数据（图标/路由/分组） | 可调用契约（调用模式/参数 schema/结果白名单） |
| 加载 | `registry` 工具 | `ToolsSchemaLoader`（mtime 热重载，改完即生效） |

#### 3.5.1 调用模式（`invocation_mode`）

`tool_bridge_service.py` 按 `invocation_mode` **进程内分发**（禁止 HTTP 自调用）：

| 模式 | 机制 | 适用 | 样板 |
|---|---|---|---|
| **`backend_sync`** | 进程内同步调 `service` 的 `method` | **高算力容器工具的首选**——直调 `<Tool>Service.submit`，因 submit 投递即返回，同步调用也毫秒级 | `kegg-enrichment` → `EnrichmentService.submit` |
| `backend_shim` | 进程内调 `shim_module.execute()` | 轻量纯计算/绘图工具 | `volcano` / `manhattan` |
| `backend_async` | 仅提交异步任务（占位） | 预留 | — |
| `open_page` | 不执行，返回前端路由引导用户 | 输入复杂、需用户在页面交互/上传的工具 | `phylogenetic-tree` |
| `analysis_flow` | 经 `analysis_flow_tool_service` 提交流水线 | **Flow 家族**（由 `FlowToolSchemaCompiler` 对 `ai.enabled` 的 Flow 动态编译），非工具箱工具 | 动态 Flow 工具 |

> **高算力工具的 AI 暴露范式**：用 `backend_sync` 包裹**与网页同一个** `<Tool>Service.submit`。LLM 调用即得 `task_id`，随后经 `cygnusx-platform` 内置 preset 的 `platform_get_task(task_id)` 轮询 `status/progress`，完成后回报用户——与网页轮询（§5.7）共用同一任务模型，AI 与页面状态天然一致。若某工具输入过于复杂、LLM 难以代为提供，可退化为 `open_page` 引导用户到页面（`phylogenetic-tree` 先例）。

#### 3.5.2 条目契约（`tools_schema.yaml`）

```yaml
- key: <tool-key>                      # 与 tools_setting.yaml 的 key 一致
  name: cygnusx_<verb>_<tool>          # LLM function 名，统一 cygnusx_ 前缀避免撞名
  description: <LLM 看到的工具描述>
  category: <enrichment/visualization/sequence/…>
  invocation_mode: backend_sync
  service: cygnusx.tools.<tool>.service.<Tool>Service
  method: submit
  requires_confirm: false              # 是否需用户二次确认
  annotations:                         # MCP Tool Annotations
    readOnlyHint: false
    destructiveHint: false
    openWorld: false
    idempotent: true
  input_schema:                        # JSON Schema Draft 7（转 OpenAI functions 时自动调整）
    type: object
    properties:
      species_id: {type: string, description: …}
      # 文件输入支持 upload://file_id 引用聊天已上传文件，由 bridge 解析
    required: [species_id]
  llm_result_fields: [task_id, stats, success, error]      # 回灌 LLM 的字段白名单
  ui_result_fields: [plotly_figure, table_data, download_urls]  # 透传前端渲染的字段白名单
```

- **参数白名单双通道**：`llm_result_fields` 决定回灌给 LLM 的精简结果（`task_id`/统计/成败），`ui_result_fields` 决定透传给聊天 UI 渲染的富结果（Plotly 图/表格/下载链）。`submit` 返回的任务 DTO 中不存在的字段自动忽略。
- **文件输入**：`input_schema` 的字符串字段可接受 `upload://<file_id>` 引用用户在聊天中上传的文件，由 `tool_bridge_service._resolve_upload_refs` 解析为文本/路径——**高算力工具的矩阵/列表类输入应支持此引用**，使 AI 能直接用聊天上传文件发起分析。

#### 3.5.3 自动成为 MCP 工具（零接线）

`infrastructure/mcp/presets.py` 动态构建内置 **`cygnusx-tools`** MCP preset：

```python
static_tools = schema_loader.to_openai_tools()          # tools_schema.yaml → OpenAI functions
handlers = {t["function"]["name"]: _cygnusx_tools_handler for t in static_tools}
# + FlowToolSchemaCompiler 动态编译 ai.enabled 的 Flow 为 MCP tool
```

所有条目的调用统一经 `_cygnusx_tools_handler` 路由到 `tool_bridge_service.execute`。因此：

- **契约**：在 `tools_schema.yaml` 追加一条，工具**自动**成为 AI 助手可调用工具与 `cygnusx-tools` MCP tool，**无需改任何代码**。
- **任务轮询**：LLM 用 `cygnusx-platform` preset 的 `platform_get_task` / `platform_list_tasks` 查询任务状态（与网页共用 `TaskModel`）。

#### 3.5.4 与独立 `mcp-server/` 的边界

仓库根的 `mcp-server/`（FastMCP）是**面向外部 MCP 客户端**（Claude Desktop 等）的独立服务，暴露**平台级资源与 Flow 分析**（`cygnusx_submit_analysis`、tasks/reports/files/sandbox/pipelines）。工具箱工具的 AI 暴露**主路径是 `tools_schema.yaml` → 内置 `cygnusx-tools` preset**；除非要把某工具额外暴露给外部 MCP 客户端，否则不需要改 `mcp-server/`。

## 四、配置三层模型

配置严格分三层，**公开边界**是核心安全约束：浏览器只能看到"展示/默认值"，看不到宿主参考路径与运行资源。

### 4.1 卡片元数据层 — `tools_setting.yaml`

仅工具箱展示用（§3.3）。不含任何运行参数。经 `GET /tools` 全量下发。

### 4.2 领域配置层 — `tool_configs/<tool>/*.yaml`

物种/参考库/默认阈值/方法开关等**领域知识**。由后端 `<Tool>ConfigManager` 按 mtime 热重载、Pydantic 校验，解析失败回退空配置（绝不抛给调用方）。

字段的公开边界（以富集 `species_config.yaml` 为样板）：

| 字段类别 | 是否可回浏览器 | 示例 |
|---|---:|---|
| 选择框/可用性 | ✅ | `id`、`display_name`、`enabled`、`analysis_types` |
| 默认阈值（可被用户在合法范围覆盖） | ✅（默认值） | `p_value_cutoff`、`q_value_cutoff` |
| 宿主参考文件路径 | ❌ 绝不 | `go_obo`、`go_annotation`、`kegg_id_map`、计数矩阵参考、注释库 |
| 内部运行标识 | ❌ | 镜像名、容器内路径、 OrgDB |

> **规则**：浏览器**不得**传入任意参考文件路径；一切参考路径由后端按 `species_id`/`config_id` 从 YAML 解析后，仅传给容器。

### 4.3 环境配置层 — `core/config.py`

镜像、网络、资源、超时等**环境差异**，统一由 `Settings` 字段（env 覆盖）控制，**不写入浏览器可见配置**。每个工具用统一前缀 `<tool>_*`（对照富集）：

```python
# src/cygnusx/core/config.py（富集样板，行 201-212）
enrichment_config_yaml: str = "tool_configs/enrichments/species_config.yaml"
enrichment_docker_image: str = "cygnusx-r-enrichment:v1"
enrichment_docker_network: str = "cygnusx_app_net"
enrichment_proxy_url: str = ""          # 可选出站代理（仅容器需联网时）
enrichment_data_mount: str = "/data/cygnusx"
enrichment_exec_timeout: int = 120      # 容器执行软超时（秒）
enrichment_memory: str = "2g"           # 容器内存上限
enrichment_cpus: float = 2.0            # 容器 CPU 核数
```

**新工具契约**：照搬上述 8 个键，前缀换成 `<tool>_*`。对应 env 变量按 Pydantic `BaseSettings` 约定为 `ENRICHMENT_DOCKER_IMAGE` → `<TOOL>_DOCKER_IMAGE` 等。

## 五、运行数据契约（核心）

### 5.1 任务目录契约

任务目录由 `StoragePathFactory`（`src/cygnusx/infrastructure/storage/path_factory.py`）统一生成，**不得自行拼路径**：

```text
{data_mount}/users/{user_id}/tasks/{task_id}/
├── input/      # 上传/落盘的输入
├── output/     # ★ 分析产物；工具可再嵌一层 project_slug
├── work/       # 中间文件
└── logs/       # 日志
```

- `task_output_dir(user_id, task_id)` → `…/tasks/{task_id}/output`；工具在其下可再嵌 `project_slug`（富集即 `output/{project_slug}/`）。
- **同路径挂载**：`{data_mount}` 默认 `/data/cygnusx`，容器以 `-v {data_mount}:/data/cygnusx` 挂载，宿主与容器内绝对路径一致，命令里输入/输出/参考一套路径两边通用。
- **隔离与归属**：目录天然按 `user_id` 隔离；所有查询/下载端点必须以 `(task_id, user_id, flow_id)` 三元组校验归属。

### 5.2 提交契约（Web 侧）

`service.submit()` 的固定七步（顺序即契约）：

1. **解析领域配置**：`config_manager.get_<x>(id)`，缺失/未启用 → `NotFoundError`/`ValidationError`；**不信前端传的参考路径**。
2. **轻量校验 + 归一化输入**：去空白/去重/格式校验（CPU 密集解析放 `asyncio.to_thread`）。
3. **建任务目录**：`get_path_factory().task_output_dir(user_id, task_id)[/ project_slug]`。
4. **输入落盘**：写成容器约定格式（如富集写无表头 `gene_list.txt`）。
5. **建 `TaskModel`**：必填 `flow_id="<tool-key>"`（任务判别器）、`user_id`、`name`、`status=QUEUED`、`parameters`（含 species/config id、project_slug、输入规模、用户阈值）、`work_dir`、`progress=0`。
6. **投递 Celery**：`<tool>_task.apply_async(args=[task_id], task_id=task_id)`（Celery task_id 与 DB 主键同 UUID）。import 放函数内避免循环依赖。
7. **立即返回** `TaskDTO(status="queued")`。

> **`flow_id` 命名**：`TaskModel.flow_id` 是无校验的 `String(100)`。工具箱工具沿用富集惯例——`flow_id` 与工具 `key` 取**同一 kebab-case slug**（如 `kegg-enrichment`、`deg-analysis`）。注意这与「分析中心 Flow 家族」的下划线纲目（`rna_seq`，ARDP §4.2）是两套命名空间，勿混用。

### 5.3 容器调用契约（Worker 侧 runner）

`runner.build_command()` 必须生成如下形态（富集样板，见附录 A）：

```bash
docker run --rm --name <tool>-<task_id[:8]> \
  --network <net> \
  [-e http_proxy=… -e https_proxy=… -e no_proxy=localhost,127.0.0.1]   # 仅 proxy_url 配置时
  -v <data_mount>:/data/cygnusx \
  --memory <memory> --cpus <cpus> \
  <image> \
  Rscript /app/run_<tool>.R --input <绝对路径> --output <绝对路径> [工具特异参数…]
```

`runner.run()` 的执行契约：

- 用 `asyncio.create_subprocess_exec(*cmd, stdout=PIPE, stderr=PIPE)`，**不用** Docker SDK、**不用** `docker exec` 进常驻容器——就是"每任务一个 `docker run --rm`"。
- `asyncio.wait_for(proc.communicate(), timeout=<exec_timeout>)`；超时 `proc.kill()`（杀 `docker run` 进程连带杀容器）并返回 `timed_out=True` 结果。
- 返回 `RunResult(returncode, stdout, stderr, timed_out)`，由 `tasks.py` 判定成败。
- 资源/网络/镜像/超时**全部来自 §4.3 的 Settings**，不硬编码。

### 5.4 分析脚本入口契约

分析脚本（R 为样板运行时）必须满足：

| 契约项 | 要求 |
|---|---|
| 位置 | 构建期 `COPY` 进镜像 `/app/run_<tool>.R`（`chmod 0555`），运行期不挂卷 |
| 参数解析 | `optparse`（R）/ `argparse`（Python）风格 CLI；`--input`/`--output` 必填；其余工具特异参数可选成对出现 |
| 输入读取 | 只从 `--input` 与 `--<参考>` 指向的挂载路径读；ID 兼容性处理（如去版本号后缀）在脚本内完成 |
| 无副作用 | 不写 `--output` 所在任务目录之外的路径；不访问网络（除非工具本质需要，见 §6.4） |
| 可独立自检 | 镜像 `CMD ["Rscript","/app/run_<tool>.R"]`，支持 `--help`，便于 `docker run --rm <image> Rscript /app/run_<tool>.R --help` 验收 |

### 5.5 标准产物契约（容器 ↔ Worker 的唯一接口）

容器与 Worker 之间**只认这一份契约**：

1. **标准 CSV**：`--output` 指向的 CSV，**列恒定**（列名/顺序由工具定义并写进工具级契约文档）；**无显著结果时只写表头**。Worker 用固定列解析为结果 DTO。
2. **图**：每类有结果的分析输出 `<name>.png` / `<name>.pdf` 到同目录（容器侧静态图仅备用；前端优先 Plotly 交互重绘，见 §7）。
3. **退出码语义**：
   - `0` = 成功（至少一类分析有结果）；
   - `非 0` = **所有**已配置分析均失败；
   - **局部失败**：仅一类失败时，保留另一类的 CSV/图 + 日志告警，仍以 `0` 退出（不让一类拖垮另一类）。
4. **大体量数据不进结果**：表达矩阵、序列等大文件只落盘 + 给下载路径，**不**塞进 `task.parameters["result"]`（结果 JSON 只放前端渲染所需的表/图数据）。

### 5.6 结果回写契约（Worker 侧 tasks）

`@shared_task(bind=True, name="cygnusx.tools.<tool>.tasks.<tool>_task", queue="analysis", time_limit=…, soft_time_limit=…)`，内部 `asyncio.run(_run(task_id))`：

| 阶段 | 动作 |
|---|---|
| 起 | 自建 DB 会话取 Task；置 `RUNNING` + `progress=10` + `started_at` |
| 重解析 | 从领域 YAML 重解析配置（权威，不用 DB 里缓存的参考路径） |
| 执行 | 由 `task.work_dir` 拼输入/输出 → `runner.run(params, container_name)` |
| 成功 | 校验 `returncode==0` → 解析标准 CSV → 结果 DTO 写回 `task.parameters["result"]`；`result_path=<output CSV>`；置 `SUCCESS` + `progress=100` + `finished_at` |
| 失败 | `returncode!=0`/超时/异常 → `error_message=str(err)[:2000]`；置 `FAILED` + `progress=100` + `finished_at` |
| 收尾 | `commit` |

> 结果存放约定：结构化结果进 `task.parameters["result"]`（JSON），原始 CSV 路径进 `task.result_path`。前端查询时由 `service.get_task()` 读出 `result` 渲染，下载时由 `service.get_result_file()` 按 `result_path` 返回。

### 5.7 轮询与展示契约（前端）

- 提交后 `GET /<tool>/tasks/{task_id}`，`setTimeout` 递归轮询，间隔 ~1.5s，`onBeforeUnmount` 清理定时器。
- 任务状态枚举固定：`queued | running | completed | failed`；`progress: 0–100`、`message` 人类可读进度、`error_message` 失败摘要、`result` 结构化结果。
- `completed` → 渲染结果 + 重载历史；`failed` → 展示 `error_message`。
- 历史：`GET /<tool>/tasks?limit=N` 按 `(user_id, flow_id)` 倒序，**不跨用户**。
- 下载：`GET /<tool>/tasks/{task_id}/download`（blob，鉴权 + 归属校验）。

## 六、分析镜像契约

### 6.1 镜像构建

每工具一个 Dockerfile：`deploy/docker/Dockerfile.<tool>`，构建上下文为 `tool_configs/<tool>/`（富集样板）：

```dockerfile
FROM bioconductor/bioconductor_docker:RELEASE_3_20        # R 工具的标准 base
# 装运行环境（构建期可联网）
RUN R -q -e 'install.packages(c("optparse", ...), repos="https://cloud.r-project.org")' && \
    R -q -e 'BiocManager::install(c("<核心包>", ...), update=FALSE, ask=FALSE)'
COPY run_<tool>.R /app/run_<tool>.R
RUN chmod 0555 /app/run_<tool>.R
WORKDIR /app
CMD ["Rscript", "/app/run_<tool>.R"]
```

- **命名**：`<vendor>-<purpose>:v<N>`（如 `cygnusx-r-enrichment:v1`、`cygnusx-r-deg:v1`），由 `<tool>_docker_image` 设置引用。
- **构建入口**：在 `Makefile` 增 `docker-build-<tool>` 目标；`docker-up-worker` 应确保该镜像已构建。

### 6.2 一工具一镜像原则

**原则上一个工具一个独立镜像**，职责单一、互不影响、可独立升级。避免"一个镜像塞多个工具"——那会让任一工具的依赖升级牵连全部。仅当两个工具运行时依赖**完全一致**且演进强绑定时才考虑合并（默认不合并）。

### 6.3 运行时依赖

- **只有 Worker 持 Docker**：Worker 容器挂 `/var/run/docker.sock` + Docker CLI；**Web 容器绝不挂 Socket、绝不装 Docker CLI**（§2.2 红线，`tools_design.md` §5.1.2）。
- **Socket GID 规范**：Worker 内 Celery 进程的附加组 GID 必须与宿主 Docker Socket 实际 GID 一致，**禁止写死 `DOCKER_GID=987/999`**；降权用 `setpriv --groups "$DOCKER_SOCKET_GID"` 而非清空附加组的 `gosu`；验收检查 `/proc/<pid>/status` 的 `Groups:`（详见 `tools_design.md` §5.1.2「Docker Socket 权限与 GID 规范」）。

### 6.4 网络与代理

- **本地分析默认不出网**：能在容器内用本地参考完成的分析（GO 本地 OBO、DESeq2/edgeR 计数矩阵），一律走本地，容器无需网络。
- **必须出网时**（如 KEGG REST）：默认经 Docker bridge 直连；配置 `<tool>_proxy_url` 后，runner 才向容器注入 `http_proxy/https_proxy/no_proxy` 环境变量。
- 容器加入的 Docker 网络由 `<tool>_docker_network`（默认 `cygnusx_app_net`）控制。

## 七、前端工作台契约

工作台页面（`<Tool>View.vue`）遵循 `tools_design.md` §6 与 `ARCHITECTURE_DESIN/frontend.md` 的标准模式（富集 `KeggEnrichmentView.vue` 为样板）：

| 复用组件 | 共享 `PageHeader`（页面级操作只放 `#actions` 插槽）、`ToolActionBar`（底部粘性提交条，`ready` 态 + ⌘↵） |

## 八、产物登记与可见性

工具产物有两种可见性，按需选择：

| 模式 | 机制 | 可见性 | 适用 |
|---|---|---|---|
| **任务内结果**（默认，富集现状） | 结果进 `task.parameters["result"]`，原始 CSV 路径进 `task.result_path`，经 `GET /<tool>/tasks/{id}/download` 下载 | 仅在该工具任务历史内可见/下载 | 结果只服务本工具页面 |
| **文件登记**（推荐用于通用产物） | 容器产出后由 Worker 调 `FileRegistry.register()/register_directory()`（`src/cygnusx/infrastructure/storage/file_registry.py`）写 `file_records` 表，`source=FileSource.<TOOL>`、`task_id` 关联 | 进「文件管理」(`/files`)，可被其他工具/流程复用 | 产物是通用数据（如 DEG 表可再喂给富集工具） |

> **注意**（项目 memory：下载产物需登记才可见）：`/files` 读的是 `file_records` 表而非磁盘扫描——**不登记就在文件管理里看不到**。若新工具产物希望跨工具复用（强烈建议 DEG 如此），在 Celery 任务成功分支调 `FileRegistry.register(...)`，并在 `src/cygnusx/domain/file/value_objects.py` 的 `FileSource` 枚举加 `<TOOL>` 值。登记是幂等的（同 `storage_path` 跳过）。

## 十一、安全与约束

1. **Docker 权限红线**：Web 容器不得持 Docker CLI / Socket；只有 Worker 持 Socket，且遵守 `tools_design.md` §5.1.2 的 GID 规范（禁写死 GID、禁 `chmod 666`、禁特权容器、禁清空附加组的降权）。
2. **提交即返回**：`submit` 不得同步等待容器；一切耗时在 Worker/容器，并设软/硬超时、内存/CPU 上限、并发与结果保留策略（资源参数来自 §4.3，不硬编码）。
3. **配置不外泄**：宿主参考路径、镜像名、容器内路径一律不回浏览器；前端不得传入任意参考路径。
4. **路径安全**：容器只写挂载任务目录内；下载端点对路径做 `relative_to(存储根)` 校验，禁 `..`/绝对路径逃逸。
5. **归属校验**：所有查询/下载以 `(task_id, user_id, flow_id)` 校验归属，历史不跨用户。
6. **容器零信任**：容器内不注入 DB 凭据、用户令牌；分析所需一切经挂载目录与 CLI 参数传入。
7. **结果体积**：大体量数据只落盘 + 给路径，不进 `task.parameters["result"]`；错误摘要截断 2000 字符。

## 十二、首个实例：差异表达分析工具（DEG）

作为本协议的**第一个新工具落地示范**（非协议本体）。R 脚本由业务方自备并调试，脚本定型后按本协议 §3–§8 接入即可。已确认决策：**输入 = 计数矩阵 + 分组表**；**镜像 = 新建独立 `cygnusx-r-deg:v1`**；统计方法（DESeq2 / edgeR）随 R 脚本确定。

### 12.1 身份与配置

| 项 | 值 |
|---|---|
| 工具 key / `flow_id` | `deg-analysis`（与富集惯例一致，kebab-case） |
| 路由 / 页面 | `/tools/deg-analysis` / `DegAnalysisView.vue` |
| 后端前缀 | `/deg`（`src/cygnusx/tools/deg/api.py`） |
| 领域配置 | `tool_configs/deg/analysis_config.yaml`（物种/默认 `padj`/`log2FC` 阈值/方法开关；公开边界同 §4.2） |
| 环境配置 | `core/config.py` 增 `deg_config_yaml / deg_docker_image="cygnusx-r-deg:v1" / deg_docker_network / deg_data_mount / deg_exec_timeout / deg_memory / deg_cpus` |
| 卡片 | `tools_setting.yaml` 追加 `key: "deg-analysis"`，`group: function`（或 `visualization`），`config_dir: tool_configs/deg` |

### 12.2 输入契约（DEG 特有，相对富集的主要新增）

富集是"一列基因 ID"，DEG 是"**计数矩阵 + 实验设计**"，这是本工具唯一没有现成模板、需要认真设计的部分：

| 输入 | 形式 | 校验要点 |
|---|---|---|
| 计数矩阵 | CSV/TSV，行=基因、列=样本，首列基因 ID，其余列为各样本整数 count | 非负整数、无缺失、列名=样本 ID |
| 分组表（design） | CSV/TSV，`sample, group`（可含 `batch` 等协变量） | 样本 ID 与矩阵列**完全对应**、每组≥2 重复 |
| 对比组（contrast） | 前端从分组推导，用户选择 `{Treat}_vs_{Control}` | 命名遵循 `{Treat}_vs_{Control}`（与 ARDP §4.6 / FlowFrame §8.5 一致） |
| 阈值 | `padj_cutoff`（默认 0.05）、`log2fc_cutoff`（默认 1） | 合法范围校验 |

### 12.3 标准产物契约（DEG）

`run_deg.R` 的 `--output` 标准 CSV 建议恒定列（最终随 R 脚本定稿）：

```text
gene_id, baseMean, log2FoldChange, lfcSE, stat, pvalue, padj, significant
```

每对比组另出 `volcano.png/pdf`、`MA.png/pdf`（可选 `heatmap`）。退出码与局部失败语义遵循 §5.5（多对比组时，单组失败保留其余组）。火山图前端可复用既有 `VolcanoPlotView.vue` 交互重绘。

### 12.4 镜像（DEG）

`deploy/docker/Dockerfile.deg`，base 同 `bioconductor/bioconductor_docker:RELEASE_3_20`，加装 `DESeq2`（和/或 `edgeR`）。可参考既有交互式沙箱镜像 `tool_configs/terminal/docker/Dockerfile.rnaseq`（已含 `r-bioc-deseq2`、`r-bioc-tximport`）的包清单——但 **DEG 工具用独立 `cygnusx-r-deg:v1`，不复用沙箱镜像**（沙箱是交互式终端容器，非 Celery 分析容器）。DESeq2/edgeR 为纯本地计算，**无需出网**，故 `deg_proxy_url` 可省。

### 12.5 产物登记（建议）

DEG 表是高复用价值产物（可再喂给富集工具）。建议 §8「文件登记」模式：Worker 成功后调 `FileRegistry.register(source=FileSource.DEG, task_id=…)`，并在 `FileSource` 加 `DEG = "deg"`，使 DEG 表在「文件管理」可见、可被富集工具直接取用——形成 **DEG → 富集** 的工具链闭环。

### 12.6 工作量估计（R 脚本已就绪前提下）

| 部分 | 估计 |
|---|---|
| 后端六件套（照富集改造） | 0.5–1 天 |
| `Dockerfile.deg` + 联调 | 0.5 天 |
| 前端 `DegAnalysisView` + 输入表单 + 火山图 | 1–1.5 天 |
| 配置/注册/文件登记/冒烟 | 0.5 天 |
| **合计** | **约 2.5–3.5 人日** |

> 架构层面零风险（有参考实现 + 自动注册 + 完整文档）；主要工作量在 §12.2 输入表单设计与前端渲染，均为成熟领域工作，不涉及架构创新。

### 12.7 AI / MCP 暴露（DEG）

按 §3.5 在 `tools_schema.yaml` 追加（`backend_sync` 包裹与网页同一个 `DegService.submit`）：

```yaml
- key: deg-analysis
  name: cygnusx_run_deg_analysis
  description: 对基因计数矩阵做差异表达分析（DESeq2/edgeR），返回 DEG 表摘要与火山图。
  category: function
  invocation_mode: backend_sync
  service: cygnusx.tools.deg.service.DegService
  method: submit
  requires_confirm: false
  annotations: {readOnlyHint: false, destructiveHint: false, openWorld: false, idempotent: true}
  input_schema:
    type: object
    properties:
      species_id: {type: string, description: 物种 ID}
      counts_ref: {type: string, description: "计数矩阵；upload://file_id 引用聊天上传的 CSV/TSV"}
      design_ref: {type: string, description: "分组表；upload://file_id 引用，含 sample,group 列"}
      contrast: {type: string, description: 对比组，如 CKX2_vs_Wo408}
      padj_cutoff: {type: number, default: 0.05}
      log2fc_cutoff: {type: number, default: 1.0}
    required: [species_id, counts_ref, design_ref]
  llm_result_fields: [task_id, stats, deg_count, success, error]
  ui_result_fields: [plotly_figure, table_data, download_urls]
```

计数矩阵与分组表经 `upload://file_id` 引用聊天上传文件（§3.5.2），AI 助手即可直接发起 DEG 分析；LLM 拿 `task_id` 后经 `platform_get_task` 轮询，完成后回报 DEG 数量与火山图。DEG 表登记进 `file_records`（§12.5）后，AI 还能把它作为后续富集工具的输入，形成 **DEG → 富集** 工具链。

```python
from fastapi import APIRouter
prefix = "/<tool>"
tags = ["<Tool> <中文名>"]
router = APIRouter()
# GET "" 配置/物种；POST "/submit"；GET "/tasks"；GET "/tasks/{id}"；GET "/tasks/{id}/download"

# src/cygnusx/tools/<tool>/tasks.py
from celery import shared_task
@shared_task(bind=True, name="cygnusx.tools.<tool>.tasks.<tool>_task",
             queue="analysis", time_limit=900, soft_time_limit=840)
def <tool>_task(self, task_id: str) -> dict:
    import asyncio
    from cygnusx.tools.<tool>.tasks_impl import _run   # 或同文件内 async def
    return asyncio.run(_run(task_id))

# src/cygnusx/tools/<tool>/runner.py
import asyncio, contextlib
from dataclasses import dataclass
@dataclass
class RunParams: input_path: str; output_path: str  # …工具特异字段
@dataclass
class RunResult: returncode: int; stdout: str; stderr: str; timed_out: bool = False
class DockerRunner:
    def build_command(self, p: RunParams, name: str) -> list[str]: ...   # §5.3 形态
    async def run(self, p: RunParams, name: str) -> RunResult:
        proc = await asyncio.create_subprocess_exec(*self.build_command(p, name),
                stdout=asyncio.subprocess.PIPE, stderr=asyncio.subprocess.PIPE)
        try:
            out, err = await asyncio.wait_for(proc.communicate(), timeout=<exec_timeout>)
        except TimeoutError:
            with contextlib.suppress(ProcessLookupError): proc.kill()
            return RunResult(-1, "", f"执行超时", True)
        return RunResult(proc.returncode or -1, out.decode(), err.decode())
```
